# HIDMaestro Internals

Technical reference for HIDMaestro. The [README](../README.md) covers what HIDMaestro is and how to use it. This document covers how it works: the descriptor and enumeration techniques, the device topology, the user-mode rationale, the validation methodology, and the timing characteristics.

For the per-release decision log and investigation notes, see [docs/investigations/](investigations/).

---

## Techniques

A few HIDMaestro techniques that are not well documented elsewhere in the virtual controller space.

### Velocity Usage Descriptor Trick

Real Xbox 360 controllers have a combined trigger axis (Z) in DirectInput: both triggers share one axis. Browsers and WGI need separate trigger values. Previous solutions had to choose: correct DI (5 axes, combined) or correct browser (separate triggers, 6 axes).

HIDMaestro uses HID velocity usages (Vx and Vy, Usage Page 0x01, Usages 0x40/0x41) to carry separate trigger values in the same HID report. DirectInput does not map velocity usages to any axis slot, so it sees 5 axes, while a reader of the HID report gets each trigger on its own. WGI reads this profile through its XUSB companion, which reports the two triggers as separate axes.

Result: 5 axes and 10 buttons in DirectInput (matching real xusb22.sys), separate triggers in the browser (matching real XInput), all from one HID descriptor.

### Data-Driven Vendor-Blob Codec (Sony USB + BT)

Sony BT controllers (DualSense, DualSense Edge, DS4 BT) declare their input as a 78-byte vendor-defined "blob": one opaque field with no descriptor-level breakdown of which bytes carry sticks vs buttons vs gyro vs CRC32. Pre-v1.3.5 the SDK couldn't pack this and fell back to emitting basic Report 1 (9 bytes), which Steam Input misclassified as USB and `dualsense-tester` couldn't parse.

v1.3.5 makes the byte layout data: profile JSON declares `extendedReport` (input) and `extendedOutputReport` (output) blocks describing every field's type, byte position, and bit range. The SDK becomes a generic codec that walks the field list. Future profiles with vendor blobs (Switch Pro extended, vendor-specific wheels) add the JSON only: no SDK code changes per profile.

The full Sony catalog ships with v1.3.5 data-driven blocks: DS5 BT (`dualsense-bt`, `dualsense-bt-full`, `dualsense-edge-bt`) gain both input + output (Report 0x31, 78-byte BT-format with `[0xA1,0x31]`/`[0xA2,0x31]` CRC32 prefixes); DS4 BT (`dualshock-4-v2-bt`) gets input + output (Report 0x11, `[0xA1,0x11]`/`[0xA2,0x11]` CRC32 prefixes); DS5 USB (`dualsense`, `dualsense-edge`) and DS4 USB (`dualshock-4-v1`, `dualshock-4-v1-full`, `dualshock-4-v2`) gain output blocks (Report 0x02 / Report 0x05; no CRC since USB is reliable). PadForge can drive any of them via `HMOutputEncoder.Encode(profile, fields)` without inline byte-packing.

```jsonc
"extendedReport": {
  "reportId": "0x31",
  "size": 78,
  "fields": [
    { "byte":  2, "type": "uint8-axis", "semantic": "leftStickX", "center": 128 },
    { "byte":  9, "bits": "0-3", "type": "hat-octant", "neutralValue": 8 },
    { "byte":  9, "bits": "4-7", "type": "button-mask", "buttons": ["X","A","B","Y"] },
    { "bytes": "74-77", "type": "crc32-le",
      "scope": { "prefix": [161, 49], "from": 1, "to": 73 } }
  ]
}
```

Round-trip in both directions: `controller.OutputDecoded` event surfaces incoming output reports as parsed-field dictionaries (rumble amplitudes, lightbar RGB, adaptive-trigger blobs). `HMOutputEncoder.Encode(profile, fields)` produces wire-format bytes from a parsed-field dictionary, used by consumers driving real devices from synthesized state without reimplementing byte layouts. `HMController.EncodeOutput(fields)` is the per-controller variant that auto-advances the rolling-counter state (Sony BT `btTag` cycles 0x00→0x10→…→0xF0→0x00 with stride 16) instead of forcing the consumer to track wraparound. `HMController.OnSubmitLatencyMicros` exposes per-frame submit latency for consumers driving timing-sensitive paths. An output button mask decodes across as many bytes as its buttons span, as the encoder writes it, and a bit past the end of a short host write reads as released.

The encoder/decoder reaches the public input-state surface too. `HMGamepadState` ships per-frame fields the Sony JSON blocks understand: `TouchpadFinger0Active/X/Y/Id` + `TouchpadFinger1Active/X/Y/Id`, `GyroPitch/Yaw/Roll` + `AccelX/Y/Z` + `SensorTimestamp`, and `BatteryLevel` (0..10) + `BatteryCharging` + `BatteryFull` + `MicMuted` + `HeadphonesConnected`. `SensorTimestamp` counts 1/3 µs ticks, the DualSense's own unit. The DualShock 4 profiles divide it by 16 into that pad's 16/3 µs ticks, and while it is 0 they stamp the time since the controller's first report. `TouchpadPacketCounter` fills the DualShock 4 touch report's packet-counter byte. Profiles that don't declare these regions silently ignore them, so the same caller code works across every controller. `dualsense-tester` (ds.daidr.me) renders touchpad coordinates, the IMU vector, and the battery panel for any DualSense or DualSense Edge virtual (USB or BT) once the consumer fills these fields.

Sony's feature answers are profile data. The six named models under `profiles/models` (`sony-dualsense`, `sony-dualsense-bt`, `sony-dualsense-edge`, `sony-dualsense-edge-bt`, `sony-dualshock4`, `sony-dualshock4-bt`) hold each pad's answer table, and the 16 Sony catalog profiles name theirs with `deviceModelFrom`. The answers carry the identity calibration for the pads' nominal units, 8192 counts per g and 16 per degree per second: zero biases, gyro references of plus and minus 8000 at a speed of 500, and accelerometer references of plus and minus 8192. SDL and Linux reduce that to a scale of exactly 1, so a value a consumer submits reaches the game at the unit the profile declares. A DualShock 4's Bluetooth report 0x05 lists the three plus references before the three minus references, unlike its USB report 0x02 and the DualSense, and each model serves its pad's order. The Bluetooth models end reports 0x05, 0x09 and 0x20 with the CRC-32 a real pad carries over that link (`crc32` on the entry). Linux checks it, and RPCS3 drops a pad whose calibration fails the check three times. Per-controller bytes, the pairing address and the serial, come from value sources the entry patches in. On UMDF2 the SDK compiles the table into the controller's `FeatureAnswers` value, and the driver answers from it only for a 2.0.0 SDK's controller (Version Handshake). On USB/IP the SDK answers from the same table.

Since 2.0.0 the field vocabulary grows by parameters, never by a type named for a device, and every parameter is refused on a type that ignores it:

| Key | On | Meaning |
|-----|----|---------|
| `min`, `max` | every type that carries a normalized value | the wire values at the SDK's 0 and 1, the type's full range by default |
| `invert` | every axis and trigger type | the wire grows the other way |
| `center` | `int16-le` | the wire value of a zero reading, 0 to 65535. 32768 writes offset binary, the PS Move's motion words. The word clamps to 0 to 65535 |
| `scale`, `negate`, `repeat` | `int16-le` of a calibrated source, `accelGX` to `gyroDpsZ` | counts per g or per degree a second, a number or an exact ratio such as `[13371, 936]`, and `[count, stride]` for a report that carries several samples |
| `dpad: "resolved"` | `button-mask`, `hat-octant` | the d-pad from `HatDegrees`, `HatHundredths`, `HatRaw` or `Hat`, the first one set |
| `"#n"` in `buttons` | `button-mask` | `HMButton` bit n |
| `levels`, `chargingValue`, `fullValue` | `uint8-level-map` | the battery byte as an 11-entry table, `fullValue` ahead of `chargingValue` |
| `clock: "accumulate"`, `divisor` | `uint16-le`, `uint32-le` of `sensorTimestamp` | elapsed time in the 1/3 microsecond ticks of `SensorTimestamp`, from the controller's clock until the first nonzero consumer stamp and from the consumer's stamps after. A repeat of the last state adds nothing, and a stamp that runs backward adds one idle interval |
| `packed-uint` | output fields | bit groups over frames of a stride, reduced by `max`, scaled and clamped to a byte, the Switch Pro's and Switch 2 Pro's rumble |

Where a profile written for 1.x left a key out and got a behavior, the key is required, so no such profile changes its bytes unseen: `max` on `uint16-trigger` and `uint16-pressure`, which 1.x wrote as 32767 at a full pull, and `invert` on an `int16-axis`, `int16-pad` or `int16-pad-or-stick` field of a Y semantic, which 1.x negated. The `ds3-battery` type is refused, with `uint8-level-map` and its table named. An output field refuses `min`, `max` and `dpad`, `invert` on any type but `uint8-axis`, and `center` on `int16-le`, since its decoder ignores them. Each refusal is an `InvalidOperationException` at create that names the profile, the field's JSON path and the value that keeps 1.x's bytes. Rolling counters compile to slots in the encoder's state, where each frame looked two counters up by name. The steam-controller-2 profile's report 0x42 timestamp accumulates, divisor 3, where a counter added 4000 per encode whatever the time. It holds while the IMU is off, as a real Triton's does: the profile's `holdWhile` names the `imuMode` register its protocol sets from the host's settings write. A port reset keeps the IMU setting, and an attach and LOAD_DEFAULT_SETTINGS clear it.

Every normalized value the SDK writes, on the descriptor path, the XUSB slice, the codec, both Switch packers and the output encoder, is `min + RoundHalfEven(v' x (max - min))` in double, where `v'` is the clamped input or 1 minus it for an inverted field (`WireArith`). Truncation sent a value a consumer normalized from a raw count back one count low on 32,895 of the 65,536 values of a 0..65535 axis and on 252 of 256 XInput trigger bytes. `arith_roundtrip_check` (S90) sends every raw value of every catalog conversion through the SDK's own code and requires it back. A NaN writes the field's resting value, 0.5 for a stick or a centered axis and 0 for a trigger, and never falls through to the key a slot reads when the first is absent. A stick the consumer leaves unwritten rests at its center: the report builder rests the axes the profile's layout names as sticks at 0.5, and every other axis as before, 0.5 when signed and 0 when not. `axisCenters` gives a descriptor-path axis the wire value it carries at 0.5, with two slopes computed at create and the distance from the center rounded once, so 0.5 and PadForge's 32768 / 65535 both land on it: 0x7F on `amazon-luna-usb` and 0x7FFF on `amazon-luna-ble`, where SDL's Luna driver reads zero (`SDL_hidapi_luna.c`). Through float normalization a consumer gets 64 or 65 values just above a 16-bit center back one count low.

DS4 Bluetooth vibration through the browser Gamepad API is fixed in v1.3.5 by setting the device's `HidD_GetAttributes` `VersionNumber` to 0: the value Chromium's `DualShock4Controller::BusTypeFromVersionNumber` checks for the BT-format report header. Pre-v1.3.5 the SDK hardcoded `0x0100` (USB), Chromium picked the wrong wire layout, and the rumble bytes never reached the device. Profiles can now override `versionNumber` in JSON; `dualshock-4-v2-bt.json` ships with `0`. Steam Input never used this gate so v1.3.5 doesn't change Steam behavior either way.

### Switch Pro Protocol

The Switch Pro Controller is not a passive HID device: hosts (SDL's `HIDAPI_DriverSwitch`, Steam, BetterJoy) drive a Nintendo init and subcommand protocol and stall without a device that answers. Since v2.0.0 that protocol is data in `profiles/nintendo/switch-pro.json`, and the SDK runs it (`Internal/ProtocolHost.cs`) behind a driver that keeps no Switch Pro code. The driver sends each frame the SDK writes and publishes each output report as written. The SDK's output reader hands the report to the protocol before it raises `OutputReceived`, and a reply goes out ahead of the next report once the driver has delivered the frame before it.

Since v1.3.21 (issue #37) the shipped descriptor is the real Bluetooth one, extracted byte-exact from a live Pro's SDP cache. It declares no 0x80/0x81 USB-init family, so those writes fail at HidClass exactly as on real Bluetooth hardware and SDL initializes over its Bluetooth path. `switch-pro-usb` carries the pad's 203-byte USB descriptor and its USB protocol: `80 01/02/03` answer `81 xx` with device type Pro and a stable fabricated MAC, and its replies and reports are 64 bytes. A profile made outside the catalog with the Switch Pro's VID and PID takes one of the two through its identity default, by connection.

Subcommands (output 0x01, padded to the 49-byte Bluetooth write size) get input-report 0x21 replies per the nxbt responder table, including SPI flash reads served from a fabricated image: factory stick calibration with center 0x800 and range 0x600, and IMU coefficients (0x4000 accel, 0x343B gyro) chosen so SDL's calibration math reduces exactly to its own default scales. Unknown subcommands get a generic ACK rather than nxbt's silent ignore, because SDL retries unanswered subcommands for ~500 ms where the Switch console does not. The device clock sends every 15 ms: genuine 12-byte 0x3F simple-mode frames (the only report DirectInput can parse) until the first subcommand arrives, then the 49-byte Bluetooth full-mode 0x30, its timer byte counted per message.

Consumers submit through the normal `SubmitState`: the profile's `stateBlock` converts the layout-mapped buttons, 12-bit packed sticks, and the calibrated IMU channel (`HMGamepadState.AccelG*` in g, `GyroDps*` in deg/s, defined in the SDL-standard sensor frame) into the wire body. Its fields own the SDL-to-Switch frame permutation, so a consumer reading motion from SDL submits it verbatim and the client-side SDL reconstructs the identical vector. HD rumble comes back decoded to coarse `leftMotor`/`rightMotor` amplitudes on `OutputDecoded` through `protocol.decoders.rumble`, the same lane Sony rumble rides. `device_oracle_check switch-engine` holds the profile data to the responder 9bd6279's driver ran, and `test/probes/switch_pro_check` replays SDL's exact init sequence over raw HID as the release gate.


### Switch 2 Pro Command Responder and Report Clock

A Switch 2 Pro Controller over USB is two interfaces, and a host starts it through the second. Interface 0 is HID. Interface 1 is vendor class with a bulk pair, where SDL's Switch 2 driver and Steam send an 8-byte header and data (command, `0x91`, transport, subcommand, 0, length, 0, 0) and read back the command, a status, the transport, the subcommand, `00 F8 00 00` and data. The pad answers every poll of its interrupt endpoint with NAK until command 03/0D arrives, then sends one report every 4.000 ms. `switch2-pro-controller-composite` reproduces that device on the USB/IP backend from a link-layer capture of a console driving a pad on firmware 1.1.5.

Windows has to bind WinUSB to interface 1 before libusb can claim it, and a real pad arranges that itself with Microsoft OS 1.0 descriptors. The profile's `usbConfiguration.microsoftOs` block carries three blobs: the string Windows reads at index 0xEE (`MSFT100` and a vendor code), the extended compatible ID naming `WINUSB` for interface 1, and the extended properties holding a `DeviceInterfaceGUID`. Windows asks for the last two with a vendor request whose `wIndex` is 4 or 5 and whose `bRequest` is the vendor code it stored for this VID, PID and revision. The backend answers on `wIndex` alone, since a real pad of the same revision may have stored a different code on that PC before the persona was ever attached. A profile without the block stalls 0xEE and every vendor request, as before.

The pad's protocol is data in its profile, `switch2-pro-controller-composite`, which the protocol engine runs: registers for whether reports are on, the selected report, the feature mask, the enabled features and the player LEDs, a flash image in `memory`, the command rules and a queue of 64 replies on the bulk IN endpoint. Each bulk OUT payload is logged raw before any rule reads it, then answered at once, because SDL waits 100 ms for each reply. A reply longer than one read spans several, so the pad's 80-byte flash reply goes out as 64 bytes and then 16 to a host that reads in 64s. The flash image holds the persona's serial at the address SDL reads a pad's serial from, stick calibration with center 0x800 over the whole 12-bit range, and a zero gyro bias, which SDL subtracts. The same serial is USB string 3 and the HID serial string, the pair PadForge's SDL fork matches to join the two interfaces of one pad. Every byte no segment names reads 0xFF, as erased flash does on the pad.

The report clock belongs to the device. Each report's motion timestamp advances 4000 microseconds, the step a real pad's reports carry. SDL counts 100 reports and takes this pad's sensor constants, a gyro scale of 34.8 rad/s, when the timestamp advanced 3600 to 4399 a report, then hands the timestamp on as each sample's time, 4,000,000 ns apart. That holds only if the reports really are 4 ms apart. Reports that followed the consumer's submit rate would carry timestamps that run fast or slow against real time. The device clock, on a high-resolution waitable timer, sends one report every 4 ms from the command that started the pad, and builds it at that moment from the consumer's newest state and the protocol state. One count of reports sent drives report `0x09`'s 8-bit counter, report `0x05`'s millisecond field (4 a report) and its motion timestamp (4000 a report, starting at 1, since SDL reads 0 as no sample). A tick that finds no read parked leaves one report owed, and the next read is answered as it arrives. A clock that was held up skips the ticks it missed and sends no burst. Reports `0x09` and `0x05` are report programs in the profile's `inputReports`. `SubmitState` writes the profile's 24-byte state block of buttons, 12-bit sticks and motion counts and only replaces what the next report is built from. A raw submit on this persona is that state block: 24 bytes, verbatim, and any other length throws `ArgumentException`. `HMProfile.BuildsItsOwnReports` says which profiles work this way.

Motion converts with the constants SDL's driver applies to this pad: 32767 counts per 8 g and per 34.8 rad/s. The pad's three fields are SDL's X, minus Z and Y, in that order. Rumble is output report `0x02`, one 16-byte block per actuator of three 40-bit frames, which the profile's `rumble` decoder reads. Each frame holds two amplitudes. SDL writes its high-frequency level in the first and its low-frequency level in the second, so `OutputDecoded` reports the largest first amplitude over the six frames as `rightMotor` and the largest second as `leftMotor`, scaled back from the 29000 that SDL scales a full motor value to.

usbip-win2 0.9.8.1 presents the full-speed bulk endpoints to Windows with a 512-byte packet size, and it completes a canceled transfer through `UdecxUrbCompleteWithNtStatus` without a call to `UdecxUrbSetBytesCompleted` (`drivers/ude/request_list.cpp`). A WinUSB read that times out on this persona therefore returns success with the previous reply's bytes, and later reads are served from the same stale buffer without a transfer reaching the device. The device's own trace shows the canceled read unlinked and no bulk IN request after it. A host that reads only after it has sent a command never abandons a read. `UsbipEmulatedDevice.BulkReadsCanceled` counts the ones that were, and S65 asserts that Steam leaves it at 0. `test/probes/switch2_composite_check` (S65) plays the driver's side of the wire against the capture, then reads the live persona through HidUsb, WinUSB, SDL3 with libusb and the Steam client.

### Composite Stream State Without SET_INTERFACE

A composite persona learns that the host opened or parked an audio stream from SET_INTERFACE, which usbip-win2 sends on behalf of its upper filter driver. The filter intercepts each SELECT_INTERFACE and tells the host controller driver with a marker request: GET_FIRMWARE_STATUS, `wIndex` 0xFFFF, with the URB function in the timeout's low word. usbip-win2 0.9.8.1 compares the marker's `bmRequestType` against 0x80. Every earlier filter sends 0x00, because the 0.9.7.x and 0.9.8.0 headers initialize `BM_REQUEST_TYPE` as `.bmRequestType = 0x80`, which sets the union's first member, the 2-bit `Recipient` field, to 0. 0.9.8.1 writes `.bmRequestType{.B = 0x80}`. The binaries agree. The 0.9.7.5 host controller driver, both 0.9.8.0 drivers and the 0.9.7.7 filter carry 0x00. The 0.9.8.1 host controller driver and filter carry 0x80.

HIDMaestro's in-place move to 0.9.8.1 replaces the host controller driver and leaves the filter alone, since updating the filter restarts every USB root hub and drops the physical controllers a consumer reads. On a moved machine the 0.9.8.1 driver passes the old filter's marker to the device as an ordinary request, so the persona receives `00 1A 0000 FFFF 0000` where SET_CONFIGURATION and SET_INTERFACE belong, while the audio flows. The audio engine therefore reads stream state from the traffic for any interface that has never received a SET_INTERFACE: the first isochronous transfer opens it at the endpoint's alternate setting, and 200 ms without one closes it. An interface that has received a SET_INTERFACE follows SET_INTERFACE alone, so a matched transport behaves exactly as before. Since 2.0.1 a machine where HIDMaestro installs the transport has no filter at all, and neither SET_CONFIGURATION nor SET_INTERFACE reaches the persona: the same rule covers it. S43 covers both paths over loopback, S45 covers the live stack, and S73 runs S45 in Windows Sandbox with no filter on the machine.

### DualShock 3 Sixaxis Mode

On Windows, PCSX2 and RPCS3 read a DualShock 3 through Sony's sixaxis.sys driver, or through DsHidMini in its SXS mode, which presents the same device: a 12-byte joystick report with no report id, and the pad's whole native 49-byte report as feature report 0. PCSX2 reads it through SDL with `SDL_HINT_JOYSTICK_HIDAPI_PS3_SIXAXIS_DRIVER` set and accepts only a pad with SDL's 16 axes, ten of which are button pressures. RPCS3 reads feature report 0xF2 and falls back to 0.

The `dualshock-3-full` profile's `stateBlock` is the native report 0x01, which `SubmitState` fills every frame: buttons, sticks, the twelve pressure bytes (`HMGamepadState.Pressure*` and the triggers), the battery byte, and the 10-bit big-endian motion sensors at 113 counts per g and 123 counts per 90 degrees per second. The SDK's protocol host derives the rest from it the way DsHidMini's SXS mode does: a layout sent on each submit builds the 12-byte input report, and a live feature report the feature reply, which turns the motion fields little-endian and mirrors accelerometer X. The driver sends the input report and answers a GET of feature report 0 from the latest reply the SDK wrote (`LiveFeatureReport`). The descriptor declares no report ids, so the HID class delivers every feature read to the driver as report 0, whatever id the reader asked for, and leaves the reader's id byte in place. A read of 0xF2 therefore returns the same report, as it does on DsHidMini.

Output arrives as report 0 with a sixaxis.sys command in its first byte, and the profile's rules fold it into a 48-byte body. For command 2, which sets the motors, everything after the three-byte command header is the native output report's body. DsHidMini applies it that way, and RPCS3 lays out its Windows report to match. Command 1 sets the four player LEDs, which the rules write into the native report's LED bitmap. Every command raises the body as native output report 0x01, so `OutputDecoded` reports the same fields whichever form the reader wrote. `test/probes/ds3_sixaxis_check` (S64) drives stock SDL with PCSX2's hints against a live persona and replays RPCS3's reads and writes, and `device_oracle_check ds3-engine` holds the profile data to the form 9bd6279's driver ran.

### Bluetooth Identity

A Bluetooth profile's parent carries the hardware and compatible IDs a real Bluetooth device of its transport carries, read from a present DualSense (classic) and Xbox Series pad (LE), and no bus type GUID. `bluetoothTransport` picks the form. `"classic"`, the default, gives `BTHENUM\{00001124-0000-1000-8000-00805f9b34fb}_VID&0002054c_PID&0ce6` and `..._LOCALMFG&0002`, with compatible IDs `BTHENUM\{00001124-...}` and `..._GENERIC`. `"le"` gives `BTHLEDevice\{00001812-0000-1000-8000-00805f9b34fb}_Dev_VID&02045e_PID&0b13_REV&0523`, the same without `_REV`, and `..._LOCALMFG&0002`, with compatible IDs `BTHLEDevice\{00001812-...}` and `BTHLEDevice\GenericATTService`. `bluetoothVendorIdSource` says who assigned the VID, the USB-IF (`"usb"`, the default, 2) or the Bluetooth SIG (`"bluetooth"`, 1, as the Luna's `_Dev_VID&010171` carries), and the LE revision is the profile's `versionNumber`. `_LOCALMFG` names the host's Bluetooth radio, and HIDMaestro writes 0002, the company of the Intel radio every Bluetooth device on the development machine carried. No INF there matches a `_LOCALMFG` ID. SDL3 and hidapi read the bus as Bluetooth from `BTHENUM` or `BTHLEDEVICE` in the parent's compatible IDs, and LE from the second, without Bluetooth hardware and without a kernel bus driver. Through 1.x every Bluetooth profile carried the LE compatible ID and a hardware ID of the form `BTHENUM\Dev_VID&02<vid>`, which no real device carries.

A create stamps the bus type GUID only on the parent it made, by its connection: GUID_BUS_TYPE_USB for a USB profile, none for a Bluetooth one, and HID class names the child. Through 1.x every create stamped GUID_BUS_TYPE_USB on every HIDMaestro devnode on the machine and on each one's first child, Bluetooth profiles and other programs' devices included.

### &IG_ Enumerator Trick

By using `VID_*&PID_*&IG_00` as the device enumerator, the HID child's device path contains `&IG_`. This has three simultaneous effects:

- **Chrome RawInput** skips it (prevents duplicate gamepad entries)
- **HIDAPI** skips it (by design for XInput-handled devices)
- **SDL3** still detects it (falls through to RawInput backend, maps by VID/PID)

One string in a device path controls three different detection paths across three different libraries.

### GameInput Mappings

WGI makes a HID device a `Gamepad` through a mapping keyed by VID and PID. Windows ships its own under `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\GameInput\Devices` (279 on Windows 11 26200), and a key at `HKLM\SYSTEM\CurrentControlSet\Control\GameInput\Devices\<VID><PID>00010005` takes priority over them. A mapping names each axis and button by its position in the order WGI enumerates them, so it reads correctly only against the descriptor it was written for.

Through v1.11.0 the SDK wrote one table for every profile Windows had no mapping for, and deleted Windows' entry for the profiles it had one for. The table fit one shape: the `HidDescriptorBuilder` game pad, with X and Y, Z and Rz, Rx, Ry and a hat in that order and ten or more buttons. Measured across the catalog, it made 25 non-Xbox profiles WGI Gamepads read through the wrong axes, 21 of them wrong even at rest: a resting DualSense read RightTrigger 0.498 and RightThumbstickY 1.000 (foundation-sunshine #1056). It also hid Windows' own DualShock 4 v1 mapping. For Xbox profiles it changed nothing WGI read, because WGI reads them through XUSB or xinputhid.

Since v1.12.0 the SDK writes a table only for a profile built in code whose descriptor has exactly that shape, and only when neither Windows nor another program has a mapping for its VID and PID. Catalog profiles get none, the same as the real devices: WGI lists a virtual DualSense as a RawGameController, as it lists a real one, and reads a virtual DualShock 4 v1 as a Gamepad through Windows' own mapping. The table goes when the last controller holding it does. Tables an older SDK left behind are recognized by their exact bytes. `RemoveAllVirtualControllers(HMCleanupScope.Everything, preserveInstall)` deletes those no live controller holds. `RemoveAllVirtualControllers()` and `(bool)` delete those no running program uses: a table stays while a present device or a `Controller<N>` configuration carries its VID and PID, and every table stays while an input section nothing explains shows a v1.11.0 create in flight. A create of a profile that takes no table deletes the one of its own VID and PID. Battery scenario S67 reads each of these cases through WGI with an XUSB pad as the positive control.

### Registry Keys Shared With Real Devices

Two keys a virtual controller writes are named by VID and PID, so a real device with the same ids uses the same key: the GameInput mapping above, and joy.cpl's OEM key `HKLM\SYSTEM\CurrentControlSet\Control\MediaProperties\PrivateProperties\Joystick\OEM\VID_xxxx&PID_xxxx`, whose `OEMName` is the name joy.cpl and DirectInput show. Through v1.11.0 the SDK overwrote `OEMName`, deleted `OEMData` and the `Axes` subkey, and left them that way. Its cleanup deleted every OEM key under the Microsoft, Sony and VID 0000 prefixes in HKLM and HKCU and cleared the HKCU joystick slots, so a real pad that shared an identity lost its joy.cpl data (foundation-sunshine #1138). A vendor prefix is not proof of ownership.

Every such write now goes through a ledger at `HKLM\SOFTWARE\HIDMaestroRegistryLedger`. Before writing, the SDK records the key's prior state and the live controllers that hold it, each named by process id, process start time and controller index. When the last holder goes, the prior state comes back, and only while the key still holds what HIDMaestro wrote: a value another program changed in the meantime stays. A key HIDMaestro created is deleted only if nothing else was written under it. A holder whose process has exited counts as released, so a crashed consumer's writes are undone by the next session's first create. The ledger and `HMOemNameOverride` share one lock, `HIDMaestro.Admin\Ledger` (see Machine-Wide Locks), and read each other's records, so `OEMName` ends at its original value in any order of claim and release. The `OEMData` value and hidden fifth axis that builds before April 6, 2026 wrote are removed where their bytes match exactly, and nowhere else. Keyboard and mouse profiles write neither key.

The device sweep's ownership guard (v1.3.16, issue #28) now covers the `Device Parameters` cleanup and the interface registrations under `DeviceClasses` as well. An entry under an enumerator real devices share (`VID_`, `XnaComposite`, `HID_IG_00`) goes only when its device is provably HIDMaestro's or has no instance record left. Battery scenario S66 plants keys for real VID and PID pairs in both hives, creates and disposes virtuals over them, runs the full cleanup, starts a fresh context, recovers from a killed consumer, and compares every value.

### xinputhid UpperFilter Tripwire

WGI (`Windows.Gaming.Input.dll`) admits devices into its provider graph through `ProviderManagerWorker::OnPnpDeviceAdded`. A Ghidra decomp of that function on Win11 26200 showed the gate: WGI accepts a device only if its ClassGuid is in a hard-coded four-entry pass-list (`HIDClass`, `XnaComposite`, one other setup class, one GameInput class) OR if `IsDeviceOrAncestorFilteredBy(path, L"xinputhid")` returns true. The fallback check is a literal `wcsncmp` against strings in the device's (or any ancestor's) `UpperFilters` MULTI_SZ.

HIDMaestro's XUSB companion (`SWD\HIDMAESTRO\<token>`) runs under the System class `{4d36e97d-...}`. That class is not on the pass-list, so before this work WGI silently skipped the companion despite it publishing the XUSB device interface: Chromium's `put_Vibration` went nowhere for Xbox 360 Wired.

The fix writes the string `"xinputhid"` to the companion's `UpperFilters` registry value via the INF's `HKR` AddReg. `xinputhid.sys` is a HID-class filter, so it never actually attaches to the System-class companion; the string sits inert in the registry and WGI's wstring compare passes anyway. The companion enters WGI via the XUSB dispatch path, and `IOCTL_XUSB_SET_STATE` starts reaching the driver with real motor bytes on `put_Vibration`.

The same string gets written per-instance to the HID parent by `DeviceOrchestrator` for XUSB-companion profiles only. That second write blocks WGI's `HidClient::CreateProvider` from synthesizing a duplicate HID-backed Gamepad for the same logical controller, so WGI shows exactly one Gamepad with live input and working vibration instead of two pads splitting the responsibilities.

The 29-byte `IOCTL_XUSB_WAIT_FOR_INPUT` reply format was nailed down in the same decomp pass: `state[9] = 0x00` so `XusbInputParser`'s built-in Gamepad template matches (a prior 0x14 value produced an all-zero `GetCurrentReading` despite input arriving), plus the `state[10] = 0x14` non-zero gate byte, `state[2] = 0x03 RESUMED` on every completion, and version bytes `0x01 0x03` at `state[0..1]`.

The companion's other two replies share one header rule: a two-byte XUSBVersion word comes first, and the payload follows it. `IOCTL_XUSB_GET_BATTERY_INFO` answers `00 00 01 03`, which is the type at byte 2 and the level at byte 3, WIRED and FULL. A caller reads the pair from byte 2 onward, because `XInputGetBatteryInformation` copies out of a struct whose first member is that version word. Packing the pair at bytes 1 and 2 instead made every virtual pad read back as NiMH at EMPTY, and SDL maps any type other than WIRED, UNKNOWN or DISCONNECTED to on-battery and EMPTY to 10 percent, so games showed a flat battery on a pad that has none (issue #61). `IOCTL_XUSB_GET_LED_STATE` follows the same shape and always did.

### SWD Migration: the XInput slot-1-skip fix

Pre-fix, HIDMaestro created its devnodes via `SetupDiCreateDeviceInfoW` under `ROOT\`: the standard root-enumerated path. Windows assigns the null-sentinel ContainerID `{00000000-0000-0000-FFFF-FFFFFFFFFFFF}` to ROOT-enumerated devices unless overridden, and the SetupAPI path provides no way to override it.

Ghidra decomp of `xinput1_4.dll` on Win11 26200 traced the consequence. `FUN_18000de2c` returns 1 when ContainerID matches the null sentinel OR when HardwareIds contains the literal `XINPUT_EMBEDDED_DEVICE` substring. Caller `FUN_18000c728` at `0x18000C8AE` does `test al, al; jne → or dword ptr [rbx], 4`, setting bit 2 on the device struct. `FUN_18000f85c`'s fallback allocator at `0x18000F9C3-C7` skips internal slot 0 for bit-2 devices when Feature Manager flag `0x39EB83D` is on; `FUN_18000f178` then promotes the first bit-2 slot to "primary" and the query-time swap at `FUN_18000f08c` surfaces an empty slot 1 to consumers.

The fix is a one-line API switch: use `SwDeviceCreate(pContainerId = real-per-controller-GUID, ...)` instead of `SetupDiCreateDeviceInfoW`. The SwDevice API takes an explicit container GUID; we pass `{48494430-4D41-4553-5452-4F000000<idx:X4>}` (ASCII "HIDMAESTRO" + 16-bit controller index) so each virtual gets a deterministic non-sentinel container shared by its main + companion devnodes. `de2c` returns 0, bit 2 stays clear, slot allocator fills 0..3 contiguously.

The xinputhid-path profiles (Xbox Series BT etc.) moved fully to `SWD\HIDMAESTRO_VID_<vid>_PID_<pid>&IG_00\` because the SwDevice path is the only reliable way to inject a real ContainerID. The non-xinputhid Xbox path keeps its main HID device on `ROOT\VID_*&PID_*&IG_00\` (existing INF binding) and moves only the XUSB companion to `SWD\HIDMAESTRO\`. On the xinputhid path, main and companion share the per-controller container GUID. On the non-xinputhid path they do not: the ROOT-enumerated main keeps the null-sentinel container `{00000000-0000-0000-FFFF-FFFFFFFFFFFF}` because SetupAPI provides no override, while its companion carries the per-controller HIDMAESTRO container (measured on 26200, issue #59). No consumer that dedups on container can relate that pair; keeping the 360 family to one WGI entity rests on the xinputhid tripwire instead.

The underscore between VID and PID in the gamepad-companion enumerator (`HIDMAESTRO_VID_045E_PID_0B13&IG_00`, not `...VID_045E&PID_0B13...`) avoids a Windows PnP edge case in which any SWD enumerator name matching the substring `VID_*&PID_*&IG_*` registers in the registry but never enumerates as a live devnode. The `&IG_00` suffix is preserved because the HID child inherits its parent's enumerator name as the first segment of its instance path, and HIDAPI/SDL3/Chromium all blocklist `&IG_` substrings to avoid duplicating XInput-claimed devices.

### Stable Device Identity Across Lives

Since v1.8.0 (issue #60) every virtual controller has a durable identity, and every id a consumer can key on comes back the same on each life of that controller: the same process recreating it, a process restart, a reboot, and a driver upgrade. The identity is the consumer's key, passed as the second argument of `CreateController` and `CreateControllerAt`. A caller that passes none gets the controller index as its key, which is what every caller got before. The one exception is a HID child whose record an older build left without its driver, which takes the next prefix (below).

What consumers key on, measured on 26200: DirectInput's instance GUID is a per-VID/PID ordinal in `HKCU` and was stable already. SDL's joystick path is the HID interface path. Steam keys a USB/IP persona's configuration on its USB serial. Windows.Gaming.Input and GameInput key on the ContainerId and the device path. XInput keys on the slot only. Before v1.8.0 the HID interface path changed on every life, because every parent devnode was created with a Windows-generated instance name and its `ParentIdPrefix`, the `1&hash&n` value the HID child's instance id is built from, was minted again each time: one reporter's pad had counted 74 lives.

Every derived value is a pure function of the key, nothing is stored, and the mechanism differs per family:

| Family | Parent | How the child path stays put |
|--------|--------|------------------------------|
| Plain HID (Sony UMDF2, generic pads, wheels) | `ROOT\HIDClass\HM_0000` (SetupAPI, explicit instance id) | The identity's `ParentIdPrefix` is written into the instance key between `SetupDiCreateDeviceInfo` and `DIF_REGISTERDEVICE`. PnP reads the value from the parent's key when the HID child first arrives and mints a counter only when it is absent. When a record of a child on that path is out of the tree, has no Driver value and names HIDMaestro in its hardware ids, the parent gives its child the next prefix, `1&hash&1` to `1&hash&3`, the first whose path holds no such record (`DeviceManager.ChildPrefixFor`). A removal vetoed before v2.0.0 left such records, and no later child on that path started. |
| Non-xinputhid Xbox (Xbox 360 wired) | `ROOT\VID_045E&PID_028E&IG_00\HM_0000` (SetupAPI) plus `SWD\HIDMAESTRO\HM_0000` (SwDevice) | Main devnode as above. The XUSB companion has no HID child, so a fixed SwDevice tuple is the whole fix. Its interface path is `SWD#HIDMAESTRO#HM_0000#{EC87F1E3-...}` on every life. |
| xinputhid Xbox (Xbox Series, One, Elite over Bluetooth) | `SWD\HIDMAESTRO_VID_045E_PID_0B13&IG_00\HM_0000` (SwDevice) | Fixed SwDevice tuple. `SwDeviceCreate` binds and starts the driver inside the call, so the child has already enumerated by the time the SDK can write anything. The identity's prefix is reconciled into the key afterwards, and the restart the creation path already performs re-keys the child under it. |
| USB/IP composite personas | `USB\VID_054C&PID_0CE6\<serial>` (usbccgp) | A profile without a captured serial (the Sony composites) serves the identity's synthetic serial at a string index the descriptor did not use, so Windows keys the USB instance on the serial instead of the vhci port. Profiles with a captured serial keep it, varied by identity. The composite parent's own `ParentIdPrefix` persists in its phantom record the way it does for real hardware. |

`HM_0000` is the token for the default key of index 0. A consumer key derives `HM_` plus sixteen hex digits, a container GUID of the same `HIDMAESTRO` family, a `1&hash&0` prefix and a `HM` plus twelve hex digit serial, all from one SHA-256 of the key.

The session-unique instance-id suffix that v1.1.30 through v1.7.3 put on every SwDevice call is gone. It existed because a `DIF_REMOVE` on a `SWDeviceLifetimeParentPresent` device left the software device alive in the kernel, and a create with the same tuple reconnected to that half-removed shell: `S_OK` with no Service, no driver, no interface. Teardown has gone through `SwDeviceSetLifetime(Handle)` plus `SwDeviceClose` since v1.1.31, which destroys the software device, and the reuse works after it. The identity lab (`test/probes/identity_lab`, run on 26200, three lives per variant) measured the matrix the issue asked for:

| Variant | Bound | Same parent | Same child |
|---------|-------|-------------|------------|
| Unique SwDevice suffix, fixed container (v1.7.3 behavior) | yes | no | no |
| Fixed suffix, fixed container, phantom record retained | yes | yes | yes |
| Fixed suffix, fixed container, phantom record purged between lives | yes | yes | no (counter 0, 1, 2) |
| Fixed suffix, purged, prefix written after create plus restart | yes | yes | yes |
| Fixed suffix, changing container, retained | yes | yes | yes |
| Fixed suffix, fast remove without waiting for the cascade, immediate recreate | yes | yes | yes |
| XUSB companion, fixed suffix, retained or purged or changing container | yes | yes | (no child) |
| ROOT parent, explicit instance id, no prefix written | yes | yes | no (counter 0, 1, 2) |
| ROOT parent, explicit id, prefix written before registration | yes | yes | yes |
| Instance key created BEFORE `SwDeviceCreate` | **no** | | |

The last row is the one hazard: a `SWD` instance key that exists before the software device does leaves a record PnP stamps with a SYSTEM-only `Properties` subkey and never enumerates, and an administrator cannot delete it. Nothing in the SDK creates one. The ROOT path may write into its key before registration, because SetupAPI itself creates that key.

Two consequences for consumers. A DirectInput ordinal still moves when a same-VID/PID pad in front of it leaves (that is DirectInput's rule, not ours), while the path and serial of the remaining pad do not. And a different profile at the same key keeps the identity and refreshes the descriptor: the battery swaps a DualShock 4 in at a DualSense's key and reads the new attributes at the old paths.

### Profiles, Device Models and Load Errors

Profile JSON loads strictly, through the source-generated context with unmapped members and repeated properties refused. A file from a directory gets every check at load. The embedded catalog's files had their model groups checked at build, where a program that does not compile fails the build with `KG0001`, and S92 loads the same files from `profiles` with every check, so the catalog's own load reads their groups without checking them again. A file that does not parse, a key the schema lacks, a key written twice, a value a check refuses, a removed spelling (`steamFirmwareStamp`, the `ds3-battery` type, `usbConfiguration.protocol`) and an id already loaded each refuse the file, and a file with no `id` is not a profile. None of them throws from the load: each becomes an entry of `HMContext.ProfileLoadIssues`, an `HMProfileLoadIssue` with the file, the profile id, the JSON path as the file writes it (`$.protocol.rules[3].reply[1].length`), the reason and its `Kind` (`Refused`, `NotAProfile` or `ModelProblem`). Files load in ordinal path order, and a repeated id refuses the later file and names the earlier one, so a user's edited copy of a catalog profile needs an id of its own. The layout is checked against the descriptor at load too.

A profile changed or built in code meets the same checks at create, and `CreateController` throws `HMProfileException` for every defect of the profile itself: a model that does not compile, a layout that does not fit the descriptor, a descriptor hex string that is not whole hex bytes, and a profile with no descriptor. It derives from `InvalidOperationException` and carries `ProfileId`, `File`, `JsonPath` and `Reason`. `HMProfileBuilder.Build` throws it for its own errors. `HMLayoutValidationException` is no longer thrown by a create.

A profile's device model comes in three groups, each resolved at load on its own: the answers (`featureStubs`, `valueSources`), the protocol (`protocol`, `stateBlock`, `inputReports`, `liveFeatureReports`) and the presentation (`xinput`, `driverMode` as its alias, `driverPid`). Within a group the first of these that applies wins, and no two merge:

1. The profile's own keys in the group.
2. `deviceModelFrom`, naming a catalog profile, a model this release holds or a model loaded from the profile's directory.
3. A name nothing loaded holds, or a model that does not fit the profile's descriptor: the identity default, and `HMProfile.DeviceModelProblem` says why.
4. No keys and no name: the identity default whose entry matches the profile, or nothing.
5. `"deviceModel": "none"`: no model.

The identity defaults are data, `profiles/models/identity-defaults.json`, written from the vendor and product gates 1.x kept in code: the Switch Pro over USB and over Bluetooth (057E:2009, models `switch-pro-usb` and `switch-pro`), a `sixaxisCompatible` profile (`dualshock-3-full`), Sony's VID 054C by product and connection, each Sony entry naming one of the six Sony models, and VID 045E with "xbox" in the id, name or product string (`xbox-360-wired`'s presentation, an XUSB companion). The code that reads the table compares a profile's identity with each entry and names no device. No catalog profile takes a group from it, and S92 fails if one does, so a profile from `HMProfileBuilder`, `HMDeviceExtractor` or a user's JSON keeps the behavior its identity got from 1.x. `HMProfile.HasDeviceModel`, `DeviceModelSource` (per group, `own`, `named:<id>`, `identity:<entry>` or `none`) and `DeviceModelProblem` report the result. `HMDeviceExtractor.Extract` writes the `deviceModelFrom` its identity gives, and `HMDeviceExtractor.ResolveDeviceModel` returns a copy with that name for a profile that has none. The extractor reads the bus as hidapi and SDL do (`hid_internal_detect_bus_type`): the first of the parent devnode's compatible IDs that holds USB, BTHENUM or BTHLEDEVICE names it, Bluetooth LE for the last, and anything else reads as USB. The parent's hardware IDs give `bluetoothVendorIdSource`, and `ToJson` writes it with `bluetoothTransport`. Through v1.12.0 the bus came from the device path, so a HIDMaestro Bluetooth controller, whose HID child is `HID\HIDCLASS\...`, extracted as USB.

A directory loaded with `LoadProfilesFromDirectory` can carry a `models` folder, named models and an `identity-defaults.json` in the catalog's formats, which load with no rebuild. Its models resolve by name for its profiles and later loads, and its identity defaults are tried before the catalog's, for profiles outside the catalog, as `identity:<file>#<entry>`. A `keyedHexFile` value source is refused on UMDF2, where the driver answers without calling the SDK.

`HMProfileBuilder.FromProfile` copies the whole profile, its model keys and `deviceModelFrom` included. Replacing a copy's descriptor drops the keys its report format governs. `ClearDeviceModel` drops the report model and keeps the presentation, and the builder gains `DeviceModel`, `DeviceModelFrom`, `DriverPid` and `FeatureAnswers`.

The `xinput` block is the presentation. `via` is `"xusbCompanion"`, an XUSB companion devnode beside the HID device as xusb22 presents a wired Xbox 360 pad, or `"xinputhid"`, Microsoft's xinputhid above the HID child, and an empty block means no XInput. `subType`, `flags`, `battery` and `information` set what the companion answers. Its four replies are data in `profiles/models/xusb-companion.json` (`xusbAnswers`), a wired gamepad's, with the profile's values written at the offsets the model names, and the SDK compiles them into the controller's `XusbAnswers` value. The companion serves them only under the version contract, and registers its XUSB interface only when it holds them, so a 1.x controller on the 2.0.0 companion gets no XInput. `HMProfile.XInput` and `HMProfileBuilder.XInput` read and set the block. The two wheel profiles report subtype 2, the wheel, and `xbox-360-wireless` presents its HID child as 045E:02A1 and reports itself wireless, with PID 0 in its 36-byte capability reply. The nine Microsoft profiles that are no XInput device (the SideWinder Force Feedback 2 and eight keyboards and mice) are parents under `ROOT\HIDClass` with no `IG_` and no XUSB compatible IDs.

A profile carries its `xinput` block, its `driverMode`, or neither. The ten Xbox 360 profiles carry the block and the twelve xinputhid profiles their `driverMode`, so no catalog profile takes its presentation from the identity default.

`HIDMaestroProfileCheck`, which ships beside the profile extractor, loads the catalog and then a file or directory as the SDK does, prints each issue of the named files as `<file> at <JSON path>: <reason>`, and each loaded profile with its `DeviceModelSource`, and exits 0, 1 or 2. `--cost` runs each of the file's programs and decoders on the interpreter as the design note's table was measured, 30 hidden launches at high priority, and prints p50 and p95 with the runtime, tiering, CPU and instruction set, each program's compile and the whole model's. `--register name=value` starts a register at a value of its own, where registers otherwise start at the protocol's initial values.

### Keyboards and Mice

A profile whose `type` is `keyboard` or `mouse` is created like any other plain HID profile and reaches Windows as the device its descriptor describes. Windows' keyboard and mouse class drivers open its collections, Raw Input lists them, and the desktop acts on the input. The catalog holds 51 keyboards and 52 mice. Each is the report descriptor of one interface of a real device, taken from public dumps: usbhid-dump output posted in project issues, libinput recordings and the Linux kernel's HID selftests. Two Bluetooth keyboard dumps end with a zero byte after the last End Collection, which Linux ignores and Windows' HID parser rejects, so those two profiles leave it out.

`SubmitMouse`, `SubmitKeyboard` and `SubmitConsumer` pack into the profile's own reports. The SDK reads the descriptor with a parser that follows the HID 1.11 item rules (section 6.2.2): global items persist and stack with Push and Pop, local items reset after each main item, a 4-byte usage carries its own page, and each report ID counts its bits from zero. Every field lands where the descriptor puts it, so a mouse whose buttons and motion sit in separate reports gets both. A relative movement larger than the descriptor's field is split across as many reports as it takes. `HidDescriptorBuilder` has starters for building one in code: `Mouse` (relative 16-bit, or absolute 0 to 32767), `Keyboard` (the boot layout), `KeyboardNkro`, `ConsumerControl` and `VendorButtons`. The packer is built once per profile and shared, and each controller packs into buffers of its own under its submit lock, so a keyboard or mouse submit allocates nothing (battery S84). Through v1.12.0 each one allocated 539 bytes for a keyboard report and 248 for a mouse report.

A relative field whose range excludes zero, such as the relative X and Y of `corsair-k70-rgb-mk2-low-profile` (1 to 32767), cannot carry a click's zero or a movement left or up. The packer writes 0, no motion, for a movement the field cannot carry at all, and owes nothing for it or for a part that overshoots, so every split of a large movement ends. After a submit has sent a long split, the controller keeps 16 frames (`KeyboardMousePacker.MotionFramesKept`) and lets the rest go. Fields whose range holds zero pack the same bytes as before. The release frame is rewritten in place.

RAWMOUSE carries five buttons. A mouse that needs more adds a second, vendor-page collection with `VendorButtons`, and `SubmitMouse` sends buttons six and up there. Raw Input lists that collection as a HID device of its own. An absolute mouse reaches Raw Input flagged `MOUSE_MOVE_ABSOLUTE`, on Windows' 0 to 65535 scale.

The input section holds one report, the newest. That suits a gamepad, whose state replaces the last, and loses data for a mouse, whose movement adds up, and for a keyboard, whose make and break must both arrive. For keyboards and mice the driver acknowledges delivery. When HID class sends its next read after one completed with a report, the driver writes that report's sequence number to `Global\HIDMaestroInputAck<N>` and signals `Global\HIDMaestroInputAckEvent<N>`. HID class sends that next read only after its completion routine has put the report in its buffer, so the report after it cannot overtake it. Acknowledging when the read completed let that happen on a machine with every core busy: with four mice each sending 500 reports at 1,000 a second, adjacent reports of one mouse swapped in 24 of 800 runs, which on a keyboard can leave a key down. Acknowledged on the next read, none of 800 swapped and none lost a report. The driver records the acknowledgement it owes before it completes the read, because HID class can send the next read the moment the first completes. Recorded after, that read can arrive first and find nothing to acknowledge, and the submit call then waits out its full 200 ms. On a busy machine that happened in nearly every run. The SDK creates both objects, since the driver runs as LocalService and cannot create a Global object, and the driver opens them when its worker starts. Before writing a report, each submit method waits for the previous report's acknowledgement and keeps reports at least 1 ms apart, the interval of a full-speed USB device polled every frame. HID class keeps a short queue for each reader. Without the spacing, a burst of 600 one-count moves went out at 27,000 reports a second and Windows dropped counts. With it, the burst takes 601 ms and every count arrives, and four threads driving four mice at 250 Hz lose nothing. A wait gives up after 200 ms. After three misses in a row the controller stops waiting until an acknowledgement arrives again, so a device Windows has stopped reading does not hold up the caller. `DeliversEveryReport` is false on a gamepad and on a driver older than v1.12.0. Windows merges consecutive mouse moves into one WM_INPUT message (RAWMOUSE has `MOUSE_MOVE_NOCOALESCE` for that reason), so the checks compare the sum of movement, not the number of messages.

Windows sends a keyboard its LED state as an output report when the keyboard arrives and on every change, and resends it to the keyboards already present when another one arrives. `KeyboardLedsChanged` raises the decoded state and `KeyboardLeds` keeps the last one. The arrival report comes while `CreateController` is still running, before a handler can be attached. Through v1.11.0 the output reader started at the ring position it found when the controller object was built, after the device had started, so the arrival report went unread, and so did anything else a host sent during creation, such as the feature reads a Sony Bluetooth host makes on arrival, which arm the extended report. Each controller's setup now records the ring position before the device exists, and the reader starts there.

A consumer that goes away with a key or button held would leave it held. Windows repeats a held key about 30 times a second until the device is removed, measured at 32 repeats in 1.5 s after a consumer was killed with F24 down, and a held Shift or Ctrl stays held for the whole desktop. ViGEmBus unplugs a client's devices from its file-close callback, which Windows calls when the client's process exits or closes its handle (`sys/Driver.cpp`, `Bus_FileClose`). A user-mode driver gets no such callback, so the SDK holds the server end of a named pipe for each controller, `\\.\pipe\HIDMaestroOwner<N>`, and the driver connects and keeps one read pending on it. Nothing is ever written to the pipe, so the read completes only when the SDK's end closes, on Dispose or when the process ends however it ends. The driver then sends the release reports the SDK keeps in the acknowledgement section, one for each input report the controller has sent: keys and buttons up, relative motion and the wheel zero, array slots empty, a hat centered, and absolute pointer axes where they were, so the pointer does not jump. Dispose sends the same reports itself before teardown. A consumer that exits normally without disposing has its devices removed by the SDK's exit handler, and a killed consumer's devices go with the next sweep of any program, as an orphaned gamepad's do. A keyboard leaves by a different route. Windows will not disable a keyboard, and while one is up it will not disable the device above it either, so the disable and uninstall the cleanup uses on every other device fail on both, as do pnputil and devcon on the root (`ERROR_NOT_DISABLEABLE`). `SetupDiRemoveDevice` still removes the keyboard itself, and the root can be disabled once it is gone. The cleanup removes any device that refuses the disable that way, children first, the order Dispose uses. `ReleasesOnConsumerExit` says whether the driver watches.

A keyboard without report IDs receives its LED report as the LED byte alone. Both backends split a report at its first byte (`HMOutputPacket.ReportId`), so on such a keyboard `ReportId` holds the LED byte and `Data` is empty. The LED decoder puts the two back together.

Four mice with one VID and PID are four Raw Input devices with four paths, and each identity key gets its own path back on every life (see Stable Device Identity Across Lives). Keyboard and mouse profiles get no GameInput mapping and no joy.cpl OEM name. Battery scenario S69 checks the parser, the starters and the packers with no device, and S70 checks the rest through Raw Input, including a consumer killed while it holds a key, a mouse button and an absolute pointer, and the cleanup that removes the devices it left.

The driver also no longer completes a second read with a synthetic report 0x20 built from the trigger values. That path was left from an April 2026 experiment with a second collection for Xbox 360 triggers. It fired on a byte scan for `85 20` in descriptors longer than 130 bytes, which matched only the DualSense family, where 0x20 is a feature report, so the five driver-backed DualSense profiles had an input report their descriptor does not declare put in their read queue on every frame.

### Programs Side by Side

Several programs that embed HIDMaestro share one machine. Through v1.12.0 every machine-wide name was keyed by a controller index that each program numbered for itself, so two programs that each created a first controller wrote the same sections and registry keys, and a driver deploy or sweep in one removed what the other used. The design note, [docs/design/coexistence.md](design/coexistence.md), has the measurements, the rejected alternatives and the sources behind each choice below.

#### Ownership Claims

A process takes one ownership claim before its first machine-wide write and holds it until it exits. The claim is a named pipe created with `FILE_FLAG_FIRST_PIPE_INSTANCE` and a maximum of one instance. Claiming is the check: the second claimant learns it lost from the same call that would have won. On the development laptop it fails with `ERROR_PIPE_BUSY`, because the instance limit is checked before the first-instance flag, and either error means the claim is held. Windows deletes the pipe when the last handle closes, which happens when the process ends however it ends, and a pipe handle has no thread affinity.

Liveness is a `WaitNamedPipe` probe with a 1 ms timeout. A missing pipe fails with `ERROR_FILE_NOT_FOUND` in under 5 µs. A true return and `ERROR_SEM_TIMEOUT` both mean a live holder, and any other error counts as live. The probe opens no handle, so probing cannot keep a claim alive. A named event judged by `ERROR_ALREADY_EXISTS` was the other candidate and lost on one point: a sweep that probes an event holds it open for the length of the probe, and a claimant arriving in that window reads a live owner where there is none.

The claim pipes live under the pipe prefix `ProtectedPrefix\Administrators\`, which the Session Manager creates at boot and under which only a token with Administrators enabled can create a pipe, so a program that is not elevated cannot create a claim first and pass for a live owner. No Learn page describes the prefixes. Every `smss.exe` read, 10.0.10240 through 26100.1, creates it, and the refusal of a token without Administrators was measured on 26200 (`MachineClaims.cs` lists the binaries). The pipes carry `O:BAD:P(A;;0x00100080;;;SY)(A;;0x00100080;;;BA)(A;;0x00100080;;;LS)`, owner Administrators and SYNCHRONIZE and FILE_READ_ATTRIBUTES for SYSTEM, Administrators and LocalService only. A process that is not elevated can still probe a claim, and can neither open one nor take one. Nothing can read or write a claim, and the driver host never opens one. It keeps opening only the owner pipe it already uses.

| Claim | Pipe name | Held for |
|-------|-----------|----------|
| Owner | `\\.\pipe\ProtectedPrefix\Administrators\HIDMaestro.Owner.<owner id>` | the process, from its first machine-wide write |
| Transport index | `\\.\pipe\ProtectedPrefix\Administrators\HIDMaestro.Index.<N>` | the controller's life |
| Identity | `\\.\pipe\ProtectedPrefix\Administrators\HIDMaestro.Identity.<token>` | the controller's life |

A claim refused with `ERROR_ACCESS_DENIED` throws `UnauthorizedAccessException`, and any other error `InvalidOperationException`. The access message depends on the token: without Administrators enabled it asks for an elevated process, and with Administrators enabled it names a pipe system without the prefix, or software that filters pipe creation, as possible causes. A sweep refused for access skips its work.

The owner id is a GUID the process draws once. Beside the owner claim sits a record at `HKLM\SOFTWARE\HIDMaestroOwners\<owner id>`, readable by everyone: process id, image path, start time, SDK version, USB/IP server port, the name of the staging directory the process uses, and one subkey per live controller with its identity token, transport index, backend, profile id, devnode instance id and vhci port. The record is written with the owner claim and stays until the process exits or is killed, so a program between its `InstallDriver` and its first create is as visible as one with controllers. A record write that fails is tried again at the next call that takes the claim. The vhci port in a controller's entry is the current one, rewritten when usbip-win2 imports the device again and 0 while it is dropped. A controller's entry is written before any PnP work and removed once its devices are gone. A record whose owner claim no longer exists describes a dead owner, which is what the sweeps act on. The process id and start time are for people reading the record. Nothing decides liveness from them.

#### Transport Index and Slot

`CreateController` numbers controllers by slot within a context. Each controller also holds a machine-wide transport index, which names every section, event, pipe and registry key and is the `ControllerIndex` the driver reads. `HMController.TransportIndex` and `HMController.SectionNames` expose it. The transport index is the slot when that number is free machine-wide and the lowest free number otherwise, so a program running alone gets the numbers it always got and native writers that compute names from the index see no change. Two programs that each create a first controller coexist, the second on the lowest free index. While a v1.12.0 program runs, read from a present device whose owner pipe the driver watches, from a USB/IP import no record names whose index's owner pipe is held, or, while a present device's index cannot be read, from the registry ledger (Census and Sweeps), the search starts at 64 (`ControllerLease.LegacyClearance`): such a program's next create takes the lowest index free among its own controllers and replaces a devnode of that index's default identity, so a lower index would let it take this program's device. Everything derived from the index moves with it: a keyless controller's identity token and so its paths and container id, every controller's HID serial and MAC bytes, a byte of the XUSB capabilities, the USB/IP bus id, and a keyless composite's USB serial and instance id. A program restarted after a crash takes its old index back only when it is 64 or more. A key of the form `index:N` with N below 64 takes index N's default identity as asked, on an index from 64. That program gives the same identity to its own controller on index N, and its next create there replaces a devnode of that name. An index N is free when all of these hold:

- its claim `HIDMaestro.Index.<N>` can be created,
- no process holds `\\.\pipe\HIDMaestroOwner<N>`, v1.12.0's owner pipe, whoever made it,
- none of the index's sections and events exists with an owner other than SYSTEM or Administrators (LocalService for the driver's StopEvent and OutputEvent), as another kind of object, refusing READ_CONTROL, failing to open for another error, or with an owner that cannot be read,
- no present HIDMaestro devnode records N as its `ControllerIndex`, unless the devnode carries the identity this create is about to reclaim,
- no USB/IP import uses it whose server port no record names. Such an import belongs to a program on an older SDK, whose composite has no devnode to record the index, and its bus id `1-<N+1>` carries it.

Whether the input section exists is no evidence either way. After an Xbox 360 controller's Dispose returns, `Global\HIDMaestroInput<N>` stays open for as long as the disposing program lives, on v1.12.0 as on this release: the SDK's own XInput calls during the create leave xinput1_4 holding a handle to the XUSB companion, which keeps the removed companion's driver host and its view of the section alive until the program polls XInput again or exits. An allocator that skipped indices with an open section would move a program off its index after such a dispose. A v1.12.0 program in the middle of creating its sections is a race this release does not close. The owner pipe's first instance is created with the first-instance flag and v1.12.0's access mode, type, instance count and timeout, which all instances of one pipe must share, before the create writes any section, so a v1.12.0 program that starts on the index between the check and the create makes the create fail with `HMResourceInUseException` rather than share the sections. An event of the index that another program made after the check refuses the create the same way. When all 4096 indices fail, the create throws `HMResourceInUseException`, whose message counts the indices skipped for a foreign object, names the first with its owner SID when one was read, and names a program built on HIDMaestro 1.12.0 or older as a possible maker only beside an owner it read.

A keyless controller's default identity derives from its transport index, so when another program holds index 0 it lands on another index and another identity. When the index's identity claim is held by another program's sweep, which holds it while it removes what a dead program left under that identity, a keyless create waits up to 120 seconds for the claim, as a keyed create does, and then reads again what it had checked the index against: another program's owner pipe or `Global\` object on the index, and the floor of 64. A claim a live record lists, as from a key of the form `index:N`, still sends the create to the next index at once. Durable device paths need an identity key, the contract since v1.8.0.

#### Identity Claims

The identity claim is taken before any PnP work. A program asking for an identity a live program holds gets `HMResourceInUseException`, derived from `InvalidOperationException`, whose message and `OwnerProcessId`, `OwnerImagePath` and `OwnerSdkVersion` name the holder from its record. The holder's devices see no PnP activity. The same check applies across contexts inside one process. While no live record lists the token, a keyed create waits for the claim up to 120 seconds, since another program's sweep holds it while it removes a dead program's device of that identity, and then takes the census again. A v1.12.0 program takes no identity claim, so when a present devnode carries the token and no record lists it, the create asks the census whether a running v1.12.0 program holds the devnode's `ControllerIndex`, and refuses the create with the same exception while one does.

A create that fails gives back what it took before it throws. A UMDF2 controller's devices are removed, its sections, events and owner pipe closed, its configuration key deleted and its registry ledger holds released, then its record entry, identity claim and index claim go, keyed or keyless. `SetupController` hands the cleanup its parent's instance ID as soon as the registration gives it, so a create that throws after that, on a failed start or a driver of another protocol, removes its parent by that ID, a plain HID parent under `ROOT\HIDClass` included, which no sweep by index reaches. A composite's device is disposed and its emulator's threads stop, also when its constructor threw. A create refused because a running v1.12.0 program took the index during the create, or because the device of a running program, or of one whose owner cannot be known, holds the ParentIdPrefix, releases only what the refused call made and touches nothing of the other program.

`ClearParentIdPrefixRivals` keeps the 0xCA invariant: no two parents whose HID children would share a device instance path. hidclass names a child after its parent's enumerator segment and ParentIdPrefix, so a rival is a parent under the create's enumerator, in ROOT or SWD, on a prefix the create's child can arrive under, or the same token under another HIDMaestro ROOT enumerator. An SWD create rewrites its retained record's prefix first, since SwDeviceCreate starts the child under it. A present rival is removed only when its owner is provably dead. When the owner is running, here or in another program, or cannot be known, the create is refused with `HMResourceInUseException` and the message names the rival devnode. When the owner cannot be known, it also names the cleanup call that removes the device. A rival that is not present is removed as before, because a ROOT record re-enumerates at boot.

#### Census and Sweeps

A sweep removes a present device only on proof that its owner is gone. The census (`OwnerCensus`) groups what it knows about each present HIDMaestro devnode by identity token:

| Present device | Owner | Action |
|----------------|-------|--------|
| In a record whose owner claim is gone | dead | removed with everything the record lists, unless a running program holds the device's index or identity |
| In no live record, its index or identity claim held | a running program on this release | left alone |
| In a live record | running | left alone, the caller's own included |
| In no record, `HIDMaestroOwner<N>` held by the program the driver watches | a running v1.12.0 program | left alone |
| In no record, the pipe gone or not the watched program's, `Global\HIDMaestroInputAck<N>` exists | a v1.12.0 program that has exited | removed |
| In no record, no owner pipe, no InputAck section | a program older than v1.12.0, state unknown | left alone |

Only a v1.12.0 or later SDK creates `HIDMaestroInputAck<N>`. A device with neither the pipe nor the section came from an older SDK whose program leaves no sign of whether it still runs. No sweep without a scope removes it. The uninstall-grade cleanup does, and so does a create that asks for the device's own identity key, because that program is asking for the device back.

The census reads a device's index from its `Device Parameters\ControllerIndex`. A v1.12.0 device whose driver install failed read no value in Windows Sandbox while its program ran, though its create had written one. The census keeps why it read none (no value, no key, a key it may not read) and logs it. A keyless device's token, `HM_<index>`, names its index, so the census takes it from there and the allocator skips that one index. A keyed device with no readable index is tied to no owner pipe: with no record naming it, it reads as a program's of unknown state and a sweep leaves it, and a dead record that names it still makes it removable. While such a device is present, the census looks for a running v1.12.0 program another way. A v1.12.0 create writes a registry ledger holder `<pid>-<start>-<index>` under `HKLM\SOFTWARE\HIDMaestroRegistryLedger\JoystickOem\<VID&PID>\Holders` before its devnode exists, for every controller but a keyboard or mouse, and removes it at teardown. This release writes the same holders only after its owner record, and its exit deletes the record only once its holders are gone, so a holder on an index below 64 whose process runs and that no live record names is a v1.12.0 program's, and it raises the floor. The census reads the holders, then the records, then the holders again, and counts a holder both reads have. A holder's process is opened for its creation time, and only one that refuses the open is looked up in the system's process list, read at most once per census, from 4 MB. The other sign is an index no live record and no present device accounts for whose owner pipe is held beside its input section and an acknowledgement section without the ended marker. A v1.12.0 program of only keyboards and mice, or one whose ledger write failed, whose device's index cannot be read, on an index a running program of this release holds, stays unseen. A device a closed program left raises no floor.

Any program can create the name `\\.\pipe\HIDMaestroOwner<N>`, so a held pipe alone proves nothing. The driver is the pipe's client and asks Windows who serves it. When its watch connects, it writes `OwnerProcessId` (`GetNamedPipeServerProcessId`), `OwnerPipeOwner` (the pipe's owner SID as text) and then `OwnerConnected` 1 under the device's `Device Parameters\HIDMaestro` key. When the server's end closes, it sets bit 31 of InputAck's capability word, the ended marker, and writes `OwnerConnected` 0. A device context deletes the three values when it starts, and the values are written only when the watch connects or ends, never per frame. The census counts a held pipe as a running v1.12.0 program while the values show a connected watch whose server still runs and was created no later than the key's last write. `OwnerConnected` 0 beside a set marker, or a recorded server that has ended, makes the pipe count for nothing. Without the values, from an older driver or a watch that has not connected, and when `OwnerConnected` is 0 beside a clear marker, it counts the pipe only while the input section exists and the marker is clear. A process the census may not open is timed from the system's process list, and one it cannot time counts as running. This driver keeps InputAck mapped for as long as the device exists. v1.12.0's driver closes it on every idle recycle, so a dead v1.12.0 program's device on that driver reads as unknown about 4 s after the program ends, and stays. A live record wins over a dead one. The census binds a present device to the record that lists its identity token, or for a device older than identity tokens its transport index, and takes a live record before a dead one. A dead record names a device only while no running program holds the device's index or identity.

The census reads the instances under the ROOT and SWD keys of `SYSTEM\CurrentControlSet\Enum` that HIDMaestro's enumerators (`HIDMAESTRO*`, `HMCOMPANION*`) or the shared ones (`VID_*`, `XnaComposite`, `HID_IG_00`, `HIDCLASS`, `SYSTEM`) hold, and checks presence with `CM_Locate_DevNode` for HIDMaestro-owned instances only, which finds a present devnode and no absent one. A shared enumerator's instance counts when its hardware ids name HIDMaestro. Past 64 candidate instances, or when a key cannot be read, it goes back to `CM_Get_Device_ID_List` with `CM_GETIDLIST_FILTER_ENUMERATOR | CM_GETIDLIST_FILTER_PRESENT` for the two roots, whose cost does not grow with absent devnodes (b470c49). That commit's development measurement put claiming at 0.57 ms at p50 and 0.66 ms at p95 of a create, census included, and the release at 0.24 ms of the dispose. With no dead record and no present device of a dead program, nothing walks the enumerators. The reclaim of exited programs runs before a create's lease on both backends, once per process, so a keyless program restarted after a crash gets its index and identity back, unless a running v1.12.0 program moved creates above its old index (Transport Index and Slot).

A sweep takes each dead group's index and identity claims before it acts on the group and keeps them until every group it removes, and every orphaned HID child it removes after them, is out of the device tree, waiting up to 10 seconds for each orphan. A create of this release takes both claims before it writes its configuration or makes a devnode, so no create lands on a group the sweep is removing, and a group whose claims another program holds is skipped. A v1.12.0 program takes no claim, so its owner pipe is checked again right before each removal and each configuration delete. A group the sweep cannot confirm gone keeps its configuration and its dead record, so the next sweep still sees a dead owner's device. A device that stays in the tree after every removal therefore costs every sweep a retry of up to 120 seconds, and up to 10 seconds per orphan. A device whose index or identity claim a program holds counts as a running program's, with or without a record, since a program on this release takes its claims before its record entry.

The phantom-record cleanup runs on a background thread once per process, started by the first of `InstallDriver`, the first create and `RemoveAllVirtualControllers()`. The call that starts it returns without waiting for it to end, a later call removes no phantom, and the next process's first cleanup removes what is left. It takes `OwnerSweep.CreateGate` for writing, and every create holds it for reading from its lease to its last record write, so the cleanup never runs during one of this process's creates. A create, and the uninstall-grade cleanup, which takes the gate for writing before it acts, wait while the cleanup runs: one pass over the phantoms, their uninstalls, at most 5 seconds of waiting in all, for the machine-wide PnP lock before each uninstall and for Windows to let the phantom go after it, and two passes over interface registrations that wait for the lock within the same 5 seconds. Each uninstall runs under the identity claim of the phantom's controller, its own token's or, for a HID child, its parent's, and the cleanup keeps that claim and the gate until a PHANTOM locate no longer finds the id or the 5 seconds are spent. A phantom whose identity claim a program holds is that program's create in flight and is skipped, and so is a default identity's phantom while a v1.12.0 program holds that index's owner pipe. `RemoveAllVirtualControllers()` and `(bool)` start the cleanup when it has not run and remove the phantom interface registrations on the caller's thread.

When the process's first claim is taken inside the program's own `ProcessExit` handler, the SDK's exit handler is registered too late to run, so a cleanup thread would end with the process, possibly inside an uninstall. `Environment.HasShutdownStarted` returns false on .NET 10, but the runtime raises `AssemblyLoadContext.Default.Unloading` before `ProcessExit` on .NET and NativeAOT (`AppContext.OnProcessExit`), and the SDK's module initializer subscribes to it (`ProcessExitSignal`). Once it has fired, the first call runs the cleanup on the calling thread before it returns, waiting at most 10 seconds for the gate. Under NativeAOT module initializers run at startup, so the signal always holds. Under .NET the initializer runs when code that refers to the SDK is first compiled, or first run where it was compiled ahead of time, so the signal misses a program in which no such code ran or was compiled before exit began, such as one that uses the SDK only inside its own exit handler, and that cleanup ends with the process. The next process's first cleanup removes what is left.

USB/IP imports are matched by server port. A server takes a loopback port from 18509 to 18524, then from 28509 to 28524, then one Windows assigns, and records it in its owner's record. An import counts as the SDK's on either range or on any port a record names, and ports compare as numbers. An import whose server port has no listener on loopback, read with `IPGlobalProperties.GetActiveTcpListeners`, belongs to a dead server and is detached. An import on this process's own port that none of its controllers made was left by the program that held the port before, and is detached. Every detach is by server port and bus id, since a dropped and re-imported device's vhci port changes. The re-attach attempts of a dropped import are canceled by exact location: each bus id a dead record names on its server's port, plus 1-1 to 1-8 on a gone port of the first range, which a v1.12.0 server canceled itself. A location a live server exports is never canceled, and a server that does not answer its device list within 1 s keeps its attempts.

The public cleanup keeps its overloads and acts on the devices of exited programs: `RemoveAllVirtualControllers()` and `RemoveAllVirtualControllers(bool preserveInstall)`. A running program's controllers, the caller's own included, stay. Both also remove the GameInput tables v1.11.0 left, except a table whose VID and PID a present device or any `Controller<N>` configuration names, and none while an input section exists that no configuration, present device, live record, foreign import or InputAck section explains, which is a v1.11.0 create whose identity cannot be read yet. Package removal (`preserveInstall: false`) happens only while no other program runs, no device remains and the caller has no controller, and it takes the deploy lock. In a process that is not elevated both overloads return without doing anything. `RemoveAllVirtualControllers(HMCleanupScope.Everything, bool)` removes every HIDMaestro device and import regardless of owner, which `HIDMaestroTest cleanup` and the battery use, and with `preserveInstall: false` it removes the packages under the deploy lock with no check for other programs or the caller's controllers. It releases this process's sections only under `CreateGate`'s write side, since a create maps its index before its controller holds it, and `SharedMemoryIO.Cleanup` throws without it. An index a controller of the calling program still holds keeps its sections. The sweep clears the driver's DELIVERED and RELEASE bits in that index's InputAck and the `DriverProtocol` word of its version section, then stops the controller's idle repeat, protocol clock and output reader and drops a protocol reply the driver never delivered. The controller's submits and PID calls still write its sections and reach nothing, `DriverVersion` reads null, `DeliversEveryReport` and `ReleasesOnConsumerExit` false, and a keyboard or mouse submit waits for no delivery. Its `Dispose` releases the sections and the index. This covers the calling program's own controllers only: a controller another running program holds still reads the removed driver's words, so its `DriverVersion` names that driver, `DeliversEveryReport` and `ReleasesOnConsumerExit` stay true, its keyboard and mouse submits wait up to 200 ms on each of the next three frames, and a protocol controller's next send waits up to 200 ms for the reply the device never delivered.

A program that exits normally without disposing has its devices removed by the SDK's own `ProcessExit` handler, registered with the owner claim. The handler waits at most 10 seconds in all for the phantom cleanup, which starts no further uninstall once the handler runs, and for a create in flight. Past that bound it removes nothing and keeps the record. Otherwise it stops the program's WinUSB re-binds, waiting out a bind in progress, detaches its imports, signals its stop events, removes its device groups one at a time on its own thread, each removal within its own bound as `Dispose` does, releases its GameInput and joy.cpl holds in one ledger scope, then restores its WinUSB entries, each entry with up to two short ledger acquisitions of its own, and deletes its record once its holds are gone. A release that fails is tried again, and a hold that still stands keeps the record until the process ends, whether or not it still lists a controller. Those WinUSB waits fall outside the 10-second bound. A device it cannot confirm gone keeps the record too. The devices stay present until a program built on this release next sweeps in these cases: a create still holds on at the bound, on another thread or waiting for another program's sweep, one phantom uninstall lasts longer than the bound, a device does not leave, or, under .NET, where the handler runs on the finalizer thread, a thread inside a create calls `Environment.Exit`. Each removal waits for the machine-wide PnP lock only within what is left of the 10 seconds, and only the time another program holds it is charged, never the removal's own work under the lock nor a wait behind another removal of this process, so another program holding that lock longer leaves the devices and the record for the next sweep too. Once the runtime has begun to exit (`ProcessExitSignal`), every take of that lock on a thread with no bound of its own, a program's own `Dispose` or cleanup from its exit handler, waits within one 10-second budget the process shares. Threads of the process take the lock through an in-process gate first, one at a time, so a budget counts only the waits for another program, and threads waiting together spend the shared one once (`DeviceManager.OtherProgramWaitTicks`). During the exit a wait behind one hold of the process's own is bounded by the whole budget, so a hold longer than that refuses the take queued behind it as if it were stuck. A controller whose teardown the budget cuts short keeps its lease, so its record entry names the devices. The runtime runs ProcessExit handlers in the order they were added (`AppDomain.OnProcessExit` invokes the event's delegate), and the SDK adds its own with the owner claim, so when the program's handler came first the SDK's handler removes those devices next, within its own budget. Otherwise the next sweep removes them through the record. A killed program runs no handler, and its devices go with the next sweep of any program, through its record. A context dropped without `Dispose` keeps its controllers, their indices and their identity keys, through a static set of leases, until the process exits, and a create of one of those keys in that process is refused until then.

#### Machine-Wide Locks

The SDK's locks are mutexes in a private namespace whose boundary holds the name `HIDMaestro` and the Administrators SID, opened under the alias `HIDMaestro.Admin` with the descriptor `O:BAD:P(A;;GA;;;SY)(A;;GA;;;BA)`. Only a process whose token has Administrators enabled can create or open it, so a program that is not elevated can neither take a lock's name first nor hold it, and a process that is not elevated gets `UnauthorizedAccessException` at its first lock. Every process opens the namespace once and keeps the handle until it exits. No session is part of the boundary, so by the Object Namespaces page a session-0 service and a desktop program share it when both are elevated. No test opened it from two sessions.

| Lock | Taken by | Wait |
|------|----------|------|
| `HIDMaestro.Admin\Deploy` | a driver deploy past its fast path, the UMDF2 create gate, `DriverBuilder.SignDrivers`, `GenerateCatalogs` and `RemoveOldDriverPackages`, the test certificate's creation, package removal, a WinUSB package add | 10 minutes, then `InvalidOperationException` |
| `HIDMaestro.Admin\Transport` | the usbip-win2 install, a host controller repair, the move to 0.9.8.1 | 10 minutes, then `InvalidOperationException` |
| `HIDMaestro.Admin\WinUsb` | a WinUSB bind's devnode work, a WinUSB restore, the WinUSB package's removal | 2 minutes, then `InvalidOperationException` |
| `HIDMaestro.Admin\WinUsbFollowUp.<entry>` | the follow-up of one lingering WinUSB entry | never waited on |
| `HIDMaestro.Admin\Ledger` | the registry ledger and `HMOemNameOverride` | no bound for most calls, 30 s, scaled, for the WinUSB claims, restores and package note reads, then `TimeoutException`. A restore that gives up keeps its entry for the next sweep |
| `HIDMaestro.Admin\Staging` | the note of a staging directory in the owner record, a staging prune | 2 minutes, then `InvalidOperationException` |
| `HIDMaestro.Admin\Pnp` | each devnode registration, each removal and uninstall through its removal test, a full deploy's pnputil install, every create's bus type stamp, the ghost XUSB sweep and the interface-class cleanup per devnode | 10 minutes, then `InvalidOperationException`. Once the process is exiting, only what is left of the exit's 10 s |

An abandoned mutex is acquired and the work under it reads the machine again. The order is the deploy lock, then the WinUSB lock, then a controller's bind gate inside the process, then the ledger's. A follow-up takes its own mutex before the WinUSB lock. The staging lock is a leaf under the deploy or transport lock or none. The transport lock has no edge with the deploy lock, so a UMDF2 create never waits for a usbip-win2 install. The PnP lock comes after the deploy lock and before the staging lock: a full deploy takes it for its pnputil install with the deploy lock held, and a software device's registration stages hmswd.exe under it. The WinUSB, follow-up, ledger and transport locks are never held with it. In a process, `OwnerSweep.CreateGate` and a controller's teardown gate come before it.

The ledger's lock also takes v1.12.0's `Global\HIDMaestro-OEM-Recovery` after its own, since a v1.12.0 program writes the same keys under it. When SYSTEM or Administrators owns that name, the lock waits for it as v1.12.0 does, without a bound unless the caller set one. When anyone else owns it, or its owner cannot be read, the lock waits five seconds and goes on without it, so a program that holds the name cannot stop every HIDMaestro program's ledger work. A process pays that wait once: after a wait has run its full five seconds, later acquisitions wait 500 ms, which still covers a v1.12.0 write, until one takes the mutex or finds it owned by SYSTEM or Administrators again. Both bounds scale with `HIDMAESTRO_TIMEOUT_SCALE` (`LegacyUnknownWaitMs`, `LegacyMarkedWaitMs`). A caller's own bound, the 30 seconds of the WinUSB claims, restores and package note reads, covers both mutexes from one deadline: a wait it cuts short throws `TimeoutException` whoever owns the legacy mutex, and only a wait that ran the lock's own five seconds or 500 ms goes on without it. A name that opens for neither SYNCHRONIZE nor modify access is not taken, and the lock goes on and logs it. Every acquisition waits for the legacy mutex, nested or not. Three ways remain for this process to write while a v1.12.0 program holds the name: a scope that went on without it while the squatter lets go, a v1.12.0 hold longer than the bound, and a DACL that admits a v1.12.0 program's token and refuses this process's. Only an unbounded wait closes the first two, and an unbounded wait would let any program stop every HIDMaestro program's ledger work by holding the name.

#### Registrations and Removals

The PnP lock and the removal test below narrow the windows in which a program of this release registers a devnode while a removal is in progress. They reduce the exposure to the two bugchecks 0x139 recorded in the coexistence design note and are not shown to stop them.

`HIDMaestro.Admin\Pnp` is held by:

- Each devnode registration the SDK makes, from the registration gate's last checks through `DIF_REGISTERDEVICE`, or `SwDeviceCreate` for the two software companions.
- Each removal and uninstall the SDK makes, from its call through its removal test: `RemoveDevice` with its children, its fallbacks and the SWD helper's close, each orphaned HID child, and each phantom record.
- A full deploy's `pnputil /add-driver /install`, which reinstalls every present devnode the package matches, other programs' controllers and their HID children included.
- Each create's bus type stamp on the parent it made.
- The ghost XUSB interface sweep and the interface-class cleanup, each per devnode.

One hold is one removal or one registration, never both. Threads of one process take the lock through an in-process gate first, one at a time, so a wait bounded for another program's hold never counts this process's own holds. Another program waits up to ten minutes, then throws `InvalidOperationException`. The longest hold is one removal, about 150 s for a devnode with a few children: the SWD helper's close (up to 8 s), the parent's 120 s budget and 2 s for its notification, 4 s per child, and the pnputil and devcon fallbacks. A registration's longest is about 95 s: three SWD helper attempts of up to 15 s, 4.5 s between them, and a removal test of up to 15 s after each that timed out.

These change devnodes outside the lock, and each is exposure the lock does not cover:

- A USB/IP import's attach and detach, after which Plug and Play enumerates or removes its HIDClass children.
- The host controller's driver update on a transport swap, which restarts every import's subtree.
- A WinUSB bind's `DiInstallDevice`, which takes the device's HID collections away.
- A registration's `DiInstallDevice` once its hold has ended. Plug and Play then links its HID child into the HIDClass list with no lock.
- A dispose's request that the driver fail its device, after which Windows removes the device and its HID children by surprise removal (below).
- Every program built before v2.0.0.

Outside the lock as well, on a controller's own devnodes or on residue: the naming writes after a registration, `RestartDevice` (public, and a program's own call of it takes no lock), the package removal's `pnputil /delete-driver`, run once no device and no other program remains, the usbip-win2 host controller's repair and installer, and a WinUSB restore's reinstall flag on a devnode that has left. S77's source check lists each of these calls and fails on one made anywhere else outside the lock.

Everything that takes time happens before the lock. Rivals of the ParentIdPrefix go, a prior life that a NORMAL locate, or for a ROOT id a PHANTOM locate, still finds goes through its own removal, each removal in a hold of its own and decided by its own test, and Windows' install queue gets up to 30 s through `CMP_WaitNoPendingInstallEvents`, the bound vJoy's installer gives the same wait (`vJoyInstallLib.cpp`, `cmdUpdate`). The gate then takes the lock and looks once more, removing and waiting for nothing: a rival or prior life back since, or an install pending while the 30 s have time left, lets the lock go and sends the gate round again, up to three times for what came back. `CMP_WaitNoPendingInstallEvents(0)` "tests whether there are pending installation events and returns immediately" (Learn). An install still pending when the 30 s end lets the registration go ahead and is logged, since it can belong to any device on the machine. A failed wait refuses the registration, as vJoy's installer stops on `WAIT_FAILED`. A prior life whose removal ends `NotGone` refuses it, as `SetupDiCreateDeviceInfoW` refuses an id whose record is still there. A software device's record is left alone: `SwDeviceClose` keeps it and `SwDeviceCreate` takes it over.

The gate sees a removal of the id by any program through the id's locates. It cannot see a removal Windows has not finished after the devnode and its record have gone. A program of this release holds the lock until its removal test has an outcome. A program before v2.0.0 holds nothing.

A software device's create that runs past its 15 s is retried after 1.5 s and then 3 s, on the same id and inside the same hold. After each attempt that timed out, the last one included, the removal test runs on the id within an attempt's 15 s, before the next attempt and before the hold ends, since an attempt that had made the device closes it when it is killed. A device still in the tree ends the attempts.

Every removal the SDK makes ends on a removal test with one of three outcomes. A failed `CM_LOCATE_DEVNODE_NORMAL` locate shows the devnode out of the tree. An uninstall, a ROOT or HID id removed by `SetupDiRemoveDevice` or `CM_Uninstall_DevNode`, also needs a failed `CM_LOCATE_DEVNODE_PHANTOM` locate, its record gone. A devnode that was in the tree when the watch registered must then deliver DEVICEINSTANCEREMOVED, "sent when a device instance that meets your filter criteria is no longer present" (CM_NOTIFY_ACTION on Learn), within 2 s more. The outcome is `Removed` when it does, `GoneWithoutRemoved` when the devnode and its record are gone and the notification is not, which is logged and counted and never refused, and `NotGone` when the devnode, or the record an uninstall should have deleted, is still there at the end of the budget. Until v2.0.0 a failed NORMAL locate ended the wait. On the bench's diag log of 2026-10-14 and 10-15, 2343 of 2343 waits for a ROOT parent returned at 0 ms that way, and fast removals waited for nothing. No locate passes `CM_LOCATE_DEVNODE_CANCELREMOVE`, which "cancels the removal of the device" when one is in progress.

A watch registers for the notification only for a devnode in the tree, since Windows refuses one for an id with no devnode (`CR_FAILURE`, measured 2026-10-15) and each registration is one more listener during a removal. One registration at most is open at a time: a parent's watch stays open through its children's removals, which open none of their own. A removal in steps on one devnode runs on one watch from its first call to its last test and counts once.

A HID child removed with its parent is tested on the parent's notification. A ROOT or HID parent's watch starts before its first child's removal call, and the child counts as removed once the parent's latest DEVICEINSTANCEREMOVED arrived after the child's call and the child is out of the tree with its record gone. Tested at its own call, no HID child's notification came within the 2 s bound in the Windows Sandbox runs of 2026-10-16, so each parent's removal took over 2.1 s. That the parent's notification follows the child's PDO deletion is inference from Learn's "Removing a Device in a Bus Driver" and "Removing a Device in a Function Driver", and S77 times each child's own notification through a registration it holds open, failing when one comes after the removal let the lock go. A software parent's children are called after its close, and one still in the tree at its call is held under the lock, once gone, for up to 2 s, until the parent's notification ends the hold. With no parent watch open, a child is removed and tested on its own, as before. `DeviceManager.RemovalsWithParent` counts the children tested this way.

Each removal kind gets the budget it needs. A parent removed by `SetupDiRemoveDevice` or `SwDeviceClose`, which can wait on open handles, gets its caller's: 120 s for a create's prior life. Every removal whose call finishes its work before it returns gets 2 s: a child, a fast removal whatever its caller passed, an orphan, a phantom, and the pnputil and devcon fallbacks. A failed call gets none. A software device's record is never waited for. So the `Everything` cleanup now waits up to 2 s per removal, where it waited for none, and a teardown's surviving HID child waits 2 s, where it waited its caller's 120 s.

A dispose of a device under `ROOT` first asks Windows to remove it as Safely Remove Hardware asks (`DeviceManager.QueryRemoveSubtree`, `CM_Query_And_Remove_SubTreeW` under the PnP lock). Every program that watches the device closes its handles before that removal: Windows' input stack for a keyboard or mouse, and a vendor's service that opens its own devices, such as Logitech's lighting service. A program that holds a HID child open without watching it refuses, and a refusal changes nothing. Only then does the dispose ask the driver to fail the device (`DeviceOrchestrator.TeardownController`). A watcher closes later after a surprise removal than after a query, so a create of the same identity right after the dispose could get the old devnode back, which the query avoids. `SharedMemoryIO.RequestSurpriseRemoval` sets `Global\HIDMaestroRemoveEvent<N>` and waits up to 2 s for `Global\HIDMaestroRemovedEvent<N>`, and the driver's input worker calls `WdfDeviceSetFailed` with `WdfDeviceFailedNoRestart` before it signals. Windows then removes the device and its HID children by surprise removal, as an unplug removes them, which no handle another program keeps open on a child can veto. The removals that follow find the children gone and the device failed, and remove it and the records. The request runs before them, outside the lock. A driver before protocol 5 does not answer, and the removals run as before. A program that keeps a HID child open keeps the devnode, flagged `DN_WILL_BE_REMOVED`, until it closes its handle.

The HID orphan sweep looks for an orphan's parent again under the lock. It leaves a child whose parent came back, as a record or in the tree, while it waited, and one whose identity claim another program holds, and it removes one whose claim this process holds.

A create throws `InvalidOperationException` when another program holds the lock for ten minutes, when its ROOT devnode's prior life or that record is still there after its removal, when a software companion's prior life is still in the tree after its removal, where the create reconnected to it, when the install wait fails, and when what the gate removed comes back three times. A gamepad or XUSB companion that is not made, for any reason, fails the create with `InvalidOperationException` naming it. Before, the create succeeded with a controller no game saw: an xinputhid controller has no other device, and an Xbox 360 controller got no XInput. A failed create's cleanup removes what it made. A create whose devnode Windows still holds for removal (`DN_WILL_BE_REMOVED`, `DeviceOrchestrator.RemovalPending`) throws `InvalidOperationException` at once, since that devnode never starts again. A create no longer restarts a leftover `ROOT\XNACOMPOSITE\0000`, which since issue #60 belongs to a program built before v1.8.0 or is residue, so it no longer takes another program's devnode down.

The exit's waits for the lock are in Census and Sweeps above.

Removals now run one at a time, in a program and across programs, so a dispose of several controllers takes about the sum of their removals, where it took about the longest one, and another program's create or removal waits that long too. Each removal also waits for its notification, up to 2 s more when it is late. On the 2.0.0 release build, against v1.12.0 on one machine with logging off over 30 runs a mode, a DualShock 4 dispose takes 59 ms against 72 ms at the median and a DualSense composite dispose 6 ms against 509 ms. S77's `measure` and `measure4` modes time one controller and four controllers disposed together, old against new. Before this change, on 238bd2b's removal path, the bench's diag log of 2026-10-14 and 10-15 put a DualShock 4 teardown at p50 77 ms and p95 192 ms (317 teardowns) and an Xbox 360 wired one at p50 151 ms and p95 276 ms (165). Those are not this release's figures. Offline, against an absent id with a stand-in lock, the gate costs 24.9 µs at p50 and 30.0 µs at p95 over 200 runs, where the two locates it replaces took 6.4 µs and 7.8 µs (development measurement). What a real back-to-back create adds, the previous create's HID child install now waited for before the lock, only a live run can show.

#### Driver Deployment

Every driver deploy holds the deploy lock for one call. One thread acquires and releases it inside the call, which is what a named mutex needs. An abandoned mutex is acquired and the deploy reads the installed state again before acting. The same-version fast path stays outside the mutex: the manifest hash in `SOFTWARE\HIDMaestro` and the driver store check. When it misses, the deploy takes the mutex and checks again, so of two programs calling `InstallDriver` at once one deploys and the other returns `AlreadyCurrent`. The driver store is listed through SetupAPI: each published `oem*.inf` in the Windows INF directory, its package in the driver store and its `[Version]` lines, the set devcon's `dp_enum` reads. It answers the same way on Windows 10, whose pnputil has no `/format xml`, and in every language. A devnode's own driver is looked up by its published name instead, which also finds a package whose INF file and FileRepository folder are gone while the driver store keeps its entry. A listing that fails is an error and never reads as "not installed": `DriverBuilder.IsDriverInstalled()` and the package removal throw `InvalidOperationException` naming it, and the usbip-win2 install refuses to run. `HMContext.IsDriverInstalled` answers false, logs the reason, and leaves `InstallDriver` to report it.

The installed version is the newest `DriverVer` among the `hidmaestro.inf` packages in the driver store. Two stamps compare by release version, then build date, then build number. `HMContext.LastDriverInstall` reports the outcome:

| Installed driver | Outcome |
|------------------|---------|
| none | `Installed`, a full deploy |
| none, held, a lone XUSB package | `Installed`, only what this build lacks is added |
| this SDK's payload | `AlreadyCurrent` |
| this SDK's stamp, record of it missing | `AlreadyCurrent`, the record is restored, nothing is reinstalled under running devices |
| this SDK's stamp, one of this build's two packages missing | `Installed`, the missing package is added |
| newer | `KeptNewer`, never downgraded |
| older, from 1.x or an older 2.0.0 build, whatever runs on it | `Upgraded` |

The 2.0.0 driver takes precedence over every older one. A deploy never keeps an older driver because devices of a running program hold it, and never refuses for that reason.

Each of `hidmaestro.inf` and `hidmaestro_xusb.inf` is compared with its own embedded stamp. A full deploy removes the older packages and installs both with `pnputil /add-driver /install`. An add runs `pnputil /add-driver` without `/install` and removes nothing, so devices of running programs stay on their package.

Nothing is refused for a holder (decision (c) of `docs/design/data-driven-devices.md`). Every device this SDK creates binds its driver, the store's newest match. `HMDriverVersionException` is thrown only when a started driver does not serve this SDK's protocol or could not read a value, and carries `InstalledVersion`, `MinimumVersion` and `Blockers`. A deploy counts the UMDF2 controller entries of running programs as holders of the driver whether or not their devices are present yet, so it never removes the packages under a create that has recorded its entry and not yet done its PnP work.

Every UMDF2 create passes a deploy gate after its record entry and before its PnP work (`DriverDeploy.EnsureForCreate`, called from `SetupControllerCore`). Under the deploy lock it reads the installed-payload record. When the record is the one this process last confirmed, the gate returns. Otherwise it checks that the driver store holds a package for each of `hidmaestro.inf` and `hidmaestro_xusb.inf`, neither older than this build's. When one is absent or older it runs the install policy above without counting the calling create's own entry as a holder, and the create fails with `InvalidOperationException` if the store still lacks one afterward. The policy adds without removing in two cases. At the installed driver's own stamp it adds whichever of this build's two packages is missing, signed and cataloged as a full deploy does it. With no main package and devices of running programs on a lone XUSB package it adds only what this build lacks, because a full deploy would remove that package and its hosts under them. With nothing on the driver it deploys in full, which removes older packages first, and over an older driver it installs this build's, whatever runs on it. A deploy cut off between the two adds, or a package removed since, no longer reads as `AlreadyCurrent`. A USB/IP composite create does not pass this gate. `UsbipBackend.CreateDevice` calls `UsbipDriverInstaller.EnsureInstalled`, which takes the transport lock for the usbip-win2 install. A deploy signs in a `package` staging directory of its own, fresh from the embedded bytes, and checks the binaries against their SHA-256 again just before signing.

A create of a plain HID or non-xinputhid controller then installs the driver on its own devnode with `DiInstallDevice` and no driver named (`DeviceNodeCreator.CreateDeviceNode`), which installs the best match the driver store holds on that device and no other. The search's choice is kept for the device's hardware and compatible ids, in the process and under `HKLM\SOFTWARE\HIDMaestro\StoreDriverChoice`, with the installed-payload record and the last write of the driver store's `FileRepository` directory (`DeviceNodeCreator.StoreDriverChoice`). While both are unchanged, the next create of the same ids builds its driver list from that one INF (`DI_ENUMSINGLEINF`) and passes the list's best-ranked driver to `DiInstallDevice`, which skips the search. A failed install, two drivers tied for the best rank or an INF gone sends the create to the search. Through v1.12.0 it called `UpdateDriverForPlugAndPlayDevices` with the VID/PID hardware id and the SDK's INF, which installs the package on every present device with a matching id. That staged the SDK's package beside one the policy had kept, and with two programs of one profile it moved the older program's controller onto the newer driver.

#### Version Handshake

`Global\HIDMaestroVersion<N>` is a 64-byte per-controller section the SDK creates beside the input section, before the devnode exists, the pattern v1.12.0 used for `InputAck<N>`. No existing layout changes. The layout is `HIDMAESTRO_VERSION_INFO` in `driver/driver.h`:

| Offset | Field | Written by |
|--------|-------|------------|
| 0 | layout version, 1 | SDK |
| 4 | oldest driver protocol the SDK runs on, 4 | SDK |
| 8 | protocol the SDK speaks, 4 | SDK |
| 12 | SDK version, four 16-bit fields | SDK |
| 20 | driver protocol, 5, and 0 until written | driver |
| 24 | driver version, four 16-bit fields, the fourth 0 | driver |
| 32 | driver capabilities: 0x3, the InputAck bits it supports | driver |
| 36 | oldest SDK protocol the driver serves, 4 | driver |
| 40, 44 | the XUSB companion's protocol and oldest SDK protocol | companion |
| 48 | identity tag: the 64-bit FNV-1a hash of the controller's identity token in UTF-16LE, no terminator (`HM_0000` gives 0x1FD048916B8D461F) | SDK |
| 56 | the value the driver could not read before it failed the start (`DriverConfigError`) | driver |
| 60 | the same for the companion | companion |

The SDK writes its half, the identity tag included, and the controller's index under `HKLM\SOFTWARE\HIDMaestro\Identity\<token>`, before any PnP work. The driver reads its device instance ID before `WdfDeviceCreate`, takes the token from its last segment, reads the index from that key, and reads the controller's 2.0.0 values (`FeatureAnswers` and the cached input report IDs) only when the section exists, its range holds protocol 4 and its tag equals the tag of the devnode's own token. Every other devnode, a 1.x program's or one a killed program's key still names, is read as a 1.x controller: the values every version writes and nothing of 2.0.0. A devnode whose index's section carries another token's tag fails its start with STATUS_DEVICE_CONFIGURATION_ERROR, and so does one with no index anywhere or no `Controller<index>` key holding a descriptor: both drivers keep no default device, where 1.x started such a devnode as an Xbox 360 pad on `Controller0`. The XUSB companion reads the identity entry the same way (`driver/hm_contract.h` holds the section's layout, the tag and the readers both drivers share), writes its own protocol fields, and reads `XusbAnswers` under the same contract. The driver writes its version, capabilities and `DriverProtocolMin` first and its protocol last, with a barrier between, at add and each time it opens the input section, and clears nothing in its cleanup. Protocol 1 is the layout set through v1.11.0, protocol 2 adds InputAck and the owner pipe (v1.12.0), protocol 3 added this section in a build that never shipped, and protocol 4 is the 2.0.0 contract. Protocol 5, in 2.0.0 too, adds `Global\HIDMaestroRemoveEvent<N>` and `Global\HIDMaestroRemovedEvent<N>`, which the SDK creates with the input event: on the first the driver's input worker fails its device (`WdfDeviceSetFailed`, `WdfDeviceFailedNoRestart`), then signals the second. The HID driver serves protocols 4 to 5 (`DriverProtocolMin` 4, `DriverProtocol` 5), the XUSB companion serves 4, and the SDK speaks 4.

A create reads the section once the device has started. Its wait for the start, a 25 ms poll, also ends when a driver's error word is set, when Windows holds the devnode for removal (`DN_WILL_BE_REMOVED`), or when the devnode reports a problem code (10, 31, 37, 39 or 43) while Windows has no device installation pending, so a start the driver fails fails the create within one poll and names the device and the code. A full sweep removes the driver package, and Windows then flags each record that named it for reinstall. A software parent's record outlives its devnode, so the next create of that identity revives it, and it reports problem 18 and then 10 until the install Windows queued restarts it. While an installation is pending (`CMP_WaitNoPendingInstallEvents` with 0) a failed start is therefore not yet final, unless the error word is set. When the wait's time runs out, any problem the devnode shows fails the create: a held failure whose queued install failed reads 28, or still 18 when Windows put the install off, and neither device starts on its own. The XUSB companion gets three waits for its interface, with a restart after each one that ends without it (`AwaitCompanionInterface`), and the last wait's verdict is final. A companion that never publishes the interface and shows no problem lets the create go on. A driver whose range from `DriverProtocolMin` to `DriverProtocol` does not hold 4 fails the create, removes its devnode and throws `HMDriverVersionException` with `Problem` `ProtocolNotServed`, and a set error word throws it with `ValueNotRead`. A create installs its own driver over an older one first, so the first is a newer driver that dropped protocol 4, which needs an SDK of its release, or a mis-stamped one. `HMController.DriverVersion` reads the driver's half, and native writers read both halves directly.

#### Driver Events

The driver creates `Global\HIDMaestroStopEvent<N>` and `Global\HIDMaestroOutputEvent<N>` with `D:P(A;;GA;;;SY)(A;;GA;;;BA)(A;;GA;;;LS)`, so a program that is not elevated can open neither. An existing object of either name is used only when it has a DACL and LocalService, SYSTEM or Administrators owns it. An OutputEvent an earlier driver made without a DACL, owned by LocalService or SYSTEM, is taken over: the driver gives it the host-only DACL, so a program moved onto this driver keeps event-driven output. A StopEvent like that is not used. When another program made either name first, the driver runs on an unnamed StopEvent and with no output doorbell: output reaches the SDK on its 8 ms poll, which tries the event again every 64 polls, and a force-killed controller on that index takes the slow removal path. The driver tries the doorbell again at each input-section map, every 256 frames and on each idle wake. The allocator skips an index whose events another program owns, so the fallback is reached by a name taken after the create's check, and by a StopEvent a driver before v2.0.0 made without a DACL: LocalService owns it, so the allocator accepts it, and the driver refuses it and runs on an unnamed StopEvent with its doorbell, since it takes the matching OutputEvent over.

Both drivers let go of their index at `EvtDeviceSelfManagedIoFlush`, which the framework calls on a surprise removal and on a removal, never on a stop for a rebalance: the sections and their views, both events, the owner pipe, and the companion's pump thread and 8 ms timer. Through v1.12.0 they let go only in the device context's cleanup, which runs on `IRP_MN_REMOVE_DEVICE`, sent only once every handle to a surprise-removed device has closed, so a driver host whose device was surprise removed and never removed kept the index's output event and the companion's timer. The release clears each field it closes, so the cleanup after a flush finds nothing left. The HID driver purges its two queues first, since neither is power managed when it runs as a filter, so no I/O callback reads a view the release unmapped. A HID request to a surprise-removed device then fails in the framework with STATUS_INVALID_DEVICE_STATE instead of reaching the output ring.

#### Staging

Everything the elevated SDK runs or hands to pnputil is staged per version and per operation under `%ProgramFiles%\HIDMaestro\Staging\<version>-<hash>\<operation>`, where the hash is the first 16 hex characters of the embedded driver payload's SHA-256. The operations are `driver` (the embedded bytes of the driver binaries and both INFs, signtool and inf2cat), `package` (one deploy's driver package, signed and cataloged), `swd` (hmswd.exe), `usbip` (the usbip-win2 installer), `usbip-ude` (the host controller package forced onto an older transport) and `winusb-<profile id>` (one profile's WinUSB package). One directory per operation keeps the catalog step's `/driver:` scan and its stale-catalog cleanup away from every other operation's files.

Program Files grants Users read and execute and nothing else, so no program without elevation can create a folder there before HIDMaestro does. `%ProgramData%` lets Users add folders (`BUILTIN\Users (CI)(WD,AD,WEA,WA)` on the folder Windows ships, read with icacls), so a program without elevation could create `%ProgramData%\HIDMaestro`, or a `Staging` folder under it, first, own it, hold a file in it so that it cannot be moved, and make every staging refuse. That is why staging moved from `%ProgramData%` to `%ProgramFiles%` before this release shipped. Every directory from `%ProgramFiles%\HIDMaestro` down is created with its security descriptor in the same call, `O:BAG:BAD:P(A;OICI;FA;;;SY)(A;OICI;FA;;;BA)`, so none exists with an inherited ACL.

Each use checks every directory on its path. A directory passes when it is not a reparse point, its owner is Administrators or SYSTEM, and no allow ACE grants a write-class right (write data, append data, write attributes or extended attributes, delete, delete child, change permissions, take ownership) to anyone but SYSTEM, Administrators and TrustedInstaller, which holds full control of what an installer makes under Program Files. `%ProgramFiles%\HIDMaestro`, which HIDMaestro creates itself, is reset in place when SYSTEM or Administrators own it and nobody else may change its DACL or owner or delete it or its entries, and refused with `InvalidOperationException` otherwise, since a hostile one there is another program's. `Staging`, a version or an operation directory that fails is moved aside to `<name>.untrusted-<guid>`, a reparse point moved as the link itself, and created again. One that cannot be moved is refused when it is hostile in the same sense, and reset in place when only its DACL is wrong. A moved-aside tree is left where it is, never deleted by path. A directory another program creates between the check and the create is refused too.

The OpenVR driver stays under `%ProgramData%\HIDMaestro\openvr\hidmaestro`, by decision. SteamVR loads the driver name `hidmaestro` from one registered path, and a second registration of that name conflicts with the first, and a v1.12.0 program running beside this one registers the `%ProgramData%` path again whenever its manifest hash differs from the one in HKLM, so a driver moved anywhere else would be registered twice. `%ProgramData%\HIDMaestro` now holds nothing else, and nothing the elevated SDK runs, loads or hands to a tool may live there. It and the OpenVR folders carry the same descriptor plus `(A;OICI;FRFX;;;BU)`, since SteamVR reads them as the user. Each is reset in place when SYSTEM or Administrators own it and nobody else may change or delete it, as when an elevated program created it, v1.12.0 included, because SteamVR maps the driver's files from there and a directory holding a mapped file cannot be renamed. Any other is moved aside like a staging directory, and refused when it cannot move. The residual: an owner keeps WRITE_DAC through a handle opened before a reset ("An object's owner implicitly has WRITE_DAC access to the object", Owner of a New Object on Learn), so a program without elevation that creates one of these folders first and holds a file under it can make `HMVR.EnsureDriverRegistered` refuse, and so can any program that holds one open for listing while the extraction renames a file into it. The refusal names the folder. None of this can make a staging refuse.

Every elevated use of a staged file runs inside a pin. `Staging` and each directory below it down to the one in use are held open without delete sharing, which no rename or delete of them can get past, and `%ProgramFiles%\HIDMaestro` cannot be renamed while they are held. That folder, `%ProgramData%\HIDMaestro` and the OpenVR folders are opened only to be checked, through their handles, so no program without elevation can make a pin fail. Each staged file is held for reading with read sharing only, which no write, rename or delete gets past, and checked against its SHA-256 through the hold: the embedded bytes, or the pinned release hash for the usbip files. A driver binary cannot be held while signtool rewrites it, so it is checked right before and held once signed, and a catalog is held once signed. The pin lasts until the use is over: the driver package's sign, catalog and add, hmswd's runs, the usbip-win2 installer's run, the host controller package's install and each WinUSB package's catalog and add. The OpenVR extraction, which writes files for SteamVR and runs none, checks its folders and holds none. A file is written to a temporary name, verified and then renamed into place, and reuse trusts no file size. The helper always comes from the embedded resource, never from beside the assembly (`Assembly.Location`, which is empty in a single-file app).

An elevated child gets a protected TEMP. hmswd, signtool and Inf2Cat run with their own staging directory as working directory, TEMP and TMP. pnputil and devcon, which have no staging directory, get `%ProgramFiles%\HIDMaestro\childtemp\<process id>-<start time>`, a folder per process with the staging descriptor. An elevated process that cannot make that folder does not run the tool with the user's own `%TEMP%`: the operation fails with `InvalidOperationException` naming the reason, a cleanup that only tries skips the tool and logs it, and the next call tries the folder again. A process that is not elevated starts no elevated child and changes nothing. reg.exe and sc.exe, run from System32, keep the caller's TEMP.

The diagnostic logs, `teardown_diag.log` under `HIDMAESTRO_DIAG=1` and `setup_timing.log` under `HIDMAESTRO_TIMING=1`, stay in `%TEMP%\HIDMaestro` and are now opened as the user: the elevated half of a split UAC token writes them through a medium-integrity token of the same user, so an elevated process never creates or appends to a file in a folder the user's programs control. SYSTEM, an administrator without a split token, or a process that is not elevated writes them as itself. So is the USB/IP read log at the path `HIDMAESTRO_DIAG_READS` names. A log that cannot be opened drops its lines. hmswd's exit code and output go into `teardown_diag.log`, and only when diagnostics are on, where each create used to leave an `hmswd_<enumerator>_<suffix>.log` written elevated. hmswd no longer keeps a self-log: it appended to `%TEMP%\HIDMaestro\hmswd_self.log`, which no SDK run could write once hmswd's TEMP became its staging directory, and the function is gone.

A deploy, which holds the deploy lock, deletes the staging directory of every version that no live owner record names, under the staging lock from its read of the records to its last delete and under a pin of `Staging`, and checks each version directory through its handle before it deletes it. A record that names no staging directory keeps every directory of its SDK version, and a moved-aside directory is never pruned. A process notes its staging directory in its record under the same lock, so a prune never removes what another build's program is about to use. The prune also removes the `childtemp` folder of every process that no longer runs, judged by process id and start time. The same-version fast path takes no lock and prunes nothing, so a directory left by a version that was running during an upgrade goes at the next deploy. The constructor prewarm stages the driver payload only when the fast path will not be taken: on a machine that already runs this build's driver, nothing reads the staged payload.

#### Compatibility

Programs built on 1.x must move to 2.0.0. The 2.0.0 driver takes precedence: a 2.0.0 program installs it over any older driver, whatever runs on it, and refuses nothing because a 1.x program is in the way. Its sweeps judge a v1.12.0 program's liveness by its owner pipes, what this release's driver records about them and the registry ledger, and never remove its controllers while it runs. The other direction cannot be fixed from here. A running v1.12.0 program's `InstallDriver` and its first create in a session each remove every HIDMaestro device on the machine, and its `InstallDriver` replaces the installed driver with its own whenever the payload differs. Every older program does the same. With no controller present at the moment of a v2.0.0 create, it leaves no sign, so its next create can take that program's low index. Its `CreateControllerAt(index)` takes whatever index it is given, and it reaches index 64 with 65 controllers alive at once. A program older than v1.12.0 leaves no sign of whether it still runs, so its devices are never removed on a guess.

### The usbip-win2 Install

The SDK installs usbip-win2's host controller from the signed package it carries (`usbip2_ude.inf`, `.sys` and `.cat`) and never runs usbip-win2's installer, which adds the root-hub filter and restarts every USB root hub doing it. Where no host controller is present it registers a `ROOT\USB` devnode with the hardware IDs `ROOT\USBIP_WIN2\UDE` and `ROOT\HIDMAESTRO_UDE`, as `devnode.exe install` does (`userspace/devnode/main.cpp` lines 232-295), under the PnP lock, then puts the package on it through `hmswd force-driver`, out of process with a 90 s timeout. A driver install that fails outright removes the devnode again. It adds no Apps entry, program folder, scheduled task, shortcut or VC++ runtime, and writes `HKLM\SOFTWARE\HIDMaestroUsbip`, the install record a full removal reads: the devnode, the published INF, whether the install added that package, the version, the time and the SDK version.

A present host controller that does not answer is restarted, never joined by a second one. The install, that repair and the move of an older host controller to 0.9.8.1 take the transport lock on a thread of their own and read the machine again under it, so two programs whose first composites arrive together find one host controller. The caller's thread holds no machine-wide lock and raises the install's progress, dropping what the callback throws. An install waits up to five minutes for a usbip-win2 installer another program started, since that installer makes a host controller of its own and declares no setup mutex. A repair whose PnP work outlives its 30 s budget keeps the lock until that work returns, while its program runs. The move looks for an older host controller without the lock and takes it only when it finds one. KMDF's `VerifierOn` and `VerboseOn` values, which the 0.9.7.5 INF wrote into the service key, are cleared when no installed host controller's INF writes them, and the driver reads them at its next load. pnputil, reg and sc run from System32.

### USB/IP Server

The SDK's server listens on loopback and admits an import only from the host controller: a connection whose other end the System process owns, as the vhci driver's kernel socket is. Any other import is answered `ST_NA`, and the device list still answers anyone. A connection that has not finished its handshake within 5 s is closed, and past 16 connections in their handshake a new one is closed at once unless the host controller opened it. A failed import reply frees the bus id. A composite create that fails after its device is registered detaches its import, and a create on another thread waits to register its device while the process's first composite create runs its stale-import sweep. A host program paused in a debugger for more than 5 s while an attach is in flight can see the attach fail and the create throw.

Each worker thread of a device closes the handles it waits on as it ends, Dispose runs once, and a transfer that arrives after Dispose ends the connection, so usbip-win2 detaches the device. Dispose wakes the input pump instead of waiting out its 500 ms frame wait. The input pump reads each frame into a buffer of its own, a report waiting for a read goes into one of at most nine buffers the device keeps, and OUT data, isochronous packet lists, URBs and microphone data reuse buffers the reader and the audio engine keep, so a frame or transfer allocates nothing. `FramesReceived` runs on the audio pump, and `ControlChanged` and both `StreamingChanged` events on an audio event thread of their own, in the host's order. A newer write to a control replaces one still waiting, stream changes are never merged, and Dispose waits up to 500 ms for a running audio handler.

### Data-Only Frames: Report and Length

A data-only frame, from `SubmitRawReport` or `SubmitState`'s legacy path, goes out from a UMDF2 driver as one input report at one length. Through v1.12.0 the driver took the first Report ID item of the first Application Collection, whatever kind of report it named, and the SDK counted that ID's input bits with a walk of its own. That walk kept Report Size, Report Count and Report ID with no stack, skipped a long item as 3 bytes, and counted the first Report ID item of any kind. So some profiles sent an output or feature ID as an input report, and some a report shorter than the descriptor declares.

The SDK now takes the report and its length from the parse it fills: for a keyboard or mouse that gets every report delivered, the descriptor's first input report, and otherwise the first input report with game pad fields. A profile's `inputReportSize` replaces the length. The SDK writes `InputReportId` into the controller's configuration, REG_BINARY: the ID, the length as a 32-bit little-endian value, then the descriptor. The driver takes the ID only when that length equals the `InputReportByteLength` it has just read and the descriptor is the one in use, so a value a killed program left never pairs its ID with the length a v1.12.0 program writes for the same index. Without the value, from a v1.12.0 program or for a profile whose `inputReportSize` is another report's length (the four Sony Bluetooth profiles at 0x31's 78 bytes, and switch-pro at 362), the driver scans the descriptor as before. A driver older than this release ignores the value, so on a v1.12.0 driver that running programs hold, the profiles below keep their old reports.

`inputReportSize` is the report's length on the wire, its ID byte included, as the SDK has always sent it. schema.json said the opposite and now says this. A profile can name the report its data frames fill with `dataReportId`, a hex byte, where the SDK's choice is wrong. It must name an input report the descriptor declares, and it is refused beside an always-armed `extendedReport`, whose report the data frames fill instead, before anything machine-wide. `HMProfileBuilder.FromProfile` copies it. `microsoft-designer-keyboard` sets 0x01. Its descriptor declares a vendor report 0x27 as its first input report, and the real keyboard sends its keys as report 0x01 of 12 bytes: "Press A" is `01 00 04 00 00 00 00 00 00 00 00 00` in Android CTS 1daba777, `microsoft_designer_keyboard_keyeventtests.json`, beside the register file the profile's descriptor comes from.

Every descriptor walker keeps the global item stack of HID 1.11 section 6.2.2.7, Push and Pop, as hid-core.c applies it. `HidReportBuilder` now expands `HidReportMap`'s fields, which already kept the stack. `PidReportIdExtractor` restores the Usage Page and Report ID on Pop, completes each usage with its page, clears local items at every main item and keys only on the PID page (0x0F). `GameInputMapping`'s measured-shape check reads `HidReportMap`, and `HidDescriptorBuilder` follows the pages that `AddRaw` bytes push and pop. `HidReportMap` and hid-tools (f4a3253) read the same input, output and feature lengths for every report of all 243 catalog report descriptors, which S37's `report_length_check` checks against `reference_lengths.json`. A create parses a profile's descriptor once, for the report builder and the keyboard and mouse packer together.

Four catalog descriptors held main items of tag 0, which HID 1.11 section 6.2.2.4 does not define, and hid-tools refused them. Each now holds its source's bytes:

- `ps3-remote`: hid-sony.c `ps3remote_rdesc`, which the profile names as its source, with two items given a data byte (below). The catalog copy had 90 bytes, with bytes doubled.
- `saitek-x52`: the 119 bytes of Launchpad bug 492056 comment 14. One byte was missing and three were changed.
- `thrustmaster-t80`: byte 79 is 09, so Rx and Ry follow as in the T-Flight HOTAS 4 and T300RS descriptors the profile says it shares. No dump of a T80's own bytes is published.
- `joypad-steam-input`: joypad-os `sinput_descriptors.h` at 9fa79f45. The copy had lost the three report ID values its macros stand for.

Windows' own parser refused three catalog descriptors. HID class runs it on the descriptor at the device's start (`HidP_GetCollectionDescription`), so each of these devices failed its start with problem code 10. S37's `report_length_check` loads the machine's hidparse.sys into its process and runs that call on every descriptor the SDK gives the driver:

- `ps3-remote`: hid-sony.c writes its Usage Minimum and one Input item with no data byte, and hidparse refuses both (0xC000001D). HID 1.11 section 6.2.2.2 gives such an item the value 0, so the profile writes both with a data byte of 0: 69 bytes and the same 12-byte report.
- `tinyusb-generic-gamepad`: its reports were not whole bytes. It now serves TinyUSB's `TUD_HID_REPORT_DESC_GAMEPAD` with its report ID 2: a 12-byte input report of six 8-bit axes, an 8-bit hat and 32 buttons, and no output or feature report, where it declared a 14-byte input, a 9-byte output and a 2-byte feature report.
- `nacon-bigben-ps4`: Linux's fixed descriptor, whose Feature item has no usage. It now serves the descriptor the pad serves (hid-bigbenff.c): a 27-byte input report with X, Y, Z and Rz and with L2 and R2 as buttons 7 and 8, beside 8-byte vendor output and feature reports, where it declared a 35-byte input report. 146B:0902 is BigBen's wired game pad for the PS3, so the profile is now "BigBen Game Pad for PS3", with "Bigben Interactive" and "Bigben Game Pad" as its USB strings. Its id is unchanged.

`gamecube-adapter` and `gamecube-adapter-hid` stay refused, as the real adapter's descriptor is: each of their ten Application collections carries Usage 0, which hidparse refuses as a top-level collection without a usage (STATUS_COULD_NOT_INTERPRET, HIDP_GETCOLDESC_TOP_COLLECTION_USAGE). `joypad-gc-adapter` parses.

The sixteen profiles whose data report changed, and the two of them that still do not match their devices, are listed in the coexistence design note (The report a data frame fills).

### Controller Ports and Device Protocols

A profile can describe a device that carries several controllers in one report, and the commands the device answers, as data. Nothing in the SDK names the Wii U GameCube adapter, checks its VID and PID, or switches on its command bytes. A new device of the same form needs a profile and no code.

`extendedReport.ports` gives the report's port blocks:

| Key | Meaning |
|-----|---------|
| `count`, `offset`, `stride` | how many blocks, where port 1's starts (the report ID is byte 0) and how far apart they are |
| `status` | the block's status byte: its offset, the `connections` a port can hold with the bits each sets (the first is the empty port, the second the default), and device-wide `flags` every status byte carries while on |
| `data` | the block's data bytes, such as `"1-8"`. An empty port's are zero |
| `snapshots` | copies of a block the device keeps, taken `on: "connect"` from the first report in which the port holds something |
| `fields` | the block's fields in the `extendedReport` vocabulary, offsets relative to the block |

`extendedOutputReport.ports` decodes output per port the same way, with whole-number fields (`uint8`, `uint8-axis`, `uint8-trigger`, `uint16-le`, `int16-le`), and `OutputDecoded` carries each as `port1.rumble` and so on. `HMController.Ports` is an `HMPortSet`, empty for a profile with one controller. Each `HMPort` has a fixed `Number`, a `Connection` named by the profile, `Connect(name)` and `Disconnect()`, `SubmitState(in HMGamepadState)` through the port's fields, `SubmitRaw` for the data bytes exactly, `GetOutput(name)` and an `OutputChanged` event raised on the output thread. `Ports.Flags["name"]` sets a device-wide flag. `HMController.SubmitState` on such a device submits to port 1. A port call writes the whole report under the controller's submit lock with no system call or allocation added: the layout is compiled once and the encoder writes into buffers the port set owns. `HMButton` gains `LeftTriggerClick` and `RightTriggerClick`, a trigger's digital click apart from its analog travel, so `HMGamepadState` expresses the GameCube controller's analog L and R, its Z and its C-stick without a device-specific state type.

`HMPort.Connect(connection)` on an empty port writes the connection with sticks centered and triggers and buttons released, as the profile's fields encode an empty `HMGamepadState`. A host takes a controller's origin from its first report (Dolphin through `SetOrigin`) and SDL widens its calibration on it, so a first report of zeros would read a resting stick as pushed for the whole connection. `Connect(connection, in HMGamepadState)` sends the connection and an input state in one report, for a WaveBird or a controller plugged in with a button held, and throws `ArgumentException` for the empty connection.

`protocol`, at the profile's top level, gives a USB/IP device registers, counters, memory images, when its input endpoint answers and on what clock, command rules, replies, decoders, a halt condition, and its answers to SET_PROTOCOL, GET_STATUS and GET_REPORT. `usbConfiguration.protocol`, where it lived before, is refused at load with its path. The full grammar is mechanism 3 of `docs/design/data-driven-devices.md`. The keys:

| Key | Meaning |
|-----|---------|
| `state` | registers of 1 to 32 bits with initial values, restored at attach and at a port reset unless `keepOnPortReset` |
| `counters` | counts of reports, frames, reads or clock periods, each written into replies and reports |
| `memory` | images a reply reads from and a rule writes into, filled, with constant segments and value segments such as the serial |
| `input` | the interrupt IN endpoint, the condition under which a poll gets a report (`["polling", "!stalled"]`), and its `clock`: for a device that sends the SDK's report, its own controller poll in ms and rules that change it while exactly the listed ports hold something, and for a device that builds its reports, a period, an origin and a missed-tick rule |
| `commands` | the interrupt OUT endpoint, whose packets are each a command, whether a SET_REPORT(Output) is one command too (its whole data stage), `setReportStripsId` for a device whose USB stack drops a leading byte equal to wValue's report ID from a data stage longer than one byte, a reply prefix and status, and rules tried in order. A rule matches a command's bytes, with `..` for any byte, and its length, then sets, stores, ORs or clears registers, writes memory, decodes or raises an output report, and queues a reply built from the registers before the rule ran: constant bytes, echoed command bytes, a register, a counter, memory, a bitmap, a layout's bytes, a value or a snapshot's bytes for every port, zeros unless its own condition holds |
| `replies` | the channel replies go out on (the input endpoint, or a bulk IN endpoint), `pending`, how many can wait (1 by default, 1 to 1024), and `overflow`, which one is dropped when they are all waiting |
| `decoders` | output reports decoded into named values that `OutputDecoded` carries |
| `halt` | the states under which the device answers nothing, and the status transfers fail with until a port reset |
| `setProtocol` | `"ack"`, or `"stall"`, the default |
| `getStatus` | `"descriptor"`: the self-powered bit the configuration declares |
| `getReport` | `"input"`, the default: the input report as it stands for its own ID, a declared ID's ID and zeros, a stall for an undeclared ID. `"reportId"`: for every report type, the requested report ID alone, and a stall for ID 0 or a one-byte request. `"deviceReport"`: for a device that builds its reports, the layout that would go out now |
| `log` | how many commands the device keeps, raw, for a consumer to read |

The device runs it on a modeled host poll. A host controller polls an interrupt endpoint every period while a transfer is queued, on a grid that starts at attach, and fills a transfer one packet of wMaxPacketSize per poll. A short packet or a full buffer ends the transfer, and a packet with no room left is babble, which fails the transfer with `-EOVERFLOW`. The period is the one Windows gives the endpoint descriptor's bInterval: 8 ms for bInterval 0 to 15, 16 ms for 16 to 35 and 32 ms beyond at low speed (`busSpeed` `"low"`), a power of two from 1 to 32 ms at full speed, and 2^(bInterval-1) microframes, at most 32, at high speed. `HMController.DeviceProtocol.HostPollInterval` models another host poll, a faster one as a filter driver that overclocks the poll makes it, and the descriptors never change. It takes only a period Windows schedules at the device's speed. A device with a source poll has a new report for a host poll only once it has read its controllers since its last report.

The SDK compiles all of it at create and again when the device is built: names become bits, conditions become a mask and the values under it, rules become byte patterns, and replies become parts with fixed offsets. A poll takes three locks, always in one order, the device's send lock, its HID lock and then the engine's, and copies one packet into a pooled buffer. A command, its reply, a report and a GET_REPORT answer allocate nothing, which S95 checks over 100,000 of each.

A profile file's device model is checked when it loads, and a mistake refuses the file into `HMContext.ProfileLoadIssues` with its JSON path. `CreateController` compiles the whole model again before it takes anything machine-wide, so a profile built or changed in code is refused with `HMProfileException` naming the profile, the JSON path and the limit: a report field of an unknown type, a semantic that names nothing the SDK has, a field wider than its report or block, a report ID that is not a hex byte, an `armOn` of an unknown type, an input report past the 80-byte extended lane, an output field past the 256-byte output ring, ports that do not fit their report, port blocks on an output report's byte 0 or on an input report's report ID, a status byte with fewer than two connections or two that share a value, report fields beside input ports, output fields over the output port blocks, output ports or fields past one OUT packet when `setReportStripsId` is set and commands arrive on the HID interface, a field outside a block's data bytes, a button name the SDK cannot express, an output port count that differs from the input's, a state a rule names but `state` does not declare, more than 64 states or 32 ports on a protocol device, a rule longer than a packet, `replies.pending` outside 1 to 1024, `setReportStripsId` without `setReport`, an endpoint the configuration descriptor lacks or of the wrong type, a reply on a device with no input endpoint, a low-speed device whose control endpoint is not 8 bytes or with an interrupt endpoint over 8 bytes or a bulk or isochronous one, an endpoint whose transfer type differs between alternate settings, an interrupt or bulk endpoint whose descriptors differ between them, an isochronous endpoint in more than one, `winUsb` on a profile that is not USB/IP, a WinUSB GUID that does not parse. The descriptor checks run at create only for a profile with `protocol` or `winUsb`. Every other USB/IP persona meets them when its device is built, after its transport index is taken. Every catalog profile compiles.

A USB/IP persona without a protocol answers GET_REPORT(Input) for a declared report ID with that report's latest bytes, or its ID and zeros before the first, and stalls an ID its descriptor does not declare. The Switch 2 Pro persona answers a declared ID with the report it would send next and ID 0 with its selected report. A protocol device answers by its `getReport` mode, and the GameCube adapter's `"reportId"` answers the requested ID alone.

#### Report Programs and the Idle Repeat

A device that builds its reports at send time splits into data: a `stateBlock`, a field list in the codec's vocabulary that `SubmitState` encodes, and `inputReports`, layouts each with a report ID, a size, a `while` condition on the protocol's registers, a `send` rule and a program over the state block (`copy`, `bits`, `const`, `xor`, `swap16`, `field`, `lookup`, `hat8`, `pack12`, `counter` and `when` blocks). `liveFeatureReports` use the same programs for a feature report whose answer is the current state. The build turns every catalog program and decoder into straight-line C# named by the hash of its canonical form, and the SDK binds it once at create. A program from outside the catalog runs on an interpreter compiled from the same validated form, with no rebuild, and a catalog program the build cannot validate fails the build with `KG0001`, its file and its JSON path. S94 runs every program three ways, generated, interpreted and through a naive evaluator written from the design note, under the JIT and NativeAOT. The costs are in mechanism 2 of `docs/design/data-driven-devices.md`.

`stream` gives a device's idle repeat: the consumer's last frame sent again one period after the last frame went out, as the real device reports at rest, with `periodMs` (fractions allowed), an optional `periodRegister` a host sets, a `while` condition, and `timestamps`, `hold` or `advance`. `extendedReport.idleFrameIntervalMs` still loads as a stream of that period. 21 catalog profiles repeat at rest: the DualSense family at 1 ms (Edge), 1.25 ms (Bluetooth) and 4 ms (USB), the DualShock 4 USB family and `steam-deck` at 4 ms, `openffboard` at 101 ms and five Thrustmaster wheels at 250 ms, all of which repeated nothing before 2.0.0, beside `steam-controller-2`, `steam-deck-composite` and `steam-controller-composite`, which already did. The repeat runs on the device clock, in one wait per period for a stream that reads no register. Each frame the consumer sends moves the clock's timer a period past it when the timer would fire within half a period (`DeviceClock.FrameSent`), so the clock stays asleep while frames arrive and wakes once per gap in them. `HMDeviceProtocol` reads a device's registers and counters (`GetRegister`, `CounterNames`, `GetCounter`), and `HostPollInterval` throws `InvalidOperationException` on a device that builds its reports or whose protocol names no input endpoint.

#### Event Handlers on SDK Threads

The nine events the SDK raises on its own threads are `OutputReceived`, `OutputDecoded` and `KeyboardLedsChanged` on the output reader, a port's `OutputChanged`, the USB audio events and `HapticReceived`. Each goes through `EventRaise`, which runs the handlers in turn, drops what one throws and writes it to the diagnostic log under `HIDMAESTRO_DIAG=1`. Before b7951e2 a throwing handler kept the handlers after it from running and made the output reader skip the rest of that packet (the keyboard's LED state, `OutputDecoded`, a port's outputs, a Bluetooth DualSense's switch to report 0x31). On a composite's USB/IP connection it closed the connection and unplugged the controller, and on the audio pump, the thread pool or the VR haptic reader it ended the program. Walking the handlers with `Delegate.EnumerateInvocationList` allocates nothing, so the output reader still allocates 0 bytes a report. A handler can dispose its own controller: `HMController.Dispose` called on the output reader, `HMVRController.Dispose` called from `HapticReceived`, and `HMContext.Dispose` or `DisposeControllersInParallel` called from a handler do not wait for the handler's own thread, and the reader raises the rest of that packet's events on the disposed controller. `Dispose` marks the controller disposed under its submit lock, so it waits for a submit in progress and a racing submit throws `ObjectDisposedException`. `OnSubmitLatencyMicros` runs after the submit lock is released, so two submitting threads can run it at once. Report IDs parse without allocating too: a profile's report ID is text, `0x31` or `31`, and `ReportIds.Parse` reads its hex digits from a span where the codec and the output reader had cut the `0x` off with `Substring` on every frame and every output packet.

### WinUSB on Request

A libusb host on Windows opens a device only through WinUSB, libusbK or libusb0, and a real WUP-028 gets Windows' HID driver, which fails it with Code 10. `HMController.BindWinUsb()` builds a driver package from the profile's `usbConfiguration.winUsb` interface GUID: an INF that includes and needs winusb.inf, generated per profile as `hmwinusb_<profile id>.inf`, and matches only a vendor-scoped compatible ID `USB\COMPAT_VID_vvvv&Class_cc&SubClass_ss&Prot_pp` as the sixteenth of its compatible IDs, behind fifteen no device carries. It therefore ranks below input.inf for every real device (0x00FF3F00 against input.inf's 0x00FF3205 on the development laptop). The SDK installs it on the one virtual devnode with `DiInstallDevice`, which installs the named driver on the named device and nowhere else, and records the binding in the registry ledger first. Nothing installs a driver on a present devnode afterward. When the last holder lets go, at dispose or at the next program's reclaim after a crash, the ledger waits until the devnode is gone (`CM_Get_DevNode_Status` returning `CR_NO_SUCH_DEVINST`) and then sets `CONFIGFLAG_REINSTALL`, so its next arrival installs by rank. A device present on the devnode meanwhile, the virtual one on its way out or a real adapter that took the instance, keeps WinUSB until it is unplugged and the devnode is marked. Only a controller teardown, the cleanup, a reclaim of the controllers of a program that has ended, a binding that moves to the devnode its dropped adapter came back on, or the follow-up marks it: a program that starts and runs sweeps the ledger only when it finds such a program. One follow-up per entry, on any program, watches for the devnode to go for five minutes, its deadline kept in wall-clock time so a reboot does not stretch it, and a teardown pays nothing for an entry another program's follow-up watches.

Before it installs, the step reads the devnode's driver list and confirms that another driver ranks above the package, and it waits until Windows has settled the devnode's driver: no installation pending in the PnP manager (`CM_WaitNoPendingInstallEvents`) and the devnode started or stopped on a decided driver. It binds only a devnode on a driver that ships with Windows. A devnode on WinUSB, libusbK or libusb0, which includes an instance Zadig bound, returns `AlreadyBound` untouched. A devnode on one of HIDMaestro's own packages, which a killed program's binding leaves until a sweep, also returns `AlreadyBound`, and the controller holds it in the ledger from then on. A devnode on any other driver is left alone and reported as `OtherDriver`. A bind reads the devnode under the machine-wide WinUSB lock, lets that lock go to add its package under the deploy lock, so it waits for another program's deploy, and takes it again. The package is added once per process, and again after a cleanup removed it. The bind then holds the WinUSB lock and its controller's bind gate and takes the ledger's lock last, the order a restore uses, so a bind and a restore on two threads cannot wait on each other. Its ledger claim, which also waits for v1.12.0's mutex beside the ledger's own, gives up after 30 s, scaled, with `TimeoutException`. Each claim writes a random 64-bit value under its holder name, so the full cleanup, which restores an entry whatever holders it saw when it queued it, tells a claim made in between by the same program and index from the one it saw and keeps the entry. A bind checks the devnode twice, the second time right before `DiInstallDevice`, and binds nothing that fails either check. When the adapter's connection drops and usbip-win2 imports it again, the binding runs again on the new devnode and lets go of the old one, and a `BindWinUsb` that threw binds nothing at a later re-import. Disposing a controller waits only for a claim and install in progress.

The bound devnode carries no reinstall flag, because Windows reports `CONFIGFLAG_REINSTALL` as install state 1 and libusb skips any device whose install state is not 0. The restore sets the flag only on a devnode that is gone instead, so the next arrival on that instance installs again by rank. When the last holder lets go, a present devnode keeps its driver and its entry, whichever driver that is, and one that was moved to another driver meanwhile is left as it is. The uninstall-grade cleanup removes no devnode: it flags a gone devnode still on a package and keeps that package, and removes the packages no devnode uses. It decides from one listing of the driver store and one walk of the USB devnodes, present and gone: a listing that fails removes nothing and changes no note, a walk that fails removes nothing and notes every listed package, and only a package the whole walk found on no devnode is deleted, with pnputil's plain `/delete-driver`. A package it keeps is noted by INF name in `HKLM\SOFTWARE\HIDMaestroPackagesLeft`, value `WinUsb` (`REG_MULTI_SZ`), written under the deploy lock and outside the ledger's root, so the cleanup's delete of the ledger leaves it. A later add of that package takes its name out. The restore that clears the last WinUSB entry, and the first sweep of each later program that finds the note and no WinUSB entry, remove the noted packages no devnode still uses and keep the rest noted, and the key goes with the last name. A package a phantom devnode keeps stays in the driver store until then, ranked below the driver Windows gives the device.

### NativeAOT, Trimming and Single-File

The project sets `IsAotCompatible`, and `aot-analyzers.globalconfig` raises the `Trimming`, `SingleFile` and `AOT` diagnostic categories to errors in Release. Profiles and layouts load through `HMJsonContext`, a source-generated `JsonSerializerContext` with no reflection resolver behind it. Its options are the ones `HMLayoutJsonOptions.Default` carried: camelCase names read case-insensitively, comments and trailing commas allowed, `HMAxis` through its own converter and every other enum as a snake_case string, each through a `JsonStringEnumConverter<TEnum>`, since the non-generic converter needs runtime code generation. The layout `kind` stays with `HMLayoutJsonConverter`, which matches it in any letter case and with or without underscores and reads each concrete layout through the `JsonTypeInfo` the options carry. `[JsonPolymorphic]` does not fit, because its discriminator matches exactly and `LoadProfilesFromDirectory` reads profiles consumers write themselves.

Generated code builds a record whose properties are init-only with one object initializer that assigns all of them, so a key the JSON leaves out arrives as `default(T)`: null for the empty lists and `new()` objects the layout records initialize, 0 for `HMTriggerButton.Stages` (initialized to 1) and `Unknown` for `HMRotaryEncoder.Role` (initialized to `Dial`). Reflection kept those initializers, and 68 of the 336 catalog profiles depend on them. The converter therefore writes the JSON out again with each such key filled from a freshly constructed record. Which keys need it is planned once per type, by comparing a fresh record with the one the same metadata builds from `{}`. `json_parity_check` reads every embedded profile through `HMJsonContext` and through v1.12.0's converter and options and requires the same contents. With the fill step disabled it fails on those 68 profiles.

Every `DllImport` is a `LibraryImport`. A declaration that took a string or `char` gets `StringMarshalling.Utf16`, and every `bool` gets `MarshalAs(UnmanagedType.Bool)`, the 4-byte Win32 `BOOL`, except the results of hid.dll's `HidD_*` functions. Those return `BOOLEAN`, one byte (`hidsdi.h`), and are read as `UnmanagedType.U1`: on an invalid handle `HidD_GetAttributes` returns FALSE in AL with the rest of EAX nonzero, which a 4-byte read takes as TRUE. Three structs were not blittable and changed layout without changing size: `HIDP_CAPS.Reserved` is a 17-element fixed buffer, the OpenVR section's `SECURITY_ATTRIBUTES.InheritHandle` is the 4-byte `BOOL`, and `CM_NOTIFY_FILTER`'s instance ID is a 200-character fixed buffer. The struct stays 416 bytes, the size `CM_Register_Notification` requires. `LibraryImport` does not marshal a managed delegate, so each wait's handler travels as a `GCHandle` in the registration's context argument and one `[UnmanagedCallersOnly]` dispatcher hands every event to it and lets no exception reach cfgmgr32. The handle is freed after `CM_Unregister_Notification`, which waits for pending callbacks to finish. The stubs of the per-frame calls (`SetEvent`, `WaitForSingleObject`, `WaitForMultipleObjects` over a preallocated handle array) convert `BOOL` in place and pin the array with `fixed`, with no allocation. The wait stubs save the last error. The frame writer's `SetEvent`, whose error nothing reads, neither clears nor saves it.

`aot_smoke` publishes one source four ways, NativeAOT and trimmed self-contained single-file for x64 and ARM64, and each app loads the catalog, installs the driver, creates `dualshock-4-v2` on the UMDF2 driver and `dualsense-composite` on USB/IP, submits input, waits for `OutputReceived` and disposes. At v1.12.0 both kinds of app load 0 of 336 profiles. The first source-generated parse in a JIT process costs about 8 ms more at the median than the reflection parse (119.9 ms against 111.9 ms over 30 runs) because the generated metadata is compiled on first use, and the second parse in the process is 1.5 ms against 1.3 ms.

## Why UMDF2 Is Enough

A common assumption is that virtual game controllers require kernel-mode drivers. Here's why UMDF2 works:

- **HID class driver is already in the kernel.** Windows ships `mshidumdf.sys` which acts as a kernel-mode HID minidriver proxy. Our UMDF2 DLL runs in user mode but the HID class stack sees a real HID device.
- **XInput discovery uses device interfaces, not bus type.** `xinput1_4.dll` finds controllers through the XUSB device interface GUID. A UMDF2 driver can register this interface from user mode.
- **GameInput reads HID reports, not driver internals.** WGI/GameInput reads from the HID preparsed data and report descriptors; it does not care whether the underlying driver is kernel or user mode.
- **SDL3 and HIDAPI check device paths and attributes.** Bus type, VID/PID, and device path strings are all settable from user mode via SetupDI and CM APIs.

The only things UMDF2 *cannot* do: create PDOs (Physical Device Objects) as children of a bus, or intercept internal kernel IOCTLs. HIDMaestro works around this by using a companion device for XUSB and root-enumerated device nodes for the HID stack.

### Startup and Hot-Plug Timing

The figures in the table were measured on releases before v2.0.0. On the 2.0.0 release build, against v1.12.0 on one machine with logging off over 30 runs a mode, the medians are a DualShock 4 create in 217 ms against 467 ms, process start to the first controller in 553 ms against 725 ms, a DualShock 4 dispose in 59 ms against 72 ms and a DualSense composite dispose in 6 ms against 509 ms.

| Operation | Measured Time |
|-----------|--------------|
| Cold start (first run: cert + sign + install + create 1) | ~18s |
| Warm start, single controller (drivers cached) | **~200ms** |
| Warm start, 4 mixed controllers (2 BT + 2 Xbox 360 wired) | **~2.2-2.8s** |
| Warm start, 6 mixed controllers (sequential) | **~3.5s** |

| 6-controller mixed cleanup (sequential) | ~3-4 s |

Cold start includes certificate creation, signing, catalog generation, driver package installation, and device creation. This only happens on first run or after SDK updates. Warm start uses event-driven polled waits that exit as soon as PnP is ready. Fixed sleeps remain only in failure retries and one drain: an SWD create that times out retries after 1.5 s and then 3 s, a package removal retries every 500 ms while the package is in use, and a cleanup that signals a controller's stop events sleeps 500 ms once to let the driver hosts drain. That cleanup also runs inside a process's first create, through the reclaim of ended programs, and at exit. Controllers are independently disposable: removing one does not disturb the others.

**Same-boot run-to-run consistency:** every launch matches the fresh-boot Phase-1 timing. The earlier regression where subsequent same-boot runs took 65s (and lost XInput visibility for the XUSB-companion path) came from reconnecting to a half-removed software device; the handle-lifetime teardown removed the cause, and since v1.8.0 every life reuses one fixed instance name. See Techniques: Stable Device Identity.

**Per-step install breakdown** (visible in stdout when `HMContext.InstallDriver` runs): extract ~20ms · remove old packages ~100ms · sign ~130ms · generate catalogs ~840ms (the largest single step, AV-sensitive) · install drivers ~580ms · total ~1.7s on a clean machine. On corporate workstations with hundreds of devices in the PnP tree, total install can stretch to 5-20s; HIDMaestro doesn't run `pnputil /scan-devices` (it's a no-op for our INFs and was the largest variable contributor).

**Batch teardown:** `HMContext.Dispose()` and the public `DisposeControllersInParallel(controllers, perControllerCallback)` run each controller's teardown on its own thread and the system-wide HID orphan sweep once at the end instead of per controller. Since v2.0.0 every devnode removal holds the PnP lock (Registrations and Removals), so the removals run one at a time and the wall clock is about the sum of the controllers' removals. The batch path still saves the per-controller orphan sweeps. A `perControllerCallback` that throws stops nothing: every controller is disposed, the orphan sweep runs, and the exceptions come out afterward in one `AggregateException`, with one controller as with many. Before v2.0.0, with the removals overlapping, four to six mixed controllers took 1.5 to 4 s. This release's figure has not been measured. Live profile-switch (single `HMController.Dispose()` mid-session) stays synchronous because slot-allocation determinism requires the old devnode fully gone before the new one is created.

**Self-healing on init:** `HMContext.InstallDriver` sweeps the devices of programs that have exited before it deploys, so orphans left by a prior crashed session are cleaned up before the new install runs, and it leaves the controllers of running programs alone. The same sweep is public as `HMContext.RemoveAllVirtualControllers()` for consumers who want explicit defensive cleanup (e.g. on app exit). In normal operation, individual `HMController.Dispose()` is sufficient, and a program that exits without disposing has its devices removed by the SDK's exit handler.

### Profile Architecture Groups and Teardown Timing

Disposal speed depends on which kernel-side drivers are in the device stack. Each additional driver in the stack adds its own PnP query-remove handshake, handle release, and notification cascade. Since v2.0.0 a dispose first asks Windows to remove a device under `ROOT` as Safely Remove Hardware asks, and only when a program refuses does the driver fail the device, so Windows removes it and its HID children by surprise removal, which no open handle can veto. HIDMaestro profiles fall into three architecture groups with dramatically different teardown characteristics:

#### 1. Plain HID: generic gamepads, wheels, HOTAS, flight sticks (~200ms)

Profiles with no XInput presentation. Includes DualSense, DualShock 4, all Logitech wheels, Thrustmaster HOTAS, flight sticks, pedals, arcade sticks, and most of the 337-profile catalog.

```
ROOT\HIDClass\HM_0000               ← our UMDF2 driver (mshidumdf host)
  └─ HID\HIDCLASS\1&hash&0&0000     ← raw HID PDO, no upper filter; the
                                       prefix is the identity's, written
                                       before registration
```

**Lightest stack.** The dispose's removal query takes the ROOT parent and its HID children, or, when a program refuses it, the driver fails the parent and Windows removes the tree by surprise removal. The removal that follows takes the parent's record. No XUSB companion device, no Microsoft upper filter. A DualShock 4 creates in 217 ms and disposes in 59 ms at the median on the 2.0.0 release build.

#### 2. Non-xinputhid Xbox: Xbox 360 Wired (~135ms post-v1.3.1)

Profiles whose `xinput` block names `"xusbCompanion"`, the Xbox 360 family. XInput is delivered via a separate SWD-enumerated XUSB companion device running `HMXInput.dll`. WGI dispatch also runs through that companion, admitted by the xinputhid UpperFilter tripwire described in Techniques.

```
ROOT\VID_045E&PID_028E&IG_00\HM_0000 ← our UMDF2 driver (main HID device)
  │                                    UpperFilters += "xinputhid" per-instance
  │                                    (in the SetupDi property state BEFORE
  │                                    DIF_REGISTERDEVICE, plus one deliberate
  │                                    devnode restart after the companion
  │                                    exists: WGI only honors the tripwire on
  │                                    a RE-arrival, never at first arrival,
  │                                    measured both ways on 26200 - issue #59)
  │                                    (SDK-written; blocks WGI from building
  │                                    a second HID-backed Gamepad for this
  │                                    logical controller)
  └─ HID\VID_045E&PID_028E&IG_00\... ← HID child (raw PDO, input.inf)
SWD\HIDMAESTRO\HM_0000               ← XUSB companion (HMXInput.dll)
  │                                    SwDeviceCreate, System class, explicit
  │                                    per-controller ContainerID (shared with
  │                                    main HID for xinput1_4 dedup).
  │                                    UpperFilters = "xinputhid" from INF
  │                                    (admits the companion to WGI's XUSB
  │                                    dispatch; xinputhid.sys does not
  │                                    actually attach, wrong device class).
  │                                    `HM_0000` = the identity token, the
  │                                    same on every life of this controller.
  └─ XUSB interface → XInput slot + WGI Gamepad (one entry, live input +
                                     working put_Vibration on Chromium)
```

**Medium stack, fast on both sides post-v1.3.2.** Two device trees to tear down. The XUSB companion runs its own WUDFHost instance hosting `HMXInput.dll`, which needs its own PnP release cycle. v1.3.1's SwD-first ordering brought disposal to ~135 ms (down from ~5,700 ms). v1.3.2's `WaitForXInputSlotClaim` 500 ms cap brought worst-case creation to ~700 ms (typical ~200 ms). Round-trip create + dispose is ~350-850 ms.

#### 3. xinputhid Xbox: Xbox Series X|S Bluetooth (~500ms post-v1.3.1)

Profiles with `driverMode: "xinputhid"`. These match `xinputhid.inf [GIP_Hid]` by hardware ID (`HID\VID_045E&PID_0B13&IG_00`), which binds Microsoft's `xinputhid.sys` as an upper filter on the HID child. xinputhid provides XInput delivery + 16-button descriptor synthesis natively: no XUSB companion needed, single Device Manager entry.

```
SWD\HIDMAESTRO_VID_045E_PID_0B13&IG_00\HM_0000
  │                                  ← our UMDF2 driver via SwDeviceCreate
  │                                    (mshidumdf host). Explicit non-sentinel
  │                                    ContainerID closes the slot-1-skip
  │                                    bit-2 path in xinput1_4!FUN_18000de2c.
  │                                    Underscore between VID and PID avoids
  │                                    the `VID_*&PID_*&IG_*` PnP edge case;
  │                                    `&IG_00` retained because the HID
  │                                    child inherits this name and HIDAPI/
  │                                    SDL3/Chromium substring-match `&IG_`.
  └─ HID\HIDMAESTRO_VID_045E_PID_0B13&IG_00\...
        │                            ← HID child (xinputhid.inf, xinputhid
        │                              upper filter)
        ├─ xinputhid.sys              ← Microsoft inbox kernel filter
        ├─ XInput delivery (internal)
        └─ 16-button HID synthesis
```

**Both sides fast post-v1.3.2.** xinputhid is a Microsoft inbox kernel filter driver. Pre-v1.3.1 *teardown* went through the full PnP query-remove → class installer → filter unload chain on every Dispose because `DeviceManager.RemoveDevice` removed HID children before the SwD parent (each child's `WaitForDeviceRemoval` then timed out at 2,000ms because the children couldn't unwind while the parent's HSWDEVICE refcount was still held). v1.3.1 closes the SwD parent first via `SwdDeviceFactory.Remove` and blocks on `CM_NOTIFY_ACTION_DEVICEINSTANCEREMOVED`; the children cascade automatically once the kernel releases the parent. Disposal ~500ms.

v1.3.2 fixes the *creation* side too. `SetupController` runs three wait budgets after `CreateGamepadCompanion`: `WaitForHidChild` (10 s), `WaitForDeviceStarted` (5 s), and `WaitForXInputSlotClaim` (15 s pre-v1.3.2, **500 ms** post). The slot-claim wait was the dominant cost: distribution is bimodal (xinputhid publishes the slot in <100 ms when healthy, never publishes when xinputhid's allocator is in a stuck state: kernel state issue, prior-session residue), so the prior 15 s budget burned the full duration on every stuck case. PadForge users observed 13-14 s freezes on a single Xbox Series BT create when this hit. The 500 ms cap sits ~5x above the slowest observed healthy claim (giving slow-but-working cases full headroom) and degrades the stuck case to a near-imperceptible pause. Controller stays functional via DI/HIDAPI/Browser/WGI when XInput doesn't pick it up; XInput consumers see the slot appear lazily on their next poll cycle. Creation latency for Xbox Series BT is ~150 ms healthy / ~600 ms worst case post-fix.

#### SwD-first removal ordering (v1.3.1)

Two of the three architecture groups (Xbox 360 Wired and Xbox Series BT) own a SwDevice-enumerated parent. SwDevice lifetimes are anchored to the HSWDEVICE handle, not the PnP devnode: children of a SwD parent cannot fully unwind their query-remove cascade until the parent's handle drops its kernel refcount. Pre-v1.3.1, `DeviceManager.RemoveDevice` issued `DIF_REMOVE` on every HID child first (each followed by a 2,000ms `WaitForDeviceRemoval` that timed out because the parent was still holding the lifetime lock), then closed the SwDevice handle. Net cost: ~5,700ms for Xbox 360 Wired, ~11,000ms for Xbox Series BT, scaling worse with more children.

v1.3.1 inverts the order: for any `SWD\` parent, close the SwDevice handle FIRST via `SwdDeviceFactory.Remove`, block on `CM_NOTIFY_ACTION_DEVICEINSTANCEREMOVED` for the parent (so callers know the kernel has actually propagated removal, not just that the handle closed), then mop up any HID children that survived the cascade: usually none, because the SwD parent's release fires its children's removal in one cascade.

Until October 2026 that block never happened. `CM_Register_Notification` refused the SDK's filter struct, declared at 432 bytes against the header's 416, with `CR_INVALID_DATA`, so every wait in `DeviceManager` returned at once and `WaitForDeviceRemoval` reported a device that was still present as not removed. Dispose went on while the SwD device was still leaving, and in 12 of 30 quick create-and-dispose cycles an Xbox 360 Wired controller's XInput slot read connected again 8 to 24 ms after Dispose returned, for about 15 ms. With the struct declared as the header defines it, the wait blocks until Windows reports the device gone. In those quick cycles Dispose took about 15 ms longer and no slot came back (S57 checks it). In create-and-dispose timing runs on five profiles, medians moved by no more than run-to-run noise.

A second optimization in the same change: when a HIDMAESTRO sweep walks registry entries that exist only as PHANTOM (registry residue from prior sessions, no live devnode), skip the `hmswd.exe` SwDeviceCreate-reconnect roundtrip entirely. Saves ~50-75ms per stale entry and prevents creep across same-process recreation cycles.

#### Why this matters for consumers

If your application needs fast profile switching (e.g. remapping a physical controller to a different virtual identity on the fly), the profile architecture group determines the user-perceived latency:

- **Switching between plain HID profiles** (DualSense ↔ DualShock 4, or any non-Xbox pair): ~280 ms round trip (~80 ms dispose + ~200 ms create). Essentially instant.
- **Switching to/from Xbox 360 Wired**: ~135 ms dispose (down from ~5,700 ms pre-v1.3.1) + ~200-700 ms create (slot-claim wait capped at 500 ms post-v1.3.2). Round-trip ~350-850 ms vs ~6.4 s pre-v1.3.1.
- **Switching to/from Xbox Series BT**: ~500 ms dispose (down from ~11 s pre-v1.3.1) + ~150-600 ms create (slot-claim wait capped at 500 ms post-v1.3.2). Round-trip ~650-1,100 ms vs ~11+ s pre-v1.3.1. PadForge user-reported: virtually instantaneous create and swap.

## Glossary

| Term | Meaning |
|------|---------|
| **XUSB** | Xbox USB protocol. The device interface GUID (`{EC87F1E3-...}`) that `xinput1_4.dll` discovers to find Xbox controllers, and the one WGI walks for XUSB-backed Gamepads. |
| **WinExInput** | Windows Extended Input. A device interface GUID (`{6C53D5FD-...}`) HIDMaestro no longer registers anywhere. Older builds put it on HID parents and the SDK still sweeps those entries away. Ghidra decomp of `Windows.Gaming.Input.dll` (Win11 26200) found zero references to this GUID; it is not actually WGI's `GamepadAdded` source. WGI admission comes from the HIDClass pass-list (plain HID profiles) or the xinputhid UpperFilter tripwire (Xbox XUSB-companion profiles). |
| **xinputhid UpperFilter tripwire** | Registry string `"xinputhid"` written to a device's `DEVPKEY_Device_UpperFilters` (via INF HKR AddReg or SetupAPI) to satisfy WGI's `IsDeviceOrAncestorFilteredBy` wstring compare. Does not load `xinputhid.sys`: the filter only attaches to HID-class devices. Admits a System-class device (the XUSB companion at `SWD\HIDMAESTRO`) to WGI's XUSB dispatch path. See Techniques. |
| **XUSB Companion** | A separate UMDF2 device (`HMXInput.dll`) that handles XUSB IOCTLs for XInput. Lives at `SWD\HIDMAESTRO\<token>`. Needed because `mshidumdf` suppresses XUSB on HID devices. |
| **SWD enumerator** | "Software-device" PnP enumerator. Devices created via `SwDeviceCreate` (cfgmgr32) appear under `HKLM\SYSTEM\CurrentControlSet\Enum\SWD\<enumerator>\<instance>`. The SwDevice API lets us specify an explicit non-sentinel `pContainerId`, which is the linchpin of the slot-1-skip fix. |
| **Ownership claim** | A named pipe created with `FILE_FLAG_FIRST_PIPE_INSTANCE` and one instance, under the `ProtectedPrefix\Administrators` pipe prefix, where only an elevated process can create one. A process holds one for itself, and each controller holds one for its transport index and one for its identity. Windows deletes it when the holder ends, so a missing claim is proof the holder is gone. See Techniques: Programs Side by Side. |
| **Transport index** | The machine-wide number that names a controller's sections, events, owner pipe and registry key and is the `ControllerIndex` the driver reads. Equal to the context's slot when that number is free on the machine. |
| **Identity token** | The instance-name segment every devnode of one virtual controller carries: `HM_0000` for the default key of index 0, `HM_` plus sixteen hex digits for a consumer key. Fixed across lives so the HID child keeps its path. Replaced the per-process session-id prefix in v1.8.0. See Techniques: Stable Device Identity. |
| **ParentIdPrefix** | The `level&hash&n` value in a parent's instance key that PnP prepends to the instance id of every child that reports a non-unique id (HID children do). Read from the key when the child first arrives, minted with a fresh counter only when absent. HIDMaestro writes the identity's value so the child path is the same on every life. A ROOT parent whose identity's child record was left without a driver writes the next value, `1&hash&1` to `1&hash&3`. |
| **ContainerID slot-1 skip** | Pre-fix bug in `xinput1_4!FUN_18000de2c`: a null-sentinel ContainerID `{00000000-...-FFFF-FFFFFFFFFFFF}` triggered a code path that set bit 2 on the device struct, made the fallback slot allocator skip iter 0, and surfaced an empty slot 1 to consumers. The SWD migration's explicit `pContainerId` closes the path. |
| **GameInput mapping** | Registry entries at `HKLM\...\GameInput\Devices\{VID}{PID}...` that tell WGI how to map HID axes/buttons to the Gamepad interface. Windows ships its own. HIDMaestro writes one only for a code-built game pad of the one shape it fits. |
| **&IG_** | "Interface Group" marker in Xbox device paths. Chrome and HIDAPI skip devices with this in the path; SDL3 falls through to its RawInput backend. |
| **Vx/Vy** | HID velocity usages (0x40/0x41). Invisible to DirectInput's axis mapper but enumerated by GameInput; used to carry separate trigger values. |
| **mshidumdf** | Microsoft's kernel-mode HID minidriver proxy that hosts UMDF2 HID drivers. |
