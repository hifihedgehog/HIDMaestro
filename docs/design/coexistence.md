# Design note: programs side by side

This note was written for a release numbered 1.13.0, which never shipped: its work ships in 2.0.0 with the conversion of every device to data (`data-driven-devices.md`).

Two or more programs that embed HIDMaestro on one machine, NativeAOT and single-file apps, and a Wii U GameCube adapter persona. HandHeld Legend reported the coexistence and AOT failures while building HHL Gamepad Link (hhl-gamepad-link, `patches/hidmaestro-hhl.patch`). This note records what is broken at b4d29d9, the mechanism chosen for each fix and the evidence behind it, and every behavior a consumer will see change.

## What is broken at b4d29d9

Each claim below was checked against the source at b4d29d9.

Controller indices are allocated per context, but everything keyed by an index is machine-wide. `HMContext.CreateController` takes the lowest index free in its own context (`HMContext.cs:370-375`), and `CreateControllerAt` checks only its own context (`471-476`). The sections and events `Global\HIDMaestro{Input,Output,PidState,InputEvent,OutputEvent,InputAck,InputAckEvent,CompanionInputEvent}<N>` are created with `CreateFileMappingW` and `CreateEventExW`, which open an existing object of the same name without complaint (`SharedMemoryIO.cs:1023`, `1109`). The owner pipe `\\.\pipe\HIDMaestroOwner<N>` allows two instances in total and ignores a failed create (`181`, `322-326`). The registry key `SOFTWARE\HIDMaestro\Controller<N>` (`DeviceOrchestrator.cs:21-23`), the `ControllerIndex` the driver reads from the device key (`driver.c:240-264`) and the last byte of the Switch Pro MAC (`driver.c:477`) are keyed the same way. Two programs that each create a first controller both get index 0 and write each other's sections and keys. Two contexts in one process collide the same way: the class comment says they share an index pool (`HMContext.cs:17-18`), but each context has its own map while `SharedMemoryIO` keeps one process-wide table per index.

Identity uniqueness is checked per context. `ThrowIfIdentityInUse` looks only at its own context (`HMContext.cs:414-425`). Two keyless programs at index 0, or two programs that pass the same key, resolve the same token. `ClearParentIdPrefixRivals` skips a parent whose name equals the caller's token (`DeviceManager.cs:481`), so the second program creates over the first program's live devnode.

Sweeps remove devices without proof that their owner is gone.

- `InstallDriver` always runs `RemoveAllVirtualControllers(preserveInstall: true)` first (`HMContext.cs:169`), which removes every other program's live controllers.
- The once-per-session cleanup in `SetupController` (`DeviceOrchestrator.cs:1344-1384`) removes every present `ROOT\SYSTEM\0000` to `0009` device whose name or hardware id contains HIDMaestro. Its `CleanupGhostDevices` removes every present HIDMaestro device under `ROOT\HIDCLASS`, `ROOT\HID_IG_00`, `ROOT\XnaComposite`, `ROOT\HIDMAESTRO` and `SWD\HIDMAESTRO` (`448-450`), every instance under `ROOT\VID_*` and `SWD\HIDMAESTRO*` present or not (`472-476`), and the interface registrations of live devices (`509-563`). `DisableGhostXusbInterfaces` disables HIDMaestro devices that are not yet started (`621-627`), which includes another program's controller in the middle of its create.
- `UsbipBackend.SweepStaleOnce` and `DetachAllOwned` detach every import in the SDK's loopback port range except, for the first, this process's own port, and cancel re-attach attempts on every port in the range (`UsbipBackend.cs:61-131`). `IsOurLocation` decides by port range alone (`133-138`).
- `RegistryLedger.PruneDead` already releases only holders whose process is provably gone (`RegistryLedger.cs:73-85`).

Driver deployment has no cross-process arbitration. `FullDeploy` replaces the installed driver whenever the embedded payload's hash differs from the installed one (`DriverBuilder.cs:453-470`), with no notion of which is newer. The staging directory `%TEMP%\HIDMaestro_<hash>` (`186`) is reused when its file count and sizes match, with no hash check (`189-195`), and `hmswd.exe` goes into one shared `%TEMP%\HIDMaestro` for every version (`SwdDeviceFactory.cs:362-363`). A non-elevated process of the same user can write both places, and the elevated SDK runs what it finds there. Two programs calling `InstallDriver` at once on a machine without the driver collide in that shared directory: run against b4d29d9, the coexistence probe's section F had one fail with "signtool failed for HIDMaestro.dll ... The file is being used by another process". Every create also installs the driver with `UpdateDriverForPlugAndPlayDevices` and the profile's VID/PID hardware id (`DeviceNodeCreator.cs:368`), which installs the SDK's own package on every present device of that id whenever it ranks better, so a newer SDK moves another program's controller of the same profile onto its driver.

HIDMaestro.Core does not build for NativeAOT, trimming or single-file publish: 19 reflection-based `JsonSerializer` calls (`ControllerProfile.cs:731`, `795`, `HMLayoutLoader.cs:35-56`), no `JsonSerializerContext`, 113 `DllImport` declarations, `Assembly.Location` at `SwdDeviceFactory.cs:348`, and no `IsAotCompatible`.

## Ownership

A process takes one ownership claim before its first machine-wide write, and holds it until it exits. Resources it allocates machine-wide, a transport index or an identity, are claimed the same way, one claim per resource.

The claim is a named pipe created with `FILE_FLAG_FIRST_PIPE_INSTANCE` and a maximum of one instance. [CreateNamedPipeW](https://learn.microsoft.com/windows/win32/api/namedpipeapi/nf-namedpipeapi-createnamedpipew) documents the flag: "If you attempt to create multiple instances of a pipe with this flag, creation of the first instance succeeds, but creation of the next instance fails with ERROR_ACCESS_DENIED." The second claimant therefore learns it lost from the same call that would have won. With a maximum of one instance it fails on this machine with `ERROR_PIPE_BUSY` instead, because the instance limit is checked first, and either error means the claim is held. The same page states that a null or non-inheritable `SECURITY_ATTRIBUTES` keeps the handle from being inherited, and that an instance is deleted when the last handle to it is closed, which the system does when the process ends. A pipe handle has no thread affinity.

Liveness is a `WaitNamedPipe` probe with a 1 ms timeout. [WaitNamedPipeW](https://learn.microsoft.com/windows/win32/api/namedpipeapi/nf-namedpipeapi-waitnamedpipew) documents that "if no instances of the specified named pipe exist, the WaitNamedPipe function returns immediately, regardless of the time-out value", that an expired wait fails with `ERROR_SEM_TIMEOUT`, and that a timeout of 0 is `NMPWAIT_USE_DEFAULT_WAIT`, the server's default, which is 50 ms when the server passed 0. Measured on this machine: a missing pipe fails with `ERROR_FILE_NOT_FOUND` in under 5 µs, and an instance its server created but never connected counts as available and returns true. A true return and `ERROR_SEM_TIMEOUT` both mean a live holder, and `ERROR_FILE_NOT_FOUND` means none. Any other error counts as live. The probe opens no handle, so probing cannot keep a claim alive.

A named kernel object judged by `ERROR_ALREADY_EXISTS` was the other candidate, and it failed on one point. Measured on this machine, 2026-10-14:

| Case | Named pipe, first instance | Named event |
|---|---|---|
| Second claimant while the holder lives | loses, `ERROR_PIPE_BUSY` | loses, `ERROR_ALREADY_EXISTS` |
| Holder killed with `TerminateProcess` | name gone at once, next claim wins | next claim wins |
| Holder killed while a prober holds a handle | probing opens no handle | next claim loses until the prober closes |
| Holder killed while a client is connected | name gone at once, next claim wins | n/a |
| Holder's child started with inherited handles outlives it | claim gone, child kept nothing | not tested |
| Cost of claim and release | 5.7 µs | 2.8 µs |
| Cost of a probe for a missing claim | 4.5 µs | n/a |

A sweep that probes a named event holds it open for the length of the probe, and a claimant arriving in that window reads a live owner where there is none. The pipe has no such window, and a connected client does not keep it alive either. The pipe is the one mechanism, used for every claim.

The claim pipes live under the pipe prefix `ProtectedPrefix\Administrators\`, which the Session Manager creates at boot and under which only a token with Administrators enabled can create a pipe. Under a plain name a program that is not elevated could create a claim first, and every HIDMaestro program would read it as a live owner's for as long as that program ran. No Learn page describes the prefixes, and the one public account (James Forshaw, "Named Pipe Secure Prefixes", 2017) names no Windows version, so the binaries were read: nine `smss.exe` files from 10.0.10240.16384 through 26100.1 (19041.x among them, which Windows 10 2004 through 22H2 run) each create `\Device\NamedPipe\ProtectedPrefix\Administrators` among its prefixes, and `npfs.sys` 10240.16384, 19041.5125 and 26100.1 carry the same prefix routines in Microsoft's public symbols (`MachineClaims.cs`). That a token without Administrators is refused there was measured on 26200 only.

The claim pipes carry `O:BAD:P(A;;0x00100080;;;SY)(A;;0x00100080;;;BA)(A;;0x00100080;;;LS)`, owner Administrators, and SYNCHRONIZE and FILE_READ_ATTRIBUTES for SYSTEM, Administrators and LocalService only. A process that is not elevated can still probe a claim, because `WaitNamedPipe` opens nothing, and it can neither open a claim nor take one. An elevated process can open one for attributes, which uses up the single instance and makes the probe answer `ERROR_SEM_TIMEOUT`, still a live holder. Nothing can read or write a claim. The driver host never opens a claim. It keeps opening only the owner pipe it already uses.

| Claim | Pipe name | Held for |
|---|---|---|
| Owner | `\\.\pipe\ProtectedPrefix\Administrators\HIDMaestro.Owner.<owner id>` | the process, from its first machine-wide write |
| Transport index | `\\.\pipe\ProtectedPrefix\Administrators\HIDMaestro.Index.<N>` | the controller's life |
| Identity | `\\.\pipe\ProtectedPrefix\Administrators\HIDMaestro.Identity.<token>` | the controller's life |

A process that cannot take its owner claim stops there. A claim refused with `ERROR_ACCESS_DENIED` throws `UnauthorizedAccessException`, any other error `InvalidOperationException` naming it, and the message says what was read: a token without Administrators enabled is asked to run elevated, and a token with Administrators enabled is told that a pipe system without the prefix, or software that filters pipe creation, can refuse a claim this way (`MachineClaims.RefusedClaim`). A sweep refused for access skips its work.

The owner id is a GUID the process draws once. Beside the owner claim sits a record under `HKLM\SOFTWARE\HIDMaestroOwners\<owner id>`, readable by everyone: process id, image path, start time, SDK version, USB/IP server port and the name of the staging directory it uses, and one subkey per live controller with its identity token, transport index, backend, profile id, devnode instance id and vhci port. The vhci port is the current one, rewritten when usbip-win2 imports the device again and 0 while it is dropped. The record is written with the owner claim, at the process's first machine-wide write, and stays until the process exits or is killed, so a program between its `InstallDriver` and its first create is as visible to other programs as one with controllers. A record write that fails is tried again at the next call that takes the claim. The process writes a controller's entry before any PnP work and removes it once the controller's devices are gone. A record whose owner claim no longer exists describes a dead owner, which is what the sweeps act on. The process id and start time are for people reading the record: nothing decides liveness from them.

## Transport index and slot

`HMController.Index` stays internal and keeps meaning what every internal caller uses it for, the index that names the machine-wide objects. The context's own numbering becomes a slot: `CreateController` takes the lowest slot free in its context, and `CreateControllerAt(index, ...)` keeps its contract of one controller per slot per context. Each controller holds a machine-wide transport index, which names every section, event, pipe and registry key and is the `ControllerIndex` the driver reads. `HMController.TransportIndex` and `HMController.SectionNames` expose it, so native writers can find their sections.

The transport index is the slot number when that index is free machine-wide, and otherwise the lowest free one. A program running alone therefore gets the numbers it always got, and native writers that compute names from the index see no change. Two programs that each create a first controller coexist, the second on the lowest free index. While a v1.12.0 program runs, the search starts at 64 instead (`ControllerLease.LegacyClearance`), below. An index N is free when all of these hold:

- its claim `HIDMaestro.Index.<N>` can be created,
- no process holds `\\.\pipe\HIDMaestroOwner<N>`, v1.12.0's owner pipe, whoever made it,
- none of the index's sections and events exists with an owner other than SYSTEM or Administrators (LocalService for the driver's StopEvent and OutputEvent), as another kind of object, refusing READ_CONTROL, failing to open for another error, or with an owner that cannot be read (`SharedMemoryIO.ForeignObjectAt`),
- no present HIDMaestro devnode records N as its `ControllerIndex`, whoever owns it, unless the devnode carries the identity this create is about to reclaim,
- no USB/IP import on 127.0.0.1 ports 18509 to 18524 uses it whose server port no owner record, live or dead, names. Such an import belongs to a program on an older SDK, whose composite has no devnode to record the index, and its bus id `1-<N+1>` carries it.

When all 4096 indices fail, the create throws `HMResourceInUseException`. Its message counts the indices skipped for a foreign object and names the first, with the owner SID when one was read. Only beside an owner it read does it name a program built on HIDMaestro 1.12.0 or older as a possible maker, and it counts apart the objects whose owner it could not read. An event of the index that another program made after the check refuses the create the same way, and the next create takes another index.

Whether the input section exists is no evidence either way. Measured on this machine: after an Xbox 360 controller's Dispose returns, `Global\HIDMaestroInput<N>` stays open for as long as the disposing program lives, more than 10 seconds in every run, on v1.12.0 as on this release. The SDK's own XInput calls during the create leave xinput1_4 holding a handle to the XUSB companion, which keeps the removed companion's driver host, and its view of the section, alive until the program polls XInput again (it closed at once when the test called `XInputGetState` on every slot) or exits. An allocator that skipped indices with an open section would move a program off its index after such a dispose. The case the section check would have covered beyond the rules above, a program older than v1.12.0 in the middle of creating its sections, is a race this release does not close.

The owner pipe's first instance is then created with `FILE_FLAG_FIRST_PIPE_INSTANCE` and v1.12.0's access mode, type, instance count and timeout, which all instances of one pipe must share. A v1.12.0 program that starts on the index between the check and the create makes this fail, and the create stops with `HMResourceInUseException` rather than share the sections. The first instance is taken before the create writes any section.

A keyless controller's default identity derives from its transport index, as it derived from the index before. When another program holds index 0, a keyless controller lands on another index and so on another identity, and the index and identity can differ between runs. Durable device paths need an identity key, which has been the documented contract since v1.8.0.

A running v1.12.0 program's next create takes the lowest index free among its own controllers and looks at no other program, and it replaces a devnode of that index's default identity as its own prior life. Measured with the old code (coexistence section W5): its second and third creates took a v2.0.0 program's indices 1 and 2, its default identity replaced that program's devnode, and that program's exit then removed two of the v1.12.0 program's devices. While one runs, a create therefore starts at transport index 64 (`ControllerLease.LegacyClearance`), which that program reaches only with 64 controllers alive at once, slot 0 on 64 and slot 1 on 65. The floor orders the indices a create tries and refuses nothing. A key `index:<N>` with N below 64 takes index N's default identity as asked, on an index from 64, though that program gives the same identity to its own controller on index N and its next create there replaces a devnode of that name (decision (c): the newer release takes precedence). A v1.12.0 program counts as running when a present device of its reads as one (the census below), when a USB/IP import no record names has its index's owner pipe held, or, while a device whose index cannot be read is present, when the census finds one running some other way: by its registry ledger holder, or on an index no live record and no present device's index accounts for (the census below). A device a closed program left never raises this floor.

Everything derived from the index moves with it: a keyless controller's identity token (`HM_0064`), and with it its instance path, ParentIdPrefix, container id and HID interface path, every controller's HID serial (`HM-CTL-0064` and up), the DualSense pairing MAC byte and the Switch Pro MAC's last byte, a byte of the XUSB capabilities, the USB/IP bus id `1-<index+1>`, and a keyless composite's USB serial and USB instance id. A keyed controller keeps its paths, container id and composite USB serial, but its HID serial and MAC bytes follow the index. A program restarted after a crash takes its old index back only when it is 64 or more. DirectInput instance GUIDs are positional and do not follow the index.

Such a program can share an index with a running program of this release, usually 0, beside a program such as PadForge. Its first create there opens this release's sections and its own owner pipe fails, because this release's two instances are the pipe's maximum, so every named object on that index carries this release's names, and its device names no index. That first create is the case outside every gate (`docs/design/data-driven-devices.md`, "One case stays outside every gate"). What tells it apart is the registry ledger: a v1.12.0 create writes a holder `<pid>-<start>-<index>` for its controller under `HKLM\SOFTWARE\HIDMaestroRegistryLedger\JoystickOem\<VID&PID>\Holders` before its devnode exists, and its teardown removes it (b4d29d9 `DeviceOrchestrator.cs:805`, `:1394`, `:1436`, `:1998`, `RegistryLedger.cs:58-59`, `:223-224`). This release writes the same holders, only after its owner record, and its exit deletes the record only once its holders are gone, so a holder whose process runs (the process with its id, opened for its creation time, has its start time, or, when that process refuses the open, the system's process list gives it that start time) and that no live record names is a v1.12.0 program's, on any index, and it raises the floor. The census reads the holders before and after the records and counts a holder both reads have. A keyboard or mouse profile writes no such holder, nor does a create whose ledger write failed (v1.12.0 swallows that error), so a v1.12.0 program of only keyboards and mice, or one whose write failed, on an index a running program of this release holds, still goes unseen while its device's index cannot be read, and its next create can land on this release's next index.

## Identity

The identity claim `HIDMaestro.Identity.<token>` is taken before any PnP work. A program asking for an identity a live program holds gets `HMResourceInUseException`, derived from `InvalidOperationException` so existing catch blocks keep working. Its message, and its `OwnerProcessId`, `OwnerImagePath` and `OwnerSdkVersion`, name the holder from its record. The first program's devices see no PnP activity, which section B of the coexistence probe checks by holding a read handle on the first program's device through the second program's attempt. The same check applies inside one process, across contexts. A sweep of another program holds an identity's claim while it removes the device a dead program left under it, and no record lists the identity then, so while no live record lists the token a keyed create waits for the claim, up to 120 seconds, the bound its own removal of that devnode would take, and then takes the census again. A context dropped without `Dispose` keeps its controllers' claims until the process exits, and a create of one of their keys in that process is refused until then, with a message that says so.

A v1.12.0 program takes no identity claim. When a present devnode carries the identity's token and no record lists it, the create asks the census whether a running v1.12.0 program holds the devnode's `ControllerIndex` (the rule under Sweeps). While one does, the create is refused with the same exception.

A create that fails gives back everything it took before it throws: a UMDF2 controller's devices are removed, its sections, events and owner pipe closed, its configuration key deleted and its registry ledger holds released, then its record entry, identity claim and index claim go, keyed or keyless, so a retry or another program can take the index at once. The devices go by the parent's instance ID, which `SetupController` hands the cleanup as soon as the registration gives it, so a parent under `ROOT\HIDClass`, which no sweep by index reaches, goes too when the create throws on a failed start. A composite's device is disposed and its emulator's threads stop, even when its constructor threw. A create refused because a running v1.12.0 program took the index during the create, or because the device of a running program, or of one whose owner cannot be known, holds the ParentIdPrefix, removes nothing of that program: it releases only what the refused call itself made.

`ClearParentIdPrefixRivals` keeps the 0xCA invariant: never two parents with one ParentIdPrefix. A present rival is removed only when its owner is provably dead. When its owner is running, here or in another program, or cannot be known, the create is refused with `HMResourceInUseException` instead, and the message names the rival devnode. When the owner cannot be known, it also names the cleanup call that removes the device. A rival that is not present is removed as before, because a ROOT record re-enumerates at boot.

## Sweeps

A sweep removes a present device only on proof that its owner is gone. What the census (`OwnerCensus`) knows about each present HIDMaestro devnode, grouped by identity token:

| Present device | Owner | Action |
|---|---|---|
| In a record whose owner claim is gone | dead | removed with everything the record lists, unless a running program holds the device's index or identity |
| In a live record | running | left alone, the caller's own included |
| In no live record, its index or identity claim held | a running program on this release | left alone |
| In no record, `HIDMaestroOwner<N>` held by the program the driver watches | a running v1.12.0 program | left alone |
| In no record, the pipe gone or not the watched program's, `Global\HIDMaestroInputAck<N>` exists | a v1.12.0 program that has exited | removed |
| In no record, no owner pipe, no InputAck section | a program older than v1.12.0, state unknown | left alone |

Only a v1.12.0 or later SDK creates `Global\HIDMaestroInputAck<N>`, and the program's owner pipe closes when the program ends however it ends. A device with neither was made by an older SDK, whose program leaves no sign of whether it still runs.

A device with an identity token belongs to the record that lists its token, and only a device older than identity tokens to the record that lists its index, since a running v1.12.0 program takes indices without looking at other programs. A program on this release takes its claims before its record entry, and the census reads the records before it lists the devices, so a device whose index or identity claim is held is a running program's, with or without a record.

The census reads a device's index from its `Device Parameters\ControllerIndex`, which every SDK writes at create. A v1.12.0 program's device whose driver install failed (a v1.12.0 program on a machine where only this release deployed, section Y21 of the coexistence probe) was read in Windows Sandbox with no readable value while its program ran, though its create had written it. The census keeps why it read no index (no value, no key, or a key it may not read) and logs it. When the value cannot be read:

- A device named by a default identity's token, `HM_<index>` in four or more digits, takes the index the token names, since the token is built from it. Such a device is judged as any other, and the allocator skips that one index.
- A keyed device has no index. The census cannot tie it to an owner pipe. When no record names it, it reads as a program's whose state is unknown, and a sweep leaves it. A dead record that names it still makes it Dead, and the sweep removes it. It raises the floor of 64 only while a v1.12.0 program is seen running on an index below 64: a registry ledger holder on that index whose process runs and is named by no live record (`RegistryLedger.LiveHolders`, read before and after the records), or, on an index no live record and no present device's index accounts for, that index's owner pipe held beside its input section and an acknowledgement section without the driver's ended marker, the evidence the census takes for a held pipe no driver reports on. The same holds for a device older than identity tokens whose index cannot be read. Once that program is gone, the device holds no index and moves no create. The uninstall-grade cleanup removes it.

A held pipe alone proves nothing, because any program can create the name `\\.\pipe\HIDMaestroOwner<N>`. The driver is the pipe's client and asks Windows who serves it. When its watch connects it writes three values under the device's `Device Parameters\HIDMaestro` key: `OwnerProcessId` from `GetNamedPipeServerProcessId`, `OwnerPipeOwner`, the pipe's owner SID as text, and `OwnerConnected` 1, written last. When the server's end closes it sets bit 31 of InputAck's capability word, the ended marker, and writes `OwnerConnected` 0. A device context deletes the three values when it starts, so they describe its own watch. A held pipe counts as a running v1.12.0 program only while the driver's values show a connected watch whose server still runs and was created no later than the key's last write. `OwnerConnected` 0 beside the marker, or a recorded server that has ended or is a newer process with the same id, makes the pipe count for nothing, and the device reads as a v1.12.0 program that has exited. Without the values (a driver older than this release, or a watch that has not connected) the pipe counts only while the input section exists and the marker is clear. A process the census may not open is timed from the system's process list, and one it cannot time counts as running.

The marker belongs to the driver: an SDK clears it when it zeroes the section at a create, and a process that is not elevated gets read access only. A native reader of InputAck tests bit 0 (delivery acknowledged) and bit 1 (release on exit) one at a time and ignores bit 31. This driver keeps InputAck mapped for as long as the device exists. v1.12.0's own driver closes it on every idle recycle, so a dead v1.12.0 program's device on that driver reads as unknown about 4 s after the program ends, and stays. Such a device is never removed by a sweep without a scope. It is removed by the uninstall-grade cleanup, and by a create that asks for the device's own identity key, because that program is asking for that device back. The transport allocator skips its index.

USB/IP imports are matched by server port. A server takes a loopback port from 18509 to 18524, then from 28509 to 28524, then one Windows assigns, and records it in its owner's record. An import counts as the SDK's on either range or on any port a record names, and ports are compared as numbers, so `018509` matches 18509. An import whose server port has no listener on the loopback interface, read with `IPGlobalProperties.GetActiveTcpListeners`, belongs to a dead server and is detached. A v1.12.0 server listens the same way. An import on this process's own port that none of its controllers made was left by the program that held the port before, and is detached. Every detach is by server port and bus id, never by a vhci port remembered from earlier, because the vhci port of a dropped and re-imported device changes.

The re-attach attempts usbip-win2 keeps for a dropped import are canceled by exact location: each bus id a dead record names on its server's port, and on a gone port of the first range the bus ids 1-1 to 1-8 a v1.12.0 server canceled itself. A location a live server exports, read from its own server or from its device list, is never canceled, since a program started since can export the same port and bus id, and a server that does not answer its device list within 1 s keeps all of its attempts. The program's own port counts as gone for the attempts, except for the bus ids it exports. An attempt that reaches a server of this release with a bus id it does not export gets ST_NODEV, and its location is canceled.

A sweep takes each dead group's index and identity claims before it acts on the group, and keeps them until every group it removes, and every orphaned HID child it removes after them, is out of the device tree, waiting up to 10 seconds for each orphan. The census is at least 500 ms old by then, since the stop events drain first, and a program restarted after a crash, or another program, could create on the same index or identity meanwhile and get the dead devnode's instance id. A create of this release takes both claims before it writes its configuration or makes a devnode, so none lands on a group the sweep holds, and a group whose claims another program holds is skipped. A v1.12.0 program takes no claim: its owner pipe is checked again right before each removal and each configuration delete. A HID child's id follows from its parent's, so the claims stay until the orphan children are gone too. A group the sweep cannot confirm gone keeps its configuration and its dead record, so the next sweep still sees a dead owner's device. A device that stays in the tree after every removal therefore costs every sweep of every program a retry of up to 120 seconds, and up to 10 seconds per orphan.

The public cleanup keeps its overloads and becomes orphan-safe. `RemoveAllVirtualControllers()` and `RemoveAllVirtualControllers(bool preserveInstall)` remove the devices of dead programs. A running program's controllers, the caller's own included, stay: section D of the coexistence probe checks that a live program's sweep leaves its own controller running. Package removal (`preserveInstall: false`) happens under the deploy lock and only while no device is present, no other v2.0.0 program runs and the caller has no controller. In a process that is not elevated both overloads return without doing anything. Both remove the GameInput tables HIDMaestro wrote through v1.11.0, as v1.12.0's cleanup did, where no running program uses them. A program on v1.12.0 or later holds a table it uses through the registry ledger, and a create of its removes one it does not use. A v1.11.0 program writes the table at its first create of an identity and reads through it while that device lives, so a table stays while a present devnode or any `Controller<N>` configuration carries its VID and PID, and every table stays while an input section exists that no configuration, present device, live record, foreign import or InputAck section explains, which is a v1.11.0 create whose identity cannot be read yet. A held v1.12.0 owner pipe explains nothing, since any program can create the name. `RemoveAllVirtualControllers(HMCleanupScope.Everything, bool)` removes every HIDMaestro device and import on the machine regardless of owner, which `HIDMaestroTest cleanup` and the battery use, and with `preserveInstall: false` it removes the packages under the deploy lock with no check for other programs or the caller's controllers. A controller the calling program still holds stays an object with no device behind it. It keeps its transport index and sections until the program disposes it, and its submits and PID calls return and reach nothing. Its idle repeat, protocol clock and output reader stop, `DriverVersion` reads null, `DeliversEveryReport` and `ReleasesOnConsumerExit` false, and a keyboard or mouse submit no longer waits for a delivery no driver will acknowledge. Another running program's controllers keep reading the removed driver's words: their `DriverVersion` names it, `DeliversEveryReport` and `ReleasesOnConsumerExit` stay true, their keyboard and mouse submits wait up to 200 ms on each of the next three frames, and a protocol controller's next send waits up to 200 ms for the reply the device never delivered.

A program that exits normally without disposing its controllers has their devices removed by the SDK's own `ProcessExit` handler, registered with the owner claim. The runtime raises `ProcessExit` while the process's other threads still run, under .NET on the finalizer thread and under NativeAOT on the thread that called `Environment.Exit` or returned from `Main`, so a create or the phantom cleanup can be in flight. The handler waits for both through `OwnerSweep.CreateGate`, at most 10 seconds in all, and the cleanup begins no further uninstall once the handler starts. Past that bound it removes nothing and keeps the record, which names every device of the process, the ones a create in flight may still make included. Otherwise it stops the program's WinUSB re-binds, waiting out a bind in progress, detaches its USB/IP imports, signals its stop events, removes its device groups one at a time on its own thread, each removal within its own bound as `Dispose` waits it out, releases its GameInput and joy.cpl holds in one ledger scope, then restores its WinUSB entries, each entry with up to two short ledger acquisitions of its own, and deletes its record once its holds are gone. A release that fails is tried again, and a hold that still stands keeps the record until the process ends, whether or not the record still lists a controller. A device it cannot confirm gone keeps the record too, so the next sweep removes it under its claims. Five exits therefore leave the process's devices present until a program built on this release next sweeps: a create still holds the gate at the bound, on another thread, waiting for another program's sweep or behind a transport install, one uninstall of the phantom cleanup outlasts the bound, a device does not leave, another program holds the PnP lock past what is left of the bound (Registrations and removals), or, under .NET, a thread inside a create calls `Environment.Exit` and the handler on the finalizer thread waits for that thread until the bound. Under NativeAOT that exit runs the handler on the creating thread, which gives up at once. PadForge's exit hook, which sweeps with `preserveInstall: true` when its engine did not shut down cleanly, relied on the sweep removing its own devices. The SDK's handler does that now. A killed program runs no handler, and its devices go with the next sweep of any program through its record.

The common case is cheap. With no dead record and no present device of a dead program, nothing walks the enumerators. The census lists the instances under the ROOT and SWD keys of `SYSTEM\CurrentControlSet\Enum` that HIDMaestro's enumerators (`HIDMAESTRO*`, `HMCOMPANION*`) or the shared ones (`VID_*`, `XnaComposite`, `HID_IG_00`, `HIDCLASS`, `SYSTEM`) hold, and checks presence with `CM_Locate_DevNode` for the HIDMaestro-owned ones only, which finds a present devnode and no absent one. A shared enumerator's instance counts when its hardware ids name HIDMaestro. Past 64 candidate instances, or when a key cannot be read, it goes back to `CM_Get_Device_ID_List` with `CM_GETIDLIST_FILTER_ENUMERATOR | CM_GETIDLIST_FILTER_PRESENT` for the two roots, whose cost does not grow with absent devnodes. A registry read per HIDMaestro devnode follows.

The phantom-record cleanup moves off the create path onto a background thread, once per process, started by the first of `InstallDriver`, the first create and `RemoveAllVirtualControllers()`. The call that starts it returns without waiting for it to end, a later call removes no phantom, and the next process's first cleanup removes what is left. The cleanup takes `OwnerSweep.CreateGate` for writing, and every create holds it for reading from its lease to its last record write, so the cleanup never runs during one of this process's creates. A create, and the uninstall-grade cleanup, which takes the gate for writing before it acts, wait while the cleanup runs: one pass over the phantoms, their uninstalls, at most 5 seconds of waiting in all, for the machine-wide PnP lock before each uninstall and for Windows to let the phantom go after it, and two passes over interface registrations that wait for the lock within the same 5 seconds. Each uninstall runs under the identity claim of the phantom's controller, its own token's or, for a HID child, its parent's, and the cleanup keeps that claim and the gate until a PHANTOM locate no longer finds the id or the 5 seconds are spent, so no create of this release registers the id while its uninstall may still be going. A phantom whose identity claim a program holds is that program's create in flight, and is skipped, and so is a default identity's phantom while a v1.12.0 program holds that index's owner pipe. `RemoveAllVirtualControllers()` and `(bool)` no longer remove phantoms themselves: they start the cleanup when it has not run, and remove the phantom interface registrations on the caller's thread.

When the process's first claim is taken inside the program's own `ProcessExit` handler, the SDK's exit handler is registered too late to run, so a cleanup thread would end with the process, possibly inside an uninstall. `Environment.HasShutdownStarted` returns false on .NET 10, but the runtime raises `AssemblyLoadContext.Default.Unloading` before `ProcessExit` on .NET and NativeAOT (`AppContext.OnProcessExit`), and the SDK subscribes to it from its module initializer (`ProcessExitSignal`). Once it has fired, the first call runs the cleanup on the calling thread before it returns, waiting at most 10 seconds for the gate, as `RemoveAllVirtualControllers()` ran its phantom pass on the caller's thread before this release. A normal first call still returns at once. Under NativeAOT module initializers run at startup, so the signal always holds. Under .NET the initializer runs when code that refers to the SDK is first compiled, or first run where it was compiled ahead of time, so a program in which no such code ran or was compiled before exit began, such as one that uses the SDK only inside that handler, misses the signal, and its cleanup ends with the process. That one case does worse than v1.12.0 when the call is a `RemoveAllVirtualControllers()`, which v1.12.0 finished on the calling thread. What an uninstall cut off there leaves is not documented: Learn describes `SetupDiRemoveDevice`'s success only. A record it leaves that still names HIDMaestro is a phantom, which the next process's first cleanup removes.

## Locks

A `Global\` mutex is open to every local program, so one that is not elevated could create a lock's name first and hold it, or give it a DACL that refuses everyone else. The SDK's machine-wide locks therefore live in a private namespace whose boundary descriptor holds the name `HIDMaestro` and the Administrators SID. "The caller must be within the specified boundary for the create operation to succeed" ([Object Namespaces](https://learn.microsoft.com/windows/win32/sync/object-namespaces)), so only a process whose token has Administrators enabled can create it, and its descriptor `O:BAD:P(A;;GA;;;SY)(A;;GA;;;BA)` lets only such a process open it. Every process opens it once under the alias `HIDMaestro.Admin` and keeps the handle until it exits, so a held lock always has a live namespace. A process that is not elevated gets `UnauthorizedAccessException` at its first lock. A session-0 service and a desktop program open the same namespace when both tokens have Administrators enabled, since no session is part of the boundary. A service running as LocalService or NetworkService is outside it. The session rule rests on the Learn page. No test opened the namespace from two sessions.

| Lock | Taken by | Wait |
|---|---|---|
| `HIDMaestro.Admin\Deploy` | a driver deploy past its fast path, every UMDF2 create's deploy gate, `DriverBuilder.SignDrivers`, `GenerateCatalogs` and `RemoveOldDriverPackages`, the test certificate's creation, package removal, and the add of a WinUSB package | 10 minutes, then `InvalidOperationException` |
| `HIDMaestro.Admin\Transport` | the usbip-win2 install, the repair of a host controller that stopped answering, and the move of an older host controller to 0.9.8.1 | 10 minutes, then `InvalidOperationException` |
| `HIDMaestro.Admin\WinUsb` | a WinUSB bind's look at the devnode and its install, a WinUSB restore, and the WinUSB package's removal | 2 minutes, then `InvalidOperationException` |
| `HIDMaestro.Admin\WinUsbFollowUp.<entry>` | the follow-up that watches one lingering WinUSB entry | never waited on |
| `HIDMaestro.Admin\Ledger` | every registry ledger and OEM name override operation | no bound for most calls. The WinUSB claims, restores and package note reads give up after 30 s, scaled, with `TimeoutException`, and a restore that gives up keeps its entry for the next sweep |
| `HIDMaestro.Admin\Staging` | the note of a staging directory in the owner record, and a staging prune | 2 minutes, then `InvalidOperationException` |
| `HIDMaestro.Admin\Pnp` | each devnode registration, each removal and uninstall through its removal test, a full deploy's pnputil install, every create's bus type stamp, the ghost XUSB sweep and the interface-class cleanup per devnode | 10 minutes, then `InvalidOperationException`. Once the process is exiting, only what is left of the exit's 10 s |

A mutex abandoned by a process that ended is acquired, and the work under it reads the machine again. The PnP lock comes after the deploy lock and before the staging lock: a full deploy takes it for its pnputil install with the deploy lock held, and a software device's registration stages hmswd.exe under it. The WinUSB, follow-up, ledger and transport locks are never held with it. In a process, `OwnerSweep.CreateGate` and a controller's teardown gate come before it. Each lock is taken in this order and never the other way: the deploy lock, then the WinUSB lock, then a controller's own bind gate inside the process, then the ledger's. A follow-up takes its own mutex before the WinUSB lock. The staging lock is a leaf, taken under the deploy lock or the transport lock or under none. The transport lock has no edge with the deploy lock, so a UMDF2 create never waits for a usbip-win2 install.

The ledger's lock also takes v1.12.0's `Global\HIDMaestro-OEM-Recovery` after its own, because a v1.12.0 program writes the same GameInput and joy.cpl keys under that name. Any program can create that name first. When SYSTEM or Administrators owns it, the lock waits for it as v1.12.0 does. When anyone else owns it, or its owner cannot be read, the lock waits five seconds and goes on without it, so a program that holds the name cannot stop every HIDMaestro program's ledger work. A process pays that wait once: once a wait has run its full five seconds, later acquisitions wait 500 ms, a bound that still covers a v1.12.0 write, until one takes the mutex or finds it owned by SYSTEM or Administrators again (both bounds scaled by `HIDMAESTRO_TIMEOUT_SCALE`). A caller's own bound, the 30 seconds of the WinUSB claims and restores, covers both mutexes from one deadline: a wait it cuts short throws `TimeoutException` whoever owns the legacy mutex, and only a wait that ran the lock's own five seconds or 500 ms goes on without it. A name that cannot be opened is not taken, and the lock goes on and logs it. Every acquisition waits for the legacy mutex, nested or not. Three ways remain for this process to write while a v1.12.0 program holds the name: a scope that went on without it while the squatter lets go, a v1.12.0 hold longer than the bound, and a DACL that admits a v1.12.0 program's token and refuses this process's. Only an unbounded wait closes the first two, and an unbounded wait would let any program stop every HIDMaestro program's ledger work by holding the name.

## Driver deployment

Every driver deploy holds the deploy lock for the length of one call. A named mutex fits here: one thread acquires and releases it inside one call ([CreateMutexW](https://learn.microsoft.com/windows/win32/api/synchapi/nf-synchapi-createmutexw)). An abandoned mutex is acquired and the deploy re-reads the installed state before acting.

The same-version fast path stays outside the mutex at its current cost: the manifest hash in `SOFTWARE\HIDMaestro` and the driver store check. When it misses, the deploy takes the mutex and checks again, so of two programs calling `InstallDriver` at once, one deploys and the other returns `AlreadyCurrent`. Section F checks it from a machine with no driver.

The installed version is the newest `DriverVer` among the `hidmaestro.inf` packages in the driver store's FileRepository. Two stamps compare by release version first, then by build date, then by build number, so a release is newer than another by its version even when the other was built later. `HMContext.LastDriverInstall` reports the outcome:

| Installed driver | Outcome |
|---|---|
| none | `Installed`, a full deploy |
| none, devices of running programs on a lone XUSB package | `Installed`, only the packages this build lacks are added |
| this SDK's payload | `AlreadyCurrent` |
| this SDK's stamp, record of it missing | `AlreadyCurrent`, the record is restored, nothing is reinstalled under running devices |
| this SDK's stamp, one of this build's two packages missing | `Installed`, the missing package is added |
| newer | `KeptNewer`, never downgraded |
| older, nothing holds it | `Upgraded`, a full deploy |
| older, held | `Upgraded`: this SDK's packages are added beside the old ones, with no device updated and no package removed |

The driver is held by the present devices of every program not known to have ended, and by the UMDF2 controller entries of running programs whose devices are not present yet, except the entry of the create that runs the policy. Each of this build's two INFs, `hidmaestro.inf` and `hidmaestro_xusb.inf`, is compared with its own embedded stamp. A full deploy, which runs only when nothing holds the driver, removes the older packages, then adds and installs both with `pnputil /add-driver /install`. An add runs `pnputil /add-driver` without `/install` and removes nothing, so the devices of running programs stay on the package they have.

The last row is v2.0.0's rule, decision (c) of `docs/design/data-driven-devices.md`, in the owner's words: "I prefer a third option: C, the V2 controllers take precedence over and supersede the V1. Period. I am NOT making accommodations for programs using the older driver release getting in the way of the new. New always takes precedence and everything works." The 1.13.0 design kept a held driver of v1.12.0 or later (`KeptInUse`) and refused one older than v1.12.0 with `HMDriverVersionException`. Both are gone. `HMDriverVersionException` remains for a started driver that does not serve this SDK's protocol or could not read a value, and carries `InstalledVersion`, `MinimumVersion` and `Blockers`.

A create must not move another program's device onto a different driver, so a create of a plain HID or non-xinputhid controller installs the driver on its own devnode with `DiInstallDevice` (`DeviceNodeCreator.CreateDeviceNode`) and no driver named, which installs the best match the driver store holds on that device and no other ([DiInstallDevice](https://learn.microsoft.com/windows/win32/api/newdev/nf-newdev-diinstalldevice)). The search's answer is kept for the device's hardware and compatible ids, in the process and under `HKLM\SOFTWARE\HIDMaestro\StoreDriverChoice`. While the installed-payload record and the last write of the driver store's `FileRepository` directory are unchanged, a create of the same ids builds a driver list from the INF the search chose (`DI_ENUMSINGLEINF`) and passes that driver to `DiInstallDevice` (`InstallBestStoreDriver`). Any failure, a missing INF included, falls back to the search. Until v2.0.0 the create called `UpdateDriverForPlugAndPlayDevices` with the VID/PID hardware id and the SDK's own INF, which "installs the driver package on all devices present in the system that have a hardware ID or compatible ID that matches" ([SetupAPI functions that simplify driver installation](https://learn.microsoft.com/windows-hardware/drivers/install/setupapi-functions-that-simplify-driver-installation)). Measured in section E: it staged the SDK's package beside one the policy had kept and bound the new controller to it, and with two programs of one profile it would move the older program's controller onto the newer driver.

## Version handshake

The protocol contract is a per-controller section, `Global\HIDMaestroVersion<N>`, 64 bytes, created by the SDK beside the input section and before the input event, the pattern v1.12.0 used for `InputAck<N>`. No existing layout changes. The layout is `HIDMAESTRO_VERSION_INFO` in `driver/driver.h`:

| Offset | Field | Written by |
|---|---|---|
| 0 | layout version, 1 | SDK |
| 4 | oldest driver protocol the SDK runs on, 4 | SDK |
| 8 | protocol the SDK speaks, 4 | SDK |
| 12 | SDK version, four 16-bit fields | SDK |
| 20 | driver protocol, 5, and 0 until written | driver |
| 24 | driver version, four 16-bit fields, the fourth 0 | driver |
| 32 | driver capabilities: 0x3, the InputAck bits it supports (delivery acknowledged, release on exit) | driver |
| 36 | oldest SDK protocol the driver serves, 4 | driver |
| 40, 44 | the XUSB companion's protocol and oldest SDK protocol | companion |
| 48 | identity tag, the 64-bit FNV-1a hash of the controller's identity token in UTF-16LE | SDK |
| 56, 60 | the value the driver, or the companion, could not read before it failed the start | driver, companion |

The driver writes its version and capabilities first and its protocol last, with a barrier between, at add and each time it opens the input section, and then lets go of the section. Protocol 1 is the layout set through v1.11.0, protocol 2 adds InputAck and the owner pipe (v1.12.0), protocol 3 added this section in a build that never shipped, and protocol 4 is v2.0.0's contract (`docs/design/data-driven-devices.md`, decision (c)): the driver reads a controller's v2.0.0 values only when the section's range holds 4 and its tag is the devnode's own. Protocol 5, also v2.0.0's, adds `Global\HIDMaestroRemoveEvent<N>` and `Global\HIDMaestroRemovedEvent<N>`: on the first, the driver's input worker fails its device with `WdfDeviceSetFailed(WdfDeviceFailedNoRestart)` and then signals the second. The HID driver's range is 4 to 5, the XUSB companion's stays 4 to 4, and the SDK, which still speaks 4, asks for the removal only of a driver whose protocol is 5 or later (`SharedMemoryIO.RequestSurpriseRemoval`). A driver keeps every older layout. `HMController.DriverVersion` reads the driver's half, and native writers read both halves directly. The capability field says what the driver supports. It is not InputAck's live word and never carries the ended marker.

## The signal gate

From 2.1.0 the SDK skips its `SetEvent` on the input event and on the companion doorbell when no driver thread waits for the frame, and the driver skips the acknowledgement's `SetEvent` for a controller whose SDK never waits on it. The words live in a new section, `Global\HIDMaestroSignal<N>`, and each skip waits on a capability the driver host announces in it, so a program before 2.1.0 on the new driver, and a 2.1.0 program on an older driver, signal and acknowledge as before. The protocol, the argument that it loses no wakeup and its checks are in `docs/design/signal-gate.md`.

## The driver's events

The driver creates `Global\HIDMaestroStopEvent<N>` and `Global\HIDMaestroOutputEvent<N>` with `D:P(A;;GA;;;SY)(A;;GA;;;BA)(A;;GA;;;LS)`, so a program that is not elevated can open neither. An object of either name that already exists is used only when it has a DACL and its owner is LocalService, SYSTEM or Administrators. An OutputEvent an earlier driver made without a DACL, owned by LocalService or SYSTEM, is taken over: the driver gives it the host-only DACL and uses it, so a program moved onto this driver keeps event-driven output. A StopEvent like that is not used. When another program made either name first, the driver runs on an unnamed StopEvent and with no output doorbell. Output then reaches the SDK on its 8 ms poll, which opens the event again about every half second, and a force-killed controller on that index takes the slow removal path. The driver tries the doorbell again at each input-section map, every 256 frames and on each idle wake. The allocator already skips an index whose events another program owns (Transport index and slot), so the fallback is reached by a name taken after the create's check, and by a StopEvent a driver before v2.0.0 made without a DACL. The allocator accepts that one, since LocalService owns it, and the driver refuses it and runs on an unnamed StopEvent, with its doorbell, since it takes the matching OutputEvent over.

Both drivers let go of their index at `EvtDeviceSelfManagedIoFlush`, which the framework calls on a surprise removal and on a removal, never on a stop for a rebalance: the sections and their views, both events, the owner pipe, and the companion's pump thread and 8 ms timer. Through v1.12.0 they let go only in the device context's cleanup, which runs on `IRP_MN_REMOVE_DEVICE`, and the PnP manager sends that only after every handle to a surprise-removed device has closed. A v1.12.0 program's companion removal started a second host for `SWD\HIDMAESTRO\HM_0000`, whose device was surprise removed 2 ms after it started and never got its removal. That host kept the pump thread and timer running and held `Global\HIDMaestroOutputEvent0` for 25 minutes, and later creates on index 0 met it. The release routine clears each field it closes, so the cleanup that follows a flush finds nothing left. The HID driver, a filter in most profiles, has no power-managed queue, so the framework would purge its queues only at the removal: its flush purges both first, so no I/O callback reads a view after the release unmaps it. A HID request to a surprise-removed device is then failed by the framework, with STATUS_INVALID_DEVICE_STATE, instead of reaching the output ring. A driver host from before this release keeps its objects until its removal. `device_oracle_check --lifecycle` (S89) checks both drivers through a surprise removal with no removal after it.

## Staging

Everything the elevated SDK runs or hands to pnputil is staged per version and per operation under `%ProgramFiles%\HIDMaestro\Staging\<version>-<hash>\<operation>`, where the hash is the first 16 hex characters of the embedded driver payload's SHA-256. The operations are `driver` (the embedded bytes of the driver binaries and both INFs, signtool and inf2cat), `package` (one deploy's driver package, signed and cataloged), `swd` (hmswd.exe), `usbip-ude` (usbip-win2's host controller package, which the SDK installs or forces onto an older transport) and `winusb-<profile id>` (one profile's WinUSB package). One directory per operation keeps the catalog step's `/driver:` scan and its stale-catalog cleanup away from every other operation's files.

Program Files grants Users read and execute and nothing else, so no program without elevation can create a folder there before HIDMaestro does. `%ProgramData%` lets Users add folders (`BUILTIN\Users (CI)(WD,AD,WEA,WA)` on the folder Windows ships, read with icacls), so a program without elevation could create `%ProgramData%\HIDMaestro`, or a `Staging` folder under it, first, own it, hold a file in it so that it cannot be moved, and make every staging refuse. That is why staging moved, before release, from `%ProgramData%` to `%ProgramFiles%`. Every directory from `%ProgramFiles%\HIDMaestro` down is created with its security descriptor in the same call, `O:BAG:BAD:P(A;OICI;FA;;;SY)(A;OICI;FA;;;BA)`, so none exists with an inherited ACL. Kitsune Input's Rust setup component enforces the same descriptor on its setup directory for the same reason.

Each use checks every directory on its path. A directory passes when it is not a reparse point, its owner is Administrators or SYSTEM, and no allow ACE grants a write-class right (write data, append data, write attributes or extended attributes, delete, delete child, change permissions, take ownership) to anyone but SYSTEM, Administrators and TrustedInstaller, which holds full control of what an installer makes under Program Files. `%ProgramFiles%\HIDMaestro`, which HIDMaestro creates itself, is reset in place when SYSTEM or Administrators own it and nobody else may change its DACL or owner or delete it or its entries, and refused with `InvalidOperationException` otherwise, since a hostile one there is another program's. `Staging`, a version or an operation directory that fails is moved aside to `<name>.untrusted-<guid>`, a reparse point moved as the link itself, and created again. One that cannot be moved is refused when it is hostile in the same sense, and reset in place when only its DACL is wrong. A moved-aside tree is left where it is, never deleted by path. A directory another program creates between the check and the create is refused too.

The OpenVR driver stays under `%ProgramData%\HIDMaestro\openvr\hidmaestro`, by decision. SteamVR loads the driver name `hidmaestro` from one registered path, and a second registration of that name conflicts with the first, and a v1.12.0 program running beside this one registers the `%ProgramData%` path again whenever its manifest hash differs from the one in HKLM, so a driver moved anywhere else would be registered twice. `%ProgramData%\HIDMaestro` now holds nothing else, and nothing the elevated SDK runs, loads or hands to a tool may live there. It and the OpenVR folders carry the same descriptor plus `(A;OICI;FRFX;;;BU)`, since SteamVR reads them as the user. Each is reset in place when SYSTEM or Administrators own it and nobody else may change or delete it, as when an elevated program created it, v1.12.0 included, because SteamVR maps the driver's files from there and a directory holding a mapped file cannot be renamed. Any other is moved aside like a staging directory, and refused when it cannot move. The residual: an owner keeps WRITE_DAC through a handle opened before a reset ("An object's owner implicitly has WRITE_DAC access to the object", Owner of a New Object on Learn), so a program without elevation that creates one of these folders first and holds a file under it can make `HMVR.EnsureDriverRegistered` refuse, and so can any program that holds one open for listing while the extraction renames a file into it. The refusal names the folder. None of this can make a staging refuse.

Every elevated use of a staged file runs inside a pin. `Staging` and each directory below it down to the one in use are held open without delete sharing, which no rename or delete of them can get past, and `%ProgramFiles%\HIDMaestro` cannot be renamed while they are held. That folder, `%ProgramData%\HIDMaestro` and the OpenVR folders are opened only to be checked, through their handles, so no program without elevation can make a pin fail. Each staged file is held for reading with read sharing only, which no write, rename or delete gets past, and checked against its SHA-256 through the hold: the embedded bytes, or the pinned release hash for the usbip files. A driver binary cannot be held while signtool rewrites it, so it is checked right before and held once signed, and a catalog is held once signed. The pin lasts until the use is over: the driver package's sign, catalog and add, hmswd's runs, the host controller package's install and each WinUSB package's catalog and add. The OpenVR extraction, which writes files for SteamVR and runs none, checks its folders and holds none. A file is written to a temporary name, verified and then renamed into place, and reuse trusts no file size. The helper always comes from the embedded resource, never from beside the assembly (`Assembly.Location`, which is empty in a single-file app).

An elevated child gets a protected TEMP. hmswd, signtool and Inf2Cat run with their own staging directory as working directory, TEMP and TMP. pnputil and devcon, which have no staging directory, get `%ProgramFiles%\HIDMaestro\childtemp\<process id>-<start time>`, a folder per process with the staging descriptor. An elevated process that cannot make that folder does not run the tool with the user's own `%TEMP%`: the operation fails with `InvalidOperationException` naming the reason, a cleanup that only tries skips the tool and logs it, and the next call tries the folder again. A process that is not elevated starts no elevated child and changes nothing. reg.exe and sc.exe, run from System32, keep the caller's TEMP.

The diagnostic logs, `teardown_diag.log` under `HIDMAESTRO_DIAG=1` and `setup_timing.log` under `HIDMAESTRO_TIMING=1`, stay in `%TEMP%\HIDMaestro` and are now opened as the user: the elevated half of a split UAC token writes them through a medium-integrity token of the same user, so an elevated process never creates or appends to a file in a folder the user's programs control. SYSTEM, an administrator without a split token, or a process that is not elevated writes them as itself. So is the USB/IP read log at the path `HIDMAESTRO_DIAG_READS` names. A log that cannot be opened drops its lines. hmswd's exit code and output go into `teardown_diag.log`, and only when diagnostics are on, where each create used to leave an `hmswd_<enumerator>_<suffix>.log` written elevated. hmswd no longer keeps a self-log: it appended to `%TEMP%\HIDMaestro\hmswd_self.log`, which no SDK run could write once hmswd's TEMP became its staging directory, and the function is gone.

A deploy, which holds the deploy lock, deletes the staging directory of every version that no live owner record names, under the staging lock from its read of the records to its last delete and under a pin of `Staging`, and checks each version directory through its handle before it deletes it. A record that names no staging directory keeps every directory of its SDK version, and a moved-aside directory is never pruned. A process notes its staging directory in its record under the same lock, so a prune never removes what another build's program is about to use. The prune also removes the `childtemp` folder of every process that no longer runs, judged by process id and start time. The same-version fast path takes no lock and prunes nothing, so a directory left by a version that was running during an upgrade goes at the next deploy. The constructor prewarm stages the driver payload only when the fast path will not be taken: on a machine that already runs this build's driver, nothing reads the staged payload.

## NativeAOT, trimming and single-file

The project sets `IsAotCompatible`, which turns on the trim, single-file and AOT analyzers. `aot-analyzers.globalconfig` raises the three diagnostic categories they report under, `Trimming`, `SingleFile` and `AOT`, to errors in Release. A temporary file holding one reflection-based `JsonSerializer.Serialize` and one `Assembly.Location` read failed the Release build with IL2026, IL3050 and IL3000. At b4d29d9 the same analyzers report 40 warnings: 38 from the 19 reflection-based `JsonSerializer` calls in `ControllerProfile.cs` and `HMLayoutLoader.cs` (18 `Deserialize` and one `Serialize`, each reported under IL2026 and IL3050), one IL3050 for the `JsonStringEnumConverter` constructed at `HMLayoutLoader.cs:93`, and one IL3000 for the `Assembly.Location` read in `SwdDeviceFactory.cs`, which the staging change removed.

Profiles and layouts load through `HMJsonContext`, a source-generated `JsonSerializerContext`, with no reflection resolver behind it. Its options are the ones `HMLayoutJsonOptions.Default` carried: camelCase names read case-insensitively, comments and trailing commas allowed, `HMAxis` through its own converter, every other enum as a snake_case string. The non-generic `JsonStringEnumConverter` needs runtime code generation, so each enum in the graph gets a `JsonStringEnumConverter<TEnum>` with the snake_case policy. `HMLayoutJsonOptions.Default` is now the context's options, which read and write the SDK's own types only.

The layout `kind` stays with `HMLayoutJsonConverter`, which reads each concrete layout through the `JsonTypeInfo` the options carry. `[JsonPolymorphic]` was considered and does not fit. Its discriminator matches exactly, while the converter has always matched `kind` in any letter case and with or without underscores, and `LoadProfilesFromDirectory` reads profiles consumers write themselves.

The generated code builds a record whose properties are init-only with one object initializer that assigns all of them, so a key the JSON leaves out arrives as `default(T)`. That is null for the empty lists and `new()` objects the layout records initialize, 0 for `HMTriggerButton.Stages` (initialized to 1) and `Unknown` for `HMRotaryEncoder.Role` (initialized to `Dial`). Reflection built the record first and kept those values, and 68 of the 336 catalog profiles depend on it. The converter therefore writes the JSON out again with each such key filled from a freshly constructed record. Which keys need it is planned once per type, by comparing a fresh record with the one the same metadata builds from `{}`, so a reflection resolver, which keeps initializers itself, plans nothing.

`json_parity_check` reads every embedded profile through `HMJsonContext` and through v1.12.0's own converter and options, and requires the same profiles with the same contents. It also checks the lenient `kind` matching and the two value-type initializers directly. With the fill step disabled it fails on 68 profiles and those checks.

`hmswd.exe` always comes from the embedded resource, staged and verified as in the staging section. There is no path beside the assembly any more. `Assembly.Location` is empty in a single-file app.

All 113 `DllImport` declarations become `LibraryImport`. Five SetupAPI declarations among them that nothing called are then removed, and the code this release adds declares 102 more the same way, 210 in all. Every one that took a string or `char` had `CharSet.Unicode`, so each gets `StringMarshalling.Utf16`. Every `bool` gets `MarshalAs(UnmanagedType.Bool)`, the 4-byte Win32 `BOOL` `DllImport` used by default, except the results of hid.dll's `HidD_*` functions. Those return `BOOLEAN`, one byte (`hidsdi.h`), and are read as `UnmanagedType.U1`: on an invalid handle `HidD_GetAttributes` returns FALSE in AL with the rest of EAX nonzero on this machine, which a 4-byte read takes as TRUE. `SetLastError` and `EntryPoint` carry over. The generated stubs pin `byte[]` and `char[]` buffers and pass them straight through, as `DllImport` did, so buffers Windows fills arrive filled. Three structs were not blittable and change layout without changing size: `HIDP_CAPS.Reserved` becomes a 17-element fixed buffer, the OpenVR section's `SECURITY_ATTRIBUTES.InheritHandle` becomes the 4-byte `BOOL` it is, and `CM_NOTIFY_FILTER`'s instance ID becomes a 200-character fixed buffer, keeping the 416 bytes `CM_Register_Notification` requires. That function took a managed delegate, which `LibraryImport` does not marshal. Each wait's handler now travels as a `GCHandle` in the registration's context argument, and one `[UnmanagedCallersOnly]` dispatcher hands every event to it and lets no exception reach cfgmgr32. The handle is freed after `CM_Unregister_Notification`, which "waits for pending callbacks to finish" ([CM_Unregister_Notification](https://learn.microsoft.com/windows/win32/api/cfgmgr32/nf-cfgmgr32-cm_unregister_notification)). A wait whose registration fails still finishes on its 50 ms re-checks, so `pnp_notify_check` (S77) counts the events the dispatcher delivers while a controller is created and disposed: 7, and 0 with the filter sizes broken. The generated stubs of the per-frame calls (`SetEvent`, `WaitForSingleObject`, `WaitForMultipleObjects` over a preallocated handle array) convert `BOOL` in place, pin the array with `fixed`, and save the last error, with no allocation. `aot_smoke` publishes one source four ways: NativeAOT and trimmed self-contained single-file, each for x64 and ARM64. Each app loads the catalog, installs the driver, creates `dualshock-4-v2` on the UMDF2 driver and `dualsense-composite` on USB/IP, submits input, writes an output report, waits for `OutputReceived`, and disposes. The battery runs the two apps for the machine's architecture as S74 and S75, and the parity check as S76. At b4d29d9 both apps load 0 of 336 profiles, because reflection-based JSON is switched off in both kinds of app.

## Building from source

`scripts\build_all.cmd` builds everything an official release carries: the UMDF2 driver, XUSB companion and SWD helper for x64 and ARM64, the OpenVR driver, and the SDK with usbip-win2's host controller driver for both architectures. Each setting below is an environment variable. MSBuild reads environment variables as properties, so one setting reaches the native scripts and the SDK project alike, and each the SDK project reads also works as `-p:` on a `dotnet build` of the SDK. `HM_WDK_ROOT_ARM64` and `HM_STAMP_TIME` are read by the native scripts only.

| Setting | Effect | Default |
|---|---|---|
| `HMSkipArm64=true` | Builds and embeds the x64 driver, companion and helper only, and leaves out the ARM64 usbip-win2 host controller. | unset |
| `HMSkipUsbip=true` | Leaves out the USB/IP transport: the host controller files, and the installers they are unpacked from. Nothing is downloaded, hashed or unpacked for it. | unset |
| `HM_SDK_ROOT` | The Windows SDK: the `um` and `shared` headers, the `um` libraries, `rc.exe`, and the signtool set the SDK embeds. | `WindowsSdkDir` when a Visual Studio or EWDK prompt set it, otherwise `%ProgramFiles(x86)%\Windows Kits\10` |
| `HM_WDK_ROOT` | The WDK: the `km` headers, the UMDF 2.15 headers and stub library, and Inf2Cat. | `WDKContentRoot` when an EWDK prompt set it, otherwise `HM_SDK_ROOT` |
| `HM_WDK_ROOT_ARM64` | The WDK for the ARM64 build. | `HM_WDK_ROOT` |
| `HM_WDK_VERSION` | The kits' version folder. | `Version_Number` when an EWDK prompt set it, otherwise `10.0.26100.0` |
| `HMWdkBin` | The folder whose `x64` and `arm64` folders hold the signtool set. | `HM_SDK_ROOT\bin\<version>\` |
| `HMInf2catBin` | The folder whose `x86` folder holds Inf2Cat. | `HM_WDK_ROOT\bin\<version>\` |

The scripts find Visual Studio through `VSINSTALLDIR` when a Visual Studio or EWDK prompt set it, and otherwise search `%ProgramFiles%\Microsoft Visual Studio` as before. Every root is checked for the folders the build reads from it, and a missing one stops the build with an error that names the setting.

The native scripts compile the driver, the companion and the OpenVR driver at `/W4`, and hmswd at `/W3`. The driver and the companion build with `/Ox /Os`, the WDK's release setting, the OpenVR driver with `/O2` and hmswd with `/O1`. At v1.12.0 the driver and the companion passed no `/O` switch, so cl.exe compiled them `/Od`. The UMDF headers and Valve's `openvr_driver.h` are passed with `/external:I` and `/external:W0`, which turn warnings off in those headers and in every header they include, while each warning in HIDMaestro's own sources still prints. No HIDMaestro header is included from an external one. `vrcontroller.vcxproj` marks the OpenVR header the same way (`ExternalIncludePath`, `ExternalWarningLevel`). The driver and the companion no longer pass `/wd4324`, which hid that warning in their own sources too. A full `build_all.cmd` printed 70 compiler warnings at c5c0f05, 50 from `openvr_driver.h`, 17 for unused helpers in `vrmath.h` and three unused parameters, and none at a6fbbe8 (development measurements). No `/WX` is set, so a new warning prints and does not stop the build.

Every INF of one build carries one `DriverVer` stamp: the build's date and, as the fourth version part, its time as HHmm. `build_all.cmd` reads the clock once into `HM_STAMP_TIME` (`yyyy-MM-ddTHH:mm`) for both architectures, and `build.cmd` and `build_companion.cmd` read it at their start when run alone, so a companion build run alone stamps both INFs of its architecture. Until v2.0.0 each script read the clock as it stamped, and a build whose stamps fell in two minutes carried two DriverVers. A caller can set `HM_STAMP_TIME` to choose the stamp. Only the native scripts read it, so `-p:` on a `dotnet build` does nothing. `stamp_inf.ps1` refuses a time later than the clock, or earlier than the newest file under `driver\`, each to the minute, since a stale stamp would build a driver the deploy policy, which never downgrades, keeps out. `pre-tag-validate.cmd` clears it, so a release carries the time its build starts. Two builds of different bytes in the same minute carry the same stamp, and the second reads as `AlreadyCurrent` where the first is installed.

Installed kits need no setting. With the NuGet WDK, `HM_WDK_ROOT` is the `c` folder of `Microsoft.Windows.WDK.x64` and `HM_WDK_ROOT_ARM64` the `c` folder of `Microsoft.Windows.WDK.ARM64`, because each package carries the UMDF stub library for its own architecture only. Microsoft's CI for windows-drivers-rs points `WDKContentRoot` at the target architecture's package the same way (`.github/actions/install-wdk/action.yaml`). The Windows SDK then comes from the installed kit, which Visual Studio's C++ workload installs and which Microsoft lists as a requirement of the NuGet WDK ([Install the WDK using NuGet](https://learn.microsoft.com/windows-hardware/drivers/install-the-wdk-using-nuget)). The SDK's own NuGet packages lay out libraries as `c\um\<arch>` rather than `Lib\<version>\um\<arch>`, so `HM_SDK_ROOT` cannot point at them. In 10.0.26100.6584 the NuGet WDK's `km` headers (649 files), UMDF 2.15 headers (36 files) and both stub libraries are byte-identical to the installed WDK of the same version.

In the EWDK, the build runs from the prompt `LaunchBuildEnv.cmd` opens, and the defaults pick up the image's kit, version and Build Tools. windows-drivers-rs reads `WDKContentRoot` and `Version_Number` "running in an eWDK prompt" (`crates/wdk-build/src/utils.rs`), and an EWDK prompt's environment posted to the OSR developer forum shows `WDKContentRoot`, `WindowsSdkDir`, `Version_Number` and `VSINSTALLDIR`, each pointing into the mounted image. The EWDK itself was not run for this release, since downloading it means accepting Microsoft's EWDK license terms. `check_build_layouts.ps1` sets those four variables to the installed kit and Visual Studio instead.

The built SDK reports what it carries through `HMBuildInfo`: `DriverArchitectures`, `UsbipArchitectures`, `HasOpenVrDriver` and `IsComplete`. Each is read once from the assembly's own resource names, so it describes the bytes actually embedded, whatever the build settings were. A controller that needs a payload this build lacks for the machine's architecture throws `HMPayloadMissingException`, derived from `InvalidOperationException`, before any machine-wide step: a composite persona without the USB/IP transport, and any controller without the driver. `InstallDriver`, `InstallUsbipBackend` and `HMVR.EnsureDriverRegistered` throw it too, and `IsUsbipBackendAvailable` is false in a build without the transport.

`Resources\` is a cache that outlives a build, so a skip build in a tree that once built everything would still find ARM64 and USB/IP files there. The resource items therefore no longer come from globs over it. Each payload file is listed when the project is evaluated, with the path the pre-build target stages it at and the name it is embedded under, and the target embeds exactly the files it staged for the settings in force. A glob was also evaluated before the target staged anything, which is why the SDK needed two builds on a fresh tree. It needs one now, and the 392 resources it embeds carry the same names and bytes as before, less the two Inf2Cat files below.

Official releases stay complete. `pre-tag-validate.cmd` clears `HMSkipArm64` and `HMSkipUsbip` before it builds, `build_info_check` (S78) fails unless the release build reports `IsComplete`, and `check_build_layouts.ps1` builds every layout above before the battery runs.

The SDK embedded eight Inf2Cat files and now embeds six. `inf2cat.exe.manifest` and `Microsoft.Kits.Logger.dll` are not in the NuGet WDK, and neither one does anything:

- None of `Inf2Cat.exe` and its four UniversalStore libraries references `Microsoft.Kits.Logger`, by assembly reference or by name in a string (ildasm 4.8). The kit's x86, x64 and ARM64 copies of the logger carry identical IL and differ only in the build path inside `AssemblyKeyFileAttribute`.
- `Inf2Cat.exe` embeds its own manifest (RT_MANIFEST 1, `asInvoker`), and on Windows Server 2003 and later "Internal manifest is preferred over external manifest" ([Internal Manifest vs External Manifest](https://learn.microsoft.com/archive/blogs/junfeng/internal-manifest-vs-external-manifest)). The external file declared a dependency on the private `wintrust.dll` beside signtool.
- In a copy of the staging layout, Inf2Cat loaded that private `wintrust.dll` with and without both files, since the folder an application loaded from comes before the system folder in the standard search order ([Dynamic-link library search order](https://learn.microsoft.com/windows/win32/dlls/dynamic-link-library-search-order)). Every run produced catalogs that `certutil -dump` shows identical apart from the list identifier, which differs between two runs of the same set as well.

Microsoft's `WindowsDriver.Common.targets` in the NuGet WDK runs Inf2Cat from `bin\<version>\x86` (`Inf2CatToolPath`, `WDKBinRoot_x86`), which holds neither file. The six files that remain are byte-identical in the installed WDK and the NuGet WDK.

## The usbip-win2 install

Through v2.0.0 the SDK ran usbip-win2's installer where no copy was installed. That installer adds the root-hub filter, `usbip2_filter`, with `pnputil /add-driver usbip2_filter.inf /install` (setup.iss at tag v.0.9.8.1, line 176). The filter is an extension INF on the generic `USB\ROOT_HUB30` (`drivers/ude_filter/usbip2_filter.inf` lines 32-43), so its install reconfigures every USB 3 root hub on the machine and restarts each one (`drivers/ude_filter/readme.txt`). Every USB device blinks, the physical controllers a program like PadForge reads among them.

Since 2.0.1 the SDK installs the host controller alone, from usbip-win2's own signed package (`usbip2_ude.inf`, `.sys` and `.cat`), which the build unpacks from the pinned installers and checks against `UsbipPackage.json`. It makes the two calls usbip-win2's `devnode.exe install` makes (`userspace/devnode/main.cpp` lines 232-295): it registers a `ROOT\USB` devnode under the INF's class with `SetupDiCreateDeviceInfo`, `DICD_GENERATE_ID`, the hardware IDs `ROOT\USBIP_WIN2\UDE` and `ROOT\HIDMAESTRO_UDE` and `DIF_REGISTERDEVICE`, under the PnP lock, then puts the package on it with `UpdateDriverForPlugAndPlayDevices` and `INSTALLFLAG_FORCE` in `hmswd force-driver`, out of process with a 90 s timeout. It never installs, updates or removes the filter, and adds no Apps entry, program folder, scheduled task, Start menu folder, shortcut or VC++ runtime.

The filter tells the host controller about each `SELECT_CONFIGURATION` and `SELECT_INTERFACE`, because UdeCx does not report them correctly for a composite device (`drivers/ude/device.cpp` lines 405-411, `drivers/ude/filter_request.cpp`). With no filter, `SET_CONFIGURATION` and `SET_INTERFACE` never reach the persona. The host controller still creates the endpoints UdeCx configures and routes each transfer by its endpoint's queue. The persona answers a `SET_INTERFACE` that does arrive, and infers the open or parked state of each audio stream from its isochronous traffic otherwise (`UsbAudioEngine`), the rule it already used beside a 0.9.7.x filter, whose request 0.9.8.1 does not recognize. S73 runs the install, the composite's input, and S45's and S65's probes in Windows Sandbox with no filter on the machine.

Where a host controller is present but does not answer, the SDK restarts it and never adds a second one beside it. Before it registers a devnode it waits up to five minutes for a usbip-win2 installer another program started, which would make a host controller of its own. It writes an owner token of its own, a custom device property, on the devnode it registers, and `HKLM\SOFTWARE\HIDMaestroUsbip`: the devnode, the token, the usbip2_ude packages the driver store held before, the published INF the devnode runs, that package's whole DriverVer value (date and version), the usbip-win2 version, the time and the SDK version. The record is written before the driver install. An install a killed process cuts short, or one whose driver install times out and never binds, leaves a driverless devnode that carries the token, and the next composite create puts the package on it again instead of restarting it, when it is the only host controller present. A driver install that times out and binds afterward leaves a working host controller, and the next composite create records its package when that package's DriverVer is the one the record names and usbip-win2's Apps entry is as the install found it, under the transport lock taken with no wait. A record from before the record kept a DriverVer is read as the running SDK's pin. Another program's package bound to the devnode is never recorded as HIDMaestro's. A removal proves the install by the token, so a devnode another installer registers later under the same instance id is not taken. The record sits outside `SOFTWARE\HIDMaestro`, which the Everything cleanup deletes, because a full removal reads it to tell HIDMaestro's install from another program's (`UsbipRemoval`).

KMDF's `VerifierOn` and `VerboseOn` values under `Services\usbip2_ude\Parameters\Wdf`, which usbip-win2 0.9.7.5's INF writes as the DWORD 1 and later INFs carry commented out, are deleted while each holds 1 and no installed host controller's INF writes them: before an install or a move to the pinned driver, and once per process on a composite create. The driver reads them when it loads.

Programs that bring usbip-win2 with them look for its installer's traces, which HIDMaestro's install does not leave. Handheld Companion's setup asks whether `USBip` is installed by its Apps entry and runs `USBip-0.9.7.7-x64.exe` when it finds none (`HandheldCompanion.iss` lines 568-577, `utils/Utils.iss` lines 75-113). VIIPER's install script looks for an Apps entry named `USBip version` and then for `System32\drivers\usbip2_ude.sys` (`scripts/install.ps1` lines 120-132), which a driver-store install never puts there, and runs the 0.9.8.1 installer. That installer adds the root-hub filter, which restarts every USB root hub, and its `devnode.exe` registers a second host controller and forces its package onto every devnode with usbip-win2's hardware id, HIDMaestro's included. HIDMaestro writes no Apps entry to stop this: a program that finds one would run on a host controller with no filter, which it may need, and fail without saying why. The SDK copes with what the installer leaves. It talks to the first host controller interface Windows lists (`VhciClient.TryGetInterfacePath`) and stamps every host controller (`UsbipDriverInstaller.StampAll`). The move to the pinned driver (`ReplaceLegacyTransport`) is unchanged in this release: it applies to any host controller whose `usbip2_ude.sys` bytes match a release an earlier HIDMaestro installed (0.9.7.7, 0.9.7.5), whoever installed it, in a Windows session where nothing has used it. Handheld Companion's 0.9.7.7 is the same release asset, so a host controller it installed is moved too, and VIIPER's 0.9.8.1 is the pinned release and left as it is. A removal compares usbip-win2's Apps entry with the state the install recorded, and finds it written by that installer since, so it leaves usbip-win2 in place unless the caller includes it.

## Changes made in review

Review of the first implementation changed the design in these places. The sections above describe the result.

- Mouse motion splits end. A relative field whose range excludes zero, such as the relative X and Y of `corsair-k70-rgb-mk2-low-profile` (1 to 32767), cannot carry a click's zero or a movement left or up. The packer writes 0, no motion, for a movement the field cannot carry at all, and owes nothing for it or for a part that overshoots, so every split of a large movement ends. Fields whose range holds zero pack the same bytes as before. After a submit has sent a long split, the controller keeps 16 frames (`KeyboardMousePacker.MotionFramesKept`) and lets the rest go. S69 packs these cases on all 57 catalog profiles with a mouse collection under a 3 s deadline.
- A WinUSB bind and a restore take their locks in one order. A bind adds its package under the deploy lock with no WinUSB lock held, since the first add takes seconds and must not run beside another program's deploy. It then takes the WinUSB lock and its controller's bind gate, reads the devnode again under them, and takes the ledger's lock last, for the claim's registry write. A restore takes the WinUSB lock and then the ledger's, so a bind and a restore on two threads cannot wait on each other. A devnode found on one of HIDMaestro's own packages, which a killed program's binding leaves until a sweep, is held in the ledger for the binding controller and restored by the ledger's rules after its dispose. A devnode on WinUSB, libusbK or libusb0 from anyone else is left as it was.
- A live record wins over a dead one. The census binds a present device to the record that lists its identity token, or, for a device older than identity tokens, its transport index, and a live record is taken before a dead one. A dead record names a device only while no running program holds the device's index or identity, by its v1.12.0 owner pipe or by this release's index and identity claims. The reclaim of exited programs runs before a create's lease on both backends, once per process, so a keyless program restarted after a crash gets its index and identity back, unless a running v1.12.0 program moved its search above that index, and a program that only creates composites clears what a killed one left.
- A takeover lands on the old index. A create that takes over an identity a pre-v1.12.0 program left lands on that device's index first and frees the index only when no other device, import or live record holds it. When it lands elsewhere, the XUSB companion the old life left still reads the old index in its driver, which cannot be restarted while a process that polled XInput holds it open. The create removes that companion and makes it again on the new index.
- The owner record covers the whole process. It is written with the owner claim and stays until the process exits, and it names the staging directory the process uses. A deploy counts the UMDF2 controller entries of running programs as holders of the driver whether or not their devices are present yet, so it cannot upgrade the driver under a create that has recorded its entry and not yet done its PnP work. Every UMDF2 create passes a deploy gate after its record entry and before it creates its devices (`DriverDeploy.EnsureForCreate`, called at `DeviceOrchestrator.cs:1309`): under the deploy lock it reads the installed-payload record, and when that changed since this process last saw the packages it checks that the driver store holds a package for each INF, of any stamp, and runs the install policy when one is absent, without counting the calling create's own entry as a holder. A USB/IP composite create does not pass it. It takes the transport lock for the usbip-win2 install instead (`UsbipDriverInstaller.EnsureInstalled`). `RemoveAllVirtualControllers()` removes the driver packages under the deploy lock and only while no other program runs, no device remains and the caller has no controller. The staging prune keeps every directory a running program's record names.
- hid.dll results are one byte. The `HidD_*` functions return `BOOLEAN` (`hidsdi.h`), so their `LibraryImport` declarations read the result as `UnmanagedType.U1`. A four-byte read of the result of `HidD_GetAttributes` on an invalid handle returns TRUE on this machine, because AL holds FALSE and the rest of EAX is nonzero.
- The usbip-win2 install holds a lock of its own, `HIDMaestro.Admin\Transport`, so a UMDF2 create never waits for it. The bundled install, the repair of a host controller that stopped answering, and the move of an older host controller to 0.9.8.1 take it on a thread of their own and read the machine again under it. Two programs whose first composites arrive together find one host controller after one installer run. - A controller plugs into an empty port at rest. `HMPort.Connect` writes the connection with sticks centered and triggers and buttons released, as the profile's fields encode an empty `HMGamepadState`. A profile's report ID is text, `0x31` or `31`. `ReportIds.Parse` reads its hex digits from a span, where the codec and the output reader had cut the `0x` off with `Substring` on every frame and every output packet. On a composite's USB/IP connection it closed the connection, and on the audio pump, the thread pool or the VR haptic reader it ended the program. ## Compatibility

A program built on v1.12.0 and a program built on this release run side by side. This release judges the v1.12.0 program's liveness by its owner pipes and by what this release's driver reports about their server, and never removes its controllers while it runs. From v2.0.0 the newer release's controllers take precedence (decision (c) of `docs/design/data-driven-devices.md`): its driver goes into the store beside the v1.12.0 one, its own controllers run on it, and the v1.12.0 program's controllers keep the driver they loaded until their devices restart. Section E1 of the coexistence probe checks it.

The other direction cannot be fixed from here. What a running v1.12.0 program can still do to a v2.0.0 program, none of which this side can prevent:

- Its `InstallDriver` calls `RemoveAllVirtualControllers(preserveInstall: true)`, and its first create in a session runs a cleanup of its own. Each removes every HIDMaestro device on the machine, and its `InstallDriver` replaces the installed driver with its own whenever the payload differs. Every program older than v1.12.0 does the same.
- With no controller present at the moment of the v2.0.0 program's create, it leaves no sign, so the create does not start at 64, and its next create takes the v2.0.0 program's low index and shares its sections. The v2.0.0 program's exit no longer removes that device.
- Its `CreateControllerAt(index)` takes whatever index it is given.
- Its create installs its own extracted INF on its devnode with `UpdateDriverForPlugAndPlayDevicesW` (b4d29d9 `DeviceNodeCreator.cs:368`), which installs the package on every present device whose hardware ID matches, so a v1.12.0 controller binds the v1.12.0 driver even where this release installed its own (setupapi log of the bench, recorded by the coexistence capture).
- It reaches index 64 with 65 controllers alive at once.

Upgrading every program on a machine to v2.0.0 or later is the fix.

During a v1.12.0 program's teardown its index can be taken, as before this release. It closes its owner pipe when the teardown starts and removes its devnode after (b4d29d9 `DeviceOrchestrator.cs:1796-1801`), and its next create of that index waits for the teardown, then takes it again. In between, a keyed device of it whose index cannot be read keeps nothing from use. Its ledger holder stays until the teardown's end (b4d29d9 `DeviceOrchestrator.cs:1998`), so while that device is present the floor stays 64 and a create of this release does not take the index. A keyboard or mouse profile has no holder, and in that window a create of this release can take its index, which the v1.12.0 program's next create then also takes. A device whose index reads keeps its index through the window.

A program older than v1.12.0 leaves no sign of whether it still runs. Its devices are never removed on a guess. From v2.0.0 they no longer block the newer driver: `InstallDriver` adds it beside theirs (section E4).

Native writers, programs that open the sections without the SDK, see the same names as before when a program runs alone, because the transport index equals the slot. When several programs run, a native writer reads the names from `HMController.SectionNames` of the program it feeds, or computes them from `HMController.TransportIndex`. The version section gives a native writer the driver's version and protocol and the SDK's. A native reader of InputAck tests its capability bits one at a time, since bit 31 is the driver's own state.

## Two bugchecks during development

The machine running the coexistence probe stopped twice with bugcheck 0x139, argument 1 = 3, a corrupted LIST_ENTRY, on 2026-10-14 at 23:48 and on 2026-10-15 at 00:41, kernel 10.0.26100.9711. Both dumps show the same stack: a process that had just registered a HIDClass devnode was writing its class GUID (`CmSetDeviceRegProp`, `PiDmListAddObject`) and linking the devnode into the PnP data model's HIDClass list, and the list's tail, its most recently linked member, had already been freed. The registering process found the corruption. It did not necessarily cause it. In both dumps, at the crash, the kernel's device-event worker was delivering a device event to user mode and reading that device's properties through the data model, and a DevQuery worker was applying an object event.

- The first crash came in a v1.12.0 peer, 341 ms old, registering `ROOT\VID_045E&PID_028E&IG_00\HM_0000`. That ID's previous devnode had been deleted about 12.6 minutes earlier, with no later install of it in the setupapi log, whose last 21 s are lost.
- The second came in a v2.0.0 peer, 290 ms old, registering `ROOT\HIDCLASS\HM_0001`, which the previous program's exit had removed 0.66 s before the crash. The device tree in the dump no longer held that ID, and the event worker was delivering a property-change event for it.

Re-registering an ID right after its removal is not enough by itself: the setupapi logs of those two days hold 2148 deletes followed by an install of the same ID, 764 of them within a second, and one crash among them. Neither dump names the freed object, since both blocks had been reused. By code order, both crashing processes would have run an uninstall pass over HIDMaestro phantoms or leftovers just before their first registration. No log of either pass survives, so this remains a hypothesis. Three changes landed within 25 hours before the first crash. 9a995e6, also in v1.12.0's release, made `CM_Register_Notification` succeed for the first time, so removal waits now wait. 30cccba moved the phantom cleanup onto a background thread. The coexistence probe began running several programs that create and remove within a second of each other. None is shown to be the cause. No WinUSB bind ran in either section, and the GameCube adapter's list member in the first dump was intact.

No Learn page documents a signal that the data model's object of a removed devnode is gone. `CM_Locate_DevNodeW` with `CM_LOCATE_DEVNODE_NORMAL` finds a device "only if the device is currently configured in the device tree", `CM_LOCATE_DEVNODE_PHANTOM` also finds a nonpresent one, and `CM_LOCATE_DEVNODE_CANCELREMOVE` "cancels the removal of the device" when one is in progress, so it cannot be used to wait for one ([CM_Locate_DevNodeW](https://learn.microsoft.com/windows/win32/api/cfgmgr32/nf-cfgmgr32-cm_locate_devnodew)). The only documented same-ID ordering is `SwDeviceClose`'s: "you can safely call SwDeviceCreate immediately after SwDeviceClose" ([SwDeviceClose](https://learn.microsoft.com/windows/win32/api/swdevice/nf-swdevice-swdeviceclose)). Every reference project that creates ROOT devnodes (devcon, Nefarius.Utilities.DeviceManagement, nefcon, vJoy, usbip-win2's devnode tool, WinUHid) lets Windows generate the instance ID. Of these, only HIDMaestro recreates a fixed ROOT ID.

## Registrations and removals

This section narrows the windows in which a program of this release registers a devnode while a removal is in progress. It rests on the hypothesis above, that a removal of a HIDClass devnode overlapping Windows' event delivery for the same device corrupts the list. It reduces the exposure. It is not shown to stop bugcheck 0x139: no run has reproduced the crash on this code or shown it gone, and a program built before v2.0.0 takes none of these steps.

### The PnP lock

`HIDMaestro.Admin\Pnp`, a mutex in the namespace of the other locks, is held by:

- Each devnode registration the SDK makes, from the registration gate's last checks through `DIF_REGISTERDEVICE`, or `SwDeviceCreate` for the two software companions.
- Each removal and uninstall the SDK makes, from its call through its removal test, and a retry's of a refused removal from after its query (below): `RemoveDevice` with its children, its fallbacks and the SWD helper's close, each orphaned HID child, and each phantom record.
- A full deploy's `pnputil /add-driver /install`, which reinstalls every present devnode the package matches, other programs' controllers and their HID children included.
- Each create's bus type stamp on the parent it made.
- The ghost XUSB interface sweep and the interface-class cleanup, each per devnode.

One hold is one removal or one registration, never both. Threads of one process take the lock through an in-process gate first, one at a time, so a wait bounded for another program's hold never counts this process's own holds. Another program waits up to ten minutes, then throws `InvalidOperationException`. The longest hold is one removal, about 150 s for a devnode with a few children: the SWD helper's close (up to 8 s), the parent's 120 s budget and 2 s for its notification, 4 s per child, and the pnputil and devcon fallbacks. A registration's longest is about 95 s: three SWD helper attempts of up to 15 s, 4.5 s between them, and a removal test of up to 15 s after each that timed out.

These change devnodes outside the lock, and each is exposure the lock does not cover:

- A USB/IP import's attach and detach, after which Plug and Play enumerates or removes its HIDClass children.
- The host controller's driver update on a transport swap, which restarts every import's subtree.
- A WinUSB bind's `DiInstallDevice`, which takes the device's HID collections away.
- A registration's `DiInstallDevice` once its hold has ended. Plug and Play then links its HID child into the HIDClass list with no lock.
- A dispose's surprise removal request (`SharedMemoryIO.RequestSurpriseRemoval`), a `SetEvent` and a wait made before its removals take the lock, after which Windows removes the device and its HID children.
- A retry's removal query of a dead program's device that a program refused before, and its request that the driver fail the device (`OwnerSweep.RefusalRetry`), made under the index and identity claims of the device's group, so no create of this release registers it meanwhile. A holder that refuses keeps the query waiting about 5.4 s, and no program waits for the lock through that. When nothing refuses, Windows removes the device and its HID children, and the retry deletes their records under the lock.
- Every program built before v2.0.0.

Outside the lock as well, on a controller's own devnodes or on residue: the naming writes after a registration, `RestartDevice` (public, and a program's own call of it takes no lock), the package removal's `pnputil /delete-driver`, run once no device remains (the full removal's after its walk, the others' with no other program running either), the usbip-win2 host controller's repair and installer, and a WinUSB restore's reinstall flag on a devnode that has left. S77's source check lists each of these calls and fails on one made anywhere else outside the lock.

### The registration gate

Everything that takes time happens before the lock. Rivals of the ParentIdPrefix go, a prior life that a NORMAL locate, or for a ROOT id a PHANTOM locate, still finds goes through its own removal, each removal in a hold of its own and decided by its own test, and Windows' install queue gets up to 30 s through `CMP_WaitNoPendingInstallEvents`, the bound vJoy's installer gives the same wait (`vJoyInstallLib.cpp`, `cmdUpdate`). The gate then takes the lock and looks once more, removing and waiting for nothing: a rival or prior life back since, or an install pending while the 30 s have time left, lets the lock go and sends the gate round again, up to three times for what came back. `CMP_WaitNoPendingInstallEvents(0)` "tests whether there are pending installation events and returns immediately" (Learn). An install still pending when the 30 s end lets the registration go ahead and is logged, since it can belong to any device on the machine. A failed wait refuses the registration, as vJoy's installer stops on `WAIT_FAILED`. A prior life whose removal ends `NotGone` refuses it, as `SetupDiCreateDeviceInfoW` refuses an id whose record is still there. A software device's record is left alone: `SwDeviceClose` keeps it and `SwDeviceCreate` takes it over.

The gate sees a removal of the id by any program through the id's locates. It cannot see a removal Windows has not finished after the devnode and its record have gone. A program of this release holds the lock until its removal test has an outcome. A program before v2.0.0 holds nothing.

A software device's create that runs past its 15 s is retried after 1.5 s and then 3 s, on the same id and inside the same hold. After each attempt that timed out, the last one included, the removal test runs on the id within an attempt's 15 s, before the next attempt and before the hold ends, since an attempt that had made the device closes it when it is killed. A device still in the tree ends the attempts.

### The removal test

Every removal the SDK makes ends on a removal test with one of three outcomes. A failed `CM_LOCATE_DEVNODE_NORMAL` locate shows the devnode out of the tree. An uninstall, a ROOT or HID id removed by `SetupDiRemoveDevice` or `CM_Uninstall_DevNode`, also needs a failed `CM_LOCATE_DEVNODE_PHANTOM` locate, its record gone. A devnode that was in the tree when the watch registered must then deliver DEVICEINSTANCEREMOVED, "sent when a device instance that meets your filter criteria is no longer present" (CM_NOTIFY_ACTION on Learn), within 2 s more. The outcome is `Removed` when it does, `GoneWithoutRemoved` when the devnode and its record are gone and the notification is not, which is logged and counted and never refused, and `NotGone` when the devnode, or the record an uninstall should have deleted, is still there at the end of the budget. Until v2.0.0 a failed NORMAL locate ended the wait. On the bench's diag log of 2026-10-14 and 10-15, 2343 of 2343 waits for a ROOT parent returned at 0 ms that way, and fast removals waited for nothing. No locate passes `CM_LOCATE_DEVNODE_CANCELREMOVE`, which "cancels the removal of the device" when one is in progress.

A watch registers for the notification only for a devnode in the tree, since Windows refuses one for an id with no devnode (`CR_FAILURE`, measured 2026-10-15) and each registration is one more listener during a removal. One registration at most is open at a time: a parent's watch stays open through its children's removals, which open none of their own. A removal in steps on one devnode runs on one watch from its first call to its last test and counts once.

A HID child removed with its parent is tested on the parent's notification. A ROOT or HID parent's watch starts before its first child's removal call, and the child counts as removed once the parent's latest DEVICEINSTANCEREMOVED arrived after the child's call and the child is out of the tree with its record gone. Each child used to be tested at its own call, and in the Windows Sandbox runs of 2026-10-16 no HID child's own notification came within the 2 s bound, while the parent's came 11 to 123 ms after its removal call, and a parent's removal, which waited for its child's, took 2,142 to 2,155 ms. A bus driver keeps the PDO of a child it still reports, and the PnP manager removes a child's drivers before it sends the parent its remove IRP ("Removing a Device in a Bus Driver" and "Removing a Device in a Function Driver" on Learn). That the parent's notification follows the child's PDO deletion is inference: no page orders DEVICEINSTANCEREMOVED against the remove IRP. S77 times each child's own notification through a registration it holds open and fails when one comes after the removal let the lock go. A software parent's children are called after its close, and a child still in the tree at its call is held under the lock, once gone, for up to 2 s, until the parent's notification ends the hold. With no parent watch open, because the parent was out of the tree or Windows refused its registration, a child is removed and tested on its own, as before.

Each removal kind gets the budget it needs. A parent removed by `SetupDiRemoveDevice` or `SwDeviceClose`, which can wait on open handles, gets its caller's: 120 s for a create's prior life. Every removal whose call finishes its work before it returns gets 2 s: a child, a fast removal whatever its caller passed, an orphan, a phantom, and the pnputil and devcon fallbacks. A failed call gets none. A software device's record is never waited for. So the `Everything` cleanup now waits up to 2 s per removal, where it waited for none, and a teardown's surviving HID child waits 2 s, where it waited its caller's 120 s.

The HID orphan sweep looks for an orphan's parent again under the lock. It leaves a child whose parent came back, as a record or in the tree, while it waited, and one whose identity claim another program holds, and it removes one whose claim this process holds.

### Creates that now fail

A create throws `InvalidOperationException` when another program holds the lock for ten minutes, when its ROOT devnode's prior life or that record is still there after its removal, when a software companion's prior life is still in the tree after its removal, where the create reconnected to it, when the install wait fails, when the devnode it would start is still its previous life's, which Windows removes once no program holds its HID child open, and when what the gate removed comes back three times. A gamepad or XUSB companion that is not made, for any reason, fails the create with `InvalidOperationException` naming it. Before, the create succeeded with a controller no game saw: an xinputhid controller has no other device, and an Xbox 360 controller got no XInput. A failed create's cleanup removes what it made. A create no longer restarts a leftover `ROOT\XNACOMPOSITE\0000`, which since issue #60 belongs to a program built before v1.8.0 or is residue: that restart took another program's devnode and its HID children down, and could fail the create on a busy lock after its own devnode was registered.

### The exit

The exit handler's removals take the lock within what is left of its 10 s, counting only the time another program holds it, never the work done under the lock nor a wait behind another removal of this process. A take that misses leaves the devices and the record for the next sweep. Once the process is exiting, every take on a thread with no bound of its own, a program's `Dispose` or cleanup from its own `ProcessExit` handler, waits within one 10-second budget the process shares, and threads that wait together spend it once. The process's own removals queue on the in-process gate without counting. During the exit a wait behind one hold of the process's own is bounded by the whole budget, since SetupAPI and CfgMgr calls take no timeout, so one hold longer than the whole 10 s, a stuck call or an xinputhid removal that slow, refuses the take queued behind it. A controller whose removal a refusal cuts short keeps its lease, so the record's entry names its devices. The runtime runs `ProcessExit` handlers in the order they were added (`AppDomain.OnProcessExit` invokes the event's delegate once), and the SDK adds its own at the program's first create, `InstallDriver` or cleanup. When the program's handler came first, the SDK's handler runs next and removes such a controller within its own 10 s. Otherwise the next sweep removes it. The phantom cleanup's waits for the lock come out of its 5 s.

### The cost

Removals now run one at a time, in a program and across programs, so a dispose of several controllers takes about the sum of their removals, where it took about the longest one, and another program's create or removal waits that long too. Each removal also waits for its notification, up to 2 s more when it is late. Release builds on one machine with logging off, 30 runs each, give medians of 59 ms for a DualShock 4 dispose against v1.12.0's 72 ms, and 6 ms for a `dualsense-composite` dispose against 509 ms. S77's `measure` and `measure4` modes time one controller and four controllers disposed together, old against new, and neither has run. Before this change, on 238bd2b's removal path, the bench's diag log of 2026-10-14 and 10-15 put a DualShock 4 teardown at p50 77 ms and p95 192 ms (317 teardowns) and an Xbox 360 wired one at p50 151 ms and p95 276 ms (165). Those are not this release's figures. Offline, against an absent id with a stand-in lock, the gate costs 24.9 µs at p50 and 30.0 µs at p95 over 200 runs, where the two locates it replaces took 6.4 µs and 7.8 µs (development measurement). What a real back-to-back create adds, the previous create's HID child install now waited for before the lock, only a live run can show.

### Tests

S77's offline part feeds the removal test and the registration gate recorded sequences through `DeviceManager`'s hooks, with no device and no elevation, and fails when either answers before the DEVICEINSTANCEREMOVED notification and the PHANTOM record's removal, or issues a CANCELREMOVE locate. It also checks the lock's bounds during the exit and its source check of the calls made outside the lock. Its live part disposes a DualShock 4, an Xbox 360 wired and an Xbox Series over Bluetooth and fails on a removal that ended with its devnode still there, on a devnode in the tree at its removal's start that left without DEVICEINSTANCEREMOVED, and on a refused registration, read from counters inside the SDK.

## Devices described as data

A profile describes its device, and the SDK holds only mechanisms any device can use. Nothing in the SDK names the GameCube adapter, checks its VID and PID, or switches on its command bytes. A new device of the same form needs a profile and no code, and a new form of device gets a new general mechanism plus the JSON that uses it. The adapter is the first profile to use the three mechanisms below, and the mechanisms are what this release ships.

### Ports

`extendedReport.ports` describes a report that carries several controllers, one block per port: a multi-port adapter, a multitap, a receiver with several pads.

| Key | Meaning |
|---|---|
| `count`, `offset`, `stride` | how many blocks, where port 1's starts (byte 0 is the report ID, so an input report with one, and every output report, start their blocks at byte 1 or later) and how far apart they are |
| `status` | the block's status byte: its offset, the `connections` a port can hold with the bits each sets (at least two: the first is the empty port, the second the default, each a value of its own that shares no bit with a flag), and device-wide `flags` every status byte carries while on |
| `data` | the block's data bytes, such as `"1-8"`. An empty port's are zero |
| `snapshots` | copies of a block the device keeps, taken `on: "connect"` from the first report in which the port holds something |
| `fields` | the block's fields in the `extendedReport` vocabulary, offsets relative to the block |

`extendedOutputReport.ports` describes an output report's blocks the same way. Its fields are whole numbers (`uint8`, `uint8-axis`, `uint8-trigger`, `uint16-le`, `int16-le`), and each is reported under its semantic.

A report with ports is written from its blocks and the status flags alone, so its own `fields` stay empty: they would take their values from one gamepad state, where each port has its own. An output report's own fields are read beside its blocks and may not overlap them.

On the SDK side, `HMController.Ports` is an `HMPortSet`, empty for a profile with one controller. Each `HMPort` has a fixed `Number`, a `Connection` named by the profile, `Connect(name)` and `Disconnect()`, `SubmitState(in HMGamepadState)` through the port's fields, `SubmitRaw` for the port's data bytes exactly, `GetOutput(name)`, and an `OutputChanged` event raised on the output thread. `Ports.Flags["name"]` sets a device-wide flag. A port call writes the whole report under the controller's submit lock, the work `SubmitState` already does, with no lock, system call or allocation added: the layout is compiled once, and the encoder writes into buffers the port set owns. `HMController.SubmitState` on a device with ports submits to port 1. On a profile with idle frames the repeat sends the report as the ports left it, so an unconnected port stays empty. `OutputDecoded` carries each port's output fields as `port1.rumble` and so on.

`HMButton` gains `LeftTriggerClick` and `RightTriggerClick`, a trigger's digital click apart from its analog travel. With them, `HMGamepadState` expresses the GameCube controller's analog L and R with their clicks, its Z and its C-stick exactly, so no device-specific state type exists.

### The device protocol

`protocol` describes how a USB/IP device behaves beyond its descriptors. This design put it under `usbConfiguration`. In 2.0.0 it is a key of the profile itself (data-driven-devices.md, mechanism 3), and the old place is refused at load.

| Key | Meaning |
|---|---|
| `state` | named on/off states with initial values, restored at attach and at a port reset |
| `input` | the interrupt IN endpoint, the states under which a poll gets a report (`"polling"`, `"!stalled"`), and its `clock`: the device's own controller poll in ms and rules that change it while exactly the listed ports hold something |
| `commands` | the interrupt OUT endpoint, whose packets are each a command, whether a SET_REPORT(Output) is one command too (its whole data stage, report ID first), `setReportStripsId`, set when the device's USB stack drops a leading report ID that matches wValue's from a data stage longer than one byte, as tinyusb does, and rules tried in order. `replies.pending` is how many replies can wait for the IN endpoint (1 by default, and with `overflow` `dropNewest` a reply that finds them all waiting is dropped). A rule matches the bytes a command starts with and its length, sets states, and queues a reply built from the state before the rule ran: constant bytes, a state as a byte, or a snapshot's bytes for every port, zeros unless its own condition holds |
| `halt` | the states under which the device answers nothing, and the status transfers fail with until a port reset |
| `setProtocol` | `"ack"`, or `"stall"`, the default |
| `getStatus` | `"descriptor"`: the self-powered bit the configuration declares |
| `getReport` | `"input"`, the default: the input report as it stands, for its own report ID, since HID 1.11 section 7.2 makes GET_REPORT mandatory. Another input report the descriptor declares answers its ID and zeros, since the protocol sends only its own report, and an ID the descriptor does not declare stalls (USB 2.0 section 9.2.7). The other USB/IP personas answer a declared ID with a sent report's latest bytes, or its ID and zeros before the first, and stall the same way. Two personas differ by design: the GameCube profile's `"reportId"` mode answers every nonzero ID with that byte, and the Switch 2 Pro persona answers a declared ID with the report it would send next and report ID 0 with its selected report. `"reportId"`: for every report type, feature included, the requested report ID alone, and a stall for report ID 0 or a one-byte request, as tinyusb answers for a firmware that supplies no report (`src/class/hid/hid_device.c`, GET_REPORT) |

The device runs it on a modeled host poll. A host controller polls an interrupt endpoint every period while a transfer is queued, on a grid that starts at attach, and fills a transfer one packet of wMaxPacketSize per poll. A short packet or a full buffer ends the transfer, and a packet with no room left in it is babble, which fails it with `-EOVERFLOW`. The period is the one Windows gives the endpoint descriptor's bInterval: 8 ms for bInterval 0 to 15, 16 ms for 16 to 35 and 32 ms beyond at low speed, a power of two from 1 to 32 ms at full speed, and 2^(bInterval-1) microframes, at most 32, at high speed (the tables under [USB_ENDPOINT_DESCRIPTOR](https://learn.microsoft.com/windows-hardware/drivers/ddi/usbspec/ns-usbspec-_usb_endpoint_descriptor)). `usbConfiguration.busSpeed` takes `"low"` as well as `"full"` and `"high"`. `HMController.DeviceProtocol.HostPollInterval` models another host poll, a faster one as a filter driver that overclocks the poll makes it, and the descriptors never change. It takes only a period Windows schedules at the device's speed, 125 µs to 4 ms at high speed, 1 to 32 ms at full speed, and 8, 16 or 32 ms at low speed, and throws `ArgumentOutOfRangeException` for any other. A device with a source poll has a new report for a host poll only once it has read its controllers since its last report.

The profile is compiled at create and again when the device is built: names become bits, conditions become a mask and the values under it, rules become byte patterns, and replies become parts with fixed offsets. A poll takes three locks, always in one order: the device's send lock, its HID lock, then the engine's. It copies one packet into a pooled buffer and allocates nothing. The input pump reads each SDK frame into one buffer it reuses and allocates nothing. Commands are rare. The replies they queue, and a GET_REPORT(Input) answer under `"input"`, are the engine's only allocations.

### WinUSB on request

`usbConfiguration.winUsb` names the `DeviceInterfaceGUIDs` value a WinUSB binding registers, and `HMController.BindWinUsb()` binds it, as described for the adapter below. The package is generated per profile from its descriptors: `hmwinusb_<profile id>.inf`, matching the device's vendor-scoped compatible ID `USB\COMPAT_VID_vvvv&Class_cc&SubClass_ss&Prot_pp`. A device that takes one has a single interface and no device class, so WinUSB goes on the device's own devnode.

### Validation

### The report a data frame fills

A data-only frame, from `SubmitRawReport` or `SubmitState`'s legacy path, goes out from a UMDF2 driver as one input report at one length. Through v1.12.0 the driver took the first Report ID item of the first Application Collection, whatever kind of report it named, and the SDK counted that ID's input bits with a walk of its own. That walk kept Report Size, Report Count and Report ID with no stack, skipped a long item as 3 bytes, and counted the first Report ID item of any kind. So some profiles sent an output or feature ID as an input report, and some a report shorter than the descriptor declares.

The SDK now takes the report and its length from the parse it fills: for a keyboard or mouse that gets every report delivered, the descriptor's first input report, and otherwise the first input report with game pad fields. A profile's `inputReportSize` replaces the length. The SDK writes `InputReportId` into the controller's configuration, REG_BINARY: the ID, the length as a 32-bit little-endian value, then the descriptor. The driver takes the ID only when that length equals the `InputReportByteLength` it has just read and the descriptor is the one in use, so a value a killed program left never pairs its ID with the length a v1.12.0 program writes for the same index. Without the value, from a v1.12.0 program or for a profile whose `inputReportSize` is another report's length (the four Sony Bluetooth profiles at 0x31's 78 bytes, and switch-pro at 362), the driver scans the descriptor as before. A driver older than this release ignores the value, so on a v1.12.0 driver that running programs hold, the profiles below keep their old reports.

`inputReportSize` is the report's length on the wire, its ID byte included, as the SDK has always sent it. schema.json said the opposite and now says this. A profile can name the report its data frames fill with `dataReportId`, a hex byte, where the SDK's choice is wrong. It must name an input report the descriptor declares, and it is refused beside an always-armed `extendedReport`, whose report the data frames fill instead, before anything machine-wide. `HMProfileBuilder.FromProfile` copies it. `microsoft-designer-keyboard` sets 0x01. Its descriptor declares a vendor report 0x27 as its first input report, and the real keyboard sends its keys as report 0x01 of 12 bytes: "Press A" is `01 00 04 00 00 00 00 00 00 00 00 00` in Android CTS 1daba777, `microsoft_designer_keyboard_keyeventtests.json`, beside the register file the profile's descriptor comes from.

Every descriptor walker keeps the global item stack of HID 1.11 section 6.2.2.7, Push and Pop, as hid-core.c applies it. `HidReportBuilder` now expands `HidReportMap`'s fields, which already kept the stack. `PidReportIdExtractor` restores the Usage Page and Report ID on Pop, completes each usage with its page, clears local items at every main item and keys only on the PID page (0x0F). `GameInputMapping`'s measured-shape check reads `HidReportMap`, and `HidDescriptorBuilder` follows the pages that `AddRaw` bytes push and pop. `HidReportMap` and hid-tools (f4a3253) read the same input, output and feature lengths for every report of all 243 catalog report descriptors, which S37's `report_length_check` checks against `reference_lengths.json`. A create parses a profile's descriptor once, for the report builder and the keyboard and mouse packer together.

Four catalog descriptors held main items of tag 0, which HID 1.11 section 6.2.2.4 does not define, and hid-tools refused them. Each now holds its source's bytes:

- `ps3-remote`: hid-sony.c `ps3remote_rdesc`, which the profile names as its source, with two items given a data byte (below). The catalog copy had 90 bytes, with bytes doubled.
- `saitek-x52`: the 119 bytes of Launchpad bug 492056 comment 14. One byte was missing and three were changed.
- `thrustmaster-t80`: byte 79 is 09, so Rx and Ry follow as in the T-Flight HOTAS 4 and T300RS descriptors the profile says it shares. No dump of a T80's own bytes is published.
- `joypad-steam-input`: joypad-os `sinput_descriptors.h` at 9fa79f45. The copy had lost the three report ID values its macros stand for.

Windows' own parser refused three catalog descriptors. HID class runs it on the descriptor at the device's start (`HidP_GetCollectionDescription`), so each of these devices failed its start with problem code 10. S37's `report_length_check` loads the machine's hidparse.sys into its process and runs that call on every descriptor the SDK gives the driver:

## The Wii U GameCube adapter persona

`gamecube-adapter` becomes a working profile: the Wii U GameCube adapter, WUP-028 (057E:0337), on the USB/IP transport, so that Dolphin, Slippi and SDL open it through libusb as they open the real one. It is a profile and nothing else: its ports, its protocol and its WinUSB GUID are the JSON below the descriptors.

Implementations, cloned beside this repository and read at the commits given: Dolphin `0d93fc0355` (`Source/Core/InputCommon/GCAdapter.cpp`), Slippi's Dolphin fork `9d13b39`, Ishiiruka `60f7b63`, SDL `804cf65` (`src/joystick/hidapi/SDL_hidapi_gamecube.c`) and its 3.4.18 release `829a65d7`, eden `1dcc574` (`src/input_common/drivers/gc_adapter.cpp`), RMG `4777ed3` (`Source/RMG-Input-GCA/main.cpp`), gcfeeder `06b2917`, Nintendont `999aa85`, ToadKing's wii-u-gc-adapter `fa098ef`, the adapter firmwares of loopj (usb-gamecube-controller-adapter `639f914`), pico-rectangle `1f0421d`, joypad-os `969c232`, HOJA-LIB-RP2040 `4ec9591` and HOJA-LIB-ESP32 `99f6bc3`, libusb `a45bb16` with Dolphin's pin `15a7ebb4` (1.0.29) and Slippi's `ba698478`, and usbip-win2 `v.0.9.8.1`. Real devices: 57 `lsusb` and `usb-devices` dumps of 057E:0337 from linux-hardware.org, the GBAtemp dump behind `gamecube-adapter-hid`, koalaboy13's command survey of a real adapter (GBAtemp thread 388169, 2015-05-05), François-Xavier Carton's Linux driver series (hid-gamecube-adapter v3, 2020), and Arte's guide to overclocking the adapter.

bMaxPacketSize0 splits the dumps in two. Nineteen units report 8, and the eighteen whose status was recorded answer GET_STATUS as self-powered (0x0001 or 0x0003), which agrees with their own bmAttributes. Thirty-eight report 64, and the twenty-six whose status was recorded answer bus-powered (0x0000 or 0x0002), which contradicts the same bmAttributes. The persona reports 8 and answers GET_STATUS with the self-powered bit.

The dumps mask the serial. `15/07/2014` is the serial of a unit filed under an issue about the official adapter (OpenEmu issue 4652, bcdDevice 1.00, full speed), of a Mayflash in Wii U mode (node-hid issue 241), of a self-described cheap clone (wii-u-gc-adapter issue 39), and of both firmwares that copy the official adapter (loopj `usb_descriptors.c:80`, pico-rectangle `gcc_to_usb_adapter.cpp:30`). No source shows a WUP-028 with any other serial. One conflict stays open: the OpenEmu unit's manufacturer string is "Nintendo Co., Ltd.", the string the self-described clone reports, while every 8-byte unit in the dumps reports "Nintendo". The persona follows the dumps.

Since every adapter carries the same serial, Windows names the first WUP-028 it sees `USB\VID_057E&PID_0337\15/07/2014` and names a second one present at the same time after its port (measured, E1 and E5 below). The profile sets `sharedSerial`, so the persona serves `15/07/2014` for every identity key, where the other USB/IP personas fold the identity into their captured serial, and a second virtual adapter gets a port-named instance exactly as a second real one does.

The report descriptor declares ten reports under Usage Page 0x05, Game Controls, each in its own Application collection: outputs 0x11 to 0x15 and inputs 0x21 to 0x25. Each Report Count is the report's length on the wire including its ID byte, so report 0x21 is declared as 37 bytes after the ID and arrives as 37 including it. The persona sends what the device sends, 37 bytes for 0x21, 25 for 0x22 and 2 for 0x24. Carton's driver had to shrink Linux's 38-byte read to 37 for the same reason (v3 1/4).

Everything the dumps do not show stalls: the device qualifier and the other-speed configuration, which a full-speed device does not have (USB 2.0 section 9.6.2), string 0xEE, and every vendor request. HandHeld Legend's adapter answered string 0xEE with Microsoft OS descriptors and reported bcdDevice 2.00, so that Windows would bind WinUSB to it unasked. A host can see both, and the persona has neither.

### What the transport changes

usbip-win2 sits between the persona's bytes and Windows, and three of its rules are visible to a host. S79 reads every descriptor both ways.

- It gives UdeCx the device's own speed, full here (`drivers/ude/device.cpp:28-51`, `to_udex_speed`, set at `507`), and USBHUB3 treats every UDE device as high speed, as usbip-win2's own note says (`drivers/ude/wsk_receive.cpp:72-76`). So for a device below high speed it rewrites each interrupt endpoint's bInterval on every full configuration read to the smallest power of two of microframes that is at least that period (`wsk_receive.cpp`, `post_control_transfer`, `patch_config`, `to_high_speed_interval`). Windows reads bInterval 7, 2^6 = 64 microframes, where the persona serves 8 ms. The arithmetic keeps 8 ms. A host that scheduled the bus would not poll at it, because the table for high-speed interrupt endpoints under [USB_ENDPOINT_DESCRIPTOR](https://learn.microsoft.com/windows-hardware/drivers/ddi/usbspec/ns-usbspec-_usb_endpoint_descriptor) gives every bInterval from 7 to 255 a period of 32 microframes, 4 ms. Nothing here is scheduled that way. usbip-win2 copies the rewritten bInterval into each submit's `interval` field and the persona reads the field and uses it for nothing (`UsbipProtocol.cs:112`), and each read is forwarded when WinUSB queues it, so the rate a host sees is the persona's own grid, which comes from the full-speed descriptor it serves (`DeviceProtocol.cs:152` and `162`). The 125.0 reports a second that S80 measures at the 8 ms poll is that grid. It does not test the rewritten value.
- The device never sees a host arm remote wakeup. Measured: three GET_STATUS requests reached the persona in a run in which SET_FEATURE and CLEAR_FEATURE never did, so a host that arms remote wakeup and then reads GET_STATUS sees the bit clear. Which layer above usbip-win2 completes the SET_FEATURE no source read here shows, and what follows is inference. UdeCx completes it itself, by [Write a UDE client driver](https://learn.microsoft.com/windows-hardware/drivers/usbcon/writing-a-ude-client-driver), "only if the preceding methods were called to add descriptor", and usbip-win2 calls none of `UdecxUsbDeviceInitAddDescriptor` and its siblings, so USBHUB3 or WinUSB, through which S80 sends it, may complete it instead. usbip-win2 learns of the arming only as the wake setting of its link-power exit callback at suspend, and does not send it on (`drivers/ude/device.cpp:201-219`, `d0_exit`, registered at `492-493`).
- usbhub3 forwards no descriptor request to a device that failed to start, and a WUP-028 fails to start on input.inf (below). A host reads strings and the report descriptor only once WinUSB is bound.

- The survey does not say what ends a stall. The persona resumes on the next 0x13, the command every host sends to start reports. No host in the references sends 0x16, 0x17 or a short 0x11.

An attach and a port reset both return the device to its initial state: no reports until 0x13 and every motor command zero. The profile maps the left stick to the main stick, the right stick to the C-stick, the trigger axes to the analog L and R, `RightBumper` to Z, `LeftTriggerClick` and `RightTriggerClick` to the L and R clicks, and the D-pad from `Hat`, with both Y fields inverted.

| 0x20 | a WaveBird, read alone as one that is not communicating | connection `wirelessNotCommunicating` | Dolphin reads it as a wireless controller and takes its origin (`862-871`, `946-954`), SDL connects a joystick for it (`SDL_hidapi_gamecube.c:379-388`), ToadKing's driver names it `STATE_WAVEBIRD` (`wii-u-gc-adapter.c:36`), as does Carton's `GC_TYPE_WAVEBIRD`. Nintendont alone reads it without 0x02 as no controller (`PADReadGC.c:412-418`) |
| 0x02 | the WaveBird is communicating, read together as 0x22 | connection `wireless` | Nintendont's note "0x22=wavebird communicating" (`PADReadGC.c:412`), loopj `gcca.c:141` |

No source shows the data bytes a real adapter sends for 0x20 alone, and no firmware in the references sends 0x20 alone: loopj reports a WaveBird only once its receiver has heard from it (`src/gcca.c:66-68`) and then sends 0x22. The persona's `Connect("wirelessNotCommunicating")` sends a controller at rest, as it does for every connection, and Dolphin keeps that first report as the port's origin.

HandHeld Legend's notes from a real adapter give the empty values: 0x00 with only the black cable, 0x04 with both cables, and 0x10 and 0x14 with a controller (HOJA-LIB-RP2040 `src/cores/core_slippi.c:103-110`). An empty port's eight data bytes are zero, as the 0x12 reply reads before polling. loopj's firmware zeroes the report and skips the data of a port with no input (`src/gcca.c:132`, `147-148`), but it never reports a port as empty: its status byte is 0x10, or 0x22 for a WaveBird, with 0x04 added (`141-145`), so a port with nothing plugged in reads 0x14. The persona follows HandHeld Legend's values above. No dump of a real empty port exists, and Dolphin, SDL, eden, gcfeeder and Linux all ignore those bytes.

A motor command is the controller's own, the port output field `rumble`: 0 stop, 1 run, 2 stop hard. SDL sends 2 under its rumble-brake hint (`SDL_hidapi_gamecube.c:557-561`). Nintendont runs a port's motor only when the command's low two bits are 1 and the port has rumble power (`PADReadGC.c:419`). SDL refuses rumble on a WaveBird or on a port without 0x04 (`552-555`), and Dolphin sends none to a WaveBird (`GCAdapter.cpp:1037-1039`). Those rules belong to the hosts, so the SDK reports the command and leaves the motor to the program.

A host on Windows reads whole reports. libusb turns on WinUSB's ALLOW_PARTIAL_READS for every endpoint (`libusb/os/windows_winusb.c:3595-3599`), with which WinUSB reads whole packets and keeps what the caller did not ask for, and hidusb reads a report's own length. A transfer with room for less than the next packet therefore never reaches the persona from Windows, and the babble rule above is tested at the transfer level in process.

### What Windows does with a WUP-028

Windows binds input.inf's HID driver to a WUP-028, and the device fails with Code 10, `STATUS_COULD_NOT_INTERPRET`: the HID parser rejects its report descriptor. Measured on the persona (E1) and on the same descriptor served by the UMDF2 driver with no USB involved (E3). A real adapter on Windows has no HID collection at all, which is why a real adapter needs Zadig.

SDL's "separate device for each slot" (`SDL_hidapi_gamecube.c:220-231`) is its PC-mode path, taken only when the vendor is not Nintendo (`203-205`), for third-party adapters in their own mode. Its WUP-028 path reads four ports from one report (`364-445`). SDL lists 057E:0337 among the devices it opens only through libusb (`src/hidapi/SDL_hidapi.c:859`) and ignores it on every other backend (`1143-1157`). The official SDL3 3.4.18 build for Windows x64 comes from `VisualC/SDL/SDL.vcxproj` (`build-scripts/release-info.json:59-82`), whose build configuration defines no `HAVE_LIBUSB`. The only libusb strings in its `SDL3.dll` are the names of two hints, `SDL_HIDAPI_LIBUSB_WHITELIST` and `SDL_HIDAPI_LIBUSB_GAMECUBE`, which `SDL_hid_init` reads outside its `HAVE_LIBUSB` block (`src/hidapi/SDL_hidapi.c:1231-1233`). Stock SDL on Windows therefore lists nothing for a real adapter, with or without Zadig. The persona is tested for the same empty list beside a controller SDL does list, and for SDL's full behavior with SDL 3.4.18 built from source with libusb.

### Zero setup for Dolphin and Slippi

`HMController.BindWinUsb()` binds WinUSB to the one virtual adapter's devnode, and nothing the device reports changes. The driver package follows Microsoft's WinUSB template, `Include` and `Needs` of winusb.inf plus a `DeviceInterfaceGUIDs` value, which libusb requires to open a WinUSB device (`libusb/os/windows_winusb.c:1876-1887`). It is generated from the profile, signed with the test certificate the driver package already uses, and added to the driver store without being installed anywhere.

Its INF names no hardware ID any device has. It matches the vendor-scoped compatible ID `USB\COMPAT_VID_057E&Class_03&SubClass_00&Prot_00` as the sixteenth of its compatible IDs, behind fifteen that no device carries, and a match that late ranks worse than input.inf's. Windows installs the best-ranked driver, the lowest rank value, on a new device. Measured: the package ranks 0x00FF3F00 against input.inf's 0x00FF3205 (S81), and in E6, with the vendor ID as the fourth compatible ID, it ranked 0x00FF3300 and still lost, while as the third it ranked 0x00FF3200 and won. Nintendo's other HID-class USB devices carry the same compatible ID and see the package listed among their compatible drivers at the same losing rank. The step installs it on the one devnode with `DiInstallDevice`, which installs the named driver on the named device and nowhere else ([DiInstallDevice](https://learn.microsoft.com/windows/win32/api/newdev/nf-newdev-diinstalldevice)). Zadig installs with `UpdateDriverForPlugAndPlayDevices` and its hardware-ID INF, which binds every present adapter (libwdi `30df0c0`, `libwdi/installer.c:876`). When no device of that ID is present, `process_error` treats `ERROR_NO_SUCH_DEVINST` as success and the installer copies the INF into the driver store with `SetupCopyOEMInf` for the next arrival (`895`, `process_error` at `577`).

Windows 10 generates no vendor-scoped compatible ID. On 19044 the adapter carries `USB\Class_03&SubClass_00&Prot_00`, `USB\Class_03&SubClass_00` and `USB\Class_03`, and input.inf ranks 0x00FF3202 (S81). The package then matches no devnode, so Windows never chooses it, and no driver list Windows builds for the adapter carries it. The bind installs the null driver on the devnode, which takes the devnode out of its setup class, then builds a class driver list from the package's INF alone and installs that driver: the two steps of Nefarius.Utilities.DeviceManagement's `PnPDevice.InstallNullDriver` and `InstallCustomDriver`. Windows builds such a list only from INFs of the devnode's own class (E8). A failure after the null driver leaves the devnode with no driver and the claim in place, and a restore flags a gone devnode that its claim found on a driver and that has none, so its next arrival installs by rank.

Before it installs, the step reads the devnode's driver list and confirms that another driver ranks above the package. Only that driver keeps Windows from choosing the package for a real device of the same kind. Every USB/IP persona has a HID interface, which input.inf matches, so the check guards the package's reach for whatever device form comes next. It also waits until Windows has settled the devnode's driver: no installation pending in the PnP manager (`CM_WaitNoPendingInstallEvents`, the cfgmgr32 macro for `CMP_WaitNoPendingInstallEvents`), and the devnode started or stopped on a decided driver. A devnode that arrives with the reinstall flag still names WinUSB while it waits for the reinstall, and a bind that read it then returned `AlreadyBound` for a device about to lose WinUSB. S81 binds five times in a row on the first call to keep it so.

`CONFIGFLAG_REINSTALL` in a devnode's ConfigFlags makes its next arrival install again by rank, and a started device ignores it (E7: a bound adapter with the flag kept WinUSB and kept reading through a re-enumeration of its parent and `pnputil /scan-devices`, then a same-serial adapter arriving after its program was killed got input.inf). The flag cannot stay on the bound devnode, though. Windows reports it as install state 1, "needs reinstall", and libusb skips any device whose install state is not 0 as one whose driver "is reporting an issue" (`libusb/os/windows_winusb.c:1831` at Dolphin's pin `15a7ebb4`, `1686` at Slippi's `ba698478`), so neither emulator could open the adapter while it was set. The restore sets the flag instead, on a devnode that is gone: at dispose, at the next program's reclaim after a crash, and at the other points listed below. A program killed while bound therefore leaves its instance on WinUSB, as Zadig would, until a HIDMaestro program's teardown, cleanup, reclaim, re-bind or follow-up releases the killed program's hold and finds the devnode gone. S81 measures both orders: an adapter arriving on the instance before the reclaim finds WinUSB and keeps it while it is present, and one arriving after the reclaim gets input.inf.

The step binds only a devnode on a driver that ships with Windows, which for a WUP-028 is input.inf. A devnode on WinUSB, libusbK or libusb0 already opens in libusb, and the step returns `AlreadyBound` without touching it. That covers an instance Zadig bound before. A devnode on one of HIDMaestro's own packages, which a killed program's binding leaves until a sweep, also returns `AlreadyBound`, and the controller holds it in the ledger from then on, so no sweep moves a live adapter to input.inf. A devnode on any other driver is left alone and reported as `OtherDriver`.

The binding goes through the registry ledger. Before the bind the ledger records the devnode, its driver and the controller as holder. When the last holder lets go, by dispose or because its process is gone, the ledger restores a devnode still on HIDMaestro's package once it is gone. A gone devnode, one `CM_Get_DevNode_Status` reports as `CR_NO_SUCH_DEVINST` (Learn, "Determining Whether a Device is Plugged In"), gets the reinstall flag. A restore installs no driver on a present devnode, whichever device it is: the one bound, on its way out, or another that arrived on the instance since. Another program's dispose, a kill or a dropped import can start a devnode's removal at any moment, and nothing a restore holds stops it, so a driver install there could change the setup class of a devnode as it leaves. A present devnode keeps its entry. One follow-up per entry on the machine, held by a mutex in the private namespace, looks again as soon as the devnode has gone, polling for up to five minutes, and a sweep after that starts another. Its deadline is UTC wall-clock time, so one written before a reboot has passed after it, and one more than five minutes ahead, as after the clock was set back, counts as five minutes from now. A teardown waits only for the devnodes its own controller held, takes the WinUSB lock for another entry only when no one holds it, skips an entry a follow-up watches, and runs no pnputil while the devnode is present. Only a controller teardown, the cleanup, a reclaim of the controllers of a program that has ended, a re-bind that moves a binding to the devnode its dropped adapter came back on, or a follow-up sets a flag. A program that starts and runs sweeps the ledger only when it finds a program that has ended, so a devnode that goes after its follow-up has ended keeps no flag until one of them runs. A teardown whose own devnode is still present hands its entry to the follow-up already watching it, with a deadline five minutes from then, and a follow-up held past its deadline, as by a frozen program, holds up no entry.

A bind reads the devnode under the WinUSB lock, lets that lock go to add its package under the deploy lock, so it waits for another program's deploy, and takes the WinUSB lock again. The package is added once per process, and again after a cleanup removed it. Its ledger claim gives up after 30 s. A bind checks the devnode twice, the second time right before `DiInstallDevice`, and binds nothing that fails either check. When the adapter's connection drops and usbip-win2 imports it again, the binding runs again on the new devnode. A `BindWinUsb` that threw binds nothing at a later re-import. Disposing a controller waits only for a claim and install in progress.

Two windows stay open, both on the device a program is binding, and no lock closes them. A bind's `DiInstallDevice` runs on its own import's devnode, checked right before the install, and a kill of the program or a connection usbip-win2 drops during that install starts the devnode's removal while the PnP manager changes its class. The ledger claim comes first, so the next sweep finds the entry, and a gone devnode is flagged or its entry deleted. What the PnP manager does with the half-applied change is not documented. Neither of the two bugchecks recorded above (Two bugchecks during development) involved a WinUSB bind. A process exit stops every re-bind of the program and waits out an install in progress before it detaches its imports, as a dispose does.

What a user sees when a devnode lingers: an adapter on an instance HIDMaestro bound keeps WinUSB for as long as its devnode is present, whether it is the virtual adapter on its way out or a real adapter, or another program's virtual one, that took the instance. A libusb host such as Dolphin opens it there. Once it is gone the instance gets the reinstall flag, and the next adapter to arrive on it installs by rank and gets input.inf. A devnode someone has moved to another driver meanwhile is theirs and stays as it is, with its entry, while it is present, and so does one whose driver cannot be read. The uninstall-grade cleanup removes no devnode: it flags a gone devnode still on a package and keeps that package, leaves a present devnode and its package as they are, and removes the packages no devnode uses. A package it keeps is noted by INF name in `HKLM\SOFTWARE\HIDMaestroPackagesLeft`, value `WinUsb`, under the deploy lock and outside the ledger's root, so the full cleanup's delete of the ledger leaves the note. A later package add takes its own name out. The cleanup that runs once the last WinUSB entry clears, and the first sweep of each later program that finds the note and no WinUSB entry, remove the noted packages no devnode, present or gone, still uses, and keep the rest noted. A cleanup decides from one listing of the driver store and one walk of the USB devnodes: a listing that fails removes nothing and changes no note, a walk that fails removes nothing and notes every listed package, and only a package the whole walk found on no devnode is deleted, with pnputil's plain `/delete-driver`. Removing a gone devnode would race a real adapter of that instance that arrives and starts its install after the check.

### Report timing and latency

The endpoints declare 8 ms, so a host polls the adapter 125 times a second, and each poll finds a report, because the adapter polls its controllers every 1.19971 ms (Arte's guide). The persona answers one packet per poll on an 8 ms grid that starts at attach, timed by a high-resolution waitable timer. A read that arrives between polls waits for the next one, as a real interrupt transfer waits for the next scheduled poll, and a clock that was held up skips the polls it missed instead of sending a burst. Hosts read with short timeouts, 16 ms in eden, gcfeeder and RMG and 100 ms in Dolphin, and Slippi warns about a slow adapter after 80 reads in a row over 15 ms (`GCAdapter.cpp:237-245`, `528`). The 8 ms grid meets all of them.

Melee players overclock the adapter by making Windows poll it every millisecond with hidusbf. Nothing changes inside the adapter: its descriptor still says 8 ms, and a 1 ms poll that finds no new controller poll gets a NAK, about one poll in six, so an overclocked adapter delivers about 833 reports a second. With controllers in ports 1 and 2 only it polls them every 0.9995 ms and delivers about 1000 (Arte's guide). USB/IP has no host schedule to overclock: usbip-win2 forwards a read the moment WinUSB queues it, so the persona alone decides when a report goes out. `HostPollInterval` sets the host poll the persona models, 8 ms by default or another period Windows schedules at full speed, and the profile's source poll and its ports 1 and 2 rule give the adapter's own NAKs.

A report carries what the adapter's latest read of its controllers found, as a real adapter's does. A program's submit therefore reaches the wire at the first host poll after the adapter's next controller read, up to 1.19971 ms after the submit plus up to one host poll.
