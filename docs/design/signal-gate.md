# Design note: the signal gate

Release 2.1.0 skips kernel transitions a frame does not need. Before it, every frame cost the SDK a `SetEvent` on the driver's input event, every Xbox 360 frame a second one on the XUSB companion's doorbell, and every delivered frame cost the driver a `SetEvent` on the delivery acknowledgement's event. The HID driver also took its locks through UMDF's wait lock, which is an auto-reset event (Windows-Driver-Frameworks `mxeventum.h`, `MxEvent::WaitFor` and `MxEvent::Set`): two system calls for every acquire and release, twice a frame. This note gives the protocol that drops what nobody waits for, the argument that it loses no wakeup, and the checks that back the argument.

## What changes

| Cost | Who pays | After |
|---|---|---|
| The HID driver's three locks | the driver host, twice a frame | slim reader/writer locks, user mode while uncontended |
| `SetEvent` on the input event | the SDK, every frame | only while a worker waits on it |
| `SetEvent` on the companion doorbell | the SDK, every frame with GIP bytes | only while a WAIT_FOR_INPUT is parked |
| `SetEvent` on the acknowledgement's event | the driver host, every delivered frame | only for a controller whose SDK waits on it |

No existing section layout, named object or profile id changes. The new words live in a new section, and each skip waits on a capability the driver host announces, so a program before 2.1.0 on the new driver, and a 2.1.0 program on an older driver, signal and acknowledge exactly as before.

## The section

`Global\HIDMaestroSignal<N>`, 256 bytes, `HIDMAESTRO_SIGNAL` in `driver/hm_contract.h`:

| Offset | Field | Written by | Read by |
|---|---|---|---|
| 0 | layout version, 1 | the SDK, once, when it creates the section | both drivers, at map |
| 4 | the HID driver's capabilities: 0x1, it counts its workers and takes handed-over frames | HID driver, `InterlockedOr` at each map and every 256 frames, `InterlockedAnd` at a recycle and as its device goes | SDK, every frame |
| 8 | the companion's capabilities: 0x1, it counts its parked requests | companion, `InterlockedOr` at add | SDK, every Xbox 360 frame |
| 64 | `InputWaiters`, the HID workers inside a counted wait | HID driver, interlocked increment and decrement | SDK, every frame |
| 68 | `InputHandoff`, a frame handed to a worker instead of signaled: its even SeqNo once final, the SeqNo with its low bit set while provisional, or 0 | SDK, interlocked exchange and compare-exchange. HID driver, interlocked exchange with 0 | both |
| 128 | `CompanionParked`, the WAIT_FOR_INPUT requests the companion holds | companion, interlocked increment and decrement | SDK, every Xbox 360 frame |

Each counted word has a cache line of its own, since two driver hosts write them. `InputHandoff` shares `InputWaiters`'s line: the same two parties touch both, in the same exchange. The SDK creates the section in `SharedMemoryIO.EnsureInputMapping` after the owner pipe and after it zeroes the input section, before the input event, with the SDDL of its other sections, and the transport allocator skips an index whose section another program owns (`IndexSections`). A create that fails at the owner pipe has written nothing in it. The SDK never zeroes an existing section: one that already exists is held by a driver host of a device on the index, or by the XUSB companion, which maps it at add and keeps it until its release, and a driver host may be counting in it. It leaves `InputHandoff` as it finds it. A final SeqNo the program before it left there is a read the worker still owes, and this program's first frame replaces it (step 3 below), as that program's left signal woke v2.0.3's worker for this program's first frame. A provisional one the worker's next take drops. It writes the capability bits again in one case: a sweep that removes the device of an index the program still holds clears them (`SharedMemoryIO.ForgetDriverLocked`), so a device the next create makes there gets every signal until its own driver host counts itself and sets its bit again. The SDK uses an existing section only when its layout is 1 and Administrators or SYSTEM own it. Otherwise it lets go of it and signals every frame. A driver host maps the section once and keeps it until its device goes, as it keeps the acknowledgement, so the name stays bound to the same object across programs on the index.

The HID driver sets its bit at each map of the input section and every 256 frames, and clears it at a recycle and as its device goes (`CloseGate`), each time while it still holds the input event. A driver host that crashes runs neither, and its bit stays set until a sweep clears it or the next context maps the section. A crash inside a counted wait leaves `InputWaiters` one high, so the SDK signals every frame. One outside it leaves the count where it was, the SDK hands frames over while it is zero, and the next context's worker takes them at its first wait: no reader exists in between. The companion sets its bit at add.

## The input event

The worker (`SharedInputWorkerProc` in `driver/driver.c`), with the signal section mapped, before each wait on the input event:

1. `InterlockedIncrement(&InputWaiters)`. An increment that leaves the count below one shows it was negative, which no correct run produces, and the worker clears its capability bit, which sends the SDK back to a `SetEvent` on every frame.
2. `InterlockedExchange(&InputHandoff, 0)`, the take. A final SeqNo is a frame handed over: `InterlockedDecrement`, and the wait polls the other events with a zero timeout, which stands for the input event, so the stop, owner and remove events keep their order on every pass. The section is read then, and the read sends whatever new frame the section holds: the frame taken, or a newer one its program stored since. When the poll returns the stop event, at a foreign stop or at teardown, the worker calls `SetEvent` on the input event for the frame and leaves its loop. v2.0.3's wait returned the stop event first too and left the program's signal set, so the recycled worker or the next device context read the frame, and they read it here the same way. At teardown with any other result of the poll, the owner pipe, the remove event, the input event or the timeout, the worker leaves with the frame unread and signals nothing. In that window v2.0.3's wait returned the program's signal, and its worker left with that wake spent. A signal back gave the next device context a wake v2.0.3's never had. In the delivery model's witnesses that wake sent a frame twice or, with SeenSeqNo left at that frame's SeqNo, lost a later one, and in `x14-take-at-teardown-*` it sends the taken frame, never sent before, on the device added again, where 533ca4a4 sends it on neither. A read that has begun is not undone: v2.0.3's wait had returned the signal by then and read it the same way, and a READ_REPORT that comes late can still take the frame from the cache, so a frame signaled back after its read would go out twice (`x11-take-read-late-read-teardown`). A provisional SeqNo is dropped, and the worker waits counted: its program, rechecking, finds it taken and signals the frame.
3. Otherwise wait, with the 500 ms timeout as before.
4. `InterlockedDecrement(&InputWaiters)` as the wait returns, before anything else.

When the poll returns the owner pipe's close, the worker reads the frame and then waits again before it handles the close. The owner read's event is manual-reset and stays set, so an input event a program set meanwhile is taken first, as v2.0.3's wait took it.

The SDK (`SharedMemoryIO.WriteInputFrame`), after the frame:

1. Store the even `SeqNo` with release order (`Volatile.Write`).
2. Read the HID driver's capabilities. Without the capability, a full fence (`Thread.MemoryBarrier`, which the companion's count below needs) and a `SetEvent`, as before.
3. With it, read `InputHandoff`. A final SeqNo still there is a read the worker owes, which will find this frame too: `Interlocked.CompareExchange(ref InputHandoff, SeqNo, that SeqNo)` puts this frame's final SeqNo in its place, a full fence, and no `SetEvent` runs. When a worker took that SeqNo first, the compare-exchange fails and the next step follows.
4. Otherwise read `InputWaiters`. With a worker counted, the frame is signaled as v2.0.3 signaled every frame: `Thread.MemoryBarrier()` when the frame has a companion event, then the `SetEvent` of step 6, with `InputHandoff` untouched and step 5 skipped. With none, `Interlocked.Exchange(ref InputHandoff, SeqNo | 1)`, the provisional SeqNo, a full fence.
5. Read the capabilities and `InputWaiters` again. With the capability still set and the count zero, `Interlocked.CompareExchange(ref InputHandoff, SeqNo, SeqNo | 1)` makes the frame final, and no `SetEvent` runs. Otherwise `Interlocked.CompareExchange(ref InputHandoff, 0, SeqNo | 1)` takes it back.
6. `SetEvent`, unless step 3 or 5 left the frame final. A compare-exchange that fails in step 5 found the provisional SeqNo taken, and the worker dropped it.

Under a program that submits once a millisecond the worker is back in its wait before every frame, so step 4 finds it counted and the frame costs three loads, of the capability, the handoff and the count, and the `SetEvent`. A frame with a companion event adds `Thread.MemoryBarrier()` after those three loads, before the companion's count is read and before the `SetEvent`. Without that branch every such frame paid for the provisional exchange, the second load of the count and the take-back, two locked operations on the line the worker writes on every pass.

### Why no wakeup is lost, and none is doubled

Call the worker's increment I and its take T, and the SDK's exchange X and its read of the count L. Both sides put full fences between their writes and their reads: `InterlockedIncrement` and `InterlockedExchange` each "generate a full memory barrier (or fence) to ensure that memory operations are completed in order" (Microsoft Learn), and .NET's `Interlocked` methods are full fences ("Full-fence operations", docs/design/specs/Memory-model.md in dotnet/runtime). So either T sees X, or L sees I. This is the store-buffering pattern, and full fences forbid its relaxed outcome on x64 and ARM64.

- T sees X. The worker takes the provisional SeqNo and drops it. The SDK's compare-exchange in step 5 fails, and the SDK signals.
- L sees I. The worker does not decrement until its wait returns, so L reads at least one, and the SDK takes the frame back and signals. The input event is auto-reset: a wait that has not started yet finds it set, and one already blocked returns.

Step 4's read of the count has no fence before it, and needs none. A count above zero belongs to a worker that has not yet decremented after its wait, so the wait it is in, or its next one after a take that finds nothing of this frame, returns this frame's `SetEvent`. Signaling a synchronization object and waiting on one each order memory around them ("Synchronization and Multiprocessor Issues", Microsoft Learn), so the read after that wait finds the frame. A zero, read before or after a worker's increment, leads to the exchange and the recheck, where the pair above decides. The branch leaves `InputHandoff` alone, so the `SetEvent` is the frame's one wakeup. The branch has no interlocked operation, and the .NET memory model does not order a volatile read after an earlier volatile write (docs/design/specs/Memory-model.md in dotnet/runtime): x64 lets the load pass the store, and on ARM64 with LRCPC `Volatile.Read` is `ldapr`, which can pass an earlier `stlr`. So for every frame with a companion event `Thread.MemoryBarrier()` runs before the companion's count is read, whether or not the doorbell then rings, and keeps the even SeqNo's store ahead of that read ("Why the last frame is served").

A frame left final (step 3 or 5) is read by the next take. A recheck that found no worker counted means the worker is outside its counted wait, so its next step on the handoff is a take at its loop top, before any wait. A worker that counted itself after the recheck and took before the frame turned final found the provisional SeqNo, and that case signals. A final SeqNo replaced in step 3 was still waiting for its take, so that take reads the section after this frame's store. Every frame gets a wakeup that reads the section after its store, a take or a signal. A read sends the section's frame only when its SeqNo differs from the last one sent, so a frame that gets both, read by an earlier frame's take and woken again by its own, goes out once.

A program killed after its exchange in step 4 and before its compare-exchange leaves a provisional SeqNo with no signal. A take drops it: v2.0.3, whose program died before its `SetEvent` in the same order, read nothing for that frame. A program killed after the frame turned final has it read by the next take, as v2.0.3 read a frame whose program died after its `SetEvent`. A program killed between a frame's store and its first step on the handoff leaves the frame with no handoff of its own: a final SeqNo of an earlier frame, still waiting for its take, reads it, as v2.0.3's left signal of that earlier frame did, and otherwise nothing does, as on v2.0.3. The same holds for a kill between step 3's read and its compare-exchange, since the SeqNo it read is still there. Earlier 2.1.0 builds exchanged the final SeqNo at once, and a frame left by a program killed before its recheck was read by a take that came before the pipe's close: sent where v2.0.3 never sent it, after the program's release frames when `OwnerGone` came first, or, with the next program started, read early and sent again after `OwnerGone` forgot the SeqNo.

On an ARM64 core without the v8.1 atomics the compiler's `InterlockedIncrement` is an `ldaxr`/`stlxr` loop with no `dmb` after it, which lets a later load run ahead of the store. The worker and the companion's IOCTL thread put `MemoryBarrier()` after their increments on ARM64, the fence .NET's JIT emits after the same loop for a full-fence `Interlocked` (`codegenarm64.cpp`).

Several workers on one named event, the orphan case of issue #38, each count themselves and take before they wait, so the count is zero only when none of them is inside a counted wait, and one of them takes any frame handed over. A `SetEvent` wakes one waiter, as before.

The 500 ms timeout wakes the worker as before and changes nothing here. A recycle closes the gate before it closes the input event (`CloseGate`): it clears the capability, a full fence, then takes the handoff. A final SeqNo becomes a `SetEvent` on the input event, a frame already sent included: its take was owed, and after the recycle forgets SeenSeqNo the recycled worker reads the section as v2.0.3's left signal had it read. A provisional SeqNo is dropped: the SDK reads the capability again after its exchange, so it sees the capability gone or its frame taken, and signals the frame itself. In Phase 1 the worker waits uncounted on the stop event and the owner read, with the gate closed, so every frame signals, and the next map sets the capability again. The device's going closes the gate the same way, while the input event is still open. Teardown returns from the wait and decrements before it checks `TearingDown`. A frame the worker took before either is in the handoff no more. It becomes a `SetEvent` when the worker's poll returns the stop event, as v2.0.3's signal stayed set, and at teardown with any other result of the poll it goes unread, as v2.0.3's spent signal did (step 2). So `CloseGate` and the worker's own exit together leave each final frame the wakeup v2.0.3's signal had. The release keeps the section mapped when its 2 s join of the worker times out, since a worker still running counts in it.

### What the argument assumes

Every waiter on the index's input event is a 2.1.0 worker that has the section mapped, or none has announced the capability. A USB/IP device's input pump also waits on the event and counts itself nowhere, so the SDK never gates a USB/IP controller (`HMController._signalView`). A device context of an older driver beside one of this driver on the same index would break the assumption: the newer one's capability would let the SDK hand frames over that the older one waits for. Two contexts share an index only while one of them tears down, and the SDK installs only a newer driver over an older one, so such a pair needs a downgrade with a device still tearing down. While it lasts, a frame handed over waits for the newer worker's take, or for the older worker's next signal.

## Which frame is new

v2.0.3's worker read only after a signal and kept one number, the last SeqNo it sent (`SeenSeqNo`): a frame went out when its SeqNo differed. Three steps forgot it, the owner pipe's close (`OwnerGone`), the recycle after idle timeouts or stale wakeups, and the add of a device, so that a program before 2.1.0 starting next, which counts from 0, has its frame equal to the last one sent go out. This driver keeps the frame read last, its SeqNo and its data (`SameAsSeen`): a frame goes out when either differs. The add forgets it. `OwnerGone` and the recycle keep it, and forget it only with a frame no read carried that they drop, as v2.0.3's reset dropped that frame, so a wakeup that reads it again sends it once. Through e9a6e92d they forgot it as v2.0.3 did, and a frame already sent went out again on the next wakeup that read it. The gate changes only how a read is woken: a take stands for a signal, one for one.

A program before 2.1.0 that starts next counts from 0 and can store a frame on the SeqNo read last with other data. v2.0.3 took it for the frame read last and skipped it, for good when no reset forgot the SeqNo after. This driver sends it, with three exceptions where v2.0.3's skip keeps the order. While a frame read since the last reset waits for a read, the new frame is skipped, and the frame waiting goes out as there. Once the watched program's pipe closed and before `OwnerGone` runs, the new frame is the next program's, which must not go ahead of the release frames `OwnerGone` queues: it is skipped, and the worker reads the section again right after `OwnerGone` (`SkippedAtEnd`). Both apply only when the frame read last was read since the last reset (`SeenSinceReset`), when v2.0.3's SeqNo is the same. After a reset v2.0.3 forgot the SeqNo and read the new frame, and so does this driver, and a frame the reset kept gives way to it. A device context's first read takes a frame on SeqNo 0 for no news, as v2.0.3's SeenSeqNo, 0 from the add, took it: the context before it may have sent that frame.

Earlier designs of 2.1.0 woke the read by comparing the section's SeqNo with a copy of the last frame read, and each copy (`GateSeq`, `DriverSeenSeq`, a SeenSeqNo carried to the next device) could go stale across a program or a device and lose or repeat a frame. The handoff carries no such copy across anything. Three rules keep a handoff from outliving the program and the worker it belongs to:

- A recycle and a device's going close the gate while the worker still holds the input event (`CloseGate`). A final frame still in the handoff becomes a `SetEvent` on the program's own input event, which goes with the program, as v2.0.3's signal did. No handoff waits in a section the companion holds across a program's end.
- `OwnerGone` leaves the handoff alone. A provisional SeqNo there is the ended program's, left as it died inside its handoff, or the next program's, whose SDK signals it, and the next take drops it. A final SeqNo there is the next program's: a program's final frames come while the worker is outside its counted wait, so the worker takes them at its next loop top, before any wait that could return that program's pipe close. The next program can make its owner pipe as soon as this program's server ends close, with the driver's client handle still open: `FILE_FLAG_FIRST_PIPE_INSTANCE` then succeeds (measured 2026-10-25). The next take reads its frame after `OwnerGone`'s reset, as v2.0.3 read that program's signal after `OwnerGone`, and the frame reaches the read cache after that reset. The owner watch is retried at a map or every 256th frame, as v2.0.3 retried it. Retried at the next frame, it watched a program that started inside the idle window, and that program's end ran an `OwnerGone` v2.0.3 did not, whose reset hid the program's last frame, cached with no read parked, from the read that came after.
- A take of the frame the worker sent last reads the section, as v2.0.3's worker read on the left signal of a frame it had read. The read finds that frame and sends nothing, or a newer frame its program stored and died before handing over, which has no other wakeup. A newer frame of a program still running is read again on its own take or signal and sent once. When the last program's final frame was still waiting for its take as the next program wrote its first frame, that take reads the next program's frame early. Through e9a6e92d `OwnerGone` then forgot the SeqNo, and that program's own take or signal sent the frame again, as v2.0.3 sent it twice on the last program's signal. `OwnerGone` now keeps the frame read last, and that read finds it and sends nothing.

An SDK zeroes the input section as it maps the index. SeqNo 0 with no data is that zeroed section, and the worker sends nothing for it. v2.0.3 read it as a frame when an input event left set for the last program's frame found it: SeenSeqNo became 0, and the read cache took an all-zero report at SeqNo 0 and sent it to a read parked. This driver does the same apart from that read: SeenSeqNo and the cache's SeqNo go to 0, the polled reports take the all-zero report, and no READ_REPORT completes with it. A program before 2.1.0 that starts next counts from 0, so its first frame, SeqNo 2, goes out even when the last frame the worker sent carried SeqNo 2, and a READ_REPORT that comes late parks instead of taking the last program's frame from the cache a second time. A polled `GET_INPUT_REPORT` returns the all-zero report, as v2.0.3's did, so a polling caller no longer sees the last program's buttons held. With `LiveFeatureReport` the feature report's answer goes empty, as v2.0.3's did.

A 2.1.0 SDK never stores SeqNo 0: at the wrap, every 2^31st frame, its SeqNo steps from 0xFFFFFFFF to 2 (`SharedMemoryIO.NextEvenSeq`), so a handoff of 0 always means none. It also counts from above the SeqNo the program before it left (`SharedMemoryIO.InputSeqStart`), so its frames never repeat the last one sent. A program before 2.1.0 stores 0 with its frame at its wrap and signals it, and that frame goes out as v2.0.3 sent it. A READ_REPORT with no frame parked takes the cached frame no read carried when its SeqNo comes after the one last delivered in serial number arithmetic (RFC 1982, `CachedAfterDeliveredLocked`), or when none was delivered since a reset. So a read that comes after the frame past the wrap takes it, where 533ca4a4's greater-than test parked it until the next frame. The resets are `OwnerGone`, the recycle, the add, and a next program's start that the worker reads with no watch open: a frame whose SeqNo repeats or goes back from the frame read last, or a zeroed section after a frame. Without that last reset a read that came after the next program's frame parked beside it until that program's SeqNo passed the last one's. It happens in the cache write of the frame read (`RestartSeen`): reset any earlier, a read that took the last frame cached before that write moved the gate back to the last program's SeqNo, and the read path's model found the order. A frame read once the watched program's pipe closed keeps the greater-than test until `OwnerGone`: it can be the next program's, carrying a SeqNo below the last program's last one delivered, and a read served it ahead of the release frames `OwnerGone` queues.

`OwnerGone` and the recycle keep a frame no read carried, where v2.0.3's reset dropped it and readers kept the state before it, a button it let go of held, until a next program sent. With release frames queued, `OwnerGone` puts it ahead of them, out of the cache, the program's last report before they let go of everything, and with none it stays the frame a late read takes, published again (`InputPublishCount`), so a READ_REPORT whose look the reset passed takes it in its second look. A frame read once the watched pipe closed goes beside release frames as at v2.0.3, since it can be the next program's, and so does the first frame a device context read, which the context before it may have sent, and a frame wider than a release slot. The recycle drops both too, since the `OwnerGone` that Phase 1 runs may queue release frames.

## The companion doorbell

The companion (`driver/companion.c`) completes parked `IOCTL_XUSB_WAIT_FOR_INPUT` requests in turns of its pump (`CompanionServeReaders`), which its pump thread runs when the doorbell rings or its kick event is set, and its 8 ms timer runs on each tick. Each handle a caller opens is a reader, and a turn serves every reader that has not had the newest frame, through that reader's oldest request (Every reader once, below). One frame can wake the pump twice, by its ring and by the kick of a request that parked as it was written, and the second turn finds every reader served.

- The IOCTL thread forwards the request to the manual queue, then, with the signal section, `InterlockedIncrement(&CompanionParked)`, then reads `SeqNo` under `GipLock`. When the request's reader has not had that frame, it sets the pump's own kick event. Every companion under the version contract, which alone registers the XUSB interface, makes the kick event, with the section or without it, and the pump waits on it even while the doorbell is closed.
- A turn decrements once it takes a request (`CompanionServeReaders`), and `EvtIoCanceledOnQueue` decrements for a request the framework cancels or purges, which it calls for every request it presented to the driver (Windows-Driver-Frameworks `fxioqueue.cpp`, `CancelForQueue`).
- The SDK rings the doorbell only when the companion's capability is clear or `CompanionParked` is not zero, after a full fence: the input event's compare-exchange or exchange, or `Thread.MemoryBarrier()` where the input event's step has no interlocked operation (no capability, or a worker counted).

The pump can take a request before its increment, so the count can be -1 for a moment. The SDK rings on any count but zero.

### Why the last frame is served

The IOCTL thread's increment and its read of `SeqNo` face the SDK's store and its read of the count across full fences, as on the input event. Either the SDK sees the request counted and rings, and the pump wakes after the request is in the queue, or the IOCTL thread sees the frame and kicks the pump. In both cases the pump reads the section after the frame was stored and serves it.

This closes a gap the doorbell had before 2.1.0. The pump could take a frame's ring before Windows.Gaming.Input sent its next request, and that request then waited for the next frame or the 8 ms timer. With the kick it waits for nothing. Without the section the SDK rings for every frame: it stores the `SeqNo` before its `SetEvent`, and the pump reads the section and looks at the queue after its wait returns that ring. Either that look found the request, parked before it, or the IOCTL thread's read, after the park, finds the frame and kicks. Through 2.1.0's gate rounds the kick was made only beside the section, so a program before 2.1.0 kept the gap: in `signal-stress` its Xbox 360 pass read 235 frames over 2 ms of 122,571 where the 2.1.0 SDK read none (SIG-stress-3).

### Every reader once

An Xbox 360 pad has several readers at once: a trace found requests of Windows.Gaming.Input, explorer and GameInputSvc parked together. Through d4103a21, as in v2.0.3, a turn completed one request, the oldest in the queue. One reader got a frame at once and the others on the timer's next ticks, 11 to 29 ms later in that trace, and a reader with two requests parked got one frame on both, the second from a tick.

xusb22 keeps one list of the waits parked through every handle of a controller. For each report from the pad it completes every one whose process passes its focus test, each with the same state, and puts the rest back. It has no timer. (xusb22.sys 10.0.26100.9549, read with its public symbols: `XInputControllerDevice::HandleWaitOrUnfilteredRequest` parks the wait, and `ProcessWaitRequests` completes them, called only from `HandleIncomingStateReport`, which `GamepadInformation::ProcessReport` runs for each report.) On real hardware every reader gets each report, once for each request it has parked.

The companion gives every handle a reader context (`WdfDeviceInitSetFileObjectConfig`, a `COMPANION_READER` on each `WDFFILEOBJECT`) and joins it to its readers at the handle's first WAIT_FOR_INPUT, under `ReadersLock`, before the request enters the queue. A turn takes `ReadersLock` and reads the section once. For each reader whose last completion carried another frame, it takes that reader's oldest request (`WdfIoQueueRetrieveRequestByFileObject`, which removes the first request of that file object under the queue's lock: Windows-Driver-Frameworks `fxirpqueue.cpp`, `RemoveNextIrpFromQueue`), writes the frame's SeqNo into the reader and completes the request, all before it releases the lock. So turns run one at a time, each new frame reaches every reader once, and a reader with several requests parked gets one a frame and never the same frame twice, where xusb22 would complete them all with one report. No reader gets a frame older than one it had, since each turn serves the newest frame and completes inside the lock.

The timer runs the same turn and serves only a reader that lacks its frame: a frame no ring or kick brought, under an SDK before the doorbell or while a recreated doorbell is not open yet. The pad reports the states it sends and xusb22 completes nothing on a timer, so nothing here goes from the timer to a reader that has the frame. A reader's first request gets the state there is, a frame or none, which fires Windows.Gaming.Input's `OnInputResumed`. A buffer under 29 bytes fails at dispatch, as xusb22 fails it (`DispatchWaitForInput`), so no reader counts as served without its frame. A reader that parks after a turn passed it kicks the pump itself: its look compares the section with its own reader's frame, and another reader's completion says nothing about this one's.

The handle's close takes its reader out under `ReadersLock` (`EvtFileClose`). The I/O manager sends the close only after every request through the handle completed, and the framework cancels the handle's parked requests at its cleanup, before the close (`fxpkggeneral.cpp`, `OnCleanup`, and `fxioqueue.cpp`, `FlushByFileObject`). A turn costs one look at the section, a decode when a reader lacks the frame, and a retrieve and a completion for each reader served.

## Parking a read

`IOCTL_HID_READ_REPORT` takes a report at once when one waits: a release frame `OwnerGone` queued, or the cached frame when no read has carried it (`InputReportPending`) and it comes after the last one delivered (Which frame is new). Otherwise the read parks in the manual queue. The worker hands each frame it reads to a parked read. Through b0fb7dc9, as in v2.0.3, both sides lost a wakeup. The handler looked under `InputLock` and parked after releasing it, and `ProcessSharedInput` took a read from the queue and only then cached the frame: a read that looked before the cache write and parked after the worker's look at the queue waited beside the frame until the next one, for every profile, and with no idle repeat for as long as the program paused. The release frames had the same window against `OwnerGone`, and a key the program held stayed down until the read got its release frame.

Both sides now publish before they look:

- The worker caches the frame under `InputLock`, marks it pending and counts it (`InputPublishCount`), then takes reads from the queue (`DeliverParked`), each with the next report under `InputLock` (`TakeReportLocked`: a release frame first, the program's last frame `OwnerGone` put ahead of them among them, then the pending frame, which it clears, notes for the acknowledgement and moves the delivered gate to). `OwnerGone` queues its release frames the same way, and `DeliverParked` replaces `DeliverReleaseFrames`.
- A READ_REPORT that parks looks again under `InputLock` once it is in the queue, and calls `DeliverParked` when a release frame waits or a frame was cached since its first look. Such a frame came while the read waited, and a read parked a moment earlier gets it from the worker whatever its SeqNo, so this read does too. A frame cached before the first look stays under the late read's test.
- A read `DeliverParked` took and found nothing for goes back to the head of the queue (`WdfRequestRequeue`), and that is a park too: while its thread held it, the worker could cache a frame and find the queue empty. So the loop looks again after the requeue, for a frame cached since it found nothing.
- A read completes inside the critical section of `InputLock` that took its report, in `DeliverParked` and in the READ_REPORT that takes the cache at once (Completion order, below).

Every queue operation runs under the queue's lock, a critical section in UMDF (Windows-Driver-Frameworks: `MxLockNoDynam::Acquire` in `mxlockum.h`, and `GetRequest`, `QueueRequestFromForward` and `Requeue` in `fxioqueue.cpp`), and `InputLock` is an SRW lock. If the worker's retrieve comes before a read's park in the queue lock's order, then the cache write, which comes before the retrieve, comes before the read's second look in `InputLock`'s order, so the look finds the frame. Otherwise the retrieve finds the read. A take that finds the frame already taken puts the read back, and one frame goes to one read (issue #8).

`WdfIoQueueReadyNotify` gives the same order. The framework calls it after the request is in an empty queue, on the forwarding thread with the queue's lock released, unless that thread is at raised IRQL with a passive-level queue or holds the queue's presentation lock (`fxioqueue.cpp`, `ProcessReadyNotify`, `CanThreadDispatchEventsLocked`), and neither applies here. So it runs at the second look's place, through the framework's dispatch loop. With one read outstanding every park empties into it, and every frame would pay that framework call where the second look costs one uncontended SRW pair. The worker would still have to publish before it retrieves. The second look adds no system call and no framework call when no race occurs: the worker and a parked READ_REPORT each take one more uncontended SRW pair a frame, and the companion's turn one critical-section pair and one SRW pair a ring, about 10 ns each on the development laptop (an offline loop, median of 21 runs of 2,000,000 pairs).

The references park reads the same way and differ only in what wakes them. vhidmini2 and DMF's VirtualHidMini, which DsHidMini uses, park every read and complete them from a timer or the device's next report with the current state. vJoy parks every read, completes one when the feeder loads a position, gated by a dirty bit its read clears (`PositionReady`), and keeps a timer as a backstop. WinUHid's producer publishes before it retrieves and puts back a request whose event another took, while its `GET_NEXT_EVENT` parks after its look with no second one, the window this driver had. None of them caches a frame for a late read, which is what needs the second look here.

### Completion order

Through 81e1fe40, as in v2.0.3, a read completed after `InputLock`, and HID class's completion routine runs on the completing thread. A thread that took frame N and lost the processor before its completion let another thread take N+1 and complete it first, and HID class's buffer got N+1 and then N. A reader on a test machine got frame 99,670 and then 99,669. Each read now completes inside the critical section that took its report, so reads complete in the order their reports were taken.

Completing calls back into none of this driver's code. In UMDF the IRP goes to the host on the completing thread (Windows-Driver-Frameworks `shared/core/um/fxirpum.cpp`, `FxIrp::CompleteRequest`), and the request's queue then runs only its own events (`fxioqueue.hpp`, `RequestCompletedCallback`, and `fxioqueue.cpp`, `DispatchEvents`), for which neither queue here registers a callback. HID class's next READ_REPORT reaches the driver as a new request on another thread and waits for `InputLock` no longer than one completion. Inside the critical section the acknowledgement also stays after the completion of the frame it names.

A single completer would keep the order as well. vhidmini2 completes every read from its timer, and DsHidMini from its one input path. This driver serves a late READ_REPORT on that READ_REPORT's own thread, though, and handing it to the worker would put a `SetEvent` and a thread switch on that path. The lock adds no call: per frame the same lock pairs and framework calls run, and the completion moves into the critical section that took the frame. Its cost is the wait above, for a thread that comes during a completion. vJoy and WinUHid complete after their locks, as this driver did.

## The acknowledgement event

`HMController` waits on `Global\HIDMaestroInputAckEvent<N>` only to deliver every report of a keyboard or mouse (`DeliversEveryReport`) and for a protocol host's replies (`ProtocolHost`). At create the SDK writes `Controller<N>\AckSignal`, 0 when neither applies (`DeviceOrchestrator.WaitsOnDelivery`). The driver reads it at add, under the contract, and with 0 stores `DeliveredSeqNo` on every delivery as before and skips only the `SetEvent`. A value it cannot read, or none, which is every program before 2.1.0, and it signals every delivery.

## The locks

`InputLock`, `OutputLock` and `FeatureLock` are `SRWLOCK`s in the zeroed device context, taken exclusive only. `SRWLOCK_INIT` is `{0}` (winnt.h, `RTL_SRWLOCK_INIT`), so the context's zeroing initializes them, and an SRW lock needs no deletion. Acquire and release order the data they guard on x64 and ARM64. WinUHid guards its HID request state the same way (`WinUHid.cpp`). A read is completed under `InputLock` (Completion order, above), so a thread can wait there for one completion.
