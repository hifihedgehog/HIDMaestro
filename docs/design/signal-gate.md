# Design note: the signal gate

Release 2.1.0 skips kernel transitions a frame does not need. Before it, every frame cost the SDK a `SetEvent` on the driver's input event, every Xbox 360 frame a second one on the XUSB companion's doorbell, and every delivered frame cost the driver a `SetEvent` on the delivery acknowledgement's event. The HID driver also took its locks through UMDF's wait lock, which is an auto-reset event (Windows-Driver-Frameworks `mxeventum.h`, `MxEvent::WaitFor` and `MxEvent::Set`): two system calls for every acquire and release, twice a frame. This note gives the protocol that drops what nobody waits for, the argument that it loses no wakeup, and the checks that back the argument.

## What changes

| Cost | Who pays | After |
|---|---|---|
| The HID driver's three locks | the driver host, twice a frame | slim reader/writer locks, user mode while uncontended |
| `SetEvent` on the input event | the SDK, every frame | only while a worker waits on it |
| `SetEvent` on the companion doorbell | the SDK, every frame with GIP bytes | only while a WAIT_FOR_INPUT is parked |
| `SetEvent` on the acknowledgement's event | the driver host, every delivered frame | only for a controller whose SDK waits on it |

No existing section layout, named object or profile id changes. The new words live in a new section, and each skip waits on a capability the driver host announces, so a program before 2.1.0 on the new driver, and a 2.1.0 program on an older driver, signal and acknowledge exactly as before.

## The section

`Global\HIDMaestroSignal<N>`, 256 bytes, `HIDMAESTRO_SIGNAL` in `driver/hm_contract.h`:

| Offset | Field | Written by | Read by |
|---|---|---|---|
| 0 | layout version, 1 | the SDK, once, when it creates the section | both drivers, at map |
| 4 | the HID driver's capabilities: 0x1, it counts its workers and takes handed-over frames | HID driver, `InterlockedOr` at each map and every 256 frames, `InterlockedAnd` at a recycle and as its device goes | SDK, every frame |
| 8 | the companion's capabilities: 0x1, it counts its parked requests | companion, `InterlockedOr` at add | SDK, every Xbox 360 frame |
| 64 | `InputWaiters`, the HID workers inside a counted wait | HID driver, interlocked increment and decrement | SDK, every frame |
| 68 | `InputHandoff`, the SeqNo of a frame handed to a worker instead of signaled, or 0 | SDK, interlocked exchange and compare-exchange. HID driver, interlocked exchange with 0 | both |
| 128 | `CompanionParked`, the WAIT_FOR_INPUT requests the companion holds | companion, interlocked increment and decrement | SDK, every Xbox 360 frame |

Each counted word has a cache line of its own, since two driver hosts write them. `InputHandoff` shares `InputWaiters`'s line: the same two parties touch both, in the same exchange. The SDK creates the section in `SharedMemoryIO.EnsureInputMapping` after the owner pipe and after it zeroes the input section, before the input event, with the SDDL of its other sections, and the transport allocator skips an index whose section another program owns (`IndexSections`). A create that fails at the owner pipe has written nothing in it. The SDK never zeroes an existing section: one that already exists is held by a driver host of a device on the index, or by the XUSB companion, which maps it at add and keeps it until its release, and a driver host may be counting in it. It does clear `InputHandoff` at its start, since that names a frame of the input section it has just zeroed. It writes the capability bits again in one case: a sweep that removes the device of an index the program still holds clears them (`SharedMemoryIO.ForgetDriverLocked`), so a device the next create makes there gets every signal until its own driver host counts itself and sets its bit again. The SDK uses an existing section only when its layout is 1 and Administrators or SYSTEM own it. Otherwise it lets go of it and signals every frame. A driver host maps the section once and keeps it until its device goes, as it keeps the acknowledgement, so the name stays bound to the same object across programs on the index.

The HID driver sets its bit at each map of the input section and every 256 frames, and clears it at a recycle and as its device goes (`CloseGate`), each time while it still holds the input event. A driver host that crashes runs neither, and its bit stays set until a sweep clears it or the next context maps the section. A crash inside a counted wait leaves `InputWaiters` one high, so the SDK signals every frame. One outside it leaves the count where it was, the SDK hands frames over while it is zero, and the next context's worker takes them at its first wait: no reader exists in between. The companion sets its bit at add.

## The input event

The worker (`SharedInputWorkerProc` in `driver/driver.c`), with the signal section mapped, before each wait on the input event:

1. `InterlockedIncrement(&InputWaiters)`. An increment that leaves the count below one shows it was negative, which no correct run produces, and the worker clears its capability bit, which sends the SDK back to a `SetEvent` on every frame.
2. `InterlockedExchange(&InputHandoff, 0)`, the take. A SeqNo other than 0 is a frame handed over: `InterlockedDecrement`, and the wait polls the other events with a zero timeout, which stands for the input event, so the stop, owner and remove events keep their order on every pass. The frame is read then. When the poll returns the stop event, or `TearingDown` is set, the worker leaves its loop without reading and calls `SetEvent` on the input event for the frame instead. v2.0.3's wait returned the stop event first too and left the program's signal set, so the recycled worker or the next device context read the frame, and they read it here the same way. A take of the frame the worker sent last reads the section too (see "Which frame is new").
3. Otherwise wait, with the 500 ms timeout as before.
4. `InterlockedDecrement(&InputWaiters)` as the wait returns, before anything else.

When the poll returns the owner pipe's close, the worker reads the frame and then waits again before it handles the close. The owner read's event is manual-reset and stays set, so an input event a program set meanwhile is taken first, as v2.0.3's wait took it.

The SDK (`SharedMemoryIO.WriteInputFrame`), after the frame:

1. Store the even `SeqNo` with release order (`Volatile.Write`).
2. Read the HID driver's capabilities. Without the capability, a full fence (`Thread.MemoryBarrier`, which the companion's count below needs) and a `SetEvent`, as before.
3. With it, `Interlocked.Exchange(ref InputHandoff, SeqNo)`, a full fence.
4. Read the capabilities and `InputWaiters` again. With the capability still set and the count zero, the frame stays handed over and no `SetEvent` runs.
5. Otherwise `Interlocked.CompareExchange(ref InputHandoff, 0, SeqNo)`. When it takes the SeqNo back, `SetEvent`. When a worker took the frame first, nothing.

### Why no wakeup is lost, and none is doubled

Call the worker's increment I and its take T, and the SDK's exchange X and its read of the count L. Both sides put full fences between their writes and their reads: `InterlockedIncrement` and `InterlockedExchange` each "generate a full memory barrier (or fence) to ensure that memory operations are completed in order" (Microsoft Learn), and .NET's `Interlocked` methods are full fences ("Full-fence operations", docs/design/specs/Memory-model.md in dotnet/runtime). So either T sees X, or L sees I. This is the store-buffering pattern, and full fences forbid its relaxed outcome on x64 and ARM64.

- T sees X. The worker takes the frame and reads it without waiting. The SDK's compare-exchange, if it runs, finds 0 and signals nothing.
- L sees I. The worker does not decrement until its wait returns, so L reads at least one, and the SDK takes the frame back and signals. The input event is auto-reset: a wait that has not started yet finds it set, and one already blocked returns.

Both cannot deliver the frame: the take and the compare-exchange act on one word, and only one of them finds the SeqNo there. A frame taken is read, or signaled when the worker leaves its loop first (step 2). So a frame gets one wakeup, the take or the signal, as v2.0.3's frame got its one signal.

A program killed between its exchange and its compare-exchange leaves its frame in `InputHandoff` with no signal. On v2.0.3 the same order is a program killed after its frame's store and before its `SetEvent`, and that frame never goes out. `OwnerGone` drops it here (see "Which frame is new"), and the frame stays unsent. A take of it before the owner pipe's close reads the section and sends it: the worker reached its loop top first, after a 500 ms timeout or with the exchange landing between its increment and its take. That is one order where this driver sends a frame v2.0.3 does not, and the program's last report is that frame instead of the one before (`x7-kill-stuck-unsent-alone-at-take`). It loses nothing and sends nothing twice. Closing it needs the handoff to tell a frame whose program finished its write from one whose program died inside it, which the protocol above cannot: a two-step handoff, a provisional SeqNo the program makes final once it knows no worker waits, would. If the next program has started by that read, its frames are not sent there (`NextProgramStarted`): they have their own take or signal, and sent early they went out again after `OwnerGone` forgot the SeqNo. A program killed between a frame's SeqNo store and its exchange leaves the frame with no handoff and no signal. A take or signal of an earlier frame that comes after the store reads it, as v2.0.3's left signal of that earlier frame did, and nothing else does, as in v2.0.3.

On an ARM64 core without the v8.1 atomics the compiler's `InterlockedIncrement` is an `ldaxr`/`stlxr` loop with no `dmb` after it, which lets a later load run ahead of the store. The worker and the companion's IOCTL thread put `MemoryBarrier()` after their increments on ARM64, the fence .NET's JIT emits after the same loop for a full-fence `Interlocked` (`codegenarm64.cpp`).

Several workers on one named event, the orphan case of issue #38, each count themselves and take before they wait, so the count is zero only when none of them is inside a counted wait, and one of them takes any frame handed over. A `SetEvent` wakes one waiter, as before.

The 500 ms timeout wakes the worker as before and changes nothing here. A recycle closes the gate before it closes the input event (`CloseGate`): it clears the capability, a full fence, then takes the handoff, and turns a frame taken there and not yet sent into a `SetEvent` on the input event. The SDK reads the capability again after its exchange, so either the take finds the frame or the SDK sees the capability gone and signals the frame itself. In Phase 1 the worker waits uncounted on the stop event and the owner read, with the gate closed, so every frame signals, and the next map sets the capability again. The device's going closes the gate the same way, while the input event is still open. Teardown returns from the wait and decrements before it checks `TearingDown`. A frame the worker took before either is in the handoff no more, and becomes a `SetEvent` as the worker leaves its loop (step 2), so `CloseGate` and the worker's own exit together leave no handed frame without its wakeup. The release keeps the section mapped when its 2 s join of the worker times out, since a worker still running counts in it.

### What the argument assumes

Every waiter on the index's input event is a 2.1.0 worker that has the section mapped, or none has announced the capability. A USB/IP device's input pump also waits on the event and counts itself nowhere, so the SDK never gates a USB/IP controller (`HMController._signalView`). A device context of an older driver beside one of this driver on the same index would break the assumption: the newer one's capability would let the SDK hand frames over that the older one waits for. Two contexts share an index only while one of them tears down, and the SDK installs only a newer driver over an older one, so such a pair needs a downgrade with a device still tearing down. While it lasts, a frame handed over waits for the newer worker's take, or for the older worker's next signal.

## Which frame is new

v2.0.3's worker read only after a signal and kept one number, the last SeqNo it sent (`SeenSeqNo`): a frame went out when its SeqNo differed. Three steps forgot it, the owner pipe's close (`OwnerGone`), the recycle after idle timeouts or stale wakeups, and the add of a device, so that a program before 2.1.0 starting next, which counts from 0, has its frame equal to the last one sent go out. This driver keeps that rule and those three resets unchanged. The gate changes only how a read is woken: a take stands for a signal, one for one.

Earlier designs of 2.1.0 woke the read by comparing the section's SeqNo with a copy of the last frame read, and each copy (`GateSeq`, `DriverSeenSeq`, a SeenSeqNo carried to the next device) could go stale across a program or a device and lose or repeat a frame. The handoff carries no such copy across anything. Three rules keep a handoff from outliving the program and the worker it belongs to:

- A recycle and a device's going close the gate while the worker still holds the input event (`CloseGate`). A frame handed over and not yet sent becomes a `SetEvent` on the program's own input event, which goes with the program, as v2.0.3's signal did. No handoff waits in a section the companion holds across a program's end.
- `OwnerGone` takes the handoff before its reset, while the worker holds the input event. In Phase 1 the gate is closed, and a frame handed over then belongs to another device context on the index (issue #38), which takes it itself. A frame the worker already sent is dropped. So is a frame of the program that ended: it can wait there only when the program died between its exchange and its `SetEvent`, and v2.0.3 never read a frame whose program died before its `SetEvent`, so the release frames stay the last report. A frame of the next program is owed. The next program can make its owner pipe as soon as this program's server ends close, with the driver's client handle still open: `FILE_FLAG_FIRST_PIPE_INSTANCE` then succeeds (measured 2026-10-25). Its frame becomes a `SetEvent` after the reset and the release frames, as v2.0.3's read of that program's signal came after them, and it reaches the read cache after the reset that would otherwise hide it from a late READ_REPORT. Every SDK with an owner pipe zeroes the acknowledgement before its first frame, which clears the release bit the driver set when its watch connected, so a frame taken beside that bit clear is the next program's. The bit is read after the take, and the section's SeqNo after the bit: an SDK zeroes the input section before the acknowledgement (2.1.0 with a full fence between, its clear of `InputHandoff`), so beside a cleared bit the section no longer holds the ended program's frame. A handed frame the section no longer holds is gone, as v2.0.3's was, and the next program's own wakeup reads its frame.
- A take of the frame the worker sent last reads the section, as v2.0.3's worker read on every input event, the left signal of a frame it had read included. The read finds that frame and sends nothing, or a newer frame the program stored since. While the program runs, that newer frame's own take or signal would read it later. A program killed between its store and its exchange leaves no other wakeup for it. A read woken by a take alone sends only the frame taken or the one its program writes after it, and nothing of a program that started since the owner watch connected. Every SDK with an owner pipe zeroes the acknowledgement as it starts, before it writes the input section, which clears the release bit the watch set, so with the bit clear the section holds that program's frames or its zeroing. The worker reads the bit right before the section, with an ARM64 fence between. A v1.11.0 program makes no acknowledgement and counts from 0, so its frames fail the SeqNo test unless one of them repeats the SeqNo after the taken frame. The zeroing is still read, as v2.0.3 read it on the last program's left signal.

An SDK zeroes the input section as it maps the index. SeqNo 0 with no data is that zeroed section, and the worker sends nothing for it. v2.0.3 read it as a frame when an input event left set for the last program's frame found it: SeenSeqNo became 0, and the read cache took an all-zero report at SeqNo 0 and sent it to a read parked. This driver does the same apart from that read: SeenSeqNo and the cache's SeqNo go to 0, the polled reports take the all-zero report, and no READ_REPORT completes with it. A program before 2.1.0 that starts next counts from 0, so its first frame, SeqNo 2, goes out even when the last frame the worker sent carried SeqNo 2, and a READ_REPORT that comes late parks instead of taking the last program's frame from the cache a second time. A polled `GET_INPUT_REPORT` returns the all-zero report, as v2.0.3's did, so a polling caller no longer sees the last program's buttons held. With `LiveFeatureReport` the feature report's answer goes empty, as v2.0.3's did.

A 2.1.0 SDK never stores SeqNo 0: at the wrap, every 2^31st frame, its SeqNo steps from 0xFFFFFFFF to 2 (`SharedMemoryIO.NextEvenSeq`), so a handoff of 0 always means none. It also counts from above the SeqNo the program before it left (`SharedMemoryIO.InputSeqStart`), so its frames never repeat the last one sent. A program before 2.1.0 stores 0 with its frame at its wrap and signals it, and that frame goes out as v2.0.3 sent it. A READ_REPORT with no frame parked takes the cached frame only when its SeqNo is above the one last delivered, as 533ca4a4's test was, so a read that comes after the frame past the wrap parks until the next frame, as there. An earlier 2.1.0 build served any SeqNo but the last delivered. Before `OwnerGone` runs, a next program's first frame can carry a SeqNo below the last program's last one delivered: that test served it to a read 533ca4a4 parked, and the program's own signal sent it again once `OwnerGone` forgot the SeqNo. No test on the two SeqNos can tell the frame after the wrap from such a frame, since a 2.1.0 program's wrap and a next program's start both bring SeqNo 2 after a SeqNo near the top.

## The companion doorbell

The companion (`driver/companion.c`) completes a parked `IOCTL_XUSB_WAIT_FOR_INPUT` from its pump thread when the doorbell rings, and from its 8 ms timer, Windows.Gaming.Input's cadence, which stays. With nothing parked, a ring only wakes the pump to find an empty queue.

- The IOCTL thread forwards the request to the manual queue, then `InterlockedIncrement(&CompanionParked)`, then reads the input section's `SeqNo` under `GipLock`. When the frame is newer than the one the last completion carried (`WaitServedSeq`, stored before each completion), it sets the pump's own kick event.
- The pump, or the timer, decrements once it takes a request (`CompanionPumpOnce`), and `EvtIoCanceledOnQueue` decrements for a request the framework cancels or purges, which it calls for every request it presented to the driver (Windows-Driver-Frameworks `fxioqueue.cpp`, `CancelForQueue`).
- The SDK rings the doorbell only when the companion's capability is clear or `CompanionParked` is not zero, after the same fence as the input event.

The pump can take a request before its increment, so the count can be -1 for a moment. The SDK rings on any count but zero.

### Why the last frame is served

The IOCTL thread's increment and its read of `SeqNo` face the SDK's store and its read of the count across full fences, as on the input event. Either the SDK sees the request counted and rings, and the pump wakes after the request is in the queue, or the IOCTL thread sees the frame and kicks the pump. In both cases the pump reads the section after the frame was stored and serves it.

This closes a gap the doorbell had before 2.1.0. The pump could take a frame's ring before Windows.Gaming.Input sent its next request, and that request then waited for the 8 ms timer. With the kick it waits for nothing. The kick needs the section, so a program before 2.1.0 on this driver keeps the old behavior, gap included: in `signal-stress` its Xbox 360 pass reads 235 frames over 2 ms of 122,571 where the 2.1.0 SDK reads none (SIG-stress-3).

## The acknowledgement event

`HMController` waits on `Global\HIDMaestroInputAckEvent<N>` only to deliver every report of a keyboard or mouse (`DeliversEveryReport`) and for a protocol host's replies (`ProtocolHost`). At create the SDK writes `Controller<N>\AckSignal`, 0 when neither applies (`DeviceOrchestrator.WaitsOnDelivery`). The driver reads it at add, under the contract, and with 0 stores `DeliveredSeqNo` on every delivery as before and skips only the `SetEvent`. A value it cannot read, or none, which is every program before 2.1.0, and it signals every delivery.

## The locks

`InputLock`, `OutputLock` and `FeatureLock` are `SRWLOCK`s in the zeroed device context, taken exclusive only. `SRWLOCK_INIT` is `{0}` (winnt.h, `RTL_SRWLOCK_INIT`), so the context's zeroing initializes them, and an SRW lock needs no deletion. Acquire and release order the data they guard on x64 and ARM64. WinUHid guards its HID request state the same way (`WinUHid.cpp`). The served input report is copied out under `InputLock` and into the request after it, so the worker never waits on the framework's buffer calls.

## Checks

- `test/probes/signal_gate_model` explores every interleaving of the SDK and one or two workers, and of the SDK, the companion's pump and a caller that keeps one WAIT_FOR_INPUT outstanding and sends the next the moment the last completes, each request's IOCTL dispatch on a thread of its own. The SDK's plain stores sit in a store buffer that drains at any later step, and an interlocked operation runs only with the buffer empty. With the exchange in the SDK and the take after the count in the worker, no final state leaves a frame unread. A plain store of the handoff in the SDK, or a take before the count, loses a wakeup, which shows the check finds one. The companion part is as before: with both fences and the kick the last frame is served, and without the kick or the SDK's fence it is not.
- The same probe checks the delivery rules above against 533ca4a4's (`DeliveryModel.cs`), order by order. Each scenario runs two or three programs on an index, each a 2.1.0 or a v2.0.x one, with an owner pipe the driver can open or without (v1.11.0), and keyboards that leave a release frame in the acknowledgement. The next program starts after the worker handled the last one's end or at any time after it. A scenario adds an idle recycle, the device's going and add, a foreign stop, a kill inside one of the first program's frames, the companion holding the signal or input section, or the SeqNo wrap. The device goes as ReleaseIndexObjects runs it: the queues are purged, TearingDown is set, then the stop event, the worker leaves at its next wait, and the release closes the gate. Memory is sequentially consistent. Each state of this driver is paired with the set of 533ca4a4 states reachable through the same outside events: every program step outside a frame's handoff, take-back and SetEvent, the kill, the recycle, the device's going and add, the foreign stop, the Phase 1 map, and HID class sending a READ_REPORT. The map and the READ_REPORT are shared while both sides wait for them, and taken first by a side that alone waits. Every read of this driver pairs with a read of each 533ca4a4 run that has a wake to read on. A kill is paired by the frame's place: before the SetEvent while the frame still waits in the handoff or was taken back, after it once a take or SetEvent woke the worker. A final state of this driver must be matched by a final state of its set that delivers no frame or release frame this one loses, sends twice only what this one sends twice, and sends a program's frame after its release frames only where this one does. A zeroed section never goes out. A step 533ca4a4 cannot follow fails the check. An outcome matched only by runs that send fewer frames is reported apart, as an extra frame. Pairs whose 533ca4a4 set holds a set already explored with the same state are pruned, which keeps every failure. The model has one device context at a time, no driver host crash, and a recycle on 250 stale wakeups that may come at any stale read.
