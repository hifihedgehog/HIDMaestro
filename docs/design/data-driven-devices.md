# Design note: every device as data

The owner's rule is that a profile describes its device and the SDK and driver hold only general mechanisms. At 9bd6279 four device families still reach hand-written code: the Switch Pro and Switch 2 Pro personas, the Sony feature answers and the DualShock 3 sixaxis form, the Valve feature channel and codec constants, and the Xbox 360 XUSB presentation keyed on Microsoft's vendor ID. This note converts all of it to six mechanisms, settles the five questions the conversion raised, and plans the fixes for the defects found on the way. The release is v2.0.0: it drops the hand-written methodology, and the drivers keep no device code, not even for programs built on earlier SDKs (decision (c)). The GameCube adapter persona of v2.0.0 is the model: its ports, protocol and WinUSB binding are JSON, and nothing in the SDK names it.

Four inventories of the device-specific code, one per family, came before this note, and three reviews of it followed. Every claim this note builds on was checked again at 9bd6279, and each file:line below is at that commit unless a reference clone is named. SDL lines are at SDL-reference 804cf65 unless marked SDL 3.4.18, the release the battery runs. An implementation plan, kept with the release's lane notes, orders the work in eight lanes: oracles first, then the arithmetic, the answer tables, the devnode presentation, the engine on USB/IP, the engine on UMDF2, the defects, and the compatibility tests.

Three rules govern every change below. A byte, identity or timing change happens only where a capture of the real device, or a reference written against it, gives the new value. Where none does, today's byte stays and the note says why. A general mechanism costs no more on the hot path than the hand-written code it replaces, measured, or the note gives the numbers. A profile that gets behavior from today's code keeps it under the v2.0.0 SDK, through its own model or the identity defaults. A program built on a v1 SDK keeps the data path every version shares and loses the extras decision (c) lists.

## The mechanisms

Six mechanisms cover every item of the four inventories. Each is parsed and validated when its profile loads, or when `HMProfileBuilder` builds the profile, and compiles at create, before the create takes anything machine-wide. A mistake is refused with the JSON path that holds it, as the v2.0.0 device model already does (`DeviceProtocol.cs:117-305`), and "Where errors appear" below says where the refusal shows.

| Mechanism | Covers |
|---|---|
| 1. The codec and one arithmetic | Switch Pro and Switch 2 Pro field packing and rumble decode, Valve stick and trigger constants and the Triton timestamp, the DualShock 3 battery byte, and the arithmetic of every normalized value the SDK writes |
| 2. State blocks, report programs, counters and the device clock | reports a device builds at send time from its state: Switch Pro 0x30, 0x3F and 0x21, Switch 2 Pro 0x09 and 0x05, the DualShock 3 sixaxis input and feature reports |
| 3. The device protocol on both transports | command rules, registers, replies, memory images, output translation and output decode: the Switch Pro and Switch 2 Pro protocols, the DualShock 3 output commands, the Triton's IMU setting |
| 4. Answer tables | feature answers on both transports (Sony, Valve) and the XUSB companion's IOCTL answers |
| 5. Value sources | per-controller values inside answers, replies and memory: MACs, serials, the controller index, Steam's current firmware build |
| 6. How a devnode presents itself | the XInput presentation block, enumerator, hardware and compatible IDs, the bus type GUID |

Where two families needed the same kind of thing, one mechanism serves both: Sony and Valve feature answers are one table, the Switch Pro, Switch 2 Pro and DualShock 3 protocols are one engine, Nintendo MACs and serials and Sony MACs are one value-source set, and every rolling counter and clock is one primitive.

The device model of a profile is the set of top-level keys these mechanisms add beside the descriptor: `protocol`, `stateBlock`, `inputReports`, `liveFeatureReports`, `featureStubs`, `valueSources`, `xinput` and `driverPid`, the last because an XInput presentation through xinputhid binds only on the PID xinputhid's INF lists (the installed `xinputhid.inf` matches `HID\VID_045E&PID_` 02D1, 02DD, 02E3, 02EA, 0B00, 0B0A, 0B13 and 02FF, and four catalog profiles present 02FF for that reason). `connection` and `versionNumber` are the profile's identity and stay its own. A profile gets its model from its own keys, from a model it names, or from the identity defaults of "Profiles made outside the catalog".

### 1. The codec and one arithmetic

The field vocabulary of `extendedReport` grows by parameters, never by device-named types.

| Key | On types | Meaning |
|---|---|---|
| `invert` | every axis and trigger type | the wire grows the other way from the SDK's 0-at-left and 0-at-top. Honored today by `uint8-axis` and `uint10-be` only. `int16-axis` negates Y by semantic (`VendorBlobCodec.cs:269-272`) and the pad types always invert Y (`311`, `320`). Both become `invert: true` in the Valve profiles. Required on an `int16-axis`, `int16-pad` or `int16-pad-or-stick` field of a Y semantic, which v1 negated without the key: a create refuses the field without it, naming its JSON path and `"invert": true` as the value that keeps v1's bytes |
| `min`, `max` | linear types | the wire value at the SDK's 0 and 1. Replaces the constants 32767 of `uint16-trigger` and `uint16-pressure` (`VendorBlobCodec.cs:343`, `360`) and the Switch Pro packer's `0x800 +/- 0x600` (`SwitchProPacker.cs:139-145`). `max` is required on `uint16-trigger` and `uint16-pressure`, which v1 wrote as 32767 at a full pull or press: a create refuses the field without it, naming its JSON path and `"max": 32767` as the value that keeps v1's bytes |
| `scale` | `int16-le` with a calibrated source (`accelGX` to `gyroDpsZ`) | counts per g or per degree per second, a number or an exact ratio `[13371, 936]`, with `negate` and `repeat: [count, stride]` for the Switch Pro's three IMU frames |
| `dpad: "resolved"` | `button-mask` `DPAD_*`, `hat-octant` | the d-pad from HatDegrees, then HatHundredths, then HatRaw, then Hat, as `SwitchProPacker.ResolveDpad` takes it (`115-137`) |
| `"#n"` in `buttons` | `button-mask` | HMButton bit n, for a profile whose buttons are layout positions (switch-pro) |
| `uint8-level-map` with `levels`, `chargingValue`, `fullValue` | new type | the battery byte as a table. `fullValue` wins over `chargingValue` when both hold, as `ds3-battery` puts 0xEF ahead of 0xEE (`VendorBlobCodec.cs:229-231`). `dualshock-3-full` carries the table `ds3-battery` holds in C# today (`864`) |
| `uint32-le`, `uint16-le` with `semantic: "sensorTimestamp"`, `divisor`, `clock: "accumulate"`, `holdWhile` | existing types | the timestamp. With `clock: "accumulate"` it runs through the accumulator below. Without it, today's division of `SensorTicks()` stays, the Stopwatch standing in for a consumer stamp of 0 (`VendorBlobCodec.cs:52-61`) |
| `packed-uint` | output fields | bit groups assembled from byte and bit positions, over `frames` of a `stride`, reduced by `max`, offset, range-checked, scaled by a ratio and clamped to 0..255, two parts combined by `max` into one semantic. Covers the Switch Pro HD rumble amplitude (`SwitchProPacker.cs:173-194`) and the Switch 2 Pro's three 40-bit frames per actuator (`Switch2ProPacker.cs:180-203`) |

A decoded output field reaches `OutputDecoded` boxed as its type says, and the type is part of the schema, op by op: `uint8`, `uint8-rolling`, `uint8-const`, `hat-octant` and `packed-uint` box `byte`, `uint8-axis` and `uint8-trigger` box `float`, `button-mask` boxes `List<string>`, `rgb24` boxes `byte[3]` and `bytes-passthrough` boxes `byte[]` (`HMOutputDecodedEventArgs.cs:20-26`, `VendorBlobCodec.cs:720-802`). The Switch decoders box `byte` today (`HMController.cs:1806-1810`, `1841-1845`), and a program that tests `leftMotor is byte` keeps working. The oracle records each field's boxed type beside its value.

Validation refuses an unknown type, a parameter a type ignores, `min` equal to `max`, a `scale` of zero, a `levels` table that is not 11 entries, and a `packed-uint` part whose bits run past the report. An output field decodes its type's full range, and only `uint8-axis` decodes inverted, so an output field with `min`, `max` or `dpad`, or with `invert` on any type but `uint8-axis`, is refused: accepted, an output trigger with `max` 200 would decode byte 200 as 0.784. The keys v1 implied, `max` on the 16-bit trigger and pressure types and `invert` on an int16 Y, are required, so a profile written for v1 never changes its bytes unseen. v2.0.0 drops two old spellings, the `ds3-battery` type and the `steamFirmwareStamp` key (mechanism 5), so neither the DualShock 3's table nor Steam's install paths stay in C#. A profile that carries one loads with an issue naming the key, its JSON path and its replacement (`uint8-level-map` with a `levels` table, or a `patch` with a `keyedHexFile` source), and its create is refused.

Compiled form: `CompiledField` gains `Min`, `Range`, a double `Scale`, a level table, and a counter slot. Every rolling field compiles to an index into a `uint[]` in the encoder state, where today each frame does two string-keyed dictionary lookups per rolling field (`VendorBlobCodec.cs:162-165`, `372-379`). Nothing per frame allocates.

The arithmetic is decision (a) below: every normalized value becomes `min + RoundHalfEven(v' x (max - min))` in double, where `v'` is the clamped float input or 1 minus it for an inverted field. That replaces the codec's float products, the descriptor path's truncation (`HidReportBuilder.cs:798`), the XUSB slice's truncation (`HMController.cs:875-880`) and the Switch Pro packer's truncation. A NaN has no place in [0, 1]. It writes the field's rest value, the value the field takes when the program leaves it unwritten: 0.5 for a stick or a centered axis and 0 for a trigger, before any inversion. Where the SDK reads `HMGamepadState.Axes`, a NaN takes its slot's rest and never falls through to another key that would feed the slot (Rx before Z, a canonical trigger before its field), and the codec and the packers give a NaN slot the same rest. One stick has one answer: XInput thumbs read 0 on both axes, the Switch Pro sticks 0x800. Values the SDK takes as integers keep their own arithmetic: the touchpad types (`VendorBlobCodec.cs:306-322`), `touchpad-finger` and `uint16-le` with `resolution` rescale integer inputs, not normalized floats, and are outside the rule.

Descriptor-path axes gain an optional `axisCenters` map in profile data, axis to wire value, for a device whose hosts center its sticks somewhere other than the midpoint. A centered field carries two slopes, computed when the profile compiles: `sL = 2(c - min)` below the center `c` and `sH = 2(max - c)` above it. With `t = v' - 0.5`, the wire is `c + RoundHalfEven(t x sL + max(t, 0) x (sH - sL))`: the two-slope value, rounded once as a distance from the center, with no branch. At the two centers the catalog uses, every tie lies at 0.25 or above, where each product and the sum are exact in double. 0.5 gives `c`, and so does PadForge's centered 0.5000076, which at 16 bits lands exactly on the tie beside the center. Rounding the wire value itself, as decision (a) rounds an uncentered field, sends that tie to 0x8000, whose high byte SDL does not read as zero. Rounding the two halves separately gives the same wire everywhere but 0.25, the one tie below the center, and costs 2.4 ns more per report on the USB profile and 0.8 ns more on the BLE one (`DD2-reportcost.csv`). Every raw value returns under double division, and under a normalization that divides each half by its own span. A consumer that divides a raw 16-bit value by 65535 in float gets the 64 even values from 32768 to 32894 back one count low, and 65 through a float reciprocal, to 32896: above the center the slope is 65536 where the consumer's is 65535, and float error carries values that close to the center across the rounding point (`DD2-centered-roundtrip.log`). An 8-bit centered axis loses none under any of the normalizations, and today's truncation loses 32,895 on the 16-bit range. The two Luna profiles set it, from SDL's Luna driver, which reads a stick byte of exactly 0x7F as zero (`SDL_hidapi_luna.c:222-223`, `324-325`): 0x7F on the four stick axes of `amazon-luna-usb`, and 0x7FFF on those of `amazon-luna-ble`, whose 16-bit fields SDL reads by their high byte (`324-333`). The codec's `uint8-axis` `center` does the same job for codec fields (`VendorBlobCodec.cs:117-118`).

The sensor timestamp with `clock: "accumulate"` keeps one accumulator per controller, in the 1/3 microsecond ticks of `HMGamepadState.SensorTimestamp`, 64 bits wide. The source is chosen once per controller: the controller's Stopwatch clock until the first nonzero consumer stamp, then the consumer's stamps for the rest of the controller's life. The frame that switches adds the clock's delta since the previous frame. Each later frame adds `d = (s - s_prev) mod 2^32`, and a `d` of 2^31 or more means the consumer's clock restarted or ran backward, and adds one nominal interval (the profile's `idleFrameIntervalMs`) instead. A consumer stamp of 0 after the switch means no stamp this frame, as `HMGamepadState.SensorTimestamp`'s documentation treats it (`HMGamepadState.cs:128-137`), and adds the clock's delta. The idle loop's repeat of the last state adds nothing on the consumer source. While `holdWhile` holds, the accumulator adds nothing and the field repeats its last value. The field carries `(acc / divisor) mod 2^width`. Triton's field takes the accumulator and `holdWhile: "imuMode==0"`, the register mechanism 3 sets from the IMU setting, because a real Triton freezes the stamp while its IMU is off ("HW timestamp, frozen unless IMU enabled", sc2-research `HID_REPORT_FORMAT.md:83` at b46d517, 9,000 identical idle frames at `:105`) and Linux emits it on every report whatever the IMU mode (`hid-steam.c:2484-2497`). How a real stamp moves when the IMU turns back on has no capture, and the design resumes from the frozen value. The DualShock 4's 16-bit stamp keeps today's division of `SensorTicks()`, the Stopwatch fallback included, byte for byte. A raw submit of report 0x42 carries the consumer's bytes and bypasses the accumulator, as today.

A second device of the same form adds JSON: a 12-bit stick with another calibration range sets `min` and `max`, a trigger with another full scale sets `max`, another battery encoding sets `levels`.

### 2. State blocks, report programs, counters and the device clock

A device that builds its reports at send time from its own state, such as the Switch Pro's timer byte or the Switch 2 Pro's report selected by a command, splits into two halves of data:

- `stateBlock`: a field list in the codec vocabulary, written at `SubmitState` into the input section. It replaces the packers' bodies byte for byte: 48 bytes for the Switch Pro, 24 for the Switch 2 Pro, 49 for the DualShock 3 (its existing native `extendedReport`). The list lowers into a state program over `HMGamepadState` and the six slots `SubmitState` resolves: button moves, flags (a trigger's digital bit, a hat direction, a touch), linear values, scaled and raw motion values, pressure bytes, 256-entry tables (a battery level, a hat), touchpad fingers, trackpad coordinates, ten-bit motion values and a CRC-32 last, each with the one arithmetic, a NaN slot taking the field's rest. The build step generates its kernel for a catalog profile, and `SubmitState` runs it through a function pointer bound once per controller, or the interpreter for a block from outside the catalog. A block runs through the codec when a field keeps state from one report to the next (a rolling counter, a timestamp) or is one the state program cannot say (a stick12-pair, a button name the state program does not know, two fields on one bit). The layouts stay the bodies of today, so a native writer reads the same bytes.
- `inputReports`: named layouts, each with a report ID, a size, a `while` condition on the protocol's registers, a `send` rule (`"clock"`, `"submit"` or `"change"`), and a program over the state block.

| Op | Effect |
|---|---|
| `copy` | a byte range of the state block to an offset |
| `bits` | bit moves, grouped at compile into one masked shift per state byte, report byte and distance, each ORed into its report byte |
| `const` | bytes at offsets |
| `xor` | a mask over a range, ORed into its report bytes, the DualShock 3's `0xFF - x` pressures |
| `swap16` | byte order of 16-bit words |
| `field` | a value read from the state block, minus a center, negated if asked, times a ratio with C truncation, plus an offset, then clamped or, with `overflow: "wrap16"`, wrapped as an unsigned 16-bit value, written as uint8 or uint16 in either order. A value is read as N bits at a bit offset or as a 16-bit word in either byte order, and every op that reads a value uses this form. The Switch Pro's 0x3F rescale of its 12-bit sticks (`driver.c:1733-1741`) and the DualShock 3's accelerometer mirror `0x3FF - x`, which wraps in `USHORT` (`driver.c:211`) |
| `lookup` | an N-bit group through a 2^N-byte table, ORed into its report byte, the d-pad bits to a hat (`driver.c:1777-1786`, `176-185`) |
| `hat8` | a stick as an eight-way hat: two values in `field`'s read form, their center, a required `deadzone` radius in counts, `yUp` when the Y value grows upward (otherwise it is negated first), and a 9-byte table giving the value for each sector, up (0) and clockwise to up-left (7), and for the center (8). With x and y the two values minus the center, a point with x squared plus y squared at most the dead zone squared is the center. Otherwise, with a the smaller and b the larger of \|x\| and \|y\|, the point is on the axis of the larger when 1,000,000 a is at most 414,214 b (up or down for y, right or left for x), and on its quadrant's diagonal otherwise. 414,214 / 1,000,000 stands for tan 22.5 degrees: the boundary is this constant, not the exact angle, so x = 5,741 and y = 13,860, a hair past 22.5 degrees from the Y axis, counts as up. No source gives a Joy-Con's boundary or dead zone, and the constant is the design's. The Joy-Con's 0x3F byte 3 (dekuNukem `bluetooth_hid_notes.md:76`, `83-89` at ac8093c) |
| `pack12` | two 16-bit values of the state block packed as a 12-bit pair in three bytes, the stick packing of `Switch2ProDevice.cs:531-536` |
| `counter` | a counter slot written at an offset in a width and byte order, with a scale and an add |
| `when` | runs the ops inside only while a condition holds |

`liveFeatureReports` use the same programs for a feature report whose answer is the current state, the DualShock 3's report 0 (`driver.c:3079-3100`). The SDK runs that program with the input program on every frame, and the driver serves the latest result on a GET by a copy, with no device code and no op list of its own.

Conditions are one grammar everywhere a `while`, `when` or rule names one. A term tests a register: `protocolSeen`, `!protocolSeen`, `inputMode==0x3F`, `inputMode!=0x3F`, `featureEnabled&0x04` (any of the bits set), or `inputMode in 30,31`. Terms join with `&&` into a group, and groups join with `||`, without parentheses. The list form v2.0.0's GameCube profile uses, `["polling", "!stalled"]`, is one group of its terms. A condition compiles to at most eight groups, each term a mask-and-compare with an equality flag, and an `in` term to a set test (a 256-bit set for an 8-bit register, a sorted array otherwise), so neither `!=` nor `in` multiplies groups. Two layouts may share a report ID only when their conditions cannot hold together. Validation decides that by enumerating the bits the two conditions test, across every register they name, up to 16 bits in all, whatever a register's width and whichever action writes it, and refuses a pair it cannot enumerate, with the path and a request to separate the layouts on fewer bits.

Counters are one primitive: a slot with a width, a stride, a wrap and an increment event, `encode` (the codec's `uint8-rolling` and `uint32-rolling`), `report` (each layout sent, the Switch 2 Pro's `n`), `frame` (any message sent, replies included, the Switch Pro timer byte the driver shares between replies and 0x30 frames at `driver.c:1631` and `1855`), or `clock` with a `periodUs`, whose value is the time since the clock's origin divided by the period, computed from the origin on every write so no remainder is lost.

The device clock is one class with `periodMs`, an `origin` (`"attach"` or `"inputOpened"`), a `missedTick` rule (`"nextPoll"`, `"owe"` or `"drop"`) and a high-resolution waitable timer. The GameCube adapter's host-poll grid, the Switch 2 Pro's 4 ms clock (`UsbipEmulatedDevice.cs:933-991`), the Switch Pro's stream and Valve's idle frames (`extendedReport.idleFrameIntervalMs`, `HMController.cs:594-615`) all run on it. `idleFrameIntervalMs` stays a key of its own and compiles to that clock with the repeat rule it has today.

The compiled form has two paths and one semantics, on the model .NET uses for regular expressions and JSON serialization. .NET's Regex source generator emits C# at build time for a pattern the code fixes at compile time: "If you're using `Regex` today in C# with arguments known at compile time, [...] you should prefer to use the source generator". A pattern built at run time goes to the interpreter, which "is the default engine employed", and a construct the generator cannot emit falls back to it: "the source generator won't emit a custom implementation and will instead fall back to caching a regular `Regex` instance". System.Text.Json's source generation moves "the metadata collection process from runtime to compile time", and its generated fast path "falls back to default serialization code if unsupported options are specified". The sources are Microsoft Learn's ".NET regular expression source generators" (2025-10-20), "Source-generation modes in System.Text.Json" (2026-08-18) and "How to use source generation in System.Text.Json" (2025-11-13). The SDK already reads profile JSON through a source-generated context (`HMJsonContext.cs:36-77`). Report programs take the same split: the catalog's programs are known at build time and generated, and a profile from outside the catalog is learned at run time and interpreted.

Three requirements bind the two paths.

One semantics. A profile's programs are parsed, validated and canonicalized once, into one intermediate form: ops with resolved byte and bit offsets, tables, conditions and the state block's size. Only validation makes that form, and the generator and the interpreter both start from it and accept nothing else. The order of writes is part of the form, and both paths run it:

1. The template: every top-level `const` byte, none set twice. It lies under everything else.
2. The unconditional ops, in list order. Each owns the bytes or bits it writes, and no two write one report bit, so their order cannot change a byte. A whole-byte op (`copy`, `swap16`, `field`, `pack12`, `counter`, `hat8`, a decode) writes over the template's byte. A `bits`, `lookup` or `xor` op ORs into its report byte, whose other bits keep the template's value. The bits it writes are a `bits` move's report bit, every bit some entry of a `lookup` table sets, and all eight bits of an `xor` byte. Validation refuses a template bit of 1 at a bit one of these ops writes, since the op could never clear it, so ORing into the byte and writing over those bits give the same byte.
3. The conditional blocks, after every unconditional op, in list order, and each block's ops in list order. A block holds only `const`, `copy` and `counter`, and its write replaces the template's, an unconditional op's or an earlier block's.

The Switch 2 Pro sketch above is valid under that order: byte 12 is 0x30 from the template and 0x38 while the block's condition holds. Validation gives every operand a domain and refuses a value outside it with its JSON path:

| Operand | Domain |
|---|---|
| a value read by `field`, `hat8` or a decode part | 1 to 25 bits, its offset within its first byte plus its width at most 32, inside the state block. Both paths read it with one unaligned 32-bit load, and the state block carries 3 bytes of slack past its end for that load |
| a big-endian word | 16 bits, starting on a byte |
| a `copy`, `xor` or `swap16` source | a byte range inside the state block |
| a `lookup` | 1 to 8 bits inside one state byte, and a table of 2^bits entries. Both paths read one byte |
| a register and a condition term | a register of 1 to 32 bits, a term's mask nonzero and inside the register's width, its value and each `in` value inside the mask |
| a `field` | a center inside the raw range of its read (0 to 2^bits - 1, or 0 to 65,535 for a big-endian word), so the difference fits the fast paths' 32-bit subtraction, a scaled range and both clamp bounds inside 2^30, so the interpreter's compare and the generated arithmetic clamp agree, and 1 or 2 output bytes |
| a `hat8` | a center inside the raw range of the narrower of its two reads, and a dead zone of 0 to 65,535 counts, so x squared plus y squared stays inside 64 bits at 25-bit reads |
| a template byte under a `bits`, `lookup` or `xor` op | no bit of 1 where the op writes |
| a decode term | at most 12 bits, and a table of 2^bits entries |
| a `counter` | 1 to 4 bytes |
| every write | inside the report |

The generator reads only the intermediate form and holds no device knowledge, so no device behavior lives only in generated code. Every op has an interpreter stage and a generator emission, and a check over the op list fails if either lacks one. A catalog program, decoder or model that fails validation fails the build, with a diagnostic naming the file and the JSON path. The build never drops it or leaves it to the interpreter.

The generator's host. The emitter runs at build time as a .NET 10 tool, not as a Roslyn source generator. A source generator runs inside the compiler, and "they must target netstandard2.0 or similar", and a dependency it uses while it runs "must be packaged directly alongside the generator assembly", with "no automatic facilities for this" (dotnet/roslyn, `docs/features/incremental-generators.cookbook.md`, read 2026-10-16). The form's code is .NET 10 code. Built for netstandard2.0 with the language polyfills added, the round 4 prototype's shared form failed with 19 errors in APIs .NET Standard 2.0 lacks: `Math.Clamp`, `Random.NextInt64`, `System.Range`, tuple and `KeyValuePair` deconstruction, and the culture-taking `StringBuilder.Append` (`DD2-form-ns20.log`). Rewriting it in that dialect would make the generator's form a second copy. The tool instead compiles the same source files the SDK compiles, from one shared folder. The model groups' types and the strict System.Text.Json context that reads them are in that folder too, and one function reads the `programs` subtree of a profile or model file out of a `JsonDocument` through that context: the build tool calls it at build time and the loader at run time, so a program parses one way and an error carries one JSON path in both. The file's root, which holds keys the tool does not model, is the SDK loader's to read strictly, and the battery runs that loader over the catalog. Tables are literal bytes computed by the code the interpreter calls, on .NET 10, the runtime the SDK runs on.

User profiles are first class. The interpreter runs every mechanism the catalog uses: every op of this section, conditional blocks, counters, hats and decodes, and in mechanism 3 the protocol engine, which has no generated half. A profile from a directory loads at run time with no rebuild, and so do the named models and identity defaults it needs, from the same directory ("Where errors appear"). A validation error names the file and the JSON path of the value it rejects, such as `$.protocol.rules[3].reply[1].length`. A program compiles in 2.5 to 173 microseconds (table below), inside the create budget of 1 ms. A user profile joins the catalog as JSON alone: the next build generates its kernels, and the equivalence check proves them against its interpreted form.

At build time the build step emits each catalog program and decoder as one straight-line C# method in a value type that implements one interface, `IReportKernel`, named by the SHA-256 of the program's canonical form. The method reads only the ops: `bits` become masked shifts, `const` bytes fold into 16-byte stores, `copy` and `field` become constant-offset loads and stores, and a field's clamp and a decode's largest term are arithmetic rather than compares, so they stay branch-free once inlined. The code that runs programs per report is generic over the kernel type: the clock loop that sends a device's frames, the USB/IP device's report source, and the submit path of a device whose `SubmitState` builds its report. The JIT and NativeAOT compile one copy of each per value type and inline the program into it, so the loop that sends a frame makes no call to build it (`DD2-jit-specloop.txt`, `DD2-aot-specloop.txt`). Those methods carry `AggressiveOptimization`, so the JIT compiles them fully at first call, and NativeAOT compiles them ahead of time. At create the compiler canonicalizes each program and looks up its hash, and one generated switch over the catalog's hashes picks the matching instantiation, once per controller. A clock loop and a USB/IP device then run with no dispatch per report. A report `SubmitState` builds is reached through a function pointer to its submit path, bound at create, and one call there runs every program the device builds from that state. The protocol engine reaches a decoder the same way, once per output report. A switch over the compiled program ids per report costs more than that pointer, and the design does not use one. A program no generated method matches runs on the interpreter: the same intermediate form compiled into stage arrays (a template copy, copies, masked-shift and table entries, fields, packs, counters, hats, decodes, conditional blocks) that one method walks without per-op dispatch. Neither path allocates per report.

### 3. The device protocol on both transports

`usbConfiguration.protocol` moves to a top-level `protocol`, which a UMDF2 profile can carry as well. v2.0.0 has not shipped, so the GameCube profile moves with it and no alias is kept. It gains:

- Registers: a `state` entry with `bits` 8, 16 or 32 and an `initial` value, tested by the condition grammar above.
- Matches: `match` takes `..` wildcards and `at`, compiled to an offset with a mask and value array.
- Actions: `set`, `store` (a command byte into a register, optionally only when it is `in` a set or `nonzero`), `storeRecord` (a list of fixed-size records in the command, the count read from a length byte, each record's key byte compared and the matching record's value bytes stored into a register), `or` and `andNot` (a command byte masked by a register), `write` (command bytes or bit moves into a memory image), `consume` (the command is not raised on `OutputReceived`, which the Switch Pro's 0x80 family needs, `driver.c:2897-2909`), `emitOutput` (raise a translated report instead of the raw one, the DualShock 3's folded report 0x01, `driver.c:1293-1324`), and `decode` (a named group of output fields in the codec's output vocabulary, declared under the protocol's `decoders`, raised on `OutputDecoded` with their boxed types, the Switch Pro's and Switch 2 Pro's rumble, `HMController.cs:1790-1855`). A decoder compiles as a report program does, generated or interpreted. A decoded field can read several bit ranges and keep the largest after mapping each through its scale or range, which both paths compile to a table of at most 4,096 entries: the Switch Pro's rumble keeps the louder of its two bands, and the Switch 2 Pro's the largest of six frames.
- Reply parts beside `hex`, `state` and `snapshot`: `echo` (command bytes), `register`, `counter` (written, then incremented), `memory` (address and length read from the command, clamped, filled and wrapped), `bitmap` (bytes chosen by the set bits of a command byte, the Switch 2 Pro's feature info, `Switch2ProDevice.cs:287-297`), `input` (bytes of a layout as it would go out now, the Switch Pro reply's buttons and sticks), `value` (bytes from a value source, mechanism 5, the Switch Pro's MAC), and a `prefix` every reply shares, with a `status` a rule can override and `prefix: false` on a rule whose reply has its own head.
- `memory`: named images of a size and a fill byte with hex segments and value-source segments, compiled to a sorted segment array.
- `commands.source`: `"interruptOut"`, `"bulkOut"`, `"setReport"` (the v2.0.0 flag), and `"outputReport"` for a UMDF2 device, whose HID output reports arrive through the driver's output ring report ID first. A SET_FEATURE reaches both the answer table's record (mechanism 4) and the rules of a `setReport` source.
- `replies`: on the input channel ahead of reports, or on a bulk IN endpoint in chunks of each read's length, with `pending` and `overflow` (`"dropNewest"`, `"dropOldest"`, `"dropOldestUnstarted"`). The Switch Pro keeps `dropOldest` and four slots, the driver's rule (`driver.c:1496-1500`). eden and BetterJoy take any 0x21 as the answer to their pending subcommand (`common_protocol.cpp:78-95` at 1dcc574, `Joycon.cs:1170-1191` at b671563), so a reply left queued answers the next command for them, as it does today.
- `getReport: "deviceReport"` on USB/IP: a declared ID gets its layout built now without counting it, and ID 0 the selected layout (`UsbipEmulatedDevice.cs:1241-1264`). On UMDF2 the driver keeps answering GET_INPUT_REPORT for report IDs 0 and 1 only, from its cache of the last frame (`driver.c:3605-3608`), so `switch-pro` refuses `HidD_GetInputReport(0x30)` before and after. For a controller a v2.0.0 SDK configured, the cache keeps only frames of the profile's `inputReports` layouts, never protocol replies, as today's Switch path caches stream frames and not 0x21 replies (`driver.c:1849-1859`). The SDK writes the cached report IDs as a registry value, and an empty list caches every frame, as the generic path does today (`driver.c:2006-2008`).
- `log`: the last N commands, which replaces the Switch 2 Pro's bulk log the probes read (`Switch2ProDevice.cs:70-75`).

Validation adds to the v2.0.0 list: a register a condition or action names that `state` does not declare, a store wider than its register, a match longer than the shortest packet its source delivers, a memory segment past its image, a reply longer than the channel's report size, a layout whose program writes past its size, on UMDF2 a layout, reply or extended report whose size differs from the declared input length of its report ID (decision (c)), which a USB/IP device need not meet, since it sends what its real device sends (the GameCube adapter's 0x21 reports are 37 bytes as SDL reads them, `SDL_hidapi_gamecube.c:242`, `372` at 3.4.18, where its descriptor declares 38 with the ID), two layouts with one report ID whose conditions can hold together, and, for a protocol in the profile's own keys, a UMDF2 protocol whose output or input report IDs the descriptor does not declare, which HidClass would refuse before the driver sees them. A model a profile takes by name or by identity default (below) is checked the same way, except that a rule or layout for a report the profile's descriptor does not declare is kept and listed in the profile's compile notes, since that is what today's code does on such a descriptor.

The Triton's IMU setting is the first `storeRecord`. The USB form gets its own catalog profile, `switch-pro-usb`, with the 203-byte USB descriptor `switch-pro.json` keeps as `nativeDescriptor` (ControllersInfo bfc11b8, the profile's descriptor through v1.3.20). That descriptor declares inputs 0x21, 0x30 and 0x81 and outputs 0x01, 0x10, 0x80 and 0x82, each of 63 bytes after the ID, and no 0x3F input and no 0x11 or 0x12 output. The profile's protocol is its own, written against that set: the rules for 0x01 and 0x10 above, the 0x80 rules with the replies the driver sends today (`81 01 00 03` and the MAC least significant byte first, `81 02`, `81 03`, and nothing for `80 04` to `80 06`, `driver.c:1572-1594`, dekuNukem `USB-HID-Notes.md`), replies of 64 bytes, a `full` layout of 64 bytes whose first 49 bytes are the Bluetooth layout's and whose tail is zero, and no `simple` layout. Over USB a real Pro never streams 0x3F: its descriptor declares none, and SDL notes that "Going into simple mode over USB disables input reports" (`SDL_hidapi_switch.c:1918`). The stream keeps today's 15 ms, the community figure hid-nintendo quotes for "pro controller (USB): every 15 ms" (`hid-nintendo.c:1440-1449` at d24e8ac). The author's own measurement there is over Bluetooth (`1456-1460`). What a real pad puts in bytes 49 to 63 of its USB 0x30 has no source, and they are zero.

Compiled form: register indices and widths, conditions as mask-and-value groups with set tests, matches as offset, mask and value arrays, actions as a short op array, reply parts with fixed offsets and lengths, memory as sorted segments. Replies go into `pending` buffers of the longest reply, allocated at create, so a command allocates nothing, where `ProtocolEngine.BuildReply` (`DeviceProtocol.cs:739`) and `Switch2ProDevice.Enqueue` (`255`) allocate one array a reply today.

On USB/IP the engine runs where the GameCube adapter's runs (`UsbipEmulatedDevice.Protocol.cs`), with bulk endpoints added. On UMDF2 it runs in the SDK, decision (b): the controller's output reader hands each output report to the engine before it raises `OutputReceived`, and the engine's messages go to the driver through the input section with the delivery acknowledgement v1.12.0 added for keyboards (`driver.c:688-705`, `2839-2845`, `HMController.cs:1423-1450`), so a reply is never overwritten by the next frame. The protocol host takes the acknowledgement alone: it defines no release frames, which the keyboard path keeps for keys and buttons (`HMController.cs:1367-1402`). The driver's input path is the one every profile uses: one READ_REPORT per new frame, the report as the SDK wrote it, its size per frame (`driver.c:1951-1958`). The driver gains no device code. The controller's protocol thread and output reader are made in the create's first step, before the devnode exists, and start when the create has read the driver's half of the version section after the device started (decision (c)). A command a host writes before then waits in the output ring. On UMDF2 a device clock's `origin: "attach"` is that start, and on USB/IP it is the device's attach. Until the driver has made the output doorbell, the reader polls the ring every 8 ms, as it does today when it cannot open the event (`HMController.cs:1683-1705`).

A Joy-Con, a Charging Grip, an NSO pad and the Switch 2 GameCube controller are the same forms. Their JSON carries the device-info byte, stick presence and SPI contents nxbt and hid-nintendo record (nxbt `protocol.py:27-42`, `363-500` at ec4b800, hid-nintendo `316-324`), and a Joy-Con's 0x3F carries its stick through `hat8`. No implementation on disk or found online generates that hat from a stick position: joycontrol sends no 0x3F, nxbt only records the mode (`protocol.py:514-515`), joycontrol-poohl sends a fixed copy of dekuNukem's sample (`protocol.py:124-126` at 0b79bf7), HOJA-LIB-ESP32 sends a fixed center (`core_switch_reports.c:75` at 99f6bc3), and joypad-os, Santroller and NS-LIB-HID send none or a blank one. No source gives the dead zone, so the catalog's `joycon-l` stays as it is in this release, and the plan proves the form with a test profile whose `deadzone` is the test's own value. Third-party Switch pads need data only: 8BitDo's M30 and SF30 never answer `80 03` (`SDL_hidapi_switch.c:718`), and the MOBAPAD wants the rumble bytes before it answers device info (`1595`). One behavior SDL records has no rule: a pad that "will shut off if we try to set it" (`1317-1321`). No catalog persona needs it.

### 4. Answer tables

`featureStubs` keeps its name and becomes the one table for answers a device gives on request, on both transports. The match moves from the table to each entry, so report-ID answers and message channels sit in one table.

| Key | Meaning |
|---|---|
| `id` | the report ID the GET arrives on, 0 for a descriptor that declares none |
| `message` | `{ "onReport", "at", "value" }`: the entry answers only while the last SET_FEATURE on report `onReport` carried `value` (one or more bytes) at offset `at` of the SET's data, counted from the report ID for a descriptor that declares report IDs and from the first data byte for one that declares none. Valve's channel is `onReport` 0 and `at` 0 on the Deck and the first Steam Controller, and report 1 at 1 on Triton (`FeatureStubTable.cs:31`, `68`, `UsbipEmulatedDevice.cs:1300-1324`) |
| `param` | `{ "at", "value" }`: a further byte of the same SET, the message's parameter, which today sits at `messageByte + 2` in code (`UsbipEmulatedDevice.cs:1317`) |
| `pages` | answers served in turn by successive GETs after the matching SET, the last one repeating. The DualSense test channel is this shape: SET 0x80 `[device][action]` with parameters after them (dualsense-tester `ds.util.ts:207-211`, `263-268` at ff340fe), then GET 0x81 polled every 10 ms, each answer `81 device action status` and 56 bytes, status 3 for a page with more to come and 2 for the last (`164-166`, `223-240`, `ds.type.ts:240-246`). A SET on `onReport` restarts the pages. That restart has no source and is the design's choice |
| `echo` | the answer is the bytes of the matching SET, Valve's `0x87` |
| `replyHead: "requestReportId"` | byte 0 of the answer is the report ID asked on, which today a nonzero `messageByte` implies (`UsbipEmulatedDevice.cs:1362`) |
| `minLength`, `sizes` | a request shorter than `minLength` fails (STATUS_BUFFER_TOO_SMALL on UMDF2, a stall on USB/IP, as each does today), and `sizes` gives the largest size the caller's buffer holds, the 41 or 37 of report 0x02: 41 when the buffer holds 41, 37 when it holds 37 to 40 (`driver.c:3308-3328`) |
| `crc32: { "seed": "A3" }` | the CRC the SDK computes at create over the report from its ID and writes in its last four bytes (`driver.c:3359-3366`) |
| `notify` | serving the answer publishes a feature-read notification, which arms `armOn` (`driver.c:3368-3369`). Absent, it is true on the usbip backend, which published one on every answered GET through v1.13.0 (`UsbipEmulatedDevice.cs:1290` at b22324e), so a user's table from v1.7 to v1.13 keeps its notifications, and false on UMDF2, whose driver notified only the Sony reads the Sony models name |
| `patch` | per-controller bytes from a value source (mechanism 5) |

A GET on report R looks first for a message entry for R whose `message` and `param` match the last SET on its `onReport`, an exact `param` before an entry without one, and then for a plain entry for R. A message entry whose SET never came, or came with another value, does not match. On UMDF2 the driver then tries the PID block's reports, whose Create New Effect report (0x11 unless the descriptor moves it) answers with success and the buffer as the caller sent it (`driver.c:3393-3400`), and then fails the request with STATUS_NOT_SUPPORTED, publishing no notification (`3404-3415`). On USB/IP no match stalls the control transfer, as today. Either way a device answers nothing for a message it does not implement.

The offset rule makes `at` name the same byte on both transports. On USB/IP the data of an unnumbered SET_REPORT starts with the message (`UsbipEmulatedDevice.cs:1300-1317`). On UMDF2, HID class hands the driver a buffer whose byte 0 is the report ID, 0 for an unnumbered report, and the driver splits it there (`driver.c:2938-2941`). The UMDF2 driver therefore keeps the SET's data without HID class's leading 0 for a descriptor that declares no report IDs, and with the ID byte for one that does. That HID class hands the driver the leading 0 rests on the driver's own split, not on a capture, so DD-2's bench run sends `HidD_SetFeature` and then `HidD_GetFeature` to a test profile without report IDs that carries a message entry, and fails unless the GET answers.

Validation checks each kind against what it names: an `id` the descriptor declares as a feature report (HidClass refuses any other before the driver sees it, commit 1c126ed), an `onReport` the descriptor declares as a feature report, a `message` or `param` offset inside that report's size, an `id` the PID block does not declare, data no longer than its size, a patch inside the data, a CRC only on an answer of five bytes or more, at most four distinct `onReport` reports, and no file-backed value source on a UMDF2 profile, whose answers the driver serves without calling the SDK. In a model taken by name or by identity default, an entry for a report the profile's descriptor does not declare is kept and listed, as in mechanism 3: HidClass refuses that GET before the driver sees it, as it does today.

Compiled form: at create the SDK resolves every patch and CRC for this controller into final bytes, one blob with a header, an entry index with each entry's match fields, and a byte arena. UMDF2: REG_BINARY `FeatureAnswers` in `SOFTWARE\HIDMaestro\Controller<N>`, parsed once in `EvtDeviceAdd` into fixed arrays in the device context, under the version contract of decision (c). The blob's header carries its length and a format number, 4 for every blob of protocol 4. The driver's limits are constants in `driver.h`: 64 entries, 64 bytes of data per answer, 16 pages per entry, four `onReport` reports and a 16 KB arena. The SDK carries the same constants, a test fails when the two disagree, and validation refuses at load a model past a limit, with its JSON path. Under the contract the driver fails its start with STATUS_DEVICE_CONFIGURATION_ERROR when a blob it should read is missing, truncated, of another format or past a limit, and first writes which value failed into the version section (decision (c)). The create then fails, removes its devnode and names the value, rather than leaving a device that answers nothing. The companion treats `XusbAnswers` the same way. On SET_FEATURE the driver keeps the data, up to 64 bytes, for each report an entry names as `onReport`, resets that report's page counters, and publishes the SET as it does today (`driver.c:2921-3002`). A GET becomes an index walk over the entries for its report and a copy, where today it walks an if-chain and runs a bit-by-bit CRC over up to 64 bytes on every Bluetooth request (`driver.c:105-127`). The companion reads `XusbAnswers` the same way, and registers its XUSB interface only for a controller whose answers it holds. USB/IP: `FeatureStubTable` holds the same arrays and hands out slices, where today each answer is `new byte[]` or a `Clone` (`UsbipEmulatedDevice.cs:1378-1436`). File-backed sources on USB/IP resolve when the answer is asked for, through a cache keyed on the file's last write time.

The Sony answers live in six named models, one for each branch of today's Sony block crossed with the Bluetooth CRC: the DualShock 4 layout of report 0x05 for 0x05C4, 0x09CC and 0x0BA0 (`driver.c:3141`), the Edge's 0x20 fields for 0x0DF2 (`3244`), and the DualSense default for every other Sony PID. The catalog's Sony profiles name theirs, and `dualshock-3` keeps today's 0x02 answer through the default model (decision (e)). The three Valve composites carry their entries with `message`, `param`, `echo` and `replyHead`. The UMDF2 `steam-controller` and `steam-deck` profiles carry no answers today and gain none, and no DualSense profile answers 0x81, as today: both shapes are expressible, and neither has a capture of a real unit's answers to author from.

The XUSB companion's answers to GET_INFORMATION, GET_CAPABILITIES (24 and 36 bytes), GET_BATTERY_INFORMATION and GET_INFORMATION_EX compile from the `xinput` block (mechanism 6) into the same kind of table, keyed by IOCTL.

### 5. Value sources

A value inside an answer, a reply or a memory image that differs per controller comes from a named source:

| Source | Value |
|---|---|
| `index` | the transport index: the last byte of today's Sony MAC, and of the Switch Pro's MAC plus 0x30 (`driver.c:3165`, `486`) |
| `serial` | the serial the device serves, per transport: on USB/IP the USB serial, `UsbDescriptorSet.InstanceSerial` (`UsbDescriptorSet.cs:107-135`), which the Switch 2 Pro's flash carries at 0x13002 (`Switch2ProDevice.cs:393-397`), and on UMDF2 the driver's `HM-CTL-<index>` string (`driver.c:340-359`) |
| `keyedHexFile` | a value read from a `KEY:HEX` line of a file found through registry values and known folders, declared in the profile's top-level `valueSources` |

A patch is `{ "at", "length", "encoding", "source", "key", "add" }` with encodings `uint8`, `uint16-le`, `uint32-le`, `ascii` and `ascii-decimal`. Steam's updater file becomes data:

```json
"valueSources": {
  "steamUpdater": { "kind": "keyedHexFile",
    "roots": [ { "registry": "HKCU\\Software\\Valve\\Steam", "value": "SteamPath" },
               { "registry": "HKLM\\SOFTWARE\\WOW6432Node\\Valve\\Steam", "value": "InstallPath" },
               { "knownFolder": "ProgramFilesX86", "path": "Steam" } ],
    "path": "bin\\hardwareupdater\\hardwareupdater.cfg" } },
"featureStubs": { "reports": [
  { "id": "0x01", "message": { "onReport": "0x01", "at": 1, "value": "83" }, "size": 64, "data": "...",
    "patch": [ { "at": 19, "length": 4, "encoding": "uint32-le", "source": "steamUpdater", "key": "TRITON_FW_TS" } ] } ] }
```

The parser keeps `SteamHardwareUpdater.ParseStamp`'s rules (`SteamHardwareUpdater.cs:101-117`): the key matches whole, an optional `0x`, one to eight hex digits, zero reads as absent. `SteamHardwareUpdater.cs` goes away, and the `steamFirmwareStamp` key with it (mechanism 1). A puck persona, whose firmware key `PROTEUS_FW_TS` is in the same file, needs one patch. The Valve unit serial answer (0xAE) stays the captured constant on every instance. Linux reads 0xAE into the device's `uniq` (`hid-steam.c:674-685`), InputPlumber answers one constant per VID and PID (`steam_deck.rs:114`, `1090-1094`), and no source shows a host keying anything on a per-unit value.

### 6. How a devnode presents itself

The XUSB presentation is chosen today by `VendorId == 0x045E` plus a name heuristic (`ControllerProfile.cs:404-423`), and the enumerator and compatible IDs by that test and by `UsesUpperFilter` (`DeviceNodeCreator.cs:101-116`, `268-271`). A profile states it instead:

```json
"xinput": { "via": "xusbCompanion", "subType": "wheel" }
```

`via` is `"xusbCompanion"`, `"xinputhid"` (what `driverMode: "xinputhid"` means today, kept as an alias) or absent for no XInput. Everything else defaults to today's answers, which are a wired gamepad's (`companion.c:834-1039`) and move into the catalog's XUSB model as data, so the companion holds no answer of its own: flags `voice` and `pmd` (0x000C), the profile's VID and PID in every reply, battery wired. A profile states only what a capture or a reference gives it. `information` and `capabilities` each take a `vid` and `pid` for a device whose replies carry other IDs than its HID child, and `flags` and `battery` take their XInput values. The companion's hardware ID, `root\VID_vvvv&PID_pppp&XI_00` (`DeviceOrchestrator.cs:894`), takes the `information` IDs, so each companion keeps the hardware ID and INF match it has today (`hidmaestro_xusb.inf:47-49`). `xbox-360-wireless` is the one profile that sets `information` and `capabilities` (decision (e)):

```json
"pid": "0x02A1",
"xinput": { "via": "xusbCompanion",
            "information": { "vid": "0x045E", "pid": "0x0719" },
            "capabilities": { "vid": "0x045E", "pid": "0x0000", "flags": ["wireless", "voice", "pmd"] } }
```

An enumerator carries `IG_` only for an XInput device. Microsoft's own test for one is the substring: "check each device ID to see if it contains "IG_" (ex. "VID_0000&PID_0000&IG_00"). If it does, then it's an XInput device" (Learn, "Comparison of XInput and DirectInput features"), and SDL skips any `IG_` path in its HIDAPI and DirectInput backends (`hid.c:1016-1018`, `SDL_dinputjoystick.c:251-255`).

`connection: "bluetooth"` gains `bluetoothTransport: "classic" | "le"`. The hardware and compatible IDs follow the forms a real device of each transport carries, read on the devbox from a present DualSense and Xbox controller: classic hardware IDs `BTHENUM\{00001124-0000-1000-8000-00805f9b34fb}_VID&0002054c_PID&0ce6` and `BTHENUM\{00001124-...}_LOCALMFG&0002`, with compatible IDs `BTHENUM\{00001124-...}` and `BTHENUM\{00001124-...}_GENERIC`, and LE hardware IDs `BTHLEDevice\{00001812-0000-1000-8000-00805f9b34fb}_Dev_VID&02045e_PID&0b13_REV&0523`, the same without `_REV`, and `..._LOCALMFG&0002`, with compatible IDs `BTHLEDevice\{00001812-...}` and `BTHLEDevice\GenericATTService`. HIDMaestro's `root\HIDMaestro` stays in every hardware ID list, since programs recognize their devices by it. SDL reports a HID device's bus from the substrings `USB`, `BTHENUM` and `BTHLEDEVICE` in its parent's compatible IDs (`hid_internal_detect_bus_type`, `hid.c:741-808` at SDL 3.4.18), and both forms carry the Bluetooth ones and no `USB`. Today the SDK writes `BTHENUM\Dev_VID&02{vid}` (`DeviceNodeCreator.cs:286`), a form no real device carries.

Compiled once per profile into a plan record: the enumerator (`VID_vvvv&PID_pppp&IG_00` only for an XInput device), the hardware and compatible ID strings, whether the GIP slice is packed, whether a companion is made, and the XUSB answers (mechanism 4). `DeviceNodeCreator`, `DeviceOrchestrator` and `HMController` read the plan where they read `RequiresXusbCompanion` and `VendorId == 0x045E`, the orphan sweep derives its HID-child prefixes from the enumerators plans produce (`DeviceOrchestrator.cs:2168-2170`), and the companion's rumble gate reads a `XusbCompanion` flag where it reads `VendorId == 0x045E`, with the same throttle (`companion.c:951-971`). The per-frame cost is the one bool read `_packsGipBuffer` already is. A PDP or Hori Xbox 360 pad, or a drum kit of subtype 0x08, needs JSON alone.

The bus type GUID. Today every create stamps GUID_BUS_TYPE_USB on every HIDMaestro devnode under ROOT and SWD and on each one's first child (`DeviceOrchestrator.cs:1111-1192`, called at `1419`), scanning the registry to find them. The companion's own devnode (`ROOT\HMCOMPANION`) matches neither scan and is not stamped. After the change each create stamps only the parent it made, with the value a real device of its connection carries, read on the devbox: GUID_BUS_TYPE_USB for USB, as the present USB HID devices read there carry, and none for Bluetooth, as none of the six present BTHENUM and BTHLEDEVICE devnodes read there carries one (wdmguid.h defines no Bluetooth bus type). The HID child is left to HidClass, which gives its children GUID_BUS_TYPE_HID, as the six present USB HID children read there carry. No Bluetooth HID child was present to read, so that half rests on HidClass being the children's bus driver on both transports. The companion stays unstamped. These stamps came from the WGI recognition experiments (668112e, 4b4f230), so the change lands only if the WGI and GameInput scenarios pass unchanged for every Bluetooth and XUSB profile.

## Profiles made outside the catalog

A profile keeps every behavior today's code gives it, however it was made. Today that behavior comes from four gates on identity: the Sony answers for VID 054C (by PID branch and connection), the Switch responder, packer and rumble decode for 057E:2009, the XUSB companion for VID 045E with "xbox" in the id, name or product string and no upper filter (`ControllerProfile.cs:404-423`), and the DualShock 3 form for `sixaxisCompatible`. The catalog carries those gates as data, a table of identity defaults in `profiles/models/identity-defaults.json` beside the named models:

| Identity | Model |
|---|---|
| VID 054C, PID 05C4, 09CC or 0BA0 | the DualShock 4 Sony answers, the Bluetooth variant for `connection: "bluetooth"` |
| VID 054C, PID 0DF2 | the Edge Sony answers, likewise |
| VID 054C, any other PID | the default Sony answers, likewise |
| VID 057E, PID 2009, Bluetooth | `switch-pro`'s model |
| VID 057E, PID 2009, USB | `switch-pro-usb`'s model |
| VID 045E, "xbox" in the id, name or product string, no upper filter | the companion with today's wired-gamepad answers |
| `sixaxisCompatible: true` | `dualshock-3-full`'s model |

Each entry is written from the gate it replaces, and DD-0's recordings of the gates are its test. The code that reads the table is general: it compares a profile's identity with each entry's fields and names no device.

A profile's model resolves at load, group by group, since each of today's gates is independent of the others: the answers (`featureStubs`, `valueSources`), the protocol (`protocol`, `stateBlock`, `inputReports`, `liveFeatureReports`) and the presentation (`xinput`, `driverPid`). Within a group the first of these that applies wins, no two sources merge, and loading never refuses a profile for a model it takes by name or by identity:

1. Its own keys in the group, validated strictly at load, as any authored profile is. A profile whose own keys fail is refused ("Where errors appear").
2. `deviceModelFrom: "<id>"` naming a catalog profile, a named model this release holds or a named model loaded from the profile's directory, validated against the profile's descriptor at load under the rule for taken models (mechanisms 3 and 4).
3. A name nothing loaded holds, a named profile with no model, or a named model that does not validate against the profile's descriptor: the identity default below, and `HMProfile.DeviceModelProblem` names the missing or failing model and the reason.
4. No keys in the group and no name: the identity default whose entry matches the profile, or nothing.
5. `"deviceModel": "none"`: no model, by the author's choice.

A name fills only the groups the profile leaves empty, and a name whose model covers none of them is recorded as unused. `HMProfile.HasDeviceModel` is true when the resolved model is not empty, `HMProfile.DeviceModelSource` says which step gave each group (`own`, `named:<id>`, `identity:<entry>`, `none`), and `HMContext.ProfileLoadIssues` lists every profile file the loader refused or loaded with a model problem, with the reason, so a program whose loader swallows exceptions can still show them.

No catalog profile takes a group from an identity default. Each carries its own keys, names its model, or has nothing in that group, so no catalog behavior stays keyed on a VID or PID, even as data. A battery assertion fails when any catalog profile's `DeviceModelSource` reads `identity:` in any group.

`HMDeviceExtractor.Extract` writes `deviceModelFrom` with the model the identity default gives, so an extracted profile states its behavior in its JSON, and its notes name the entry. `HMDeviceExtractor.ResolveDeviceModel(HMProfile)` returns a new profile with that name for a profile that has no own keys and no name, and returns the same instance otherwise. It never overwrites a model a profile carries. A stored profile needs neither call to keep its behavior, since step 4 applies at every load.

### Where errors appear

Every profile file is parsed and validated when it loads, and a profile `HMProfileBuilder` makes is validated when `Build` runs. The loader reads profile JSON through the source-generated context with unmapped members and repeated properties refused (`JsonUnmappedMemberHandling.Disallow`, `AllowDuplicateProperties = false`), where `HMJsonContext` sets neither today (`HMJsonContext.cs:36-58`). Under today's options `{"id":"user-pro","inptuReports":{...}}` loads with no input reports, a misspelled key inside `protocol` is skipped, and a second `protocol` replaces the first. Under the strict options each is refused, at `$.inptuReports`, `$.protocol.sise` and `$.protocol` (`SP\dd2\form` mode `json`, `DD2-jsoncheck.log`). Read through the SDK's own context with the strict options, 305 of the 336 catalog profiles load and 31 are refused for two keys the object model leaves unmapped today, and for nothing else: `nativeDescriptor` in 30 profiles, the descriptor read from the real device beside the one the profile presents, and a `comment` inside `steam-deck-composite`'s extended report (`SP\dd2\r4\strictcat`, `DD2-strictcatalog.log`). `nativeDescriptor` becomes a mapped string no code reads, and `comment` becomes a mapped documentation key on the extended report, as it already is on a feature answer (`ControllerProfile.cs:693-695`), so a user's copy of `steam-deck-composite` from v1.7.0 on still loads. Read the same way, the 260 earlier catalog versions of the v1.0.0 to v1.12.0 tags are refused for these two keys and no other (`SP\rev4\strict-old.log`, and `DD2-r5-strict-oldprofiles.log`, which lists every key a file carries rather than its first). With both mapped, the one earlier copy that v2.0.0 still refuses is `steam-controller-2` of v1.9.1, for its `steamFirmwareStamp`, by design and with the replacement named.

A file that does not parse, a key the schema lacks, a key written twice, a value validation refuses, one of the two dropped spellings, and a profile id already loaded each become an entry of `HMContext.ProfileLoadIssues` with the file, the JSON path and the reason, and the profile is refused. The path is the one the file writes, `$.layout.sticks[1].clickButton` for a stick's click inside the layout: every array index, and each key as the file spells it, since the reader matches keys without regard to case. Files load in ordinal path order, and a repeated id refuses the later file and names the earlier one, so a user's edited copy of a catalog profile needs an id of its own. A file with no `id` is listed as not a profile. A null or a value of the wrong shape where a check reads a list, an object or a name is refused at its path like any other value, and an exception no check expected refuses its own file at `$` with the exception named: a load never throws for a file's content, and one bad file never keeps the rest of its directory from loading. A model a profile takes by name or by identity that fails (step 3 above) is listed too, and the profile loads with the identity default. The entry names the value that went wrong in the file that holds it: the profile's `$.deviceModelFrom` for a name no model answers, and the model file and its key for a model that does not fit the profile, whose id and file the reason names. Nothing is dropped without an entry: `ProfileDatabase.Load`'s silent catch (`ControllerProfile.cs:891-895`) and the duplicate skip in `HMContext.LoadProfilesFromDirectory` (`HMContext.cs:296-312`, whose summary says a later load wins) go. A layout is checked against the descriptor at load too, where today `HMLayoutValidator` runs only when a create first builds the report (`ControllerProfile.cs:528-533`), so a layout that names an axis or button the descriptor lacks is a load issue with its path.

One exception type reports a bad profile at create. `CreateController` throws `HMProfileException`, derived from `InvalidOperationException` as the SDK's other exceptions are, with `ProfileId`, `File`, `JsonPath` and `Reason`, for every defect of the profile itself: a model that does not compile, a layout that does not fit the descriptor (in a profile built in code), and a profile with no descriptor, which today throws `ArgumentException` (`HMContext.cs:405-406`, `542-543`). `HMProfileBuilder.Build` throws it for its own errors. `HMLayoutValidationException`, which derives from `Exception` (`HMLayoutLoader.cs:500`), is no longer thrown by a create. `HMLayoutValidator.Validate`, public in `HIDMaestro.Internal` (`HMLayoutLoader.cs:296-298`), keeps throwing it for a caller that validates a layout itself. A null profile is still `ArgumentNullException`. The coexistence design's Migration item for `CreateController` (`docs/design/v1.13.0.md:285`) names `HMProfileException`, and Migration lists the two types it replaces at create.

A directory a program loads can hold what a JSON author would otherwise need a rebuild for: named models and an `identity-defaults.json` in a `models` folder, in the catalog's formats. The loader reads `models/**` as models and never as profiles, in a user's directory as in the catalog, whose embedded profile glob leaves the folder out and embeds it under a logical name of its own (mechanism 2). Its models resolve by name for its profiles and for later loads, for a builder copy of one of its profiles and for the profile `ResolveDeviceModel` returns, and two directories loaded into one context at once keep both folders' models. Its identity defaults are tried before the catalog's, for profiles outside the catalog only, and a use reads `identity:<file>#<entry>` in `DeviceModelSource`. A model id or entry name that repeats one already loaded is refused as a repeated profile id is. Three limits stay, and the user-profile documentation states them: a `keyedHexFile` source is refused on UMDF2, where the driver serves answers without calling the SDK, `deviceModelFrom` names only a model the release or a loaded directory holds, and a profile outside the catalog runs on the interpreter until it joins the catalog.

## Decisions

### (a) One arithmetic: nearest, ties to even, in double

Every normalized-to-wire conversion computes `min + RoundHalfEven(v' x (max - min))` in double, where `v'` is the clamped float input or `1 - v` for a field whose wire grows the other way. A float carries 24 significant bits, so the product is exact in double for any range below 2^29, and the only rounding is the last one. A ratio scale such as `[13371, 936]` is `(v x 13371) / 936`, one exact product and one correctly rounded division. XInput's thumb Y grows upward, so the XUSB slice treats it as an inverted field, and its 10-bit trigger slice carries the smallest value whose `g x 255 / 1023` (the companion's integer decode, `companion.c:643-644`) is the trigger byte, so every companion, old or new, reads back the byte the rule chose. A NaN input writes the field's rest value, the value of the axis left unwritten with nothing on its fallback key (0.5 for a stick or centered axis, 0 for a trigger), and never reads the fallback key (mechanism 1), on every path: the descriptor path, the XUSB slice, the codec, the centered axes, both Switch packers and the output encoder. Today each site writes what its encoding gives a NaN, so one XInput stick reads full left on X and full up on Y.

The test ran offline on the devbox, and the plan carries it into the tree as `arith_roundtrip_check`. It runs the SDK's own code at 9bd6279 beside transliterations of each old formula and finds them equal: 2,012,299 codec inputs, 1,227,144 descriptor-path writes over every one of the catalog's 24 descriptor ranges, 2,212,299 packer inputs, no mismatch. Then it takes every raw integer of every width the catalog uses and of every width from 1 to 16 bits, signed and unsigned, 76 conversions in all, normalizes each three ways a consumer would (double division, float division, float times the reciprocal), encodes it and reads it back. Under the new arithmetic every raw value returns, for every normalization. Under today's:

### (b) The protocol runs in the SDK, on both transports

One engine, in C#, serves every protocol. A UMDF2 persona's commands reach it through the output ring, and its replies and reports reach the driver through the input section in order. The driver keeps no protocol interpreter, so no two engines must agree.

Measured offline on the devbox: two processes share Local\ sections laid out like the output ring and the input section, the SDK side runs the SDK's own `ProtocolEngine` on each command (the GameCube profile's one-byte 0x12 rule) and writes the reply under the input seqlock, and a worker in the driver-side process waits on the input event as `SharedInputWorkerProc` does. The time is the command's write to the worker holding the reply. Each condition ran as 30 independent launches, a new process pair each, of 1,000 commands 200 microseconds apart, every sample recorded in arrival order with its index (`SP\dd2\rttbench` with `HMRTT_DUMP`, `DD2-rtt-ordered.log`):

| Condition | p50 / p95 / p99 | max | over 1 ms | over 5 ms | over 64 ms |
|---|---|---|---|---|---|
| idle, normal priority | 9.1 / 26.1 / 42.3 microseconds | 24.45 ms | 35 of 30,000 | 13 | 0 |
| idle, both threads above normal | 9.1 / 25.5 / 36.9 | 0.44 ms | 0 | 0 | 0 |
| a blocking gen-2 collection every 50 ms in the SDK process | 11.8 / 1,040.7 / 1,820.0 | 3.96 ms | 1,600 | 0 | 0 |
| the same, above normal | 19.4 / 1,094.5 / 2,055.0 | 21.87 ms | 1,667 | 6 | 0 |

The samples over 5 ms sit inside single launches at scattered positions, launch 16 of the normal-priority idle run (positions 0 to 836) and launch 2 of the above-normal collection run (positions 635 to 868), the pattern other work on the machine leaves. Nothing correlated them with that work. A second session's review run gave the same shape: idle at normal priority 27.1 / 41.5 / 53.6 microseconds with a 3.44 ms maximum, and above normal 24.9 / 40.8 / 57.0 with 2.81 ms. The in-driver engine with no hop answers in 0.5 microseconds at p50.

The consumers' budgets, from their source (SDL-reference 804cf65, jc_toolkit 9d0cc45, BetterJoy b671563, eden 1dcc574, Chromium device/gamepad 8f4e5324):

| Consumer | Window per attempt | Attempts |
|---|---|---|
| jc_toolkit | one 64 ms read, at most 9 reads (`jctool.cpp:196-224`) | 20 resends |
| eden, its own Pro driver, off by default | 66 ms per read, at most 12 (`common_protocol.cpp:78-95`), and any 0x21 ends the wait | 7 for SPI, on an address mismatch |
| SDL | 100 ms from the write's return (`SDL_hidapi_switch.c:416-417`, `521`) | 5 (`1251-1260`), and a failed factory stick read fails the open (`1018-1021`, `1661-1664`) |
| BetterJoy | 100 ms per read, at most 10 (`Joycon.cs:1170-1191`) | 100 for SPI (`1317-1322`) |
| Chromium | 3,000 ms (`nintendo_controller.cc:82-90`) | 4 sends a step, then a restart, without end |

A stalled stream is looser still: SDL reconnects a Bluetooth pad in full mode after 3,000 ms of silence (`SDL_hidapi_switch.c:2866-2873`), and no other host reacts. SDL's own comment puts a real pad's average reply at about 30 ms (`416`). The slowest sample of the 120,000 above took 24.45 ms, under half the tightest window, which jc_toolkit retries. The protocol thread runs above normal priority, as the idle-frame pump and the USB/IP input pump do (`HMController.cs:610-613`).

The live measurement is prepared and not yet run: a probe creates `switch-pro`, runs SDL's Bluetooth init and 100 SPI reads per run, times each reply and the 0x30 cadence, and writes every sample with its run, kind and time since start, under three loads on its own process: none, a thread forcing a blocking gen-2 collection every 50 ms, and EcoQoS execution-speed throttling. It runs as ten launches of three runs each, a new controller per launch, so a slow create or a process-wide state shows in one launch and not in all. Each launch exits 0 only when no subcommand goes unanswered, none takes longer than 64 ms and the p99 is under 5 ms, and the pooled samples must hold the same. It runs against 9bd6279 and against the conversion.

The driver interpreter was the alternative. It would keep replies in the driver host, but it is a second engine in C that must match the C# one rule for rule, and every new protocol feature would land twice. A shared native engine would put a native DLL into a single-assembly SDK that ships NativeAOT and single-file builds. The measurements leave no reason for either.

One behavior differs. With the program hung or gone, today's driver still answers subcommands from the last state, and the SDK path answers nothing, as a real pad with a hung controller chip answers nothing. A killed program's devices are removed by the next sweep.

### (c) Version 2.0.0: no device code, and programs built on v1 SDKs

The release is v2.0.0, and it drops the hand-written methodology. The Sony feature table and its CRC, the DualShock 3 sixaxis form, the Switch Pro responder, and the XUSB gamepad answers with their vendor-ID rumble gate leave `driver.c`, `driver.h` and `companion.c` entirely. That is the whole of the 24 regions DD-0's static check names, 20 in `driver.c`, 2 in `driver.h` and 2 in `companion.c`, including the parts inside shared functions (`ProcessSharedInput`'s Switch return and DualShock 3 derivation, the READ_REPORT, WRITE_REPORT, SET_OUTPUT_REPORT and GET_FEATURE branches, the stream thread's start and cleanup) and the context fields they use (`driver.h:96-113`, `258-312`, `companion.c:69-76`). The `Bluetooth` and `Ds3Sixaxis` reads go with them, since nothing else read either. So does the device each driver starts as before it reads its configuration: `G_DefaultReportDescriptor`, an Xbox 360 gamepad's (`driver.h:589-590`), the 045E:028E attributes and "Controller (XBOX 360 For Windows)" string `EvtDeviceAdd` sets first (`driver.c:2513-2537`), and the companion's 045E:028E (`companion.c:457-460`). A devnode without its configuration fails its start (Defects). No marked region, no model mode, no older-driver mode and no SDK mode decision remain. The static check allows no device-specific region in the SDK, the drivers, the companion or hmswd. The OpenVR host in `HMVR` and `VrDriverBuilder` keeps its SteamVR names, since it hosts HIDMaestro's own controllers under SteamVR and names no device.

The version contract. Before the devnode exists (`DeviceOrchestrator.cs:1267-1277`, `SharedMemoryIO.cs:409-424`) the v2.0.0 SDK writes into `Global\HIDMaestroVersion<N>` 4 as both its oldest driver protocol (`SdkProtocolMin`) and the protocol it speaks (`SdkProtocolMax`), and the controller's identity tag: the 64-bit FNV-1a hash of its identity token's UTF-16LE code units, with no terminator, the bytes the driver holds in its instance ID. `HM_0000` hashes to 0x1FD048916B8D461F and `HM_0123456789ABCDEF` to 0x3B86F3634086D831, vectors `driver.h` and the SDK's test both carry. Tokens are `HM_` and uppercase hex or four digits (`DeviceIdentity.cs:94`), so no case folding is needed. The section keeps one job: it tells a driver whose configuration a devnode carries. The driver reads a controller's v2.0.0 values (`FeatureAnswers`, `XusbAnswers`, `XusbCompanion`, `LiveFeatureReport` and the cached input report IDs) and starts the protocol host's lanes only when, at `EvtDeviceAdd`, the section exists, `SdkProtocolMin <= 4 <= SdkProtocolMax`, and the tag equals the tag of the devnode's own token. A later SDK that speaks 5 and still runs on 4 therefore still gets its values read by this driver, and every blob format is frozen at protocol 4: a later protocol adds values and changes none. A v1.12.0 program creates no section (`driver.c:619-641` opens it best effort), and a section dies with the program that made it, because the driver lets go after writing its half (`616-641`). A value a killed v2.0.0 program left in the configuration key therefore never reaches a v1 program that takes the index later: the driver does not read it. A 9bd6279-era build, which wrote protocol 3 and never shipped, counts as a v1 program. The decision is made once at add and holds for the devnode's life.

One field per driver. The HID driver writes its half at add: `DriverProtocol` 4, `DriverVersion`, `DriverCapabilities`, and `DriverProtocolMin` 4, the oldest SDK protocol it serves. The companion writes its own field, `CompanionProtocol` and `CompanionProtocolMin`, and nothing of the HID driver's. Neither clears anything in its cleanup callback, and a restart writes the same values again, so a companion restart during a create (`DeviceOrchestrator.cs:942-948`, `965-967`) cannot zero the HID driver's protocol before the SDK reads it. A driver that cannot read a blob it should (mechanism 4) writes which value failed into its own error word, `DriverConfigError` or `CompanionConfigError`, before it fails its start. The SDK runs on a driver whose range from `DriverProtocolMin` to `DriverProtocol` holds 4, and reads the companion's field for a controller with a companion, so a later driver that drops protocol 4 is refused rather than passing a check of the maximum alone. No release has shipped this section, and its fields keep their offsets: the reserved bytes 36 to 63 (`driver.h:392-402`) carry `DriverProtocolMin` at 36, `CompanionProtocol` at 40, `CompanionProtocolMin` at 44, the identity tag at 48, `DriverConfigError` at 56 and `CompanionConfigError` at 60.

The index before the first start. Today the driver and the companion read `ControllerIndex` from the device's hardware key at add and fall back to 0 (`driver.c:243-264`, `companion.c:457-476`). The ROOT path writes it before it installs the driver (`DeviceNodeCreator.cs:332-349`), but both SWD paths write it after `SwDeviceCreate` has bound and started the driver (`DeviceOrchestrator.cs:791-813`, `909-929`), so a fresh token's first start reads index 0 and a later life's reads the index of its previous life. The v2.0.0 SDK writes the controller's index under `SOFTWARE\HIDMaestro\Identity\<token>` where it writes the instance configuration (`WriteInstanceConfig`), before the deploy gate and any PnP work, and deletes it with the controller's configuration. The driver, before `WdfDeviceCreate`, reads its device instance ID through `WdfFdoInitQueryPropertyEx` (`DEVPKEY_Device_InstanceId`, for which Learn gives UMDF 2.0 and says a driver calls it "only before calling WdfDeviceCreate", and the WDK's UMDF 2.15 header declares it, `wdf/umdf/2.15/wdffdo.h:226-269`, the version the INFs pin at `hidmaestro.inf:107` and `hidmaestro_xusb.inf:117`), takes the token from its last segment, which issue #60 fixed on both enumerators (`SWD\<enumerator>\<token>` and `ROOT\<enumerator>\<token>`, `DeviceNodeCreator.cs:133`), and reads that key. The identity tag then proves the index is this devnode's. A v2.0.0 program writes the entry and the section before any PnP work, so a devnode with no entry, or whose entry names a section that is gone, does not speak 4 or carries another token's tag, as an entry a killed program left does, is a v1 program's. It reads no v2.0.0 value and takes `ControllerIndex` from the hardware key as every version does, and if that index's section carries another token's tag, the devnode is not that controller and fails its start with STATUS_DEVICE_CONFIGURATION_ERROR, which the v1 program's own restart after its index write recovers. The same early read gives `FunctionMode` its own controller's key (Defects). Two drivers on disk read the same key: BthPS3PSM through `WdfFdoInitAllocAndQueryPropertyEx` at add, before `WdfDeviceCreate`, under KMDF (BthPS3 1bdde12 `BthPS3PSM/Device.c:108-112`, `392-414`), and DsHidMini, a UMDF2 driver, through `WdfDeviceAllocAndQueryPropertyEx` after it (271dfc3 `driver/Ds3.c:305-313`). In the WDF source both calls reach one function, which asks the device stack's `GetUnifiedPropertyData` (Windows-Driver-Frameworks b6191d9 `src/framework/shared/core/um/fxdeviceum.cpp:1568-1645`, the FDO entry at `fxdeviceinitapi.cpp:1655`, its FDO check at `1748`). What no source on disk shows is the closed UMDF host serving that call on the stack before `WdfDeviceCreate`, so the design takes the dependency without a fallback, since `WdfFdoInitAllocAndQueryPropertyEx` makes the same call, and DD-2's first bench run proves it live before DD-3, DD-5 and DD-6 build on it. `SwDeviceCreate`'s property list was the other way to pass the index, but Learn says only that those properties are set "after it is created but before a notification that the device has been created are sent" (SwDeviceCreate, ms.date 2018-12-05), which does not order them against the driver's start.

A v1 program on the v2.0.0 driver. A v1.12.0 program's `InstallDriver` replaces an installed driver whose payload differs from its own and removes every HIDMaestro device first (`docs/design/v1.13.0.md`, "Compatibility"), so it runs on its own driver whenever that call succeeds. It meets the v2.0.0 driver when it creates without calling `InstallDriver` or when the call fails, and a native writer meets it the same way. No shared section's layout changes, so its controllers run the data path every layout version shares, and the driver does only this for them:

- It reads the values v1.12.0 writes and every version reads: the descriptor, `VendorId`, `ProductId`, `VersionNumber`, the strings, `InputReportByteLength`, `ControllerIndex` and `FunctionMode` (`DeviceOrchestrator.cs:639-690`). It reads no v2.0.0 value, and no code reads `Bluetooth` or `Ds3Sixaxis`.
- A frame of the data lane goes out under the descriptor's first report ID at the declared input length, as at 9bd6279 (`driver.c:1903-1958`). A frame of the extended lane goes out verbatim when its length equals the declared input length of the report its first byte names, or, for a descriptor without report IDs, of its one input report. Any other frame is not sent, and the last sent report stands. The driver builds that table of lengths from the descriptor at add, so it needs no new value and holds for v1 programs and for any later device. 9bd6279 bounded the frame only by the 80-byte buffer, and `InputReportByteLength` would be the wrong bound, since the SDK computes it from the first report ID the descriptor names (`DeviceOrchestrator.cs:2480-2531`). `dualsense-bt` declares inputs 0x01 of 10 bytes and 0x31 of 78, and its 0x31 frames pass that bound only because the profile sets `inputReportSize` to 78, as every catalog UMDF2 profile with an extended report but `dualshock-3-full` sets it. Of the catalog's 11 UMDF2 extended reports, 10 equal their report's declared length, and the 11th, `dualshock-3-full`'s 49-byte native report, is no input report its descriptor declares (12 bytes, no IDs) (`SP\dd2\r4\idlen.py`, `DD2-idlen.log`).
- Output reports and SET_FEATURE reach the output ring as they do for every profile. GET_FEATURE answers the PID block's reports as it does for every profile and fails any other report with STATUS_NOT_SUPPORTED, publishing no notification (`driver.c:3404-3415`). GET_INPUT_REPORT of IDs 0 and 1 returns the last frame, with no report-ID filter.
- The companion reads its answers only under the contract and registers its XUSB interface (`companion.c:589`) only when it holds them. Without them it registers none, so no reader opens a device that would answer nothing.
- No stream thread and no protocol host start, and no device answer is made up.

Three more consequences follow from the policy and from v1.12.0's own create. A v1.12.0 program with no controllers present is invisible to the census, so a v2.0.0 program's policy can upgrade the driver under it, and its next create runs on the v2.0.0 driver with the losses above without calling `InstallDriver` again. A v1.12.0 XUSB create on the v2.0.0 driver waits 5 s for the XUSB interface and restarts the companion, three times, before it gives up on the interface (b4d29d9 `DeviceOrchestrator.cs:1048-1053`), since a companion without answers registers none. A v1.12.0 create through either SWD path on a fresh token starts its devnode once with no index anywhere, which fails that start (Defects), and its own restart after its index write starts it on its index. Whether `hmswd`'s create reports that failed first start as a failed callback, which would fail the v1 create, is not settled from source. DD-7's v1 tests create a fresh-token xinputhid profile and a fresh-token XUSB profile to settle it, and if the callback fails, the table's xinputhid and XUSB rows gain that loss for a v1.12.0 program's first create of each token.

One case stays outside every gate. A v1.12.0 program picks indexes from 0 inside its own process (b4d29d9 `HMContext.cs:366-373`) and opens existing sections, so it can land on an index a running v2.0.0 program holds. Both programs then write one input section, which is broken before any gate, and the coexistence design records that a v1.12.0 program cannot be fixed from here (`docs/design/v1.13.0.md`, "Compatibility").

A v2.0.0 program on an older driver. `DriverDeploy.MinimumDriverVersion` becomes 2.0.0 (`DriverDeploy.cs:45`), so the deploy policy the coexistence design set out (`docs/design/v1.13.0.md:108-121`, `DriverDeploy.cs:161-260`) reads:

| Installed driver | Outcome |
|---|---|
| none | `Installed` |
| this SDK's payload, or its stamp with the record missing | `AlreadyCurrent` |
| newer | `KeptNewer`, never downgraded, and the SDK runs on it at protocol 4 or later |
| older, no present device of any program on it | `Upgraded` |
| older, held by devices of running or unknown programs, 2.0.0 or later | `KeptInUse` |
| older, held the same way, older than 2.0.0 | `HMDriverVersionException` naming each holder |

The last row is today's rule for drivers older than 1.12.0, moved to 2.0.0, and it replaces the older-driver mode. `InstallDriver` reaches the policy directly. The create reaches it through its deploy gate, which today runs the policy only when the driver store lacks a package of either INF, of any version (`DriverDeploy.cs:277-298`, `DriverBuilder.cs:740-770`). Where a v1.12.0 program such as PadForge has installed its own driver, the store holds that driver's two packages, the gate passes, and the create would bind the old driver and fail only afterward. The gate therefore also runs the policy when the newest installed stamp of either INF is older than `MinimumDriverVersion`, so a create meets the same rule as `InstallDriver`, before any PnP work. Both INFs count, since `InstalledDriver()` reads `hidmaestro.inf` alone (`DriverDeploy.cs:86-90`), and a store holding a 2.0.0 `hidmaestro.inf` beside an older `hidmaestro_xusb.inf`, as a half-failed install leaves it, would otherwise pass the gate and fail at the companion's start. The policy reads both too. A held driver is kept in use only when both INFs' newest packages meet the floor, and is refused otherwise under alternative A, naming the older INF's version. A newer main package stays, and this build's package of the other INF is added beside it when that one is below the floor and nobody holds it. An INF with no package at all gets this build's, held or not, since adding a package touches nothing installed. The gate's cache follows the same rule: it confirms the installed manifest (`DriverDeploy.cs:294`) only when both stamps meet the floor, so its fast return (`282-284`) never skips the check for a driver older than 2.0.0, whose program writes the same manifest record (b4d29d9 `DriverBuilder.cs:421-422`, `470`). With no holder, the policy upgrades the driver, and a v1 program that starts afterward without reinstalling runs on the v2.0.0 driver as above. `KeptInUse` remains for an older v2 build that live controllers hold. After the deploy step the create reads the version section once the device has started. Its wait for the start (`WaitForDeviceStarted`, a 25 ms poll of `DN_STARTED`, `DeviceOrchestrator.cs:1634-1655`) also ends when the devnode reports a problem code, a failed add or start, or when a driver's error word is set, so a start the driver fails fails the create within one poll, not at the wait's 5 s budget. The codes are 10, 31 and 37 for a failed start, add or DriverEntry, 39 for a driver that did not load and 43 for one that failed after it started, as a crashed UMDF host leaves its device (`cfg.h:77`, `98`, `104`, `106`, `110`), and the error names the code it read. The ROOT path's own wait for its HID child, inside `DeviceNodeCreator.CreateDeviceNode`, ends the same way: the enumeration notification still wakes it as the child appears, and it re-checks for a failed start every 25 ms. A driver whose range does not hold 4, or a companion whose field does not, fails the create, removes its devnode and throws `HMDriverVersionException` naming the driver's version and the devnode, which is what a mis-stamped driver, or a later one that dropped protocol 4, gives. The exception's `Problem` says which case it is: `HeldOlderDriver` at the gate, whose `Blockers` are the devices and programs to close, `ProtocolNotServed` for that range, and `ValueNotRead` for a set error word, whose `Blockers` hold the create's own removed devnode. Only an older driver is answered by `InstallDriver`: a newer one that dropped protocol 4 needs an SDK of its release, and the message says so. A start failing with no error word throws `InvalidOperationException` with the problem code. The coexistence design's version-section fields change with this (`docs/design/v1.13.0.md:127-140`): the SDK writes 4 as its oldest driver protocol and its own, and the v2.0.0 driver keeps every older section layout without the device behavior older drivers attached to them.

What a create does on an older driver that live v1 controllers hold is the owner's choice between two rules. Both are written out here so either can be applied as soon as the owner answers, and neither puts device code in v2.0.0. The coexistence design's headline was that a v1.12.0 program and this release run side by side (`docs/design/v1.13.0.md:118`, `268`), and its probe's section E1 checks that with a generic pad, BEEF:F0E1 (`coexist_check\Program.cs:547`).

Alternative A refuses every create on that driver.

- Every UMDF2 create of a v2.0.0 program throws `HMDriverVersionException`, whatever the profile. Its `Blockers` name the devnodes and "a running program built on HIDMaestro 1.12.0" (`DriverDeploy.cs:314-331`), and `MinimumVersion` reads 2.0.0.
- USB/IP creates go on: they do not run on the HIDMaestro driver, the deploy gate is on the UMDF2 path (`HMContext.cs:457-458`, `DeviceOrchestrator.cs:1309`), and the policy's census leaves USB/IP controllers out (`DriverDeploy.cs:197`). The 8 USB/IP catalog personas create beside PadForge.
- No v2.0.0 controller ever runs on a driver older than 2.0.0, so the post-start check requires protocol 4 on every create.
- The coexistence headline changes: while a v1.12.0 program's controllers are up, PadForge's included, no v2.0.0 program creates a UMDF2 controller, until that program moves to v2.0.0 or its controllers go. E1's generic create expects the exception, and the Compatibility paragraph says so.
- Code: the floor and the gate's stamp check, nothing more.

Alternative B allows the create on that driver when the profile's resolved model is empty in every group and no identity-default entry matches it.

- The identity defaults are the v1.12.0 driver's gates: the Sony table on VID 054C, the Switch responder on 057E:2009, the sixaxis form on `Ds3Sixaxis` and the Bluetooth CRC on `Bluetooth` (b4d29d9 `driver.c:471-472`, `524-530`, `2784-2792`), and the companion's vendor gate, which runs only where there is a companion. A profile that passes the rule reaches none of that code, provided no `Ds3Sixaxis` or `Bluetooth` a v1 program left survives in its key, and DD-2's `WriteInstanceConfig` deletes the controller's key and writes it anew, so none does. Such a profile has no companion and no xinputhid parent, so it takes the ROOT path, which writes `ControllerIndex` before it installs the driver (`DeviceNodeCreator.cs:332-349`), and the old driver reads the right index at its first start.
- In the catalog, 291 of the 328 UMDF2 profiles pass: the generic gamepads, wheels, flight sticks and pedals, the keyboards and mice, the PID force-feedback profiles, the Luna and UMDF2 Valve profiles, the Nintendo profiles other than 057E:2009, and the Microsoft profiles without "xbox". 37 do not: 14 Sony profiles, 12 xinputhid profiles, 10 XUSB profiles and `switch-pro`, and `switch-pro-usb` will be a 38th (`SP\dd2\r4\eligible.py`, `DD2-r3fb14-eligible.log`, read at 9bd6279 with each family's converted keys).
- The deploy gate and the post-start check read one predicate, computed at load from the resolved model and the identity-default table, both data. The gate evaluates it before its cached fast return (`DriverDeploy.cs:282-284`), and confirms the manifest only for a driver of 2.0.0 or later, as above. Otherwise the first create that passes the rule on a held v1.12.0 driver would confirm v1.12.0's manifest, and the program's next create, of `dualsense-bt`, would take the fast return, bind the v1.12.0 driver and meet its Sony table, caught only by the post-start check after PnP work. The price is that each create on a held v1.12.0 driver takes the policy's census again. For a profile that passes the rule, the post-start check accepts a driver that writes no version section.
- On the old driver such a controller has what a v1.12.0 program's generic controller has, and lacks what only the v2.0.0 driver does: the exact-length bound on extended frames, the failed start for a missing configuration, the index read before `WdfDeviceCreate`, so `FunctionMode` still comes from `Controller0` for every index (b4d29d9 `driver.c:2152-2165`), and `HMController.DriverVersion`, which reads null.
- The program's own controllers on the old driver hold it too. Until its last one is disposed, its create of a profile that fails the rule throws `HMDriverVersionException` naming "this program" (`DriverDeploy.cs:323`), and the policy cannot upgrade the driver after the v1.12.0 program exits.
- E1 keeps its generic create beside the v1.12.0 peer and its expectation, the Compatibility paragraph holds for the profiles that pass, and DD-7's refusal case moves to `dualsense-bt`.
- Code: the predicate, and a test that holds it to a golden list over the catalog. It names no device.

Under either rule, a v1.12.0 PadForge that launches beside a v2.0.0 program removes that program's controllers, since its `InstallDriver` removes every HIDMaestro devnode first (plan, PadForge list).

The tests run in `coexist_check`, whose v1.12.0 and v1.11.0 peers are built against the released DLLs at pinned hashes (`CoexistCheck.csproj`, `fetch_legacy.ps1`). A v1.12.0 peer, with its `InstallDriver` call skipped, creates on the v2.0.0 driver, after the probe has checked each devnode's driver version, one profile of each UMDF2 row of the table above: `amazon-luna-usb`, `xbox-one-s` (xinputhid), `dualshock-4-v2`, `dualsense-bt`, `dualshock-3-full`, `switch-pro` and `xbox-360-wired`. For each it records the frames sent, every declared feature ID with its status and notification, the replies to SDL's init, and the companion's interfaces and IOCTL answers, and every row must hold as the table states. The input bytes must equal the bytes the peer wrote under the rules above, every Sony feature ID must fail as not supported with no notification, no 0x21 reply may follow a subcommand, `dualshock-3-full` must send no frame, and the Xbox 360 pad's companion must expose no XUSB interface, after three 5 s waits and three restarts. The peer also creates a fresh-token xinputhid profile and a fresh-token XUSB profile, which settles the open question above. Four stale-state cases run too: a killed v2.0.0 program leaves `FeatureAnswers`, `XusbAnswers`, `XusbCompanion` 1, `LiveFeatureReport` 1 and a cached report-ID list in its key, then the v1.12.0 peer creates `dualsense-bt`, `xbox-360-wired`, `dualshock-3-full` and a generic profile on that index. No GET is answered from the blob, GET_FEATURE of the DualShock 3's report 0 fails and serves no live store, no XUSB interface appears, and every frame reaches the input cache. Two refusal cases run as well, following the owner's choice. Under alternative A, a v2.0.0 peer whose create of a generic profile meets a v1.12.0 driver held by a running v1.12.0 peer gets `HMDriverVersionException` naming that peer and creates nothing. Under alternative B, the generic create succeeds on the v1.12.0 driver, and the peer's create of `dualsense-bt` gets the exception and creates nothing. Under both, the same create with every holder gone upgrades the driver and succeeds.

### (d) Public API named after a device

`SteamFirmwareStampSpec` and `FeatureStubReport.SteamFirmwareStamp` (`ControllerProfile.cs:686-716`) go away, replaced by `FeatureStubReport.Patch` (`AnswerPatchSpec`) and `ControllerProfile.ValueSources` (`ValueSourceSpec`). The JSON key `steamFirmwareStamp` goes with them (mechanism 1). `ControllerProfile.IsXboxBranded` goes with the heuristic, which moves into the identity defaults as data, and `RequiresXusbCompanion` stays as a read of the resolved `xinput` block. `ControllerProfile.SixaxisCompatible` goes, since no driver reads `Ds3Sixaxis` any more. The JSON key `sixaxisCompatible` stays readable and picks the DualShock 3 model through the identity defaults. `HMButtonRole.Xbox` and `HMButtonRole.Ps` stay in the stable namespace, where v1.12.0 shipped them (`HMLayout.cs:92`): they name the legend a layout prints on a system button, as `Guide`, `Home` and `Capture` do, and no SDK or driver code reads them. No member is kept for compatibility: the types live in `HIDMaestro.Internal`, and the docs say what that namespace promises, which today they do not. The README and `docs/INTERNALS.md` state it: the types in `HIDMaestro.Internal` are the profile JSON's object model, public so a program can read and build profiles, and they follow the JSON schema, so a key the schema renames or removes changes them, and the Migration section lists each change. The stable surface is the `HIDMaestro` namespace, which gains `HMProfile.HasDeviceModel`, `HMProfile.DeviceModelSource`, `HMProfile.DeviceModelProblem`, `HMProfile.BuildsItsOwnReports`, `HMContext.ProfileLoadIssues`, `HMDeviceExtractor.ResolveDeviceModel` and `HMProfileException`, and nothing device-named. v2.0.0 already lists one change in that namespace (`HMLayoutJsonOptions.Default` became read-only).

`HMProfileBuilder.FromProfile` copies the whole profile, and the builder gains `DriverPid`, `XInput`, `FeatureAnswers` (the JSON of the `featureStubs` key, so no public member names a type of `HIDMaestro.Internal`), `DeviceModelFrom`, `DeviceModel` (`"none"`, as a file says it) and `ClearDeviceModel`. A code-built copy of a catalog profile behaves as the catalog profile: a copy of a USB/IP persona is a USB/IP persona and a copy of `dualshock-3-full` keeps `sixaxisCompatible`. Replacing the copy's descriptor drops the keys that descriptor's report format governs ("Profiles made outside the catalog").

## Proving the converted paths byte-identical

Today's code is the oracle. The first lane of the plan records it at 9bd6279 before anything changes: the codec, the packers, the descriptor path and the XUSB slice for scripted and seeded random states on every affected profile, with each decoded field's boxed type, `Switch2ProDevice` for scripted and random command streams, the USB/IP feature answers through `usbip_server_check --offline`, and the driver's Switch responder, Sony table, DualShock 3 form and companion answers through a native harness that compiles those functions from `git show 9bd6279:driver/driver.c` against stubbed WDF calls, as `gc_dolphin_check` builds Dolphin's code. The harness compiles the merged base's sources too, since the base moves past 9bd6279. Every later lane replays the recordings. A difference fails unless it is in the change list of decision (a) or (e).

Each replay test proves it can fail before it counts: a mutation run, one op or byte of the converted program changed, must make the replay fail, and the lane keeps that log. Each converted program meets the replays twice, generated and interpreted, and mechanism 2's equivalence check compares those two forms and the naive evaluator byte for byte. A lane's other failing-first tests assert a behavior the base gets wrong. A test that fails only because a key or type does not exist yet does not count. Replay cannot prove locking, since the native harness runs one fiber at a time, and no lane cites it for that.

The plan names the harness defects the review of the first lane found and makes each fix a precondition of the first replay that relies on it: wait timeouts recorded and honored, write requests carrying their report ID where MsHidUmdf puts it, the instance configuration produced by the SDK's own `WriteInstanceConfig` rather than a hand copy, the Switch 2 Pro decode and raw submits recorded, the live comparison failing on empty recordings and on a driver that is not 9bd6279's, version-section parameters (absent, protocol 3, protocol 4) in the harness, and `record` refusing to overwrite the oracle from a converted tree.

A static check, `device_shortcut_check`, fails at 9bd6279 and passes at the end. It lexes C# and C with comments and string contents apart, drops keywords, splits identifiers at CamelCase, snake_case and digit boundaries into lowercase words, and applies four rules:

- A, names: a word from a list of device and vendor names in any identifier, file or type name, unless the whole identifier is on an allowlist with its reason (HID usage names such as `HatSwitch`, `SafetySwitch`, `ActuatorOverrideSwitch`, `ProfileSwitch` and `ModeSwitch*`, the `Xbox` and `Ps` button roles, and the OpenVR host in `HMVR` and `VrDriverBuilder`, which hosts HIDMaestro's own controllers under SteamVR and names no device).
- B, IDs: a catalog vendor ID, or a product ID of the catalog or of a listed device, as a number in any base, a local or constant traced to an ID comparison, a string (`VID_045E`, or an INF `%token%` resolved), or as split bytes in an initializer or a pair of comparisons, when the other operand or the initializer's name is a vendor, product or device ID, and catalog product strings, profile ids and device words as string literals or as constants followed into a search. The XUSB INF's three model lines are allowed by line, decision (e).
- C, single-profile fields: a profile key, or a value of an enumerated key, that exactly one catalog profile sets and the SDK or a driver reads, unless the allowlist names the general mechanism it belongs to.
- D, no exempt regions: no region of any scanned file is exempt from A to C, and a `frozen-compat` marker anywhere fails.

It scans the SDK's sources including the generated JSON context and the generated program kernels, the build tool that emits them, the drivers' C and headers, the OpenVR driver's sources, hmswd, the INFs and the resource scripts, and prints every finding and every allowed name with its reason. The identity defaults and named models are JSON, outside its scope, as every profile is.

## What a program sees change

- Descriptor-built axes round to nearest. An unsigned axis of 2^n - 1 counts rests one count higher (0..255 rests at 128, 0..65535 at 32768), except where a profile's `axisCenters` gives its device's center. Every raw value a program reads from a device and passes back now arrives as that value, except on a 16-bit centered axis, where a program that normalizes in float gets 64 or 65 values just above the center back one count low. XInput thumbs rest at 0 and 0, and every XInput trigger byte arrives as passed, where today 252 of 256 arrive one lower. A stick the program does not write rests at its center, and a NaN in `Axes` writes the axis's rest value on every path, never the value of a fallback key, where today it wrote what each encoding gave a NaN (XInput X full left and Y full up, the codec's sticks and the Switch 2 Pro's at 0).
- A profile keeps the behavior today's gates give its identity, through the catalog's identity defaults, unless it carries its own model, names one, or says `"deviceModel": "none"`. The extractor names the model in the JSON it writes, `FromProfile` copies the whole profile, and `HMProfile.DeviceModelSource` and `DeviceModelProblem` say where a model came from and what went wrong.
- `HMProfileBuilder.FromProfile` copies the whole profile, so a plain copy of a USB/IP persona is a USB/IP persona and a copy of `dualshock-3-full` keeps `sixaxisCompatible`. Replacing a descriptor the builder holds with different bytes drops every key its report format governs ("Profiles made outside the catalog"), so a program sets the layout, the input size and the rest again after the new descriptor. A builder given no VID or PID still refuses, and a copy keeps its source's, 0x0000 included.
- A usbip answer table from v1.7 to v1.13 has no `notify` keys and keeps publishing the feature-read notification on every answered GET, since `notify` defaults to true on usbip. An entry stops it with `"notify": false`.
- `SubmitRawReport` on a device that builds its own reports writes its state block, and throws `ArgumentException` for another length. The Switch 2 Pro composite threw `NotSupportedException`.
