# Design note: v1.13.0

Two or more programs that embed HIDMaestro on one machine, NativeAOT and single-file apps, and a Wii U GameCube adapter persona. HandHeld Legend reported the coexistence and AOT failures while building HHL Gamepad Link (hhl-gamepad-link, `patches/hidmaestro-hhl.patch`). This note records what is broken at b4d29d9, the mechanism chosen for each fix and the evidence behind it, and every behavior a consumer will see change.

## What is broken at b4d29d9

Each claim below was checked against the source at b4d29d9.

Controller indices are allocated per context, but everything keyed by an index is machine-wide. `HMContext.CreateController` takes the lowest index free in its own context (`HMContext.cs:370-375`), and `CreateControllerAt` checks only its own context (`471-476`). The sections and events `Global\HIDMaestro{Input,Output,PidState,InputEvent,OutputEvent,InputAck,InputAckEvent,CompanionInputEvent}<N>` are created with `CreateFileMappingW` and `CreateEventExW`, which open an existing object of the same name without complaint (`SharedMemoryIO.cs:1023`, `1109`). The owner pipe `\\.\pipe\HIDMaestroOwner<N>` allows two instances in total and ignores a failed create (`181`, `322-326`). The registry key `SOFTWARE\HIDMaestro\Controller<N>` (`DeviceOrchestrator.cs:21-23`), the `ControllerIndex` the driver reads from the device key (`driver.c:240-264`) and the last byte of the Switch Pro MAC (`driver.c:477`) are keyed the same way. Two programs that each create a first controller both get index 0 and write each other's sections and keys. Two contexts in one process collide the same way: the class comment says they share an index pool (`HMContext.cs:17-18`), but each context has its own map while `SharedMemoryIO` keeps one process-wide table per index.

Identity uniqueness is checked per context. `ThrowIfIdentityInUse` looks only at its own context (`HMContext.cs:414-425`). Two keyless programs at index 0, or two programs that pass the same key, resolve the same token. `ClearParentIdPrefixRivals` skips a parent whose name equals the caller's token (`DeviceManager.cs:481`), so the second program creates over the first program's live devnode.

Sweeps remove devices without proof that their owner is gone.

- `InstallDriver` always runs `RemoveAllVirtualControllers(preserveInstall: true)` first (`HMContext.cs:169`), which removes every other program's live controllers.
- The once-per-session cleanup in `SetupController` (`DeviceOrchestrator.cs:1344-1384`) removes every present `ROOT\SYSTEM\0000` to `0009` device whose name or hardware id contains HIDMaestro. Its `CleanupGhostDevices` removes every present HIDMaestro device under `ROOT\HIDCLASS`, `ROOT\HID_IG_00`, `ROOT\XnaComposite`, `ROOT\HIDMAESTRO` and `SWD\HIDMAESTRO` (`448-450`), every instance under `ROOT\VID_*` and `SWD\HIDMAESTRO*` present or not (`472-476`), and the interface registrations of live devices (`509-563`). `DisableGhostXusbInterfaces` disables HIDMaestro devices that are not yet started (`621-627`), which includes another program's controller in the middle of its create.
- `UsbipBackend.SweepStaleOnce` and `DetachAllOwned` detach every import in the SDK's loopback port range except, for the first, this process's own port, and cancel re-attach attempts on every port in the range (`UsbipBackend.cs:61-131`). `IsOurLocation` decides by port range alone (`133-138`).
- `RegistryLedger.PruneDead` already releases only holders whose process is provably gone (`RegistryLedger.cs:73-85`).

Driver deployment has no cross-process arbitration. `FullDeploy` replaces the installed driver whenever the embedded payload's hash differs from the installed one (`DriverBuilder.cs:453-470`), with no notion of which is newer. The staging directory `%TEMP%\HIDMaestro_<hash>` (`186`) is reused when its file count and sizes match, with no hash check (`189-195`), and `hmswd.exe` goes into one shared `%TEMP%\HIDMaestro` for every version (`SwdDeviceFactory.cs:362-363`). A non-elevated process of the same user can write both places, and the elevated SDK runs what it finds there. Two programs calling `InstallDriver` at once on a machine without the driver collide in that shared directory: run against b4d29d9, the coexistence probe's section F had one fail with "signtool failed for HIDMaestro.dll ... The file is being used by another process". Every create also installs the driver with `UpdateDriverForPlugAndPlayDevices` and the profile's VID/PID hardware id (`DeviceNodeCreator.cs:368`), which installs the SDK's own package on every present device of that id whenever it ranks better, so a newer SDK moves another program's controller of the same profile onto its driver.

HIDMaestro.Core does not build for NativeAOT, trimming or single-file publish: 19 reflection-based `JsonSerializer` calls (`ControllerProfile.cs:731`, `795`, `HMLayoutLoader.cs:35-56`), no `JsonSerializerContext`, 113 `DllImport` declarations, `Assembly.Location` at `SwdDeviceFactory.cs:348`, and no `IsAotCompatible`.

## Ownership

A process takes one ownership claim before its first machine-wide write, and holds it until it exits. Resources it allocates machine-wide, a transport index or an identity, are claimed the same way, one claim per resource.

The claim is a named pipe created with `FILE_FLAG_FIRST_PIPE_INSTANCE` and a maximum of one instance. [CreateNamedPipeW](https://learn.microsoft.com/windows/win32/api/namedpipeapi/nf-namedpipeapi-createnamedpipew) documents the flag: "If you attempt to create multiple instances of a pipe with this flag, creation of the first instance succeeds, but creation of the next instance fails with ERROR_ACCESS_DENIED." The second claimant therefore learns it lost from the same call that would have won. With a maximum of one instance it fails on this machine with `ERROR_PIPE_BUSY` instead, because the instance limit is checked first, and either error means the claim is held. The same page states that a null or non-inheritable `SECURITY_ATTRIBUTES` keeps the handle from being inherited, and that an instance is deleted when the last handle to it is closed, which the system does when the process ends. A pipe handle has no thread affinity.

Liveness is a `WaitNamedPipe` probe with a 1 ms timeout. [WaitNamedPipeW](https://learn.microsoft.com/windows/win32/api/namedpipeapi/nf-namedpipeapi-waitnamedpipew) documents that "if no instances of the specified named pipe exist, the WaitNamedPipe function returns immediately, regardless of the time-out value", that an expired wait fails with `ERROR_SEM_TIMEOUT`, and that a timeout of 0 is `NMPWAIT_USE_DEFAULT_WAIT`, the server's default, which is 50 ms when the server passed 0. Measured on this machine: a missing pipe fails with `ERROR_FILE_NOT_FOUND` in under 5 µs, and an instance its server created but never connected counts as available and returns true. A true return and `ERROR_SEM_TIMEOUT` both mean a live holder, and `ERROR_FILE_NOT_FOUND` means none. Any other error counts as live. The probe opens no handle, so probing cannot keep a claim alive.

A named kernel object judged by `ERROR_ALREADY_EXISTS` was the other candidate, and it failed on one point. Measured on this machine, 2026-10-14:

| Case | Named pipe, first instance | Named event |
|---|---|---|
| Second claimant while the holder lives | loses, `ERROR_PIPE_BUSY` | loses, `ERROR_ALREADY_EXISTS` |
| Holder killed with `TerminateProcess` | name gone at once, next claim wins | next claim wins |
| Holder killed while a prober holds a handle | probing opens no handle | next claim loses until the prober closes |
| Holder killed while a client is connected | name gone at once, next claim wins | n/a |
| Holder's child started with inherited handles outlives it | claim gone, child kept nothing | not tested |
| Cost of claim and release | 5.7 µs | 2.8 µs |
| Cost of a probe for a missing claim | 4.5 µs | n/a |

A sweep that probes a named event holds it open for the length of the probe, and a claimant arriving in that window reads a live owner where there is none. The pipe has no such window, and a connected client does not keep it alive either. The pipe is the one mechanism, used for every claim.

The claim pipes carry `D:P(A;;0x00100080;;;SY)(A;;0x00100080;;;BA)(A;;0x00100080;;;LS)`, SYNCHRONIZE and FILE_READ_ATTRIBUTES for SYSTEM, Administrators and LocalService only. Measured on this machine: a non-elevated process can still probe a claim, because `WaitNamedPipe` opens nothing, and its attempts to open the pipe or to take the claim both fail with `ERROR_ACCESS_DENIED`. An elevated process can open one for attributes, which uses up the single instance and makes the probe answer `ERROR_SEM_TIMEOUT`, still a live holder. Nothing can read or write a claim. The driver host never opens a claim. It keeps opening only the owner pipe it already uses.

| Claim | Pipe name | Held for |
|---|---|---|
| Owner | `\\.\pipe\HIDMaestro.Owner.<owner id>` | the process, from its first machine-wide write |
| Transport index | `\\.\pipe\HIDMaestro.Index.<N>` | the controller's life |
| Identity | `\\.\pipe\HIDMaestro.Identity.<token>` | the controller's life |

The owner id is a GUID the process draws once. Beside the owner claim sits a record under `HKLM\SOFTWARE\HIDMaestroOwners\<owner id>`, readable by everyone: process id, image path, start time, SDK version and USB/IP server port, and one subkey per live controller with its identity token, transport index, backend, profile id, devnode instance id and vhci port. The process writes a controller's entry before any PnP work and removes it once the controller's devices are gone, and the record goes with its last controller. A record whose owner claim no longer exists describes a dead owner, which is what the sweeps act on. The process id and start time are for people reading the record: nothing decides liveness from them.

## Transport index and slot

`HMController.Index` stays internal and keeps meaning what every internal caller uses it for, the index that names the machine-wide objects. The context's own numbering becomes a slot: `CreateController` takes the lowest slot free in its context, and `CreateControllerAt(index, ...)` keeps its contract of one controller per slot per context. Each controller holds a machine-wide transport index, which names every section, event, pipe and registry key and is the `ControllerIndex` the driver reads. `HMController.TransportIndex` and `HMController.SectionNames` expose it, so native writers can find their sections.

The transport index is the slot number when that index is free machine-wide, and otherwise the lowest free one. A program running alone therefore gets the numbers it always got, and native writers that compute names from the index see no change. Two programs that each create a first controller coexist, the second on transport index 1. An index N is free when all of these hold:

- its claim `\\.\pipe\HIDMaestro.Index.<N>` can be created,
- no v1.12.0 program holds `\\.\pipe\HIDMaestroOwner<N>`,
- no present HIDMaestro devnode records N as its `ControllerIndex`, whoever owns it, unless the devnode carries the identity this create is about to reclaim,
- no USB/IP import uses it whose server port no v1.13.0 record names. Such an import belongs to a program on an older SDK, whose composite has no devnode to record the index, and its bus id `1-<N+1>` carries it.

Whether the input section exists is no evidence either way. Measured on this machine: after an Xbox 360 controller's Dispose returns, `Global\HIDMaestroInput<N>` stays open for as long as the disposing program lives, more than 10 seconds in every run, on v1.12.0 as on this release. The SDK's own XInput calls during the create leave xinput1_4 holding a handle to the XUSB companion, which keeps the removed companion's driver host, and its view of the section, alive until the program polls XInput again (it closed at once when the test called `XInputGetState` on every slot) or exits. An allocator that skipped indices with an open section would move a program off its index after such a dispose. The case the section check would have covered beyond the rules above, a program older than v1.12.0 in the middle of creating its sections, is a race this release does not close.

The owner pipe's first instance is then created with `FILE_FLAG_FIRST_PIPE_INSTANCE` and v1.12.0's access mode, type, instance count and timeout, which all instances of one pipe must share. A v1.12.0 program that starts on the index between the check and the create makes this fail, and the create stops with `HMResourceInUseException` rather than share the sections.

A keyless controller's default identity derives from its transport index, as it derived from the index before. When another program holds index 0, a keyless controller lands on another index and so on another identity, and the index and identity can differ between runs. Durable device paths need an identity key, which has been the documented contract since v1.8.0.

## Identity

The identity claim `\\.\pipe\HIDMaestro.Identity.<token>` is taken before any PnP work. A program asking for an identity a live program holds gets `HMResourceInUseException`, derived from `InvalidOperationException` so existing catch blocks keep working. Its message, and its `OwnerProcessId`, `OwnerImagePath` and `OwnerSdkVersion`, name the holder from its record. The first program's devices see no PnP activity, which section B of the coexistence probe checks by holding a read handle on the first program's device through the second program's attempt. The same check applies inside one process, across contexts.

A v1.12.0 program takes no identity claim. When a present devnode carries the identity's token and no record lists it, the create probes the owner pipe of the devnode's `ControllerIndex`. A held pipe refuses the create with the same exception.

`ClearParentIdPrefixRivals` keeps the 0xCA invariant: never two parents with one ParentIdPrefix. A present rival is removed only when its owner is provably dead. When its owner is running, here or in another program, or cannot be known, the create is refused with `HMResourceInUseException` instead, and the message names the rival devnode and says how to remove it when its program is gone. A rival that is not present is removed as before, because a ROOT record re-enumerates at boot.

## Sweeps

A sweep removes a present device only on proof that its owner is gone. What the census (`OwnerCensus`) knows about each present HIDMaestro devnode, grouped by identity token:

| Present device | Owner | Action |
|---|---|---|
| In a record whose owner claim is gone | dead | removed with everything the record lists |
| In a live record | running | left alone, the caller's own included |
| In no record, `HIDMaestroOwner<N>` held | a running v1.12.0 program | left alone |
| In no record, no owner pipe, `Global\HIDMaestroInputAck<N>` exists | a v1.12.0 program that has exited | removed |
| In no record, no owner pipe, no InputAck section | a program older than v1.12.0, state unknown | left alone |

Only a v1.12.0 or later SDK creates `Global\HIDMaestroInputAck<N>`, the driver of the device keeps it open for as long as the device exists, and the program's owner pipe closes when the program ends however it ends. A device with the section and without the pipe therefore belongs to a v1.12.0 program that is gone. A device with neither was made by an older SDK, whose program leaves no sign of whether it still runs. Such a device is never removed by a sweep without a scope. It is removed by the uninstall-grade cleanup, and by a create that asks for the device's own identity key, because that program is asking for that device back. The transport allocator skips its index.

USB/IP imports are matched by server port. A server records its port in its owner's record. An import whose server port has no listener on the loopback interface, read with `IPGlobalProperties.GetActiveTcpListeners`, belongs to a dead server and is detached, and the re-attach attempts against that port are cancelled. A v1.12.0 server listens the same way. An import on this process's own port that none of its controllers made was left by the program that held the port before, and is detached. A dead record's composites are also detached by their server port and bus id.

The public cleanup keeps its overloads and becomes orphan-safe. `RemoveAllVirtualControllers()` and `RemoveAllVirtualControllers(bool preserveInstall)` remove the devices of dead programs. A running program's controllers, the caller's own included, stay: section D of the coexistence probe checks that a live program's sweep leaves its own controller running. Package removal (`preserveInstall: false`) happens only when no device of any program is left. `RemoveAllVirtualControllers(HMCleanupScope.Everything, bool)` removes every HIDMaestro device and import on the machine regardless of owner, which `HIDMaestroTest cleanup` and the battery use.

A program that exits without disposing its controllers has their devices removed by the SDK's own `ProcessExit` handler, registered with the owner claim. PadForge's exit hook, which sweeps with `preserveInstall: true` when its engine did not shut down cleanly, relied on the sweep removing its own devices. The SDK's handler does that now. A killed program runs no handler, and its devices go with the next sweep of any program through its record.

The common case is cheap. With no dead record and no present device of a dead program, nothing walks the enumerators. Presence comes from `CM_Get_Device_ID_List` with `CM_GETIDLIST_FILTER_ENUMERATOR | CM_GETIDLIST_FILTER_PRESENT` for the ROOT and SWD roots, two calls, then a registry read per HIDMaestro devnode. The phantom-record cleanup moves off the create path onto a background thread, once per process. It takes `OwnerSweep.CreateGate` for writing and every create takes it for reading, so it never runs during one of this process's creates. A phantom whose identity claim another program holds is that program's create in flight, and is skipped.

## Driver deployment

Every driver and transport deploy holds the machine-wide mutex `Global\HIDMaestro.Deploy` for the length of one call. A named mutex fits here: one thread acquires and releases it inside one call ([CreateMutexW](https://learn.microsoft.com/windows/win32/api/synchapi/nf-synchapi-createmutexw)). An abandoned mutex is acquired and the deploy re-reads the installed state before acting.

The same-version fast path stays outside the mutex at its current cost: the manifest hash in `SOFTWARE\HIDMaestro` and the driver store check. When it misses, the deploy takes the mutex and checks again, so of two programs calling `InstallDriver` at once, one deploys and the other returns `AlreadyCurrent`. Section F checks it from a machine with no driver.

The installed version is the newest `DriverVer` among the `hidmaestro.inf` packages in the driver store's FileRepository. Two stamps compare by release version first, then by build date, then by build number, so a release is newer than another by its version even when the other was built later. `HMContext.LastDriverInstall` reports the outcome:

| Installed driver | Outcome |
|---|---|
| none | `Installed` |
| this SDK's payload | `AlreadyCurrent` |
| this SDK's stamp, record of it missing | `AlreadyCurrent`, the record is restored, nothing is reinstalled under running devices |
| newer | `KeptNewer`, never downgraded |
| older, no present device of any program on it | `Upgraded` |
| older, devices of running programs or of unknown programs on it, v1.12.0 or later | `KeptInUse` |
| older, held the same way, older than v1.12.0 | `HMDriverVersionException` naming the devices and their programs |

`HMDriverVersionException` derives from `InvalidOperationException` and carries `InstalledVersion`, `MinimumVersion` and `Blockers`.

"Runs on the installed driver" has to be true of every device the SDK creates, so a create installs the driver on its own devnode with `DiInstallDevice` and no driver named, which installs the best match the driver store holds on that device and no other ([DiInstallDevice](https://learn.microsoft.com/windows/win32/api/newdev/nf-newdev-diinstalldevice)). Until v1.13.0 the create called `UpdateDriverForPlugAndPlayDevices` with the VID/PID hardware id and the SDK's own INF, which "installs the driver package on all devices present in the system that have a hardware ID or compatible ID that matches" ([SetupAPI functions that simplify driver installation](https://learn.microsoft.com/windows-hardware/drivers/install/setupapi-functions-that-simplify-driver-installation)). Measured in section E: it staged the SDK's package beside one the policy had kept and bound the new controller to it, and with two programs of one profile it would move the older program's controller onto the newer driver.

## Version handshake

The protocol contract is a per-controller section, `Global\HIDMaestroVersion<N>`, 64 bytes, created by the SDK beside the input section and before the input event, the pattern v1.12.0 used for `InputAck<N>`. No existing layout changes. The layout is `HIDMAESTRO_VERSION_INFO` in `driver/driver.h`:

| Offset | Field | Written by |
|---|---|---|
| 0 | layout version, 1 | SDK |
| 4 | oldest driver protocol the SDK runs on, 2 | SDK |
| 8 | protocol the SDK speaks, 3 | SDK |
| 12 | SDK version, four 16-bit fields | SDK |
| 20 | driver protocol, 0 until written | driver |
| 24 | driver version, four 16-bit fields | driver |
| 32 | driver capabilities, the InputAck bits | driver |
| 36 | reserved, 28 bytes | |

The driver writes its version and capabilities first and its protocol last, with a barrier between, each time it opens the input section, and then lets go of the section. Protocol 1 is the layout set through v1.11.0, protocol 2 adds InputAck and the owner pipe (v1.12.0), and protocol 3 adds this section. A driver keeps every older layout, so an SDK runs on any driver at or above its oldest protocol. `HMController.DriverVersion` reads the driver's half, and native writers read both halves directly.

## Staging

Everything the elevated SDK runs or hands to pnputil is staged per version and per operation under `%ProgramData%\HIDMaestro\Staging\<version>-<hash>\<operation>`, where the hash is the first 16 hex characters of the embedded driver payload's SHA-256. The operations are `driver` (the driver binaries, both INFs, signtool and inf2cat), `swd` (hmswd.exe), `usbip` (the usbip-win2 installer) and `usbip-ude` (the host controller package forced onto an older transport). One directory per operation keeps the catalog step's `/driver:` scan and its stale-catalog cleanup away from every other operation's files.

Every directory is created with its security descriptor in the same call, so none exists with an inherited ACL: `O:BAG:BAD:P(A;OICI;FA;;;SY)(A;OICI;FA;;;BA)` for the staging tree, and the same plus `(A;OICI;FRFX;;;BU)` on `%ProgramData%\HIDMaestro`, which also holds the OpenVR runtime that SteamVR loads as the user. Kitsune Input's Rust setup component enforces the same two descriptors on its setup directory for the same reason.

Each use checks every directory on the path from `%ProgramData%\HIDMaestro` down. A directory passes when it is not a reparse point, its owner is Administrators or SYSTEM, and no allow ACE grants any write-class right (write data, append data, write attributes or extended attributes, delete, delete child, change permissions, take ownership) to anyone else. A version or operation directory that fails is moved aside to `<name>.untrusted-<guid>` and created again. `%ProgramData%\HIDMaestro` and `Staging` are reset in place instead, because vrpathreg stores an absolute path into the first. A reparse point at either of those two is refused, since setting security on it would set it on its target.

SHA-256 is checked against the embedded bytes, or the pinned release hash for the usbip files, when a file is written, when an existing file is reused, and immediately before use: signtool and inf2cat before every deploy, the two driver binaries before signtool rewrites them, hmswd before every run, and the usbip installer before it runs. A file is written to a temporary name, verified and then renamed into place. Reuse trusts no file size. The helper no longer comes from beside the assembly (`Assembly.Location`, which is empty in a single-file app) and always comes from the embedded resource. Each elevated helper runs with its own staging directory as its working directory. Logs stay in `%TEMP%\HIDMaestro`, since nothing runs from there.

A deploy, which holds the deploy mutex, deletes the staging directory of every version that no live owner record names, and every moved-aside directory. The same-version fast path takes no lock and prunes nothing, so a directory left by a version that was running during an upgrade goes at the next deploy. The constructor prewarm stages the driver payload only when the fast path will not be taken: on a machine that already runs this build's driver, nothing reads the staged payload.

## NativeAOT, trimming and single-file

The project sets `IsAotCompatible`, which turns on the trim, single-file and AOT analyzers. `aot-analyzers.globalconfig` raises the three diagnostic categories they report under, `Trimming`, `SingleFile` and `AOT`, to errors in Release. A temporary file holding one reflection-based `JsonSerializer.Serialize` and one `Assembly.Location` read failed the Release build with IL2026, IL3050 and IL3000. At b4d29d9 the same analyzers report 40 warnings: 39 from the 19 reflection-based `JsonSerializer` calls in `ControllerProfile.cs` and `HMLayoutLoader.cs`, and IL3000 for the `Assembly.Location` read in `SwdDeviceFactory.cs`, which the staging change removed.

Profiles and layouts load through `HMJsonContext`, a source-generated `JsonSerializerContext`, with no reflection resolver behind it. Its options are the ones `HMLayoutJsonOptions.Default` carried: camelCase names read case-insensitively, comments and trailing commas allowed, `HMAxis` through its own converter, every other enum as a snake_case string. The non-generic `JsonStringEnumConverter` needs runtime code generation, so each enum in the graph gets a `JsonStringEnumConverter<TEnum>` with the snake_case policy. `HMLayoutJsonOptions.Default` is now the context's options, which read and write the SDK's own types only.

The layout `kind` stays with `HMLayoutJsonConverter`, which reads each concrete layout through the `JsonTypeInfo` the options carry. `[JsonPolymorphic]` was considered and does not fit. Its discriminator matches exactly, while the converter has always matched `kind` in any letter case and with or without underscores, and `LoadProfilesFromDirectory` reads profiles consumers write themselves.

The generated code builds a record whose properties are init-only with one object initializer that assigns all of them, so a key the JSON leaves out arrives as `default(T)`. That is null for the empty lists and `new()` objects the layout records initialize, 0 for `HMTriggerButton.Stages` (initialized to 1) and `Unknown` for `HMRotaryEncoder.Role` (initialized to `Dial`). Reflection built the record first and kept those values, and 68 of the 336 catalog profiles depend on it. The converter therefore writes the JSON out again with each such key filled from a freshly constructed record. Which keys need it is planned once per type, by comparing a fresh record with the one the same metadata builds from `{}`, so a reflection resolver, which keeps initializers itself, plans nothing.

`json_parity_check` reads every embedded profile through `HMJsonContext` and through v1.12.0's own converter and options, and requires the same profiles with the same contents. It also checks the lenient `kind` matching and the two value-type initializers directly. With the fill step disabled it fails on 68 profiles and those checks.

`hmswd.exe` always comes from the embedded resource, staged and verified as in the staging section. There is no path beside the assembly any more. `Assembly.Location` is empty in a single-file app.

All 113 `DllImport` declarations become `LibraryImport`, 120 with the seven the claims already used. Every one that took a string or `char` had `CharSet.Unicode`, so each gets `StringMarshalling.Utf16`. Every `bool` gets `MarshalAs(UnmanagedType.Bool)`, the 4-byte Win32 `BOOL` `DllImport` used by default, and `SetLastError` and `EntryPoint` carry over. The generated stubs pin `byte[]` and `char[]` buffers and pass them straight through, as `DllImport` did, so buffers Windows fills arrive filled. Three structs were not blittable and change layout without changing size: `HIDP_CAPS.Reserved` becomes a 17-element fixed buffer, the OpenVR section's `SECURITY_ATTRIBUTES.InheritHandle` becomes the 4-byte `BOOL` it is, and `CM_NOTIFY_FILTER`'s instance ID becomes a 200-character fixed buffer, keeping the 416 bytes `CM_Register_Notification` requires. That function took a managed delegate, which `LibraryImport` does not marshal. Each wait's handler now travels as a `GCHandle` in the registration's context argument, and one `[UnmanagedCallersOnly]` dispatcher hands every event to it and lets no exception reach cfgmgr32. The handle is freed after `CM_Unregister_Notification`, which "waits for pending callbacks to finish" ([CM_Unregister_Notification](https://learn.microsoft.com/windows/win32/api/cfgmgr32/nf-cfgmgr32-cm_unregister_notification)). A wait whose registration fails still finishes on its 50 ms re-checks, so `pnp_notify_check` (S77) counts the events the dispatcher delivers while a controller is created and disposed: 7, and 0 with the filter sizes broken. The generated stubs of the per-frame calls (`SetEvent`, `WaitForSingleObject`, `WaitForMultipleObjects` over a preallocated handle array) convert `BOOL` in place, pin the array with `fixed`, and save the last error, with no allocation. `aot_smoke` publishes one source four ways: NativeAOT and trimmed self-contained single-file, each for x64 and ARM64. Each app loads the catalog, installs the driver, creates `dualshock-4-v2` on the UMDF2 driver and `dualsense-composite` on USB/IP, submits input, writes an output report, waits for `OutputReceived`, and disposes. The battery runs the two apps for the machine's architecture as S74 and S75, and the parity check as S76. At b4d29d9 both apps load 0 of 336 profiles, because reflection-based JSON is switched off in both kinds of app.

## Building from source

`scripts\build_all.cmd` builds everything an official release carries: the UMDF2 driver, XUSB companion and SWD helper for x64 and ARM64, the OpenVR driver, and the SDK with both usbip-win2 installers. Each setting below is an environment variable. MSBuild reads environment variables as properties, so one setting reaches the native scripts and the SDK project alike, and each also works as `-p:` on a `dotnet build` of the SDK.

| Setting | Effect | Default |
|---|---|---|
| `HMSkipArm64=true` | Builds and embeds the x64 driver, companion and helper only, and leaves out the ARM64 usbip-win2 installer. | unset |
| `HMSkipUsbip=true` | Leaves out the USB/IP transport: both installers and the host controller files. Nothing is downloaded, hashed or unpacked for it. | unset |
| `HM_SDK_ROOT` | The Windows SDK: the `um` and `shared` headers, the `um` libraries, `rc.exe`, and the signtool set the SDK embeds. | `WindowsSdkDir` when a Visual Studio or EWDK prompt set it, otherwise `%ProgramFiles(x86)%\Windows Kits\10` |

| `HMWdkBin` | The folder whose `x64` and `arm64` folders hold the signtool set. | `HM_SDK_ROOT\bin\<version>\` |

The scripts find Visual Studio through `VSINSTALLDIR` when a Visual Studio or EWDK prompt set it, and otherwise search `%ProgramFiles%\Microsoft Visual Studio` as before. Every root is checked for the folders the build reads from it, and a missing one stops the build with an error that names the setting.

Installed kits need no setting. With the NuGet WDK, `HM_WDK_ROOT` is the `c` folder of `Microsoft.Windows.WDK.x64` and `HM_WDK_ROOT_ARM64` the `c` folder of `Microsoft.Windows.WDK.ARM64`, because each package carries the UMDF stub library for its own architecture only. Microsoft's CI for windows-drivers-rs points `WDKContentRoot` at the target architecture's package the same way (`.github/actions/install-wdk/action.yaml`). The Windows SDK then comes from the installed kit, which Visual Studio's C++ workload installs and which Microsoft lists as a requirement of the NuGet WDK ([Install the WDK using NuGet](https://learn.microsoft.com/windows-hardware/drivers/install-the-wdk-using-nuget)). The SDK's own NuGet packages lay out libraries as `c\um\<arch>` rather than `Lib\<version>\um\<arch>`, so `HM_SDK_ROOT` cannot point at them. In 10.0.26100.6584 the NuGet WDK's `km` headers (649 files), UMDF 2.15 headers (36 files) and both stub libraries are byte-identical to the installed WDK of the same version.

In the EWDK, the build runs from the prompt `LaunchBuildEnv.cmd` opens, and the defaults pick up the image's kit, version and Build Tools. windows-drivers-rs reads `WDKContentRoot` and `Version_Number` "running in an eWDK prompt" (`crates/wdk-build/src/utils.rs`), and an EWDK prompt's environment posted to the OSR developer forum shows `WDKContentRoot`, `WindowsSdkDir`, `Version_Number` and `VSINSTALLDIR`, each pointing into the mounted image. The EWDK itself was not run for this release, since downloading it means accepting Microsoft's EWDK license terms. `check_build_layouts.ps1` sets those four variables to the installed kit and Visual Studio instead.

The built SDK reports what it carries through `HMBuildInfo`: `DriverArchitectures`, `UsbipArchitectures`, `HasOpenVrDriver` and `IsComplete`. Each is read once from the assembly's own resource names, so it describes the bytes actually embedded, whatever the build settings were. A controller that needs a payload this build lacks for the machine's architecture throws `HMPayloadMissingException`, derived from `InvalidOperationException`, before any machine-wide step: a composite persona without the USB/IP transport, and any controller without the driver. `InstallDriver`, `InstallUsbipBackend` and `HMVR.EnsureDriverRegistered` throw it too, and `IsUsbipBackendAvailable` is false in a build without the transport.

`Resources\` is a cache that outlives a build, so a skip build in a tree that once built everything would still find ARM64 and USB/IP files there. The resource items therefore no longer come from globs over it. Each payload file is listed when the project is evaluated, with the path the pre-build target stages it at and the name it is embedded under, and the target embeds exactly the files it staged for the settings in force. A glob was also evaluated before the target staged anything, which is why the SDK needed two builds on a fresh tree. It needs one now, and the 392 resources it embeds carry the same names and bytes as before, less the two Inf2Cat files below.

Official releases stay complete. `pre-tag-validate.cmd` clears `HMSkipArm64` and `HMSkipUsbip` before it builds, `build_info_check` (S78) fails unless the release build reports `IsComplete`, and `check_build_layouts.ps1` builds every layout above before the battery runs.

The SDK embedded eight Inf2Cat files and now embeds six. `inf2cat.exe.manifest` and `Microsoft.Kits.Logger.dll` are not in the NuGet WDK, and neither one does anything:

- None of `Inf2Cat.exe` and its four UniversalStore libraries references `Microsoft.Kits.Logger`, by assembly reference or by name in a string (ildasm 4.8). The kit's x86, x64 and ARM64 copies of the logger carry identical IL and differ only in the build path inside `AssemblyKeyFileAttribute`.
- `Inf2Cat.exe` embeds its own manifest (RT_MANIFEST 1, `asInvoker`), and on Windows Server 2003 and later "Internal manifest is preferred over external manifest" ([Internal Manifest vs External Manifest](https://learn.microsoft.com/archive/blogs/junfeng/internal-manifest-vs-external-manifest)). The external file declared a dependency on the private `wintrust.dll` beside signtool.
- In a copy of the staging layout, Inf2Cat loaded that private `wintrust.dll` with and without both files, since the folder an application loaded from comes before the system folder in the standard search order ([Dynamic-link library search order](https://learn.microsoft.com/windows/win32/dlls/dynamic-link-library-search-order)). Every run produced catalogs that `certutil -dump` shows identical apart from the list identifier, which differs between two runs of the same set as well.

Microsoft's `WindowsDriver.Common.targets` in the NuGet WDK runs Inf2Cat from `bin\<version>\x86` (`Inf2CatToolPath`, `WDKBinRoot_x86`), which holds neither file. The six files that remain are byte-identical in the installed WDK and the NuGet WDK.

## The usbip-win2 install

The SDK runs the bundled installer only where no copy of usbip-win2 is installed, and now with the smallest set the installer allows:

```
/VERYSILENT /SUPPRESSMSGBOXES /NORESTART /COMPONENTS=main,client /TASKS=vcredist /NOICONS
```

What each switch does, from the installer's script (`userspace/innosetup/setup.iss` at tag v.0.9.8.1) and the Inno Setup 7.1 help for its command line. The compiled scripts inside both pinned installers, extracted with innounp 2.71.1, match the source in every entry used here, and differ from each other only in architecture and the VC++ redistributable's file name. innoextract 1.9 cannot read them: they carry Inno Setup Setup Data 7.0.0.3, and it stops at 6.0.5.

- `main` and `client` carry `Flags: fixed` (setup.iss lines 127-128), and the help says `/COMPONENTS` "does not change the state of components that include the fixed flag". `client` is the drivers themselves: the filter installed with pnputil and the host controller installed by `devnode.exe` (lines 176-177). `/COMPONENTS=main,client` deselects `gui`, `sdk` and `pdb` (lines 129-131), which `full`, the default type, installs.
- `/TASKS=vcredist`. The help says "Only the specified tasks will be selected", and every other task is deselected, which also skips the restore of a previous install's task choices (`UsePreviousTasks=yes`). `devnode.exe` and the `libusbip.dll` it loads import `MSVCP140.dll` and `VCRUNTIME140.dll`, and the runtime installs before the driver steps (line 170), so the runtime cannot be left out. `desktopicon` belongs to the `gui` component (line 166) and goes with it.
- `/NOICONS`, "initially check the Don't create a Start Menu folder check box". The uninstall shortcut belongs to `main` (line 135), so this is the only switch that removes it.
- `/NORESTART` is required: the installer sets `AlwaysRestart=yes` (line 112), and the help says that without it a very silent setup "will reboot without asking".

Left on the machine by the installer and not removable from its command line: `usbip.exe`, `devnode.exe`, `libusbip.dll`, `resources.dll` and `Readme.md` under Program Files, the uninstaller and its Apps entry, the scheduled task "USBip Detach All On Reboot Or Shutdown", and the VC++ runtime. HandHeld Legend's patch passes the same `/COMPONENTS`, `/TASKS` and `/NOICONS` values, and those values are the right ones.

One gap is closed besides. `PrepareToInstall` (setup.iss lines 504-535) runs the uninstaller of any copy whose record exists under `SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\{199505b0-b93d-4521-a8c7-897818e0205a}_is1` and whose uninstaller file is still there. `GetInstalledUninstallString` (lines 433-502) looks in the 64-bit view of HKLM, then the 32-bit view, then HKCU, and takes the uninstaller's path out of `UninstallString` whether it is quoted or not. The SDK checked only the driver store, so a machine with the record and without the driver package would have had its old copy uninstalled first. The SDK now reads the record the same way, from the same three places, and does not run the installer over it.

## Budgets

Every budget is measured on the devbox with `perf_budget_check`, built against this tree and, with `-p:HmBase=true`, against b4d29d9, 30 runs or more each. The release notes carry the numbers.

The per-frame paths gain no system call, lock or cross-process check, and none allocates. S84 calls each submit path thousands of times on a live controller and fails on any allocation: `SubmitState` and `SubmitRawReport` on a DualShock 4, `SubmitState` on an Xbox 360, `SubmitKeyboard`, `SubmitMouse`, and a GameCube adapter port's `SubmitState` and the controller's. At b4d29d9 the keyboard and mouse paths allocated 539 and 248 bytes a report: the packer built each frame, a set of the keys held and the release frame anew, and found the release frame's slot through a closure. The packer is shared by every controller of a profile, so it now writes into buffers each controller keeps and uses under its submit lock, and the release frame is rewritten in place. The output reader allocates 32 bytes a report, as it did. A frame reaches the driver's delivery acknowledgement as fast as it did.

## Compatibility

A program built on v1.12.0 and a program built on this release run side by side. This release judges the v1.12.0 program's liveness by its owner pipes, never removes its controllers while it runs, and runs its own controllers on the v1.12.0 driver when the v1.12.0 program's controllers hold it. Section E1 of the coexistence probe checks it.

The other direction cannot be fixed from here. A v1.12.0 program, and every older one, calls `RemoveAllVirtualControllers(preserveInstall: true)` inside its `InstallDriver`, which removes every HIDMaestro device on the machine, and replaces the installed driver with its own whenever the payload differs. Starting such a program while a v1.13.0 program runs removes the v1.13.0 program's controllers. Upgrading every program on a machine to v1.13.0 or later is the fix.

A program older than v1.12.0 leaves no sign of whether it still runs. Its devices are never removed on a guess, and they block a driver upgrade. When the installed driver predates v1.12.0 and such a device is present, `InstallDriver` throws `HMDriverVersionException` naming it (section E4).

Native writers, programs that open the sections without the SDK, see the same names as before when a program runs alone, because the transport index equals the slot. When several programs run, a native writer reads the names from `HMController.SectionNames` of the program it feeds, or computes them from `HMController.TransportIndex`. The version section gives a native writer the driver's version and protocol and the SDK's.

## Migration

What a program built on an earlier release sees change:

- `RemoveAllVirtualControllers()` and `RemoveAllVirtualControllers(bool)` no longer remove the controllers of running programs, the caller's own included. A tool that wants every controller gone, such as an uninstaller or a test harness, calls `RemoveAllVirtualControllers(HMCleanupScope.Everything, preserveInstall)`.
- A program that exits without disposing its controllers has their devices removed as it exits.
- `InstallDriver` no longer removes devices of running programs before deploying, never downgrades the driver, and may keep an older driver in use. `HMContext.LastDriverInstall` says which. It can throw `HMDriverVersionException`.
- `CreateController` throws `HMResourceInUseException` when another live controller on the machine holds the identity key, where it allowed the second program to create over the first.
- A keyless controller can land on a transport index other than its slot when another program uses that index, so its default identity and device paths can differ between runs. Pass an identity key for stable paths.
- `CreateController` compiles the profile's device model before anything else and throws `InvalidOperationException`, naming the JSON path, for a profile whose ports, protocol or WinUSB block does not compile. Every catalog profile compiles.
- `HMButton` bits 23 and 24 gain names, `LeftTriggerClick` and `RightTriggerClick`. A descriptor-built report maps them to buttons 24 and 25, as it mapped those bits before.
- New: `HMController.TransportIndex`, `SectionNames` and `DriverVersion`, `HMContext.LastDriverInstall`, `HMCleanupScope`, `HMResourceInUseException`, `HMDriverInstallOutcome` and `HMDriverVersionException`. For devices described as data: `HMController.Ports`, `DeviceProtocol` and `BindWinUsb`, `HMPortSet`, `HMPort`, `HMPortFlags`, `HMPortOutputEventArgs`, `HMDeviceProtocol` and `HMWinUsbBinding`.

## Devices described as data

A profile describes its device, and the SDK holds only mechanisms any device can use. Nothing in the SDK names the GameCube adapter, checks its VID and PID, or switches on its command bytes. A new device of the same form needs a profile and no code, and a new form of device gets a new general mechanism plus the JSON that uses it. The adapter is the first profile to use the three mechanisms below, and the mechanisms are what this release ships.

### Ports

`extendedReport.ports` describes a report that carries several controllers, one block per port: a multi-port adapter, a multitap, a receiver with several pads.

| Key | Meaning |
|---|---|
| `count`, `offset`, `stride` | how many blocks, where port 1's starts (the report ID is byte 0) and how far apart they are |
| `status` | the block's status byte: its offset, the `connections` a port can hold with the bits each sets (the first is the empty port, the second the default), and device-wide `flags` every status byte carries while on |
| `data` | the block's data bytes, such as `"1-8"`. An empty port's are zero |
| `snapshots` | copies of a block the device keeps, taken `on: "connect"` from the first report in which the port holds something |
| `fields` | the block's fields in the `extendedReport` vocabulary, offsets relative to the block |

`extendedOutputReport.ports` describes an output report's blocks the same way. Its fields are whole numbers (`uint8`, `uint8-axis`, `uint8-trigger`, `uint16-le`, `int16-le`), and each is reported under its semantic.

On the SDK side, `HMController.Ports` is an `HMPortSet`, empty for a profile with one controller. Each `HMPort` has a fixed `Number`, a `Connection` named by the profile, `Connect(name)` and `Disconnect()`, `SubmitState(in HMGamepadState)` through the port's fields, `SubmitRaw` for the port's data bytes exactly, `GetOutput(name)`, and an `OutputChanged` event raised on the output thread. `Ports.Flags["name"]` sets a device-wide flag. A port call writes the whole report under the controller's submit lock, the work `SubmitState` already does, with no lock, system call or allocation added: the layout is compiled once, and the encoder writes into buffers the port set owns. `HMController.SubmitState` on a device with ports submits to port 1. `OutputDecoded` carries each port's output fields as `port1.rumble` and so on.

`HMButton` gains `LeftTriggerClick` and `RightTriggerClick`, a trigger's digital click apart from its analog travel. With them, `HMGamepadState` expresses the GameCube controller's analog L and R with their clicks, its Z and its C-stick exactly, so no device-specific state type exists.

### The device protocol

`usbConfiguration.protocol` describes how a USB/IP device behaves beyond its descriptors.

| Key | Meaning |
|---|---|
| `state` | named on/off states with initial values, restored at attach and at a port reset |
| `input` | the interrupt IN endpoint, the states under which a poll gets a report (`"polling"`, `"!stalled"`), and its `clock`: the device's own controller poll in ms and rules that change it while exactly the listed ports hold something |
| `commands` | the interrupt OUT endpoint, whether SET_REPORT(Output) is read the same way, and rules tried in order. A rule matches the bytes a packet starts with and its length, sets states, and queues a reply built from the state before the rule ran: constant bytes, a state as a byte, or a snapshot's bytes for every port, zeros unless its own condition holds |
| `halt` | the states under which the device answers nothing, and the status transfers fail with until a port reset |
| `setProtocol` | `"ack"`, or `"stall"`, the default |
| `getStatus` | `"descriptor"`: the self-powered bit the configuration declares |

The device runs it on a modeled host poll. A host controller polls an interrupt endpoint every period while a transfer is queued, on a grid that starts at attach, and fills a transfer one packet of wMaxPacketSize per poll. A short packet or a full buffer ends the transfer, and a packet with no room left in it is babble, which fails it with `-EOVERFLOW`. The period is the one Windows gives the endpoint descriptor's bInterval: a power of two from 1 to 32 ms at full speed, and 2^(bInterval-1) microframes, at most 32, at high speed (the tables under [USB_ENDPOINT_DESCRIPTOR](https://learn.microsoft.com/windows-hardware/drivers/ddi/usbspec/ns-usbspec-_usb_endpoint_descriptor)). `HMController.DeviceProtocol.HostPollInterval` models a faster host, as a filter driver that overclocks the poll makes one, and the descriptors never change. A device with a source poll has a new report for a host poll only once it has read its controllers since its last report.

The profile is compiled when the device is built: names become bits, conditions become a mask and the values under it, rules become byte patterns, and replies become parts with fixed offsets. A poll takes one lock and copies one packet. Commands are rare, and their replies are the only allocations.

### WinUSB on request

`usbConfiguration.winUsb` names the `DeviceInterfaceGUIDs` value a WinUSB binding registers, and `HMController.BindWinUsb()` binds it, as described for the adapter below. The package is generated per profile from its descriptors: `hmwinusb_<profile id>.inf`, matching the device's vendor-scoped compatible ID `USB\COMPAT_VID_vvvv&Class_cc&SubClass_ss&Prot_pp`. A device that takes one has a single interface and no device class, so WinUSB goes on the device's own devnode.

### Validation

`CreateController` compiles the whole device model before it takes anything machine-wide, so a mistake in a profile is refused with the JSON path that holds it: ports that do not fit their report, a field outside a block's data bytes, a button name the SDK cannot express, an output port count that differs from the input's, a state a rule names but `state` does not declare, an endpoint the configuration descriptor lacks or of the wrong type, a reply on a device with no input endpoint, a WinUSB GUID that does not parse. Every profile in the catalog compiles, and S79 checks that.

## The Wii U GameCube adapter persona

`gamecube-adapter` becomes a working profile: the Wii U GameCube adapter, WUP-028 (057E:0337), on the USB/IP transport, so that Dolphin, Slippi and SDL open it through libusb as they open the real one. It is a profile and nothing else: its ports, its protocol and its WinUSB GUID are the JSON below the descriptors.

Implementations, cloned beside this repository and read at the commits given: Dolphin `0d93fc0355` (`Source/Core/InputCommon/GCAdapter.cpp`), Slippi's Dolphin fork `9d13b39`, Ishiiruka `60f7b63`, SDL `804cf65` (`src/joystick/hidapi/SDL_hidapi_gamecube.c`) and its 3.4.18 release `829a65d7`, eden `1dcc574` (`src/input_common/drivers/gc_adapter.cpp`), RMG `4777ed3` (`Source/RMG-Input-GCA/main.cpp`), gcfeeder `06b2917`, Nintendont `999aa85`, ToadKing's wii-u-gc-adapter `fa098ef`, the adapter firmwares of loopj (usb-gamecube-controller-adapter `639f914`), pico-rectangle `1f0421d`, joypad-os `969c232`, HOJA-LIB-RP2040 `4ec9591` and HOJA-LIB-ESP32 `99f6bc3`, libusb `a45bb16` with Dolphin's pin `15a7ebb4` (1.0.29) and Slippi's `ba698478`, and usbip-win2 `v.0.9.8.1`. ### What the device reports

All 57 dumps agree on every field below but two: the control endpoint's packet size, and the strings of seven units. The dumps mask the serial. The paragraphs after the table take those three in turn.

| Field | Bytes or value |
|---|---|
| Device | `12 01 00 02 00 00 00 08 7E 05 37 03 00 01 01 02 03 01`: USB 2.00, class in the interface, bMaxPacketSize0 8, bcdDevice 1.00, strings 1, 2 and 3, one configuration |
| Configuration | `09 02 29 00 01 01 00 E0 FA`: 41 bytes, one interface, self-powered with remote wakeup, 500 mA |

| Speed | full |
| Strings 1, 2, 3 | `Nintendo`, `WUP-028`, `15/07/2014` |
| Report descriptor | the 214 bytes in `gamecube-adapter-hid`. bMaxPacketSize0 splits the dumps in two. Nineteen units report 8, and the eighteen whose status was recorded answer GET_STATUS as self-powered (0x0001 or 0x0003), which agrees with their own bmAttributes. Thirty-eight report 64, and the twenty-six whose status was recorded answer bus-powered (0x0000 or 0x0002), which contradicts the same bmAttributes. Every clone string in the set, "GameCube For Switch" on three units and "Nintendo Co., Ltd." on four, sits in the 64 group. A Mayflash adapter in Wii U mode reports 64 with Nintendo's strings and serial (node-hid issue 241), and loopj's firmware, whose device descriptor is commented "identical to OEM adapter", sets 8 (`src/usb_descriptors.c:27-43`, `ports/rp2xxx/tusb_config.h:9`). The persona reports 8 and answers GET_STATUS with the self-powered bit.

The dumps mask the serial. `15/07/2014` is the serial of a unit filed under an issue about the official adapter (OpenEmu issue 4652, bcdDevice 1.00, full speed), of a Mayflash in Wii U mode (node-hid issue 241), of a self-described cheap clone (wii-u-gc-adapter issue 39), and of both firmwares that copy the official adapter (loopj `usb_descriptors.c:80`, pico-rectangle `gcc_to_usb_adapter.cpp:30`). No source shows a WUP-028 with any other serial. One conflict stays open: the OpenEmu unit's manufacturer string is "Nintendo Co., Ltd.", the string the self-described clone reports, while every 8-byte unit in the dumps reports "Nintendo". The persona follows the dumps.

Since every adapter carries the same serial, Windows names the first WUP-028 it sees `USB\VID_057E&PID_0337\15/07/2014` and names a second one present at the same time after its port (measured, E1 and E5 below). The profile sets `sharedSerial`, so the persona serves `15/07/2014` for every identity key, where the other USB/IP personas fold the identity into their captured serial, and a second virtual adapter gets a port-named instance exactly as a second real one does.

The report descriptor declares ten reports under Usage Page 0x05, Game Controls, each in its own Application collection: outputs 0x11 to 0x15 and inputs 0x21 to 0x25. Each Report Count is the report's length on the wire including its ID byte, so report 0x21 is declared as 37 bytes after the ID and arrives as 37 including it. The persona sends what the device sends, 37 bytes for 0x21, 25 for 0x22 and 2 for 0x24. Carton's driver had to shrink Linux's 38-byte read to 37 for the same reason (v3 1/4).

Everything the dumps do not show stalls: the device qualifier and the other-speed configuration, which a full-speed device does not have (USB 2.0 section 9.6.2), string 0xEE, and every vendor request. HandHeld Legend's adapter answered string 0xEE with Microsoft OS descriptors and reported bcdDevice 2.00, so that Windows would bind WinUSB to it unasked. A host can see both, and the persona has neither.

### What the transport changes

usbip-win2 sits between the persona's bytes and Windows, and three of its rules are visible to a host. S79 reads every descriptor both ways.

- It presents every device at high speed, and for a full-speed device it rewrites each interrupt endpoint's bInterval on every full configuration read to the same period in microframes (`drivers/ude/wsk_receive.cpp`, `post_control_transfer`, `patch_config`, `to_high_speed_interval`). Windows reads bInterval 7, 2^6 microframes, where the persona serves 8 ms. The period is the same.
- UdeCx completes SET_FEATURE(DEVICE_REMOTE_WAKEUP) itself and never forwards it ([Write a UDE client driver](https://learn.microsoft.com/windows-hardware/drivers/usbcon/writing-a-ude-client-driver), the list of standard requests the class extension handles). A host that arms remote wakeup and then reads GET_STATUS sees the bit clear. Measured: three GET_STATUS requests reached the persona in a run in which SET_FEATURE and CLEAR_FEATURE never did.
- usbhub3 forwards no descriptor request to a device that failed to start, and a WUP-028 fails to start on input.inf (below). A host reads strings and the report descriptor only once WinUSB is bound.

| 0x14 | reply `24 01` when it was polling and `24 00` when not, then no more reports | survey |
| 0x15 | the device stops answering | survey: "libUSB gives an IO error", "requires it to be unplugged and reconnected" |
| 0x16, 0x17, or a 0x11 shorter than 5 bytes | input reports stall | survey |
| any other first byte | ignored | survey |

The survey swaps the endpoint numbers ("Commands are written to the in endpoint (0x81)"). Every host above writes to 0x02 and reads from 0x81. The OUT endpoint's packets are at most 5 bytes, so a 6-byte write reaches the device as two commands, which is how the protocol engine reads every OUT transfer. A SET_REPORT(Output) on the control endpoint is read the same way.

In the profile the table is this protocol:

Three rows rest on less than a capture of real hardware.

- loopj answers 0x13 with a two-byte report 0x23 and treats 0x15 as a reboot (`src/gcca.c:212-233`), and the descriptor does declare 0x23 and 0x25 as two-byte inputs. The survey ran each command on a real adapter and saw 0x21 reports after 0x13 and an error after 0x15. The persona sends neither 0x23 nor 0x25.
- After 0x15 the persona fails every transfer with `-EPROTO`, the status a Linux host gives a device that stops answering, which usbip-win2 passes to Windows as a transaction error (`drivers/libdrv/usbd_helper.cpp:73-74`) and libusb reports as `LIBUSB_ERROR_IO`. It recovers when the host resets its port or the program creates the controller again. A real adapter rebooted the way loopj models it would also come back on a port reset. No source says whether it does, and no host in the references sends 0x15.
- The survey does not say what ends a stall. The persona resumes on the next 0x13, the command every host sends to start reports. No host in the references sends 0x16, 0x17 or a short 0x11.

An attach and a port reset both return the device to its initial state: no reports until 0x13 and every motor command zero. The ports keep what the program last submitted, as the controllers stay plugged in, and each held port's origin is taken again. Linux's reset-resume handler sends 0x13 again for exactly this (v3 4/4). libusb's reset on WinUSB only aborts and resets the pipes (`libusb/os/windows_winusb.c`, `winusbx_reset_device`), so Slippi's reset after an I/O error (`GCAdapter.cpp:254-262`) is not a port reset.

Report 0x21 is the report ID and then nine bytes per port: a status byte, a button byte (A 0x01, B 0x02, X 0x04, Y 0x08, then D-pad left, right, down and up 0x10 to 0x80), a second button byte (Start 0x01, Z 0x02, R 0x04, L 0x08), main stick X and Y, C-stick X and Y, and the analog L and R (Dolphin `GCAdapter.cpp:904-936`, SDL `SDL_hidapi_gamecube.c:409-442`, Carton v3 1/4). Both stick Y values grow upward: SDL's mapping inverts them (`SDL_gamepad.c:1130`), Linux reports `255 - data[4]`, and Nintendont's note on the raw values reads "EE ... 80 ... 18 (up, center, down)" (`PADReadGC.c:695`). The profile maps the left stick to the main stick, the right stick to the C-stick, the trigger axes to the analog L and R, `RightBumper` to Z, `LeftTriggerClick` and `RightTriggerClick` to the L and R clicks, and the D-pad from `Hat`, with both Y fields inverted.

| Status bit | Meaning | Profile | Source |
|---|---|---|---|
| 0x04 | rumble power, the second USB cable | flag `rumblePower`, on by default | Carton's `GC_FLAG_EXTRAPOWER`, SDL `382`, Nintendont `PADReadGC.c:412` |
| 0x10 | a wired controller | connection `wired`, the default | Dolphin `862-871`, SDL `384`, Carton's `GC_TYPE_NORMAL` |
| 0x20 | a WaveBird receiver | connection `wirelessReceiverOnly` | Dolphin `862-871`, SDL `384`, Carton's `GC_TYPE_WAVEBIRD` |
| 0x02 | the WaveBird is communicating, read together as 0x22 | connection `wireless` | Nintendont `PADReadGC.c:412-414`, loopj `gcca.c:141` |

HandHeld Legend's notes from a real adapter give the empty values: 0x00 with only the black cable, 0x04 with both cables, and 0x10 and 0x14 with a controller (HOJA-LIB-RP2040 `src/cores/core_slippi.c:103-110`). An empty port's eight data bytes are zero, as loopj sends them and as the 0x12 reply reads before polling. No dump of a real empty port exists, and Dolphin, SDL, eden, gcfeeder and Linux all ignore those bytes.

A motor command is the controller's own, the port output field `rumble`: 0 stop, 1 run, 2 stop hard. SDL sends 2 under its rumble-brake hint (`SDL_hidapi_gamecube.c:557-561`). Nintendont runs a port's motor only when the command's low two bits are 1 and the port has rumble power (`PADReadGC.c:419`). SDL refuses rumble on a WaveBird or on a port without 0x04 (`552-555`), and Dolphin sends none to a WaveBird (`GCAdapter.cpp:1037-1039`). Those rules belong to the hosts, so the SDK reports the command and leaves the motor to the program.

A host on Windows reads whole reports. libusb turns on WinUSB's ALLOW_PARTIAL_READS for every endpoint (`libusb/os/windows_winusb.c:3595-3599`), with which WinUSB reads whole packets and keeps what the caller did not ask for, and hidusb reads a report's own length. A transfer with room for less than the next packet therefore never reaches the persona from Windows, and the babble rule above is tested at the transfer level in process.

### What Windows does with a WUP-028

Windows binds input.inf's HID driver to a WUP-028, and the device fails with Code 10, `STATUS_COULD_NOT_INTERPRET`: the HID parser rejects its report descriptor. Measured on the persona (E1) and on the same descriptor served by the UMDF2 driver with no USB involved (E3). A real adapter on Windows has no HID collection at all, which is why every Dolphin guide starts with Zadig.

SDL's "separate device for each slot" (`SDL_hidapi_gamecube.c:220-231`) is its PC-mode path, taken only when the vendor is not Nintendo (`203-205`), for third-party adapters in their own mode. Its WUP-028 path reads four ports from one report (`364-445`). SDL lists 057E:0337 among the devices it opens only through libusb (`src/hidapi/SDL_hidapi.c:859`) and ignores it on every other backend (`1143-1157`). The official SDL3 3.4.18 build for Windows x64 comes from `VisualC/SDL/SDL.vcxproj` (`build-scripts/release-info.json:59-82`), whose build configuration defines no `HAVE_LIBUSB`. The only libusb strings in its `SDL3.dll` are the names of two hints, `SDL_HIDAPI_LIBUSB_WHITELIST` and `SDL_HIDAPI_LIBUSB_GAMECUBE`, which `SDL_hid_init` reads outside its `HAVE_LIBUSB` block (`src/hidapi/SDL_hidapi.c:1231-1233`). Stock SDL on Windows therefore lists nothing for a real adapter, with or without Zadig. The persona is tested for the same empty list beside a controller SDL does list, and for SDL's full behavior with SDL 3.4.18 built from source with libusb.

### Zero setup for Dolphin and Slippi

`HMController.BindWinUsb()` binds WinUSB to the one virtual adapter's devnode, and nothing the device reports changes. The driver package follows Microsoft's WinUSB template, `Include` and `Needs` of winusb.inf plus a `DeviceInterfaceGUIDs` value, which libusb requires to open a WinUSB device (`libusb/os/windows_winusb.c:1876-1887`). It is generated from the profile, signed with the test certificate the driver package already uses, and added to the driver store without being installed anywhere.

Its INF names no hardware ID any device has. It matches the vendor-scoped compatible ID `USB\COMPAT_VID_057E&Class_03&SubClass_00&Prot_00` as the sixteenth of its compatible IDs, behind fifteen that no device carries, and a match that late ranks worse than input.inf's. Windows installs the best-ranked driver, the lowest rank value, on a new device. Measured: the package ranks 0x00FF3F00 against input.inf's 0x00FF3205 (S81), and in E6, with the vendor ID as the fourth compatible ID, it ranked 0x00FF3300 and still lost, while as the third it ranked 0x00FF3200 and won. Nintendo's other HID-class USB devices carry the same compatible ID and see the package listed among their compatible drivers at the same losing rank. The step installs it on the one devnode with `DiInstallDevice`, which installs the named driver on the named device and nowhere else ([DiInstallDevice](https://learn.microsoft.com/windows/win32/api/newdev/nf-newdev-diinstalldevice)). Zadig installs with `UpdateDriverForPlugAndPlayDevices` and then stages its hardware-ID INF (libwdi `30df0c0`, `libwdi/installer.c:876`, `895`), which binds every present adapter and every later one.

Before it installs, the step reads the devnode's driver list and confirms that another driver ranks above the package. Only that driver keeps Windows from choosing the package for a real device of the same kind. Every USB/IP persona has a HID interface, which input.inf matches, so the check guards the package's reach for whatever device form comes next. It also waits until Windows has settled the devnode's driver: no installation pending in the PnP manager (`CM_WaitNoPendingInstallEvents`), and the devnode started or stopped on a decided driver. A devnode that arrives with the reinstall flag still names WinUSB while it waits for the reinstall, and a bind that read it then returned `AlreadyBound` for a device about to lose WinUSB. S81 binds five times in a row on the first call to keep it so.

`CONFIGFLAG_REINSTALL` in a devnode's ConfigFlags makes its next arrival install again by rank, and a started device ignores it (E7: a bound adapter with the flag kept WinUSB and kept reading through a re-enumeration of its parent and `pnputil /scan-devices`, then a same-serial adapter arriving after its program was killed got input.inf). The flag cannot stay on the bound devnode, though. Windows reports it as install state 1, "needs reinstall", and libusb skips any device whose install state is not 0 as one whose driver "is reporting an issue" (`libusb/os/windows_winusb.c:1831` at Dolphin's pin `15a7ebb4`, `1686` at Slippi's `ba698478`), so neither emulator could open the adapter while it was set. The restore sets the flag instead, on a devnode that is gone: at dispose, and at the next program's reclaim after a crash. A program killed while bound therefore leaves its instance on WinUSB, as Zadig would, until the next HIDMaestro program starts and reclaims its hold. S81 measures both orders: an adapter arriving on the instance before the reclaim finds WinUSB and goes back to input.inf at the reclaim, and one arriving after it gets input.inf.

The step binds only a devnode on a driver that ships with Windows, which for a WUP-028 is input.inf. A devnode on WinUSB, libusbK or libusb0 already opens in libusb, and the step returns `AlreadyBound` without touching it. That covers an instance Zadig bound before. A devnode on any other driver is left alone and reported as `OtherDriver`.

The binding goes through the registry ledger. Before the bind the ledger records the devnode, its driver and the controller as holder. When the last holder lets go, by dispose or because its process is gone, the ledger restores a devnode still on HIDMaestro's package: a present one is installed again by rank, and a gone one gets the reinstall flag. A devnode someone has moved to another driver meanwhile is theirs and stays as it is. The uninstall-grade cleanup removes every non-present devnode still on a package and then the packages themselves.

| A real adapter arrives | It gets | Evidence |
|---|---|---|
| while the virtual adapter is bound | its own port-named instance on input.inf, as without HIDMaestro | E5, E6, S81 |
| after the virtual adapter was disposed | the restored instance on input.inf | ledger restore, S81 |
| after the virtual adapter's program was killed, once a HIDMaestro program has reclaimed its hold | input.inf, through the reinstall flag the reclaim sets | S81 |
| after the virtual adapter's program was killed, before any reclaim | the instance's WinUSB, as after Zadig, until the reclaim reinstalls it by rank | S81 |

Dolphin opens the first adapter it can (`GCAdapter.cpp:588-596`). A real adapter on input.inf beside the bound virtual one fails to open, and Dolphin moves on to the virtual one.

### The profiles

- `gamecube-adapter` keeps its id and becomes the persona above. Its name gains the catalog's `Full` marker, which no other adapter profile carries. Its note said the adapter uses raw bulk endpoints. It is a HID-class device with two interrupt endpoints. Its layout becomes `controller_adapter` with four ports.
- `gamecube-adapter-hid` carries the 214 bytes the dumps show. Its note called Usage Page 0x05 a vendor page and said report 0x21 "declares Count=37 but sends 36". The corrected note gives Game Controls, the declared-count rule above, and Code 10 on Windows, which this UMDF2 profile gets as the real adapter does. Its manufacturer string becomes the dumps' `Nintendo`.
- `joypad-gc-adapter` is joypad-os's emulated adapter, not Nintendo's. The catalog copy gained three bytes, 0x11, 0x21 and 0x13 ahead of each `A1 03`, so it holds 73 bytes where joypad-os declares 70 (`src/usb/usbd/descriptors/gc_adapter_descriptors.h:125-168`). It is corrected to joypad-os's 70. Its note says so, gives report 0x21 as 36 bytes after the ID, and keeps the strings joypad-os serves (`216-217`).

### Report timing and latency

The endpoints declare 8 ms, so a host polls the adapter 125 times a second, and each poll finds a report, because the adapter polls its controllers every 1.19971 ms (Arte's guide). The persona answers one packet per poll on an 8 ms grid that starts at attach, timed by a high-resolution waitable timer. A read that arrives between polls waits for the next one, as a real interrupt transfer waits for the next scheduled poll, and a clock that was held up skips the polls it missed instead of sending a burst. Hosts read with short timeouts, 16 ms in eden, gcfeeder and RMG and 100 ms in Dolphin, and Slippi warns about a slow adapter after 80 reads in a row over 15 ms (`GCAdapter.cpp:237-245`, `528`). The 8 ms grid meets all of them.

Melee players overclock the adapter by making Windows poll it every millisecond with hidusbf. Nothing changes inside the adapter: its descriptor still says 8 ms, and a 1 ms poll that finds no new controller poll gets a NAK, about one poll in six, so an overclocked adapter delivers about 833 reports a second. With controllers in ports 1 and 2 only it polls them every 0.9995 ms and delivers about 1000 (Arte's guide). USB/IP has no host schedule to overclock: usbip-win2 forwards a read the moment WinUSB queues it, so the persona alone decides when a report goes out. `HostPollInterval` sets the host poll the persona models, 8 ms by default or a faster power of two, and the profile's source poll and its ports 1 and 2 rule give the adapter's own NAKs.

A report carries what the adapter's latest read of its controllers found, as a real adapter's does. A program's submit therefore reaches the wire at the first host poll after the adapter's next controller read, up to 1.19971 ms after the submit plus up to one host poll.

### Tests

Each fails on b4d29d9, where `gamecube-adapter` has no descriptor and neither the port model nor the protocol engine exists. S79 reaches newer members by reflection, so it builds there and passes 2 of its 11 checks before it stops at the persona it cannot create. S80 to S83 do not compile there: `HMController.Ports`, `BindWinUsb`, `DeviceProtocol` and the trigger clicks are new.

- S79 `gc_descriptor_check` compiles every catalog profile's device model, checks the catalog (one `Full` among the 057E:0337 profiles, both corrected descriptors, the adapter layout), and compares the persona's bytes with the dumps three ways: what the persona serves, what Windows enumerates through the vhci root hub with `IOCTL_USB_GET_DESCRIPTOR_FROM_NODE_CONNECTION` before any driver loads, and what libusb reads through WinUSB after `BindWinUsb`. It also checks the stalls, the instance id `USB\VID_057E&PID_0337\15/07/2014` and Code 10 on input.inf.
- S80 `gc_protocol_check` runs through WinUSB after `BindWinUsb`: SET_PROTOCOL, GET_STATUS, no data before 0x13, reports after it, each port's input, connection and rumble while the other ports keep their bytes, 0x12, 0x14, stalls and ignored bytes, SET_REPORT and GET_REPORT, the 8 ms and 1 ms rates, 0x15 and the port reset, and a new adapter afterward. It drives the engine in process on exact clock ticks for babble, short packets and the source poll arithmetic.
- S81 `gc_winusb_check` covers the binding: its rank below input.inf, one devnode bound and no other beside a second adapter, no reinstall flag on the bound devnode, `AlreadyBound`, the restore on dispose and the flag it leaves on the gone devnode, five bind cycles each on the first call, and a killed owner's instance with an adapter arriving before the reclaim and after it.
- S82 `gc_dolphin_check` compiles Dolphin's and Slippi's `GCAdapter.cpp` and `LibusbUtils.cpp` unmodified, each with the libusb and fmt its tree pins, against stand-in headers for the parts of Dolphin they include (configuration, logging, core state). The emulators call these functions only while a game runs, which is why the test drives them directly. Each build reads all four ports with distinct input and the origin of each new connection, sends rumble to each wired port and sees that port's event, sends none to a WaveBird, and sees a port leave and return. It also takes the latency and rate measurements, counting delivered reports where the device sends them.
- S83 `gc_sdl_check` runs two `SDL3.dll` files, each in its own process: the official 3.4.18 release for Windows x64, and 3.4.18 (`829a65d7`) built from source by SDL's CMake with libusb 1.0.29 (`15a7ebb4`), which libusb's own MSVC project builds. The official build lists no joystick for the adapter, on input.inf and again on WinUSB, while it lists a DualShock 4 persona created in the same run. The libusb build lists one gamepad per connected port, with the port's number as its player index and the port's wired or wireless state. It refuses rumble on a WaveBird, and on a wired port while the `rumblePower` flag is off. Each wired port's rumble reaches that port alone, and SDL's rumble-brake hint gives 2 for a hard stop. A port leaves and returns with its number. The probe takes the SDL latency and rate measurements.
